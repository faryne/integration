# 個人化入口頁（iGoogle-like）規劃

> 狀態：**規劃中，未動工**。分支 `docs/portal-spec`。產品名稱與網域未定，下文先稱「Portal」。

## 結論先講

- **所有資料來源都是 recipe**：自己的爬蟲、內建腳本、他人分享的腳本、他站的 JSON/XML/RSS，都用同一份宣告式 recipe 描述（fetch → extract → transform → output）。差別只在 `extract.type`，不另外做一套「外部資料源」機制。
- **呈現用固定 renderer，不執行他人的 HTML/JS**：recipe 只產出標準化資料，前端用內建的 list/card/table/number/chart 元件來畫。XSS 風險直接歸零，iGoogle 式的自訂 gadget 留到 P4 用 sandboxed iframe 再評估。
- **伺服器端執行，相同腳本加相同參數跨使用者共用快取**：熱門公開腳本的成本不會隨安裝數成長，也不會把目標站打爆。
- **抓取層要做 SSRF 隔離**：公開註冊代表任何人都能叫伺服器去抓任意 URL。現有的 `service/helper/http.go` 的 `DoRaw` 沒有 IP 檢查也沒有大小限制，不能直接拿來跑使用者腳本。
- **腳本形式分兩步**：P1 只做宣告式 recipe，P3 才開 JS（goja），而且要放在獨立 worker process 裡跑。
- **Repo 定位待決**：見 §13。傾向「C 混合」起步：程式寫在 faryne.dev 裡，但抓取 executor 從第一天就拆成獨立 process，日後要整包獨立也好切。

## 1. 目標 / 不做

**目標**
- 使用者登入後可以建立一或多個專頁（tab），在 grid 上自由擺放、縮放 widget。
- 每個 widget 等於「一支腳本＋使用者填的參數」，例如「RSS 列表＋某個 feed URL」或「匯率卡片＋幣別」。
- 腳本有三種來源：內建（官方維護）、自己寫的、他人公開分享的；可以 fork。
- 腳本可以抓 HTML（沿用爬蟲 lib 的 selector），也可以直接吃他站的 JSON/XML/RSS。
- 公開註冊，自己的腳本和專頁可以選擇公開。

**不做（至少在 P1～P2）**
- 自訂 HTML/JS 的呈現（P4 再評估）。
- 給使用者腳本用 headless Chrome（成本高、濫用面大）。既有的 chromedp 只給內建 provider 用。
- 雙向寫回（widget 只讀，不代替使用者對他站送表單或發文）。
- 真離線或 PWA 同步（沿用既有原則：離線一律顯示無法使用）。

## 2. 名詞

| 名詞 | 說明 |
|---|---|
| Page（專頁） | 使用者的一個 tab，裡面有多個 widget 和 grid 版位 |
| Widget | 版位上的一個區塊實例：`script_version`＋`params`＋版位（x/y/w/h）＋標題覆寫 |
| Script（腳本） | 一份 recipe，有作者、可見度和多個不可變的版本 |
| Recipe | 腳本內容本體，宣告式 JSON（P3 起可以含 JS step） |
| Renderer | 前端固定的呈現元件，吃標準化資料 |
| Provider | Go 寫死的內建資料來源（例如既有的匯率、ETF、消防爬蟲），recipe 可以用 `provider` step 呼叫 |
| Executor | 伺服器端執行 recipe 的元件，負責 fetch、extract、transform、快取 |

## 3. Recipe 規格（P0/P1 核心）

### 3.1 結構

```jsonc
{
  "version": 1,                       // recipe 格式版本，不是腳本版本
  "params": [                         // 使用者在 widget 上填的參數，用來產生設定表單
    { "key": "feed", "type": "url", "label": "RSS 網址", "required": true },
    { "key": "limit", "type": "int", "default": 10, "min": 1, "max": 50 }
  ],
  "fetch": {
    "url": "{{params.feed}}",         // 只允許 params 插值，不允許任意運算式
    "method": "GET",                  // P1 只開 GET；POST 留到 P2（GraphQL 類來源需要）
    "headers": { "Accept": "application/rss+xml" }  // header 走白名單（Accept、Accept-Language、P2 的 Authorization 由 secret 帶入）
  },
  "extract": { "type": "rss" },       // html | json | xml | rss | provider
  "transform": [
    { "op": "limit", "n": "{{params.limit}}" }
  ],
  "output": "items",                  // 輸出標準 item 陣列，或 "value"（單一數值或物件）
  "render": {
    "renderer": "list",
    "map": { "title": "title", "url": "link", "time": "pubDate" }
  },
  "ttl": 900                          // 秒；Executor 會套用下限（見 §6）
}
```

### 3.2 extract 類型

| type | 說明 | 實作 |
|---|---|---|
| `html` | 沿用現有 `crawler.SelectorRequest`（`service/crawler/index.go`），補上「Multiple 子節點展開成多筆 item」的能力 | goquery |
| `json` | 他站 JSON API，用 JSONPath 取值 | 新增 JSONPath 套件（例如 `github.com/PaesslerAG/jsonpath`） |
| `xml` | 一般 XML，用 XPath 取值 | `github.com/antchfx/xmlquery` |
| `rss` | RSS/Atom，內建 parser，免寫規則 | `github.com/mmcdole/gofeed` |
| `provider` | 呼叫 Go 寫死的內建來源，`{ "type": "provider", "name": "rates.bank", "args": {...} }` | 註冊表 `map[string]Provider`，模式參考 `service/rates/fetcher.go` 的 `Banks` |

- 他站 JSON/XML 只是 `extract.type` 不同，跟爬 HTML 走同一條 pipeline、同一套快取與 SSRF 規則。
- `provider` 是把既有 Go 爬蟲（匯率、ETF、消防等）接進來的方式：這些 provider 不需要 fetch step，參數由 provider 自己定義 schema。

### 3.3 transform 運算（P1 白名單）

`pick` / `rename` / `filter`（欄位比較：eq/contains/gt/lt）/ `sort` / `limit` / `dedupe` / `format`（日期、數字、截字）/ `absolute_url`（相對網址補成絕對網址）。
刻意**不做**任意運算式，需要邏輯時等 P3 的 JS step。

### 3.4 標準輸出

```jsonc
// output = "items"
[{ "title": "", "url": "", "image": "", "time": "RFC3339", "value": 0, "extra": {} }]
// output = "value"
{ "value": 31.52, "label": "USD/TWD", "delta": -0.03, "time": "RFC3339" }
```

### 3.5 範例

**他站 JSON 匯率卡片**

```jsonc
{
  "version": 1,
  "params": [{ "key": "currency", "type": "enum", "options": ["USD","JPY","EUR"], "default": "USD" }],
  "fetch": { "url": "https://example.com/api/rates.json" },
  "extract": { "type": "json", "path": "$.rates[?(@.code=='{{params.currency}}')]" },
  "transform": [{ "op": "rename", "from": "spot_sell", "to": "value" }],
  "output": "value",
  "render": { "renderer": "number", "map": { "value": "value", "label": "code" } },
  "ttl": 600
}
```

**HTML 爬蟲（沿用 SelectorRequest）**

```jsonc
{
  "version": 1,
  "params": [],
  "fetch": { "url": "https://example.com/news" },
  "extract": {
    "type": "html",
    "rules": [{ "name": "items", "pattern": "ul.news > li", "multiple": true, "child": [
      { "name": "title", "pattern": "a", "trim": true },
      { "name": "link",  "pattern": "a", "attrs": ["href"] }
    ]}]
  },
  "transform": [{ "op": "absolute_url", "field": "link" }, { "op": "limit", "n": 10 }],
  "output": "items",
  "render": { "renderer": "list", "map": { "title": "title", "url": "link" } },
  "ttl": 1800
}
```

## 4. Renderer

| renderer | 吃的資料 | 用途 |
|---|---|---|
| `list` | items | 新聞、RSS、排行 |
| `card` | items（有 image） | 帶圖的列表 |
| `table` | items＋欄位設定 | 表格資料 |
| `number` | value | KPI、匯率、股價 |
| `chart` | items（time＋value） | 折線、長條，沿用 MUI x-charts |
| `image-grid` | items（image） | 圖片牆 |
| `text` | value（純文字） | 公告、單句 |

- Renderer 只吃資料，所有字串一律當純文字輸出（不用 `dangerouslySetInnerHTML`）。連結只允許 http/https。
- 圖片走 image proxy（或至少加 `referrerpolicy="no-referrer"`），避免洩漏使用者 IP 和頁面網址給第三方站。
- P4 才評估 iGoogle gadget 式的自訂呈現：放在 sandboxed iframe（`sandbox="allow-scripts"`、獨立 origin）裡，用 postMessage 餵資料。

## 5. 執行與快取

```
Widget 請求 ─▶ API ─▶ 快取（Redis）命中？ ── 是 ─▶ 回傳（過期但在 stale 區間內 → 回舊資料＋背景刷新）
                            │ 否
                            ▼
                 singleflight(cache key) ─▶ Executor（獨立 process，見 §7、§12）
                            │
                 fetch（SSRF guard）→ extract → transform → 寫回快取
```

- **cache key** ＝ `hash(script_version_id + 正規化後的 params)`。相同腳本加相同參數跨使用者共用：100 人裝同一支公開腳本，只抓一次。
- **TTL 下限**：例如 300 秒，provider 可以自訂更短（ETF 10 秒那類由 provider 自己控制）。recipe 填的 ttl 低於下限會被拉高。
- **singleflight**，加上 **stale-while-revalidate**：過期後的一段時間內先回舊資料，背景重抓；抓失敗就繼續回舊資料並標示「資料時間」。
- **限流**：每個目標 host 的並發數與 QPS 上限（禮貌爬取，也避免被封 IP）；每個使用者每小時「快取未命中所觸發的實際抓取」配額。
- **Redis 不可用**：降級成直接抓，但仍受 singleflight 和 host 限流保護（參考 `service/fire_department/realtime.go` 的降級寫法）。快取批次讀寫參考 `service/etf/realtime_price.go`（MGet＋singleflight＋Pipeline）。
- **預熱**：不做全量預熱。只對「近 N 小時內有人看過的 cache key」用排程背景刷新（`cronjobs.go` 加一個 group），讓熱門 widget 常保新鮮。

## 6. 安全（公開註冊必備）

### 6.1 SSRF 防護（P0 必做，沒做完不能開公開註冊）

- 只允許 `http` / `https`，port 只開 80 / 443。
- 在 `net.Dialer.Control` / `DialContext` 檢查**解析後的實際 IP**：擋 private（10/8、172.16/12、192.168/16）、loopback、link-local（含 `169.254.169.254` 雲端 metadata）、CGNAT、multicast、IPv6 ULA/link-local。在 dial 階段檢查才能同時防 DNS rebinding。
- 每次 redirect 都重新檢查，最多 3 次。
- 回應大小上限（例如 2 MB，用 `io.LimitReader`），總 timeout 10 秒，不帶 cookie，固定 UA（標明是 Portal 抓取並附聯絡頁）。
- 不走 `CF_WORKER_PROXY_URL` 台灣 proxy（那是內建 provider 專用，不開放給使用者腳本）。
- 現有的 `helper.DoRaw` 沒有以上任何一項，所以 Executor 要用**獨立的 fetcher**，不能共用 `crawler.CrawlByUrl*`。可以重用的是 `crawl()` / `query()` 的抽取邏輯，抓取層要換掉。

### 6.2 Secret（P2）

- 有些來源需要 API key。使用者層級的 secret 用 AES-GCM 加密存 DB，recipe 用 `{{secret.NAME}}` 引用。
- 引用 secret 的腳本只能是 private；fork 時不複製 secret。
- 帶 secret 的請求結果**不進共用快取**（cache key 要加上 user id），避免 A 的付費 API 結果被 B 讀到。

### 6.3 公開腳本治理

- 發布時自動 dry-run：用預設參數跑一次，失敗不能發布。
- 檢舉與下架沿用 SteamLoom 檢舉機制的模式（`DevelopDocuments/storyteller/檢舉機制_2026-10-10.md`、`後台檢舉處理_2026-10-10.md`），後台掛在整合後台。
- 網域封鎖名單：被目標站要求停止抓取時，可以全域封鎖某個 host。
- robots.txt 是否遵守：**待決**（見 §15）。公開服務建議遵守，至少對 `extract.type=html` 的抓取遵守。

## 7. 分享模型

- 腳本可見度：`private` / `unlisted`（有連結才看得到）/ `public`（出現在市集）。
- **版本不可變**：每次儲存產生一個新的 `script_version`。widget 可以「釘選版本」或「跟隨最新」，預設跟隨最新；作者發布的新版 dry-run 失敗時，跟隨者自動停在舊版。
- fork：複製最新版成為自己的腳本，記錄 `forked_from`。
- 市集排序：安裝數、近 7 日安裝、更新時間；內建腳本置頂並加標記。
- 專頁也可以公開（唯讀分享），訪客看到的資料走同一份快取。

| POST/PATCH/DELETE | `/portal/me/pages/:id/widgets[/:wid]` | widget CRUD |

- 每頁都有中文 breadcrumb，API 錯誤跳 Snack。

## 10. JS 腳本（P3）

- 在 recipe 加 `{ "op": "js", "code": "..." }` 這種 transform step，或整支腳本用 JS 寫。
- 引擎用 goja，用 `vm.Interrupt` 做 timeout（例如 500 ms）。**goja 沒有記憶體上限**，所以一定要跑在獨立 worker process，用 cgroup / `ulimit` 限制記憶體，crash 只影響該 worker。
- 只暴露：`fetch`（走 §6.1 的同一個 SSRF guard，每次執行最多 N 次）、`crawler.select(html, rules)`、JSON 與日期工具。不暴露 fs、process、timer 迴圈。
- **替代方案**：JS 只負責 transform，並且放在**瀏覽器的 Web Worker** 執行（fetch 仍在伺服器端）。伺服器零執行風險，代價是無法共用 transform 結果的快取，公開專頁的訪客也要各自算一次。資料量小的 widget 可以接受，P3 動工時再比較。

## 11. 分期

| 階段 | 內容 | mockup |
|---|---|---|
| P0 | 抽取層擴充（html 多筆展開、json、xml、rss、provider 註冊表）、transform 白名單、SSRF-safe fetcher、Executor（快取、singleflight、限流） | 不需要 |
| P1 | 自用專頁（grid、多 tab）、內建腳本 5～10 支、recipe 編輯器＋dry-run、他站 JSON/RSS | 需要 |
| P2 | 公開分享、unlisted、fork、版本釘選、市集、檢舉與後台、配額、secret、公開專頁 | 需要（市集、詳細頁） |
| P3 | JS 腳本（goja worker 或 Web Worker） | 不需要 |
| P4 | 自訂 renderer（sandboxed iframe） | 需要 |

公開註冊至少要等 P0 的 SSRF 防護與 P2 的配額、檢舉都完成才開；P1 期間只開給自己用。

## 12. Executor 隔離方式

不論 §13 選哪個 repo 方案，Executor 都建議做成**可以單獨部署的 process**：
- 透過 AMQP 或內部 HTTP 收「執行 recipe」的請求，回傳結果。專案已有 AMQP（`rabbitmq/amqp091-go`），可以沿用。
- 這個 process 不持有 MySQL 帳密，只連 Redis（寫快取），或連 Redis 也不要、直接回傳結果。
- 部署在獨立 container，用網路政策擋掉內網（跟 §6.1 的 IP 檢查形成雙層防護）。
- 本機開發時可以直接在主 process 內呼叫（介面相同、用 build tag 或設定切換），不用多開服務。

## 13. Repo 定位分析（待決）

### 方案

- **A：一開始就獨立 repo**。自己的 DB、Redis、Firebase 專案、Docker 部署（tw-fire-realtime 模式：`go:embed` 前端、multi-arch、GHCR）。
- **B：在 faryne.dev 內做**。照現有多品牌模式：後端路徑前綴 `/portal`、前端 `isPortalSite()`＋`portalPath()`、nginx 依網域轉送、獨立 Firebase 專案＋joyu 式的 per-request ID token。
- **C：混合**。程式在 faryne.dev（同 B），但 Executor 從第一天就是獨立 process 或 container（§12），模組邊界比照獨立 repo 切乾淨（`service/portal/...` 不 import 主站其他業務 service）。

### trade-off

| 面向 | A 獨立 repo | B faryne.dev 內 | C 混合 |
|---|---|---|---|
| 上線速度 | 慢：auth、DB、部署、CI 都要重建 | 最快 | 快（多一個 executor 部署） |
| SSRF 隔離 | 天然隔離 | 最差：抓取跟主站 DB 帳密在同一個 process | 好：executor 不持有主站帳密 |
| 重用既有基礎 | 低：要複製 crawler、firebase token 驗證、output、檢舉後台 | 高 | 高 |
| 跟「整合進統一 tech stack」策略 | 相反，需要站得住的理由 | 一致 | 一致 |
| self-host、開源、給別人架 | 最容易 | 難（綁在 faryne.dev monorepo） | 中：日後抽出成本低 |
| 主站被拖累的風險（資源、被封 IP） | 無 | 有：大量外部抓取會吃主站資源，目標站封的是主站 IP | 執行資源分開，但出口 IP 仍可能相同（看部署） |
| 維運負擔 | 多一套系統要顧 | 不增加 | 小幅增加 |

### 共用件與共用方式

| 共用件 | 位置 | 規模 | A 案的處理 |
|---|---|---|---|
| 爬蟲抽取邏輯 | `service/crawler/`（index.go 19 行、function.go 179 行） | 小 | 複製（tw-fire-realtime 前例），或抽成獨立 Go module 讓兩邊 import。Portal 會大幅擴充抽取層，**建議反過來**：在 Portal 內長成完整的 lib，faryne.dev 日後再改 import 它 |
| Firebase ID token 驗證 | `service/auth/firebase_token.go`（223 行） | 小 | 複製 |
| 標準回應 | `service/output/` | 小 | 複製 |
| HTTP helper | `service/helper/http.go` | 小，而且不適合跑使用者腳本 | 不共用，Portal 自己寫 SSRF-safe fetcher |
| 檢舉後台、整合後台 | 主站 `backend_admin` | 中 | 要重做，或先用最陽春的 DB 直接操作 |
| 內建 provider（匯率、ETF、消防等） | 各 `service/*` | 大 | A 案下 provider 只能改成打 faryne.dev 的公開 API，不能直接呼叫 Go 函式 |

### 傾向（待使用者決定）

傾向 **C 起步**，理由：
1. 安全上真正需要隔離的只有「抓取」這一層，C 已經把它隔開，不需要為了隔離把整個產品搬出去。
2. 內建 provider 是差異化賣點，在 faryne.dev 內可以直接呼叫既有的 Go 爬蟲，A 案只能繞公開 API。
3. 跟「先整合進統一 tech stack」的策略一致；模組邊界切乾淨，日後真的要開源或 self-host，再抽成 A 的成本可控。

會讓結論翻成 A 的條件：想要讓別人 self-host 或開源、預期流量大到會拖累主站，或希望 Portal 跟主站的部署節奏完全脫鉤。

## 14. User stories

1. **自己的晨間儀表板**：我建一個「早上」tab，放消防即時（內建 provider）、匯率卡片（內建）、三個 RSS（他站 RSS），早上打開一頁看完。
2. **把自己的爬蟲變成 widget**：我在編輯器貼上某論壇的 selector 規則，dry-run 看到列表正確，存成 private 腳本放進專頁；之後覺得好用改成 public，讓別人也能裝。
3. **安裝他人的腳本**：訪客在市集找到「某漫畫網站新刊列表」，填入自己追的作品 ID 當參數，裝到專頁；作者之後修了 selector，訪客的 widget 自動跟上新版。
4. **作者改壞了**：作者發布的新版 selector 寫錯，dry-run 失敗，跟隨最新的安裝者自動停在舊版，不會整排 widget 變空白。

## 15. 常見 fail 與對應

| 現象 | 原因 | 對應 |
|---|---|---|
| widget 突然空白或資料錯亂 | 目標站改版，selector 失效 | 抓取成功但抽出 0 筆時視為失敗，繼續回舊快取並標示資料時間；連續失敗 N 次通知腳本作者 |
| 某個來源一直 403 或 429 | 被目標站封 IP 或限流 | host 層級的限流與退避（exponential backoff），持續失敗就暫停該 host 一段時間；必要時加進封鎖名單 |
| 熱門公開腳本把目標站打爆 | 每個安裝者各自觸發抓取 | 共用快取＋singleflight＋TTL 下限，抓取次數跟安裝數脫鉤 |
| 參數太多樣導致共用快取失效 | 每個人填不同參數（例如各自的 feed URL） | 這是預期內的，靠每個使用者配額＋host 限流控制總量 |
| 作者改版害到安裝者 | 新版有 bug | 版本不可變＋dry-run 失敗不前進＋可以釘選版本 |
| 惡意腳本打內網或雲端 metadata | SSRF | §6.1 的 dial 階段 IP 檢查＋redirect 重驗＋executor 網路隔離 |
| 惡意腳本拿 Portal 當掃描器或 DDoS 跳板 | 大量不同 host 的抓取 | 每個使用者配額、dry-run 配額更嚴、新帳號配額更低、異常偵測後停權 |
| 回應很大或很慢拖垮 executor | 目標回傳大檔或慢速回應 | 2 MB 上限＋10 秒 timeout＋executor 並發上限 |
| 快取雪崩 | 大量 key 同時過期 | TTL 加隨機抖動＋stale-while-revalidate |
| 編輯器 dry-run 被濫用成免費代理 | dry-run 不寫 DB、沒有快取 | dry-run 獨立配額、結果只回前 N 筆、不回原始 body |
| 他站 JSON 含惡意字串（XSS） | renderer 直接塞 HTML | renderer 一律純文字輸出、連結只允許 http/https |
