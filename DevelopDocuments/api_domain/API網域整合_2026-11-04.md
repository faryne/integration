# API 網域整合（各網域 /api＋CORS 白名單）規格

- 狀態：步驟 0～2 的 nginx 設定已實作（2026-11-04），待部署；步驟 3～5（前端切換、CORS 收斂、收尾）尚未開始
- 前置：[整合後台](../backend_admin/整合後台_2026-11-04.md) 已完成

## 目標

1. 各站前端改打自己網域的 `/api`：`faryne.dev/api`、`galgame.tv/api`、`neko.maid.tw/api`，`steamloom.works/api` 維持現狀。
2. 後端 CORS 從 `*` 收斂成白名單。
3. **過渡期間任何舊版呼叫端都不能壞**，包括還開著舊版分頁的使用者、外部已設定好的 MCP client、userscript。

## 現況重點（盤點結論）

- **後端路由本來就沒有 `/api-integration` 前綴**，是 nginx `location /api-integration/` 剝掉後再轉給後端。所以後端路由一行都不用改，`/api` 只是 nginx 多一個入口。
- 各站前端 build 時的 `VITE_API_BASE`（`makefile`）：

| 站 | 前端託管 | 現在的 API base | 要改成 |
|---|---|---|---|
| faryne.dev | nginx → proxy 到 Firebase（beta.faryne.dev） | `https://faryne.dev/api-integration` | `https://faryne.dev/api` |
| neko.maid.tw | nginx → proxy 到 Firebase（nekomaid.web.app） | `https://faryne.dev/api-integration`（跨站） | `https://neko.maid.tw/api` |
| galgame.tv | **直連 Firebase，nginx 沒有它的 server block** | `https://faryne.dev/api-integration`（跨站） | `https://galgame.tv/api` |
| steamloom.works | nginx | `https://steamloom.works/api` ✅ | 不變 |

- 登入走 `X-Encrypt-Key` header，不是 cookie。CORS 不需要 `AllowCredentials`，改 API 網域也不影響登入狀態（登入狀態存在前端 origin 的 localStorage，前端 origin 沒變）。
- 後端用 `X-Real-IP`（只信任 127.0.0.1）取得使用者 IP，AV 上稿、VTuber 搜尋的 IP 限流都靠它。新的 `/api` 入口一定要帶 `X-Real-IP`。
- 前端沒有 service worker，舊版 bundle 只會留在「還沒重新整理的分頁」和 index.html 的 HTTP 快取裡，不會長期殘留。

## 不在前端裡的呼叫端（過渡期的主要風險）

| 呼叫端 | 打的位置 | 是否受 CORS 影響 | 處理 |
|---|---|---|---|
| 舊版前端分頁（三個站） | `faryne.dev/api-integration/*`，Origin 是自家網域 | 是 | `/api-integration` 永久保留，白名單包含所有自家網域 → 不會壞 |
| 已設定好的 MCP client（PAT） | `faryne.dev/api-integration/storyteller-mcp` | 否（非瀏覽器） | 保留舊路徑；MCP 連接頁改顯示新網址 |
| SteamLoom MCP／OAuth（含 Writer 桌面版） | `steamloom.works/mcp`、`/oauth/*`、`/.well-known/*`、`/api` | Writer 由 Go 端發請求（ApiProxy），不受影響 | 不動 |
| userscript `threads-capture` | `faryne.dev/api-integration/tools/threads/oembed_capture` | 否（`GM_xmlhttpRequest`） | 保留舊路徑；腳本有空再改新網址 |
| userscript `nekomaid-retriever` | `neko.maid.tw/retrieve.json` | 否 | 不動 |
| Firebase Hosting 的 `/sns/*` 302 | `faryne.dev/api-integration/sns/...` | 否 | 保留舊路徑；`firebase.json` 順便改成新路徑 |
| 爬蟲 SNS 預覽、neko.maid.tw RSS | nginx 直接 rewrite 到後端，不經過前綴 | 否 | 不動 |

**結論：`/api-integration` 要永久保留當 alias**。成本只是 nginx 多一個 location，換來外部呼叫端永遠不用跟著改。

> 另外發現一個跟這案無關、但早就壞掉的東西：userscript `av-image-replacer` 打的是 `faryne.dev/api/opendata/dmm/video`。這個路徑 prod 目前回的是前端 HTML，而且腳本解析的是舊 PHP 版 API 的 `data.rows` 格式。`/api` 上線後它會改成拿到後端的 404 JSON，一樣是壞的。要修得另外改腳本。

## 設計

### nginx

- 把 `/api-integration/` 那段 proxy 設定（`X-Real-IP`、timeout 600s、502/503/504 錯誤頁）抽成共用 snippet：`httpd_conf/snippets/faryne_api_proxy.conf`。faryne.dev、neko.maid.tw、galgame.tv、steamloom.works 的 `location /api/` 和 faryne.dev 的 `location /api-integration/` 都 `include` 這一份，避免四份設定各自漂移。
- `location /api/` 一律整段轉給後端並剝掉前綴，跟 steamloom.works 現在的寫法一致。**不做**「每個網域只開放自己的路徑」：權限本來就由後端的 session／is_admin 把關，分網域限制路徑只會增加維護成本。
- 502/503/504 錯誤頁原本寫死 `Access-Control-Allow-Origin: *`，改成用 `map $http_origin $cors_origin` 回應白名單內的 origin。新版前端是同源請求，用不到這個 header；它是留給還在打 `/api-integration` 的舊分頁。
- **galgame.tv 搬到 nginx 後面**：比照 neko.maid.tw 加一個 server block，`/api/` 轉後端、`/` proxy 到 `galgame-tv.web.app`；port 80 的 redirect 區塊也要加上 galgame.tv。之後要讓 galgame.tv 也有爬蟲預覽（`@galgame_sns`）就有地方掛，這次先不做。

### galgame.tv 的現況與搬遷方式（2026-11-04 實測）

| 觀察 | 結果 | 代表的意思 |
|---|---|---|
| `dig galgame.tv` | `104.21.70.237`、`172.67.140.122` | Cloudflare 橘雲（proxy） |
| 瀏覽器拿到的憑證 | `*.galgame.tv`、Let's Encrypt、90 天 | Cloudflare Universal SSL，由 CF 自動續期 |
| 直連主機 54.199.205.75、SNI 帶 galgame.tv | 拿到 `faryne.dev` 的憑證（SAN 沒有 galgame.tv），落到 faryne.dev 的 server block | **機器上的 nginx 沒有 galgame.tv 的設定** |
| 經 CF 打 `galgame.tv/api-integration/...` | 回 HTML（`x-served-by` 是 Firebase CDN） | **CF 回源目標是 Firebase**，不是這台主機 |

因為已經開了橘雲，搬遷比一般切 DNS 簡單：

- **只要在 Cloudflare 把回源目標從 Firebase 改成主機 IP，維持橘雲**。訪客解析到的一直是 Cloudflare 的 IP，所以沒有 DNS 快取、TTL 的問題，改了立即生效，改回去也立即回滾。原本規格裡的降 TTL、Firebase 自訂網域保留一週都不需要了。
- **回源憑證：用 Cloudflare Origin CA**（主機上沒有 galgame.tv 的 Let's Encrypt，2026-11-04 確認）。
  - 在 CF 後台 SSL/TLS → Origin Server 產生，涵蓋 `galgame.tv`、`*.galgame.tv`，效期 15 年、不用續期。只有 Cloudflare 會信任它，但 galgame.tv 全部經過 proxy，剛好夠用。
  - 憑證與私鑰放在主機上（例如 `/etc/ssl/cloudflare/galgame.tv.pem`、`.key`，權限 600），**不進 repo**；nginx 設定只引用路徑。
  - Cloudflare 的 SSL/TLS 模式要是 **Full (strict)**，回源才會驗證憑證。
- **真實 IP**：開橘雲時，nginx 的 `$remote_addr` 是 Cloudflare 的 IP。要在 nginx 的 http 區塊加上 `set_real_ip_from <Cloudflare IP 段>` 和 `real_ip_header CF-Connecting-IP`（放在 `httpd_conf/snippets/cloudflare_real_ip.conf`），`X-Real-IP` 才會是使用者的真實 IP。只信任來自 Cloudflare IP 段的 header，灰雲的 faryne.dev、neko.maid.tw 不受影響。
  - ⚠️ **既有地雷（已確認）**：steamloom.works 也是橘雲，機器上的 nginx 沒有任何 `real_ip` 設定（2026-11-04 確認，機器設定與 repo 相同）。SteamLoom 的稽核紀錄 IP、OAuth 動態註冊的 IP 限流、`/mcp` 的 client IP 現在拿到的都是 Cloudflare 邊緣 IP。這跟本案無關，**另開小改動先修**，本案直接沿用那份 snippet。

### 後端 CORS（`main.go`）

分兩組，用 Fiber cors 的 `Next` 互斥：

| 路徑 | CORS | 理由 |
|---|---|---|
| `/storyteller-mcp*`、`/oauth/*`、`/.well-known/*` | 維持 `*` | 公開協定端點，用 bearer token／PAT 驗證，瀏覽器版 MCP client（例如 MCP Inspector）需要跨站呼叫 |
| 其他全部 | 白名單 | — |

- 白名單由 `config` 的 `CORS_ALLOW_ORIGINS`（逗號分隔）提供，預設值是 prod 清單：`https://faryne.dev`、`https://www.faryne.dev`、`https://beta.faryne.dev`、`https://galgame.tv`、`https://www.galgame.tv`、`https://neko.maid.tw`、`https://steamloom.works`、`https://www.steamloom.works`。
- 非 production（`!IsProduction()`）時再用 `AllowOriginsFunc` 放行任何 port 的 `http://localhost`、`http://127.0.0.1`，本機 vite 換 port 不用改設定。
- `ExposeHeaders: X-Session-Expires-At` 照舊。

### 前端

- `makefile` 三個 build target 改成各自網域的 `/api`。維持絕對網址、不改成相對路徑 `/api`：直接開 `beta.faryne.dev`、`*.web.app` 時才不會打到 Firebase 拿到 HTML。
- `pages/storyteller/mcpClientSetup.ts`：faryne.dev 的 MCP 端點顯示改成 `https://faryne.dev/api/storyteller-mcp`，舊網址繼續可用。
- `firebase.json` 的 `/sns/*` 302 改成 `/api/sns/...`。
- 本機 `.env`（`VITE_API_BASE=http://localhost:8080`）不變。

## 過渡計畫

原則：**每一步都向下相容，新舊路徑並存**；前端最後才切；CORS 收斂前先看實際流量。每一步都可以單獨回滾。

| 步驟 | 內容 | 舊版呼叫端 | 回滾方式 |
|---|---|---|---|
| 0. 觀察 | nginx access log 加 `$http_origin`，跑 1～2 週，統計打 `/api-integration` 的 Origin 有哪些 | 無影響 | 拿掉 log 欄位 |
| 1. 開新入口 | faryne.dev、neko.maid.tw 加 `location /api/`（共用 snippet），`/api-integration` 改用同一份 snippet | 無影響 | 拿掉 location |
| 2. galgame.tv 搬進 nginx | 準備回源憑證 → 加 Cloudflare real IP 設定與 galgame.tv server block、`nginx -t` → 用 `curl --resolve galgame.tv:443:<主機IP>` 直連驗證頁面與 `/api` → Cloudflare 把 galgame.tv 的回源紀錄改指主機（維持橘雲，SSL 模式 Full (strict)） | 前端此時仍打 `faryne.dev/api-integration`，不受影響；CF 改回源立即生效，沒有空窗 | Cloudflare 把紀錄改回原本的 Firebase 值（切換前先記下來） |
| 3. 前端切換 | 三站改用新的 `VITE_API_BASE` 重新部署；MCP 連接頁、`firebase.json` 一起改 | 舊分頁繼續打 `/api-integration`，CORS 仍是 `*` | 重新部署舊 build |
| 4. CORS 收斂 | 依步驟 0 的統計確認沒有漏掉的 Origin 後上線白名單 | 舊分頁的 Origin 都在白名單內 | `CORS_ALLOW_ORIGINS=*` 或還原程式 |
| 5. 收尾 | 更新 `httpd_conf/nginx` 開頭的說明、開發文件；`/api-integration` **保留不刪** | — | — |

**順序的理由**
- 步驟 2 一定要在步驟 3 之前：如果 galgame.tv 前端先改打 `galgame.tv/api`，但 DNS 還指著 Firebase，請求會被 Firebase 的 `** → index.html` rewrite 吃掉，回來的是 HTML。
- 步驟 4 放在最後：CORS 是這案唯一會讓既有呼叫端「突然壞掉」的變更，跟其他步驟分開上線，出事時一眼就知道是它。

## 部署步驟 0～2（nginx，2026-11-04 實作）

repo 異動：
- `httpd_conf/snippets/faryne_api_proxy.conf`：API 入口共用設定（location 內 include）。
- `httpd_conf/snippets/faryne_api_errors.conf`：502／503／504 錯誤頁（server 內 include）。
- `httpd_conf/nginx`：
  - 新增 `log_format with_origin`，faryne.dev 的 access log 改用這個格式。
  - faryne.dev、neko.maid.tw 加 `/api/`，faryne.dev 的 `/api-integration/` 改用共用 snippet。
  - steamloom.works 的 `/api/` 改用共用 snippet，順便補上原本沒有的錯誤頁。
  - 新增 galgame.tv 的 server block，port 80 的 redirect 也加上 galgame.tv。
- `/api/` 一律寫成 `location ^~ /api/`，避免被 neko.maid.tw 的 `retrieve.json` 這類 regex location 搶走。

已用 docker 版 nginx 載入整份設定驗證（各憑證路徑放假憑證，後端換成會回傳收到內容的假服務）：
- `nginx -t` 通過。
- 四個網域的 `/api/*` 都有剝掉前綴並帶上 `X-Real-IP`；`/api-integration/*`、`/mcp`、neko.maid.tw 的 `/retrieve.json` 照舊。
- steamloom.works 的前端路由 `/api-keys` 沒有被 `/api/` 吃掉。
- 後端掛掉時，四個網域的 `/api/*` 都回 `application/json` 的標準錯誤格式。
- faryne.dev 的 access log 最後一欄有記到 Origin。

機器上的部署順序：
1. **檢查憑證檔**：`.cert` 第一行應該是 `-----BEGIN CERTIFICATE-----`，`.pem` 應該是 `-----BEGIN PRIVATE KEY-----`；私鑰權限設成 600。
2. **套用 nginx**：把三個 snippet 複製到 `/etc/nginx/snippets/`，更新 site 設定，跑 `sudo nginx -t` 後 reload。
3. **切換前直連驗證**：在機器上用 `curl -sk --resolve galgame.tv:443:127.0.0.1 "https://galgame.tv/api/galgame/brands?per_page=1"`，要回 JSON。從外面打 `https://faryne.dev/api/galgame/brands?per_page=1`、`https://neko.maid.tw/api/galgame/brands?per_page=1`，也都要回 JSON。
4. **Cloudflare**：galgame.tv 的 SSL/TLS 模式設成 **Full (strict)**。原本回源的 Firebase 也有合法憑證，所以可以先改。接著記下 galgame.tv、www.galgame.tv 原本的 DNS 紀錄，改指 `54.199.205.75`，維持橘雲。
5. **切換後驗證**：
   - `https://galgame.tv/api/galgame/brands?per_page=1` 回 JSON（切換前回的是 HTML）。
   - galgame.tv 的頁面正常。
   - access log 裡 galgame.tv 的請求是使用者真實 IP。
6. **觀察一週後統計 Origin**（步驟 0）：`sudo grep -h '/api-integration/' /var/log/nginx/access.log* | grep -o '"[^"]*"$' | sort | uniq -c | sort -rn`，用結果確認 CORS 白名單。

回滾：步驟 4 出事就把 Cloudflare 紀錄改回原本的值；nginx 改壞了就還原 site 設定後 reload（新 snippet 留著不影響）。

## User Stories

1. 使用者在 galgame.tv 瀏覽時，DevTools 只看得到 `galgame.tv/api/...` 的同源請求，不再有跨站到 faryne.dev 的 preflight。
2. 某人開著舊版 neko.maid.tw 分頁一整天沒重新整理，期間 API 上線新入口、CORS 收斂，他的分頁照常可用。
3. 作者的 Claude Desktop 還設定著 `faryne.dev/api-integration/storyteller-mcp`，什麼都不用改照常能用；新來的作者在連接頁看到的是 `/api` 新網址。
4. 某個不在白名單的網站用瀏覽器直接 `fetch` faryne.dev 的 API，被 CORS 擋下；用 `curl` 或 userscript 的 `GM_xmlhttpRequest` 則不受影響。

## 常見失敗與應對

| 情境 | 應對 |
|---|---|
| 新的 `/api` 少帶 `X-Real-IP`，所有人被當成同一個 IP 一起限流 | 共用 snippet 統一帶；步驟 1 上線後用兩個不同 IP 打 VTuber 搜尋確認限流各自計算 |
| 改回源後 Cloudflare 回 525／526（回源 SSL 失敗） | 主機沒掛 galgame.tv 憑證，或 Full (strict) 下憑證不被信任；切換前先用 `curl --resolve` 驗證；出事時把 CF 紀錄改回 Firebase |
| 橘雲下限流全部算到 Cloudflare 的 IP 上 | 加 `cloudflare_real_ip.conf`；步驟 2 驗證時確認後端 log 的 IP 是使用者 IP |
| Cloudflare 的 IP 段改了，real IP 失效 | IP 段變動很少；snippet 註明來源網址（`https://www.cloudflare.com/ips/`），出問題時重新抓一次即可 |
| 前端先部署、galgame.tv DNS 還沒切，API 拿到 HTML | 步驟順序強制 2 → 3；部署 galgame 前先 `curl https://galgame.tv/api/galgame/brands` 確認回的是 JSON |
| CORS 收斂後有漏掉的合法 Origin | 步驟 0 的 log 先統計；萬一還是漏了，`CORS_ALLOW_ORIGINS` 改 env 加上去後重啟即可，不用改程式 |
| 後端掛掉時，舊分頁拿到的 502 沒有 CORS header，前端看到的是網路錯誤 | nginx 錯誤頁改用 `$cors_origin`，白名單 origin 照樣拿得到標準錯誤格式 |
| MCP Inspector 這類瀏覽器版 client 連不上 | 協定端點維持 `*` |
