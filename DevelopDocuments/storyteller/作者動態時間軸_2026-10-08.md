# 作者動態時間軸

- 狀態：已實作並併入 main（`196771f`，未 push）；mockup 見 `author-timeline-mockup/`
- Branch：`feature/steamloom-author-timeline`
- 前置：多筆名（`storyteller_author_profiles`）、站內通知（`站內通知_2026-10-01.md`）、被追蹤通知與筆名回追（`被追蹤通知與筆名回追_2026-10-07.md`）

## 目標

1. 作者／筆名頁多一個「動態」分頁，作者可以發想法、公告（類 X 的短貼文）。
2. 登入的人可以留言、按讚；不做轉推。
3. 作者在自己的貼文底下回覆時，自動用**這則貼文的身份**（本人或筆名）回覆。
4. 有人留言／回覆 → 進作者的站內通知。

## 身份規則（隱私核心，跟回追同一套邏輯）

- **每個身份各自一條時間軸**：本人頁只列 `profile_id = 0` 的貼文，筆名頁只列該筆名的。本人頁絕不合併筆名貼文（合併就等於公開 P＝本人）。
- **發文身份＝所在頁面的身份**：擁有者在筆名 P 的頁面發文就是 P 發的，不需要身份選擇器。
- **留言身份**：
  - 在「自己某個身份」的貼文底下 → 自動用該貼文的身份（P 的貼文底下就是 P 在回）。
  - 其他地方 → 本人身份。v1 不提供「以筆名在別人的貼文留言」（同追蹤按鈕 v1 不給選擇器）。
- **留言者必須有筆名**：本人身份 `pen_name` 空白時不能留言，前端引導先設定筆名。理由：不能退回 `fallbackAuthorName`（會吐 email），而一串留言全是「一位讀者」也沒辦法對話。按讚不需要。
- **按讚不公開按讚者名單**，只顯示數字：`likes` 只記帳號、不記身份，從根本上不可能洩漏筆名關係，也省掉名單 UI。
- **封鎖以作者身份為單位**：記「哪個身份（user_id＋profile_id）封鎖了哪個帳號」。在筆名 P 封鎖的人，在本人貼文底下照樣能留言；若封鎖對整個帳號生效，被封鎖者去另一個身份一試就知道兩者是同一人。要兩邊都擋就各封一次。

## Schema（MySQL 5.7）

```sql
CREATE TABLE storyteller_author_posts (
  id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  public_id VARCHAR(32) NOT NULL,
  user_id BIGINT UNSIGNED NOT NULL,          -- 擁有者帳號，不對外輸出
  profile_id BIGINT UNSIGNED NOT NULL DEFAULT 0, -- 發文身份；0 = 本人
  body TEXT NOT NULL,                         -- 純文字，上限 1000 字
  pinned_at TIMESTAMP NULL DEFAULT NULL,      -- 置頂（每身份最多 1 則），給「公告」用
  attach_type VARCHAR(16) NOT NULL DEFAULT '', -- 作品卡：'' / 'project' / 'story'（某一話）
  attach_id BIGINT UNSIGNED NOT NULL DEFAULT 0,
  notified_at TIMESTAMP NULL DEFAULT NULL,    -- 追蹤者通知掃描處理過的時間；NULL = 還沒處理
  is_deleted TINYINT(1) NOT NULL DEFAULT 0,
  deleted_at TIMESTAMP NULL DEFAULT NULL,
  created_at / updated_at,
  UNIQUE KEY (public_id),
  KEY idx_timeline (user_id, profile_id, is_deleted, id),
  KEY idx_notify_scan (notified_at, is_deleted)
);

CREATE TABLE storyteller_comments (           -- 刻意做成通用留言表，見「與討論區的關係」
  id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  public_id VARCHAR(32) NOT NULL,
  target_type VARCHAR(32) NOT NULL,           -- v1 只有 'author_post'
  target_id BIGINT UNSIGNED NOT NULL,
  parent_id BIGINT UNSIGNED NOT NULL DEFAULT 0, -- 0 = 頂層留言；回覆只掛在頂層下（兩層）
  reply_to_id BIGINT UNSIGNED NOT NULL DEFAULT 0, -- 直接回覆的那則回覆；回覆頂層留言時為 0（＝parent）
  user_id BIGINT UNSIGNED NOT NULL,
  profile_id BIGINT UNSIGNED NOT NULL DEFAULT 0,
  body TEXT NOT NULL,                         -- 上限 500 字
  is_deleted / deleted_at / created_at,
  UNIQUE KEY (public_id),
  KEY idx_target (target_type, target_id, parent_id, id)
);

CREATE TABLE storyteller_author_blocks (        -- 作者封鎖名單；之後討論區共用
  id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  user_id BIGINT UNSIGNED NOT NULL,             -- 封鎖者帳號
  profile_id BIGINT UNSIGNED NOT NULL DEFAULT 0, -- 封鎖者身份；0 = 本人
  blocked_user_id BIGINT UNSIGNED NOT NULL,     -- 被封鎖的帳號（不分對方用哪個身份）
  is_deleted / deleted_at / created_at,         -- 解除封鎖＝soft delete；重新封鎖時復活同一列
  UNIQUE KEY (user_id, profile_id, blocked_user_id),
  KEY idx_blocked (blocked_user_id)
);

CREATE TABLE storyteller_author_post_likes (
  post_id BIGINT UNSIGNED NOT NULL,
  user_id BIGINT UNSIGNED NOT NULL,
  created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (post_id, user_id)
);
```

- **留言數＝頂層留言＋回覆，排除已刪除**；時間軸卡片的 💬 與單頁標題用同一個數字。
- 讚／留言數**不做反正規化計數欄位**：時間軸一頁 20 則，用兩支 `GROUP BY post_id` 批次查詢即可，省掉計數漂移的問題。量真的大了再加。
- 讚是硬刪（取消讚就 DELETE），不需要 soft delete。

## 內容規則

- 純文字、保留換行、URL 自動連結；**不做** Markdown、圖片、自由輸入的 @提及、hashtag。
- **回覆對象（@）是結構化欄位**：在第二層按「回覆」會帶出「↪ 回覆 @青嵐」，存成 `reply_to_id`，前端不能手改、只能按 × 改回「回覆整串」。顯示名稱即時依該則留言的身份查詢；被回覆的那則已刪除就顯示「↪ 回覆 已刪除的留言」。回覆頂層留言時不顯示（本來就看得出來）。
  - 不做自由輸入：不解析內文、不能 @ 任意人，避免變成 mention 洗版／騷擾管道，也不用做 autocomplete。
  - 後端驗證 `reply_to_id` 必須屬於同一個 `parent_id` 串。
- 貼文、留言都**不能編輯**，只能刪除重發（省掉「已編輯」與編輯歷史）。發文框因此提供「預覽」，發佈前先確認標籤與作品卡的樣子。
- **劇透／R18 標籤**：存成純文字標記 `[spoiler]…[/spoiler]`、`[r18]…[/r18]`，顯示時摺成「🙈 劇透・點擊顯示」「🔞 R18・點擊顯示」。
  - 發文框、留言框都有「🙈 劇透」「🔞 R18」按鈕，把選取的文字包起來，使用者不用記語法。
  - 劇透：點了就展開。R18：沒有年齡確認 cookie（`nekomaid_r18_confirmed`）時先跳既有的「我已滿 18 歲」確認，確認過才展開；確認後全站限制級封面也一起解鎖（同一個 cookie）。
  - 不支援巢狀；沒有關閉的標記當一般文字顯示。後端不解析、只計入字數上限。
  - **摘要一律遮掉**：通知 payload 的貼文／留言摘要、之後的分享預覽，由後端在產生摘要時把標籤內容換成［劇透］／［R18］，前端拿不到原文。
- **作品卡**：只有貼文能附（留言不行），一則最多一張，可以附整部作品或某一話。
  - 候選只列**發文身份署名、目前公開**的作品（話的署名看 `storyteller_story_profiles`，作品看其下有沒有該身份署名的話）。附上別的身份的作品＝公開兩個身份是同一人，後端必須驗證，不能只靠前端過濾。
  - 作品之後轉私密、刪除或話被撤回 → 卡片顯示「這部作品目前無法瀏覽」，不給連結。
  - 限制級作品封面沿用 `useGatedCoverUrl`。
- 刪除：
  - 貼文：擁有者，confirm 後 soft delete，底下留言一起看不到。
  - 留言：留言者本人，或**貼文擁有者**（管自己的版面）可刪，confirm 後 soft delete。
  - **刪除一律留佔位**：頂層顯示「此留言已刪除」、回覆顯示「此回覆已刪除」，不顯示名字與時間；不因為沒有回覆就直接消失（規則一致，也不會讓 @ 對象斷掉）。
- 封鎖：
  - 貼文擁有者在留言旁按「封鎖」→ confirm（註明「只對這個身份有效」）。
  - 被封鎖者：不能在該身份的貼文留言／回覆（之後的討論區也一樣），留言框換成「{身份} 已限制你在這裡留言」；**閱讀、按讚不受影響**。明示封鎖，不做影子封鎖。
  - 對方既有留言保留，作者可逐則刪。
  - 封鎖名單放工作台「設定 → 封鎖名單」，依身份切換，可解除封鎖（confirm）。
  - 後端在建立留言時檢查（含回覆別人的回覆），回 403；前端從 `GET /posts/:post` 的 `can_comment=false, comment_blocked=true` 決定 UI。
- 頻率限制（Redis INCR + TTL）：發文 10 則／小時、留言 30 則／10 分鐘／帳號，超過回 429 + snack。

## 通知

| kind | 觸發 | 收件人 | view | group_key |
|---|---|---|---|---|
| `post.commented` | 頂層留言 | 貼文擁有者 | `comment`（新） | `post.commented:{comment_public_id}` |
| `author.posted` | 發新動態（排程掃描） | 這個身份的所有追蹤者（依帳號去重） | `posted`（新） | `author.posted:{user}:{profile}:{yyyy-mm-dd}` |
| `post.replied` | 在某則留言底下回覆 | 該頂層留言的留言者，以及 `reply_to_id` 那則的留言者（去重）；貼文擁有者若不在其中，另收 `post.commented` | `comment` | `post.replied:{comment_public_id}` |

- 自己對自己的貼文／留言不發通知。
- 同一個帳號同時符合多個收件身份時只發一則（優先 `post.replied`）。
- 讀者也會收到「作者回覆了你的留言」，不然讀者永遠不知道作者回了。
- **按讚不發通知**（見不做）。
- **`author.posted` 每個身份每天最多一則**：併進既有的 `RunNotificationPublishScan`（每 5 分鐘），撈 `notified_at IS NULL AND is_deleted = 0` 的貼文，依身份聚合後對追蹤者 `INSERT IGNORE`，再回寫 `notified_at`。同一天之後的貼文 group_key 相同，不會再跳通知；內容頁即時列出該身份當天的動態。
  - 收件人＝追蹤「該身份」的帳號（`author_profile_id` 對應），本人與筆名的追蹤者互不相干，不會洩漏。
  - 發文後 5 分鐘內就刪掉的貼文不會通知。
  - 被封鎖的人照樣收到（封鎖只擋留言，不擋閱讀）。
- payload：留言者身份快照（pen_name／頭像）、貼文摘要（前 80 字）、留言內容摘要、`post_public_id`、`comment_public_id`；`Internal` 存 actor 的 user/profile id，輸出前清空，沿用 `DecorateNotifications` 即時補最新身份。
- 貼文或留言已刪除 → 通知內容頁顯示「這則留言已刪除」、不給連結。
- 通知連結到貼文單頁並捲到該留言（`#c-{comment_public_id}`）。

## API

```
GET    /storyteller/user/:pen/posts?cursor=          公開，20 則/頁，置頂優先再依 id desc
GET    /storyteller/posts/:post                       公開，單則＋留言（頂層 asc，每則回覆 asc）
POST   /storyteller/user/:pen/posts                   擁有者；身份由 :pen 決定；body, attach_type?, attach_id?
GET    /storyteller/user/:pen/attachable-works        擁有者；該身份署名且公開的作品與話（作品卡候選）
DELETE /storyteller/posts/:post                       擁有者
PUT    /storyteller/posts/:post/pin  / DELETE …/pin   擁有者；置頂新的會自動取消舊的
POST   /storyteller/posts/:post/comments              body, parent?, reply_to?；身份後端判定，前端不傳
DELETE /storyteller/comments/:comment                 留言者或貼文擁有者
POST   /storyteller/comments/:comment/block           貼文擁有者；以該貼文的身份封鎖留言者，前端不傳身份
GET    /storyteller/blocks?as=                        工作台封鎖名單；as = 筆名，省略為本人

PUT    /storyteller/posts/:post/like  / DELETE …/like 冪等
```

## 與「專案／故事討論區」的關係

> 討論區使用者另行規劃，**不在本 branch 處理**；以下僅記錄留言表為何做成通用結構與當時的建議。

留言表刻意做成 `target_type + target_id`，下一步不管做哪種討論都直接複用留言、刪除權限、通知、頻率限制。

我的建議是討論區先做 **「每話留言（章評）」**，不要先做版務型的「專案討論版」：

1. **防劇透天然成立**：留言掛在第 N 話底下，會看到的人就是讀到第 N 話的人，不用另外做劇透標記。
2. **符合讀者先行策略**：讀完就留，摩擦最低；討論版要讀者主動開串，小站很容易變成一片空白，空版比沒有版更傷。
3. **實作成本**：`target_type = 'story'` 就上線，閱讀頁底部掛同一個留言元件；討論版則要多一層「串（thread）」與版務。
4. 作者→讀者的單向公告已經由這次的動態時間軸補上，專案討論版的需求剩「讀者之間聊」，等章評有量再看要不要升級。

## User Stories

| # | 情境 | 期望 |
|---|---|---|
| U1 | 我在本人頁發公告並置頂 | 本人頁動態分頁第一則就是它，筆名頁看不到 |
| U2 | 我在筆名 P 的頁發文 | 只出現在 P 的時間軸，本人頁完全看不到 |
| U3 | 讀者 A 在 P 的貼文留言 | 我收到「A 留言了你的貼文」，點進去捲到該留言 |
| U4 | 我在那則留言底下回覆 | 回覆顯示為 P，A 收到「P 回覆了你的留言」，看不出 P 是我 |
| U5 | 讀者 C 也回覆 A 的留言 | A 收到 `post.replied`，我收到 `post.commented` |
| U6 | 讀者沒設筆名想留言 | 留言框提示先設定筆名 |
| U7 | 有人在我貼文底下洗版 | 我能逐則刪、封鎖（皆 confirm）；對方也會被頻率限制擋下 |
| U8 | 我刪掉筆名 P | P 的貼文、P 身份發的留言一併 soft delete；相關通知顯示已刪除 |
| U9 | 我在本人身份封鎖 A | A 不能在本人貼文留言，但可以在 P 的貼文留言、仍可讀可按讚 |
| U10 | 讀者 C 回覆了 B 在 A 主留言底下的回覆 | 顯示「↪ 回覆 @B」；A、B 各收一則 `post.replied` |
| U11 | 刪掉一則沒有回覆的留言 | 留下「此留言已刪除」佔位，留言數 −1 |
| U12 | 我在 P 的頁面發文 | P 的追蹤者 5 分鐘內收到「P 發了新動態」；當天再發第二則不會再跳通知 |
| U13 | 我在 P 的頁面附作品卡 | 候選只有 P 署名的公開作品；就算直接打 API 附本人的作品也會被擋 |
| U14 | 我用劇透標籤包住第 12 話的反轉 | 動態上摺起來；追蹤者通知摘要顯示［劇透］ |
| U15 | 未確認年齡的讀者點 R18 標籤 | 先跳年齡確認，確認後展開，限制級作品卡封面也一起出現 |

## 常見失敗與應對

| 情境 | 應對 |
|---|---|
| 本人頁查詢漏了 `profile_id = 0`，筆名貼文混進本人頁 | repository 時間軸查詢強制帶 profile_id；service 測試寫一條「P 的貼文不出現在本人時間軸」 |
| 前端傳留言身份被竄改 | 前端不傳身份，後端由「viewer 是否擁有貼文身份」判定 |
| 通知 payload 的 `Internal` 輸出到前端 | 沿用 `toOutput` 統一清空；既有測試涵蓋 |
| 留言寫入成功、通知寫入失敗 | 只記 ERROR，不 rollback（同追蹤通知） |
| 熱門貼文被留言洗爆通知 | v1 一則留言一則通知；之後改成每則貼文依日聚合 |
| 貼文已刪除後還有人打留言 API | service 檢查貼文存在且未刪除，回 404 |
| 時間軸讚數／留言數 N+1 查詢 | 一頁兩支批次 `GROUP BY`，固定查詢數 |
| 刪筆名時漏處理貼文 | `DeleteAuthorProfile` 同交易 soft delete 貼文與該身份的留言 |
| 封鎖檢查只做在頂層留言，回覆漏檢 | 建立留言的 service 單一入口統一檢查，測試含「被封鎖者回覆別人的回覆」 |
| 封鎖誤做成帳號層級，洩漏筆名關係 | 查詢強制帶封鎖者 profile_id；測試「P 封鎖的人可在本人貼文留言」 |
| `reply_to_id` 指到別串或別篇貼文 | service 驗證與 parent 同串，否則 400 |
| 摘要沒遮，劇透／R18 內容出現在通知列表或分享預覽 | 後端產生摘要時統一走 `maskExcerpt`；測試涵蓋兩種標籤與未關閉標記 |
| 附上不屬於發文身份的作品，洩漏筆名關係 | service 驗證作品／話的署名含發文身份，否則 400；測試「P 附本人作品被擋」 |
| 作品附上後轉私密，卡片還露出標題與封面 | 輸出時即時檢查可見性，不可見只回 `unavailable` |
| 追蹤者很多，掃描一次插入大量通知 | 沿用既有新話通知的批次 INSERT；先觀察量級 |
| 置頂兩則（併發） | 置頂時同交易先清掉同身份其他 pinned_at |

## 實作備註（跟規格草稿不同的地方）

1. **作品卡欄位改成 `attach_project_id`／`attach_story_id`**：草稿寫 `attach_type + attach_id`，但「附某一話」時輸出還是要作品名稱與封面，兩個 id 一起存比較直接；`attach_story_id = 0` 就是附整部作品。API 收 `attach_project_public_id`／`attach_story_public_id`。
2. **作品卡可見性沿用作者頁的 `identityVisibleStoriesJoin`**：「這個身份署名、目前公開」跟作者頁作品分頁同一套判斷（`IdentityVisibleStoryRefs`），驗證、輸出、候選清單三處共用，不另寫規則。
3. **留言通知多帶 `thread_public_id`**：從通知直接回覆時要知道那一串的頂層留言（parent）。草稿沒有這個欄位。
4. **通知內容頁的快速回覆**：用貼文單頁 API（`GET /posts/:post`）的 `comment_state`／`comment_as` 決定能不能回、以誰的身份回，前端仍然不傳身份。
5. **`comment_state`** 取代草稿的 `can_comment`／`comment_blocked`：`ok`／`login`／`pen_name`／`blocked` 四種，前端直接對應三種提示。
6. **留言者身份不存在**（帳號刪了、本人清掉筆名）時 `author` 不輸出，前端顯示「已不存在的使用者」、不給連結；不會退回 display name／email。
7. **刪筆名**：`DeleteAuthorProfile` 同交易 soft delete 該筆名的動態、以它身份發的留言、它的封鎖名單；`GET /profiles` 多回 `post_count`，刪除確認視窗會寫「N 則動態也會一起刪除」。
8. **頻率限制**：OAuth 原本私有的固定視窗計數抽成 `service/client/redis_ratelimit.go`（`AllowFixedWindow`），兩邊共用。Redis 異常時放行並記 WARN，不讓社群功能整個掛掉。
9. **錯誤碼**：403001 沒有權限／403002 被封鎖／409004 留言前要先設筆名／429001 太頻繁；輸入錯誤一律 `PostValidationError` → 400、直接顯示訊息。
10. **「發了新動態」日界線用固定 UTC+8**（`time.FixedZone`），不依賴主機時區與 tzdata。
11. **前端共用**：API 錯誤訊息抽成 `helpers/apiError.ts`（`notificationErrorMessage` 改成指向它）；劇透／R18 解析在 `helpers/postMarkers.ts`，貼文、留言、預覽共用 `PostMarkerText`。
12. **稽核**：10 個寫入路由都進 registry（`post.*`、`comment.*`、`author.block`／`author.unblock`），前端活動紀錄補上中文標籤；順手補了既有缺漏的 `notification.follow_back` 標籤。
13. **「發了新動態」通知帶作品名**（確認後追加）：每則快照多一個 `work`（「《作品》冊・話」純文字、不帶封面），掃描當下作品已不可見就不列；通知內容頁在摘要下顯示「附上《作品》…」。快照寫入後不再回頭更新：作品之後刪除或轉私密，舊通知仍留著當時的作品名，**使用者確認不用處理**——點進動態時作品卡會顯示「這部作品目前無法瀏覽」即可。
14. **預覽＝發佈後的樣子**（確認後修正）：預覽框內是「文字＋作品卡」，預覽時不另外顯示可移除的作品卡。原本作品卡在預覽框外、順序相反，看起來像只預覽到作品卡。
15. **移除非必要說明文字**（確認後修正）：發文框只留「以 X 發佈」；空狀態只有標題（`CustomEmptyState` 的 description 改選填）；拿掉附上作品對話框、留言框、封鎖名單頁的補充說明。confirm 文案保留。
