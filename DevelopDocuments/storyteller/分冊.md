# 分冊

## 目的

故事專案裡的故事數量一多（三四十篇），現有的扁平列表／閱讀頁目錄會變得又長又難掃視。需要一個「冊」的概念把故事分組，同時這個資料模型要能自然銜接未來「單冊／單話販售」的需求，不能是個之後要整個打掉重做的臨時方案。

## 為什麼不是獨立資料表，也不是純顯示用的分組欄位

原本評估過兩個方案：

1. **純顯示用的分組標籤**（`Story` 加一個 `volume_label` 字串欄位，單純拿來在列表/目錄分組顯示）：改動最小，但冊本身沒有身份（沒有 id），之後要做「賣一整冊」就沒有東西可以掛價格／購買記錄，等於白做。
2. **獨立的 Volume 資料表**：冊有自己的身份，但要另外建一張表、一整套 CRUD API、跟 `Story` 建關聯，前後端都要多維護一套幾乎跟 `Story` 平行的邏輯。

**定案：冊本身也是一筆 `Story`**，透過 `parent_id` 表示隸屬關係。理由：

- 冊直接沿用 `Story` 既有的 `public_id`、`sort`、存檔／版本歷史機制，不用另外做一套 Volume 的 API／MCP schema。
- 之後要做單冊／單話販售，購買記錄可以統一指向 `story_id`——不管買的是一整冊還是單篇章節，都是同一張表、同一種外鍵，不需要「故事」跟「冊」兩套平行的購買邏輯。

## 資料模型（定案）

`Story` 新增兩個欄位：

- **`parent_id`**（nullable，self-reference 指向另一筆 `Story` 的 `id`）：表示這篇故事隸屬於哪一冊。冊本身的 `parent_id` 必為 `NULL`。
- **`is_volume`**（bool，預設 `false`）：明確標記這筆是「冊」還是「一般故事」，**不用「內容是否為空」這種隱含約定判斷**。原因：全站有大量地方（字數統計、故事列表、閱讀頁目錄、拖曳排序、MCP 的 `list_projects`／`get_story`）會直接掃過 `stories` 陣列，如果靠內容是否為空判斷，使用者手滑存一篇空白草稿就會被誤判成冊，或反過來冊被塞了內容也不會被擋下來。

冊本身的內容欄位（`latest_content`、`word_count` 等）維持存在但不使用（等同一篇只有標題的空故事）。編輯冊時只能改標題，不會動到內容/摘要/狀態等欄位。

### 排序規則

`sort` 的語意改成「同一個 `parent_id` 底下的兄弟排序」，不需要另外發明「冊的順序」欄位：

- 冊彼此之間的順序：`parent_id IS NULL` 且 `is_volume = true` 的這批，用 `sort` 排。
- 未分冊故事的順序：`parent_id IS NULL` 且 `is_volume = false` 的這批，同樣用 `sort` 排。**顯示順序是先列出所有的冊（依冊的 sort），未分冊故事整批排在最後**，當作「還沒收進任何冊」的收尾區——原本定案是排最前面，但實際用起來會跟「把新冊往前挪」的拖曳操作混在一起，容易搞不清楚在拖哪個區塊，所以改成冊在前、未分冊在後，兩個區塊都要有明確的視覺／文字標示（例如「冊」「未分冊故事」的分段標題）區分開來。
- 冊內故事的順序：`parent_id = 該冊.id` 的這批，用 `sort` 排。

拖曳排序時如果把一篇故事拖到別的冊底下，除了改 `sort`，要**連動把 `parent_id` 改成目標冊的 `id`**，否則使用者會以為換組了、實際上分組還是舊的，畫面會不一致。

### 刪除規則（定案）

冊非空（底下還有 `parent_id` 指向它的故事）**不能刪除**，需要先把底下故事移出或刪光。不做 cascade delete，避免誤刪整冊內容。

### 巢狀限制（定案）

**不支援冊中冊**。`is_volume = true` 的故事，`parent_id` 一定是 `NULL`；一般故事的 `parent_id` 只能指向 `is_volume = true` 的故事，不能指向另一篇一般故事。後端存檔時需要驗證這條規則。

## 冊的活動歷史（定案）

目的：讓使用者（之後也包含通知功能）能看到「這一冊最近新增／搬入／搬出了哪些故事、故事內容有什麼變動」，不需要細節（不用完整 diff），只需要記到故事跟版本 id 的層級。

拆成兩種完全不同性質的資料，分開處理：

1. **內容變動**（同一篇故事、冊隸屬沒變，只是存了新版本）：**不新增資料表**，用衍生查詢——`storyteller_story_versions` join `storyteller_stories`，以目前的 `parent_id` 分組即可（`storyteller_story_versions` 本來每次存檔就會寫一筆，`story_id` 也已經有了）。
2. **冊隸屬關係異動**（新增到某冊、從某冊搬到另一冊、從某冊移出、故事在某冊裡被刪除）：這幾種本質上是同一種形狀的事件——「這篇故事的冊隸屬從 X 變成 Y」，X／Y 都可能是 `NULL`。**這種歷史無法用衍生查詢生出來**（`parent_id` 只保留當下的值，異動之後舊的隸屬關係就查不到了），需要新增一張表 `storyteller_story_volume_events` 明確記錄：
   - `id`
   - `story_id`
   - `from_volume_id`（nullable，異動前所屬的冊，沒有冊則為 `NULL`）
   - `to_volume_id`（nullable，異動後所屬的冊，沒有冊則為 `NULL`）
   - `created_at`

   查一冊的隸屬異動時間軸：`WHERE from_volume_id = :id OR to_volume_id = :id`——同一筆紀錄會同時出現在來源冊跟目標冊的時間軸裡。

   寫入時機（兩個寫入點）：
   - **存檔時**：比對存檔前後的 `parent_id`，有變化就寫一筆（涵蓋「建立故事時直接指定冊」「編輯時換冊」「編輯時移出冊」三種情況，`from`／`to` 依實際情況帶 `NULL`）。
   - **刪除故事時**：如果被刪除的故事當下 `parent_id` 不是 `NULL`，額外補寫一筆 `to_volume_id = NULL`，否則冊被刪掉一篇故事後，時間軸上會完全看不出這篇曾經存在過。

之後這張表也可以直接當作「這一冊有更新」通知功能的資料來源（呼應作者頁通知待辦），不需要另外設計一套。

## 閱讀頁目錄項目上限（獨立於分冊，一併記錄）

閱讀頁側欄「故事索引」目前是把整個專案的故事一次全部渲染出來，**這件事不管有沒有做分冊都需要處理**：沒有分冊時，故事一多側欄本身就是一長串；做了分冊之後，單一冊內的故事數量一樣可能超過門檻（分冊解決的是「跨冊分組」，不會限制「單一冊內能塞幾篇」）。

先記錄下來，細節待確認：

- **上限 N 抓多少**：待確認，需要抓一個實際數字（例如 50／100），或改成「超過門檻才觸發限制」而不是固定分頁大小。
- **超過 N 之後怎麼呈現**：待確認，可能選項包含分頁、虛擬滾動（virtualized list，DOM 只渲染可視範圍內的項目）、索引內加搜尋／篩選。目前傾向虛擬滾動優先評估，因為不會打斷「捲動找章節」的既有操作習慣，但還沒定案。
- **這個限制只套用在閱讀頁目錄，還是工作台故事列表（`ProjectDetail.tsx`）也要一起處理**：待確認，兩邊的資料量成因不同（工作台是作者自己管理，閱讀頁是給讀者看），限制的必要性跟門檻可能不一樣，需要分開判斷。

## API 設計方向

`GET /projects/:id/stories` 這類既有的列表 API，**過濾邏輯放在後端**，不要讓每個前端頁面各自判斷「這筆是不是冊」：

- 預設只回傳一般故事（`is_volume = false`），維持現有前端頁面（字數統計、MCP 回傳等）幾乎不用改。
- 額外開一個方式取得冊（例如 `is_volume=true` 的 query 參數，或獨立的 `GET /projects/:id/volumes`），只有「需要顯示分冊結構」的頁面才去組 `冊 → 故事` 的樹狀關係。

## 前端影響範圍

- **故事列表**（`ProjectDetail.tsx`）：依冊分組顯示，冊在前、未分冊故事整批排最後，兩個區塊都有分段標題（「冊」／「未分冊故事」）。分頁 tab 名稱從「故事」改成「故事與冊」。拖曳跨組時連動修改 `parent_id`（見上方排序規則），冊彼此之間也支援拖曳排序。
- **閱讀頁目錄**（`Reader.tsx` 側欄「故事索引」）：比照列表頁分組順序與標題（冊在前、未分冊故事在後），可展開／收合。這是這次要解決的主要痛點。
- **故事編輯頁 / 冊的編輯方式**：待確認，見下方。
- **MCP 工具**（`storyteller_upsert_story` 等）：暫不開放 AI agent 直接設定/建立冊，之後有需要再加 schema。

## 待確認事項

- **冊的編輯要不要共用 `StoryEditor.tsx`？** 傾向不共用，另外做一個輕量的「新增／重新命名冊」對話框（只有一個標題輸入框）。理由：`StoryEditor.tsx` 目前已經是大檔案，冊沒有 markdown 內容、不需要 AI Agent 面板／字數統計，硬塞進同一頁做條件渲染只會讓這個檔案更難維護，不如切開。
- **冊的活動歷史要不要有對應的顯示畫面？** 這次先確保資料寫得進去、查得出來（見上方「冊的活動歷史」），實際顯示畫面（冊詳情頁的時間軸、或跟通知功能一起做）先不在這次範圍內，之後視通知功能規劃再一併設計。
- **未分冊故事之後要不要允許使用者手動再拖進某一冊、以及冊要不要有自己的摘要/封面**（為了販售頁面的呈現）——目前範圍先不做，晚一點視販售功能的實際需求再評估要不要幫 `Story` 加對應欄位。
- **閱讀頁目錄項目上限**：N 值、超過後的呈現方式、是否也套用到工作台故事列表——見上方「閱讀頁目錄項目上限」章節，尚未定案。
