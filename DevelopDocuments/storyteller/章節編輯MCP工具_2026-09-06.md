# 章節編輯 MCP 工具規格

## 背景與範圍限制（確認過，2026-09-06）

- **前端網頁完全不開放章節讀取／編輯**——不做任何前端 UI/路由，這點沒有例外。
- **AI 助理面板（AAS）只開放「讀」，不開放「寫」**：`list_*_chapters`／`get_*_chapter` 這兩個唯讀工具開放給 AAS，讓它可以用比整篇內容更省 token 的方式回答「第三章在講什麼」這類問題；`replace`／`insert`／`delete` 這三個寫入工具**維持 MCP-only**。理由：唯讀工具不會經過 `CaptureWriteToolsAsProposals`，不會產生任何新的 proposal 卡片，AAS 開放它們對前端零影響；寫入工具會變成 proposal，而現有的 proposal 卡片是整篇 diff 呈現，章節級異動需要另外設計「這是第幾章的異動」的呈現方式（另外抓舊內容做 diff、insert/delete 各自要新的卡片樣式），這塊複雜度不划算才不開放。
- **MCP 完整開放全部 10 個工具**（讀＋寫），外部 agent 沒有「前端要顯示什麼」的問題。
- **故事（Story）與設定集（Lore）都要做**，兩邊工具完全對稱（比照 `storyteller_list_story_versions`/`storyteller_list_lore_versions` 這種既有的對稱慣例）。設定集的內容一樣是用同一套 markerId／標題段落格式儲存（`UpdateLore`/`CreateLore` 都呼叫共用的 `backfillStoryMarkerIds`，`service/storyteller/storyteller.go:2325`/`:2366`），章節掃描邏輯可以直接套用，不用另外設計一套。

`編輯頁大綱與書籤_2026-09-02.md` 的 TOC 功能已經上線，前端 `extractDocumentMarkers`/`extractHeadingOutline`（`static_site/src/pages/storyteller/wysiwygCore/extractHeadingOutline.ts`）已經證明「標題 markerId + 位置」可以拿來當章節邊界的地基，這份規格是把同樣的概念搬到後端，讓 MCP client（AI agent）可以針對「一個章節」而不是整篇故事做讀寫，不用每次都整篇 `storyteller_upsert_story` 覆蓋。

## 章節的定義：任一層級標題都是邊界，不做巢狀

**章節 = 從一個標題行（H1~H6 任一層級皆可）開始，到下一個標題行（不分層級）之前的所有內容**（包含標題行本身）。不做「H1 底下巢狀 H2 子章節」這種階層語意——理由：

- 這個 app 的標題層級（`headingLevel` 0-6，`markerParagraph.ts` 定義）本來就沒有強制作者一定要照階層使用，有人可能全篇只用 H2 當章節標記。
- 巢狀語意會讓「章節範圍」變成要額外指定「到哪一層算章節結束」，徒增 MCP 工具的參數複雜度，換來的彈性目前沒有實際需求撐腰。
- 「任一標題都是邊界」是最簡單、最不會讓 AI agent 搞錯範圍的定義，之後如果真的需要巢狀（例如「整個 Part 1 底下所有章節」），再疊加一個「依層級篩選」的參數也不遲，不會跟這次的資料結構衝突。

**具體舉例確認語意**（對應「H2 > H4 > H6 這種混層級標題，改 H6 只動這組 H6」的確認）：假設結構是 `H2(A)` → `H4(B)` → `H6(C)` → `H6(D)` → `H2(E)`，`storyteller_replace_story_chapter` 帶 `C` 的 `marker_id`，範圍是「`C` 這一行到 `D` 這一行之前」——**不會**因為 `C` 是 H6、往上找到 H4/H2 才算章節結束，也**不會**把 `D`（下一個 H6）併進來。換句話說「章節邊界」只看「下一個標題行，不管它是第幾層」，跟目前這個標題自己是第幾層無關。這正是你問題裡確認的行為。

標題行的判定沿用 `backfillStoryMarkerIds`（`service/storyteller/storyteller.go:2001`）已經有的邏輯（開頭 1~6 個 `#` 加一個空白），並且**必須跳過 fenced code block 內容跟 table 列**（code block 裡的 `# comment` 或 table 儲存格文字不能被誤判成標題邊界）——這段「逐行走訪、跳過 code fence／table」的邏輯 `backfillStoryMarkerIds` 已經寫過一次，這次建議抽成共用 helper（例如 `walkStoryContentLines(content, callback)`），讓新的章節掃描函式跟 `backfillStoryMarkerIds` 共用，不要複製一份幾乎一樣的迴圈。

## 工具註冊機制：讀寫分開兩個 provider function，讀的併入主註冊表、寫的獨立出去

**關鍵發現**：AI 助理面板（`agentic_query.go` 的 `RunStoryAgenticQuery`/`RunLoreAgenticQuery`，共 4 處呼叫點）直接呼叫 `StorytellerToolRegistry().All()` 取得整份工具清單（只包 `ScopeToolsToProject`，沒有其他過濾）；`WriteStorytellerToolNames()`（`agent_proposal.go:104`）則是拿 `StorytellerToolRegistry().All()` 扣掉 `ReadOnlyStorytellerTools()`（`agent_scope.go:45`，用 `storyteller_get_`/`storyteller_list_` 前綴過濾）算出來的「需要變成 proposal 的工具清單」。這代表：**只要工具名稱是 `storyteller_get_*`／`storyteller_list_*` 開頭、且被加進 `StorytellerToolRegistry()`，天生就會被歸類成唯讀工具、AAS 可以直接呼叫、不會變成 proposal**——完全不用寫任何額外的排除或允許清單，靠命名前綴跟「有沒有加進主註冊表」這兩件事自然決定行為。

因此這次刻意把 10 個章節工具拆成兩個 provider function，分別餵給不同的註冊表：

1. `storytellerChapterReadToolSpecs()`（`storyteller_list_story_chapters`／`storyteller_get_story_chapter`／`storyteller_list_lore_chapters`／`storyteller_get_lore_chapter`，共 4 個）——**加進 `StorytellerToolRegistry()` 現有的 provider function 清單**（`tool_registry.go` 的 `[][]ToolSpec{...}` 多一行），這樣 MCP 跟 AAS 都會自動拿到，而且因為名稱是 `get_`/`list_` 開頭，`ReadOnlyStorytellerTools()`／`WriteStorytellerToolNames()` 會自動把它們歸類成唯讀、不會變成 proposal。
2. `storytellerChapterWriteToolSpecs()`（`storyteller_replace_story_chapter`／`storyteller_insert_story_chapter`／`storyteller_delete_story_chapter`／對應的 lore 三個，共 6 個）——**不加進 `StorytellerToolRegistry()`**，只餵給一個新的獨立函式：

   ```go
   // StorytellerMCPOnlyToolRegistry 回傳只給外部 MCP client 用、AI 助理面板
   // 看不到的工具（目前是章節寫入：replace/insert/delete）。章節的「讀」
   // （list/get）已經因為 get_/list_ 命名前綴，加進 StorytellerToolRegistry()
   // 後就自動變成 AAS 可用的唯讀工具，不用特別處理；只有「寫」需要這層隔離，
   // 因為 AAS 現有的 proposal 卡片是整篇 diff 呈現，還沒有「章節級異動」的
   // 呈現方式。之後如果要開放，直接把 storytellerChapterWriteToolSpecs() 併進
   // StorytellerToolRegistry() 的迴圈即可，不用重新設計。
   func StorytellerMCPOnlyToolRegistry() *ToolRegistry {
       registry := NewToolRegistry()
       for _, spec := range storytellerChapterWriteToolSpecs() {
           registry.Register(spec)
       }
       return registry
   }
   ```

3. `service/mcp/storyteller_tools.go` 的 `registerStorytellerTools()` 除了原本的 `StorytellerToolRegistry().All()`（現在已經含 4 個章節讀取工具），再多一個迴圈註冊 `StorytellerMCPOnlyToolRegistry().All()`（6 個章節寫入工具）——MCP 這邊兩份加起來剛好是完整的 10 個。
4. `agentic_query.go` 四處 `tools := StorytellerToolRegistry().All()` **完全不用改**——4 個讀取工具自動含在裡面（AAS 可唯讀呼叫），6 個寫入工具本來就不在這份清單裡（AAS 自然看不到），兩邊都不需要額外寫排除/允許邏輯。

這個設計的好處：讀/寫的可見範圍差異，完全靠「加不加進 `StorytellerToolRegistry()`」跟「命名前綴」這兩個既有機制自然決定，不用另外維護一份工具名稱允許清單去手動控制誰看得到什麼。

## 怎麼知道要改的是哪個章節、標題改名怎麼處理

**定位方式**：跟 `storyteller_list_story_versions`/`storyteller_get_story_version` 那組工具一樣，`marker_id` 是**不透明識別碼**，AI agent 不會自己編、也不會用標題文字去猜——標準流程是先呼叫 `storyteller_list_story_chapters` 拿到「目前所有章節的 `marker_id` + 標題文字」清單，看著標題文字挑出要改哪個章節，再拿對應的 `marker_id` 去呼叫 `get`/`replace`/`delete`。這跟現有版本歷史工具的使用模式完全一致，AI agent 不需要新學一套定位邏輯。

**標題改名會怎樣**：章節的身分是標題行的 `marker_id`，不是標題文字本身，所以：

- **正常改名**（AI 在 `storyteller_replace_story_chapter` 的新 `content` 裡，把標題行維持原本的 `⟦markerId⟧...⟦/markerId⟧` 包裹、只改中間的文字，例如把 `⟦abc123⟧# 第六章⟦/abc123⟧` 改成 `⟦abc123⟧# 第六章：決戰⟦/abc123⟧`）：`marker_id` 不變，還是同一個章節，下次 `list_story_chapters` 會看到新標題掛在同一個 `marker_id` 底下。這是**建議的正常改名方式**，工具描述裡要明講。
- **意外改名**（AI 沒有保留原本的包裹符號，直接寫一行新的 `# 第六章：決戰`）：`backfillStoryMarkerIds` 既有的邏輯會把它當成一行全新內容，配發一個全新的 `marker_id`——章節本身的內容沒有跑掉（還是同一段落順序），但這個章節的 `marker_id` 已經換了。為了不讓 AI agent 之後對著舊的 `marker_id`操作卻找不到章節，**`storyteller_replace_story_chapter`／`storyteller_insert_story_chapter` 的回傳值必須包含存檔後這個章節實際的 `marker_id`／`heading_level`／`title`**（不是原樣回傳輸入的 `marker_id`，是存檔後重新掃描一次拿到的真實值），讓 AI agent 永遠有辦法接上最新狀態，不用自己猜有沒有變過。

## 新增工具（Story／Lore 各 5 個，共 10 個，命名對稱）

### `storyteller_list_story_chapters`

- Input：`project_public_id`、`story_public_id`。
- 掃描 `LatestContent`，回傳章節摘要陣列（不含正文，比照 `storyteller_list_story_versions` 只回摘要的慣例）：`marker_id`（標題行的 markerId）、`heading_level`、`title`（標題文字，去除 `#` 與 markerId 包裹符號）、`word_count`（該章節內文字數，複用既有 `wordCount` 計算邏輯）、`order`（在文章中的順序，從 0 開始）。
- 故事完全沒有任何標題時，回傳空陣列（不是錯誤）。

### `storyteller_get_story_chapter`

- Input：`project_public_id`、`story_public_id`、`marker_id`。
- 回傳該章節的完整原始內容（含標題行本身，含所有 `⟦markerId⟧...⟦/markerId⟧` 包裹符號——**不要**把包裹符號剝掉，AI agent 要看到真正的儲存格式，之後 `storyteller_replace_story_chapter` 才知道哪些行是可以原樣保留的舊行）。
- `marker_id` 找不到，或找到但那一行不是標題行（是一般段落的 markerId），回錯誤，不要靜默回傳空內容或整篇內容。

### `storyteller_replace_story_chapter`

- Input：`project_public_id`、`story_public_id`、`marker_id`（要替換的章節，由其標題行的 markerId 指定）、`content`（新的章節內容，**必須包含新的標題行**，內容格式跟 `storyteller_upsert_story` 的 `content` 参数一样，可以是帶 `⟦id⟧` 包裹的行，也可以是新行不帶包裹交給 backfill 自動補）、`base_version_id`（選填，樂觀鎖，語意跟 `storyteller_upsert_story`/`storyteller_patch_story` 一致）。
- 邏輯：
  1. 找出 `marker_id` 對應的標題行位置，跟下一個標題行（或文件結尾）的位置，算出這個章節目前佔的行範圍。
  2. 用新的 `content` 整段取代這個範圍（前後其他章節的行完全不動，包含它們的 markerId）。
  3. 拼回完整內容後，跑一次 `backfillStoryMarkerIds`（沿用既有機制：沒帶 id 的新行自動補新 id，已經帶合法 id 的行原樣跳過）。
  4. 走既有的 `UpdateStoryWithVersion`（樂觀鎖、建新版本）流程存檔，行為跟 `storyteller_patch_story` 更新 `content` 欄位一致，不要另外發明一套存檔機制。
- `marker_id` 找不到、或不是標題行：回錯誤，不允許「意外新增一個章節」這種副作用。
- 新的 `content` 如果完全沒有標題行（使用者/AI 忘記帶標題）：回錯誤，避免章節邊界因為這次替換而消失，導致下次 `list_story_chapters` 少一筆、後面內容全部併入前一章的詭異結果。
- **回傳值**：存檔成功後重新掃描一次章節邊界，回傳這個章節現在真正的 `marker_id`／`heading_level`／`title`（原因見上一節「標題改名怎麼處理」），不是原樣回傳輸入參數。

### `storyteller_insert_story_chapter`

- Input：`project_public_id`、`story_public_id`、`content`（新章節內容，必須以標題行開頭，規則同上）、`after_marker_id`（選填——帶某個既有章節的 markerId，新章節插入在該章節範圍結束之後；不帶則插入在文件最末端）、`base_version_id`（選填，樂觀鎖）。
- `after_marker_id` 帶了但找不到、或不是標題行：回錯誤。
- 存檔機制同 `storyteller_replace_story_chapter`，回傳值同樣是存檔後重新掃描拿到的真實 `marker_id`／`heading_level`／`title`。

### `storyteller_delete_story_chapter`

- Input：`project_public_id`、`story_public_id`、`marker_id`、`base_version_id`（選填，樂觀鎖）。
- 直接把該章節（標題行＋內文）從內容中整段移除，其餘章節不動。
- 刪除後如果整篇內容變成空字串，比照現有故事內容可以是空字串的既有規則（不特別擋，跟 `storyteller_patch_story` 把 `content` 改成空字串的行為一致）。
- `marker_id` 找不到或不是標題行：回錯誤。

## Lore 對稱工具

`storyteller_list_lore_chapters`／`storyteller_get_lore_chapter`／`storyteller_replace_lore_chapter`／`storyteller_insert_lore_chapter`／`storyteller_delete_lore_chapter`——欄位、邏輯、錯誤處理、回傳值規則跟上面 Story 版本**完全對稱**，差異只有：

- Input 用 `lore_public_id` 取代 `story_public_id`。
- 存檔走 `UpdateLoreWithVersion`（`repository/storyteller/storyteller.go:1580`），不是 `UpdateStoryWithVersion`。
- 章節掃描函式共用同一份（`storyChapterSpans`，見下方「共用邏輯」），不用為 Lore 另外寫一份——資料格式一致，差異只在存檔呼叫的是哪個 repository 方法。

## 共用邏輯

上述 Story／Lore 共 10 個章節工具都需要「掃描內容、依標題行切出章節邊界」這個核心運算，建議寫成一個共用函式：

```go
type storyChapterSpan struct {
    MarkerID     string
    HeadingLevel int
    Title        string
    StartLine    int // 標題行本身
    EndLine      int // 不含，下一個標題行或 len(lines)
}

func storyChapterSpans(content string) []storyChapterSpan
```

`storyteller_list_story_chapters`／`get`／`replace`／`insert`／`delete` 都呼叫這個函式取得章節邊界，再各自做摘要/擷取/拼接，不要各自重寫一份掃描邏輯。

## 常見 fail 應對

- 空故事（`LatestContent` 是空字串）：`storyteller_list_story_chapters` 回空陣列；`get`/`replace`/`delete` 帶任何 `marker_id` 都回「找不到章節」的錯誤；`insert` 不帶 `after_marker_id` 時允許在空文件上插入第一個章節。
- `marker_id` 存在但對應的是表格列或 code block 內的 marker（不是標題）：一律視為「不是章節」回錯誤，不要嘗試猜測使用者想要什麼。
- 兩個章節標題文字重複（例如兩個都叫「第一章」）：不影響操作，因為定位全部用 `marker_id`，不靠標題文字比對。
- 樂觀鎖衝突（`base_version_id` 不是最新版本）：行為跟現有 `storyteller_patch_story`/`storyteller_upsert_story` 一致，沿用現有的衝突回應格式，不要另外發明一套。

## 不做

- 不做巢狀章節（見上方「章節的定義」）。
- 不做任何前端 UI 或路由。
- 不開放章節**寫入**給 AI 助理面板（見上方「背景與範圍限制」「工具註冊機制」——刻意決定，理由是避免 AAS 的提案預覽 UI 要多支援一種「章節級異動」的呈現方式），但架構上仍設計成未來要開放只是一行改動（把 `storytellerChapterWriteToolSpecs()` 併入 `StorytellerToolRegistry()` 的迴圈）。章節**讀取**（`list`/`get`）則直接開放給 AAS，因為唯讀工具不會觸發 proposal、對前端零影響。
- 不做章節搬移/重新排序的工具（`insert` + `delete` 組合起來已經可以達到「搬到別的位置」的效果：先在新位置 insert 一份，再 delete 舊的，不需要專門的 move 工具）。
- 不做「依標題文字搜尋章節」的工具——定位一律靠 `marker_id`，文字搜尋交給 AI agent 自己看 `list_*_chapters` 的結果判斷，工具端不用另外做模糊比對。
