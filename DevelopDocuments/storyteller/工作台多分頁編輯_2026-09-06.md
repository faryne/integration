# 工作台多分頁編輯 + 樹狀側欄規格草案

## 狀態說明

這份文件是**窮舉版**，目的是把規格內容跟可能碰到的問題一次列完，方便你自己判斷要砍掉哪些、保留哪些，做減法之後再回頭定案。文件裡沒有下「建議做/不建議做」的結論，只列事實與取捨——除非特別標注「建議」。

## 目的

1. 左側欄從現在的兩層（區塊 > 收藏集）改成三層樹狀（冊 > 故事、設定集分類 > 設定、資產集 > 資產），點擊個別項目直接開新分頁。
2. 右欄從「同一時間只能顯示一篇正在編輯的內容」改成「可以同時開好幾篇（故事/設定/資產），用分頁切換，背景分頁不會因為切走而丟失編輯狀態」。

## 現況架構（決定了這次改動的難度落在哪）

- `ProjectWorkspacePreview.tsx`：用一串三元運算子依 URL 決定渲染哪個編輯器，**同一時間只掛載一個編輯器實例**（`static_site/src/pages/storyteller/ProjectWorkspacePreview.tsx:589-653`）。
- 路由是「一個路由對應一篇正在編輯的內容」（`static_site/src/App.tsx:345-385`），沒有多開概念，URL 無法同時代表好幾份文件。
- 側欄目前兩層（區塊 > 收藏集），`static_site/src/pages/storyteller/ProjectWorkspacePreviewComponents.tsx:66-172`，點進收藏集是換路由到列表頁，不會在側欄展開到個別故事/設定/資產。
- 自動存檔是**元件層級**的 `useRef` + `setInterval`（`StoryEditor.tsx:339-361`、`:638-695`），元件 unmount 時 `clearInterval`，狀態完全綁在單一編輯器實例上。
- 離開頁面警示（`WorkspaceLeaveGuard.ts`，共 28 行）是**模組層級單一 callback 插槽**，設計前提明講「同一時間右欄最多只會掛一個編輯器」，多個編輯器同時掛載會互相覆蓋。
- 樂觀鎖版本號（`latestVersionIdRef`）也是元件實例內的 ref，背景分頁版本號不會自動更新。
- Tiptap 編輯器（`StorytellerWysiwygEditor.tsx`）用 `useEditor`，**實例壽命綁在 React mount/unmount**，換內容是同一實例呼叫 `setContent`，不是重建。
- 側欄資料抓取：故事/冊/設定分類/資產集清單是一次抓全部（無分頁），但**設定／資產本身（個別項目）是依收藏集分頁抓取**（一頁 20-24 筆），不是一次全撈。
- AI 助理面板（`StorytellerEditorSideTabs`/`StorytellerAgentPanel`）也是在 `StoryEditor.tsx` 元件內掛載，跟編輯器綁在同一個生命週期。
- 目前程式庫裡**沒有「多份可編輯內容同時掛載、分頁切換不丟狀態」的先例**——版本歷史比對是唯讀 diff，不是可編輯實例；AI 助理側邊 tabs 是同一份文件底下的多個輔助面板，語意不同。這部分是全新設計，沒有既有模式可以照抄。

## 需要新增/大改的部分

### 1. 分頁管理層（全新，這是整個功能的地基）

需要一個「目前開了哪些分頁」的狀態管理層，脫離現在「URL 直接對應內容」的模型，改成：

- 一個分頁清單：每個分頁記錄 `{ id, type: story|lore|asset, publicId, title, dirty狀態 }`。
- 分頁清單要放在比 `ProjectWorkspacePreview.tsx` 更高層的地方（或用 Context/Zustand 之類的狀態管理），因為要跨路由存活。
- 「點側欄項目」的行為要從「navigate 到新路由」改成「開一個新分頁（如果已經開過就切過去，不要重複開）」。

### 2. 自動存檔／離開警示／樂觀鎖 從「元件層級」提升到「分頁管理層」

三者目前都假設「同一時間只有一個編輯器實例」，這個假設在多分頁下不成立，三個都要重新設計：

- **自動存檔**：要嘛把 `useRef`/`setInterval` 這組邏輯搬到分頁管理層，每個分頁各自維護一份計時器（不論是否為目前顯示中的分頁都要繼續跑，否則背景分頁打字打了老半天，切回來才發現都沒存到）；要嘛接受「背景分頁不自動存檔，只有前景分頁會存」這個閹割版本（代價：使用者可能誤以為背景分頁也在自動存，實際上沒有）。
- **離開頁面警示**：從「模組層級單一插槽」改成「Map<分頁 id, 檢查函式>」，判斷「還有沒有任何分頁有未存檔變更」要改成掃過整個 Map，不是只看最後註冊的那個。
- **樂觀鎖版本號**：背景分頁的 `base_version_id` 在使用者切走後不會自動更新，需要決定「切回分頁時要不要重新 fetch 最新版本比對」——不重新比對的話，背景分頁存檔時可能觸發衝突（`version_conflict`），使用者會很困惑「我明明沒被誰改過」。

### 3. Tiptap 編輯器實例的常駐策略

`StorytellerWysiwygEditor` 目前是「元件掛載才建立實例、卸載就銷毀」。多分頁如果要「切換分頁不丟編輯狀態（游標位置、undo history、還沒送出的 IME 組字）」，理論上背景分頁的編輯器實例也要留著，不能真的 unmount——做法是常駐掛載但用 CSS 隱藏（`display:none`），不是條件渲染。這代表：

- 開幾個分頁，記憶體裡就同時活著幾個完整的 Tiptap/ProseMirror 實例（含底層的 decoration plugin、語法高亮、書籤標記等，這些都不便宜）。
- 需要決定「分頁數量上限」，避免使用者無限開分頁把瀏覽器分頁本身拖垮。
- 如果接受「切分頁允許重建實例、犧牲一點游標/undo 狀態」，可以退而求其次採條件渲染（跟現在做法一樣，只是多包一層分頁管理），記憶體成本低很多，但體感上分頁切換不是真正「無縫」。

### 4. 路由與網址策略

現有路由是「一個 URL 對應一份文件」，多分頁後這件事要重新定義，常見兩種做法各有取捨：

- **URL 只代表目前作用中的分頁**，其餘分頁存在瀏覽器分頁的 client state（例如存進 `sessionStorage`），重新整理網址列能回到最後作用中的那篇，但其他背景分頁清單會不見（除非額外存進 localStorage 並在頁面載入時還原）。
- **URL 編碼整組已開分頁清單**（例如 query string 塞多個 id），網址列變得很長很醜，但重新整理後整組分頁狀態都能還原、也可以分享網址給別人（不過對方看到的是別人的編輯內容，這個功能對「作者自己編輯」的場景意義不大）。

### 5. 樹狀側欄的資料抓取

- 「冊 > 故事」這層資料已經一次抓齊全（故事清單本來就沒有分頁），可以直接組樹。
- 「設定集分類 > 設定」「資產集 > 資產」這兩層如果要在側欄樹狀展開到個別項目，現有 API 是**分頁抓取**（一頁 20-24 筆），不是一次性清單，需要新增一支不分頁的輕量清單端點（只回 id/title，不用回完整內容），或是做「展開節點時才分頁抓取、捲動載入更多」這種懶載入 UI（複雜度更高）。
- 樹要做展開/收合狀態記憶（使用者展開了哪些節點，重新整理後要不要記得）。

## 可能碰到的問題（風險清單，供減法參考）

1. **記憶體/效能**：多個 Tiptap 實例同時常駐（如果選擇常駐策略）——沒有實測過的未知數，不確定瀏覽器裝置在幾個分頁之後會開始明顯變慢。
2. **自動存檔的 API 壓力**：好幾個分頁的計時器可能在同一時間點都觸發存檔，會不會需要做請求排隊/節流，避免同時打好幾個 PATCH 請求。
3. **樂觀鎖衝突的使用者體感**：背景分頁自動存檔時，使用者根本沒在看那個分頁，若這時候真的發生版本衝突（例如同時開了同一篇故事的兩個分頁，或 AI 助理面板同時在改），使用者事後才會發現，需要一個「有分頁衝突」的全域提示機制（不能只在該分頁內部顯示，因為使用者可能沒切過去）。
4. **AI 助理面板要跟著哪個分頁**：目前 AI 助理面板是掛在編輯器元件內的，多分頁後是「每個分頁各自一份 AI 助理面板」還是「AI 助理面板固定一份、跟著目前作用中的分頁切換對話內容」，這兩種對話歷史的保存方式完全不同，需要另外決定。
5. **關閉分頁時的確認流程**：比照現有離開頁面警示，關閉單一分頁（不是離開整個瀏覽器分頁）如果有未存檔內容，要不要跳確認框；跟「離開整個工作台頁面」的警示邏輯要分開處理，不能共用同一套判斷。
6. **刪除/搬移操作與已開啟分頁的一致性**：如果使用者在側欄刪除了一篇正在某個分頁打開的故事，那個分頁要怎麼處理（自動關閉？顯示「已被刪除」的錯誤狀態？）。
7. **正在使用中的功能是否也要 per-tab**：版本歷史面板、書籤/TOC 大綱、資產取代等這些依附在編輯器旁邊的功能，是不是也要各自獨立於每個分頁，還是可以共用一份（例如版本歷史 dialog 本來就是彈窗，可能不用 per-tab）。
8. **手機版/窄螢幕的分頁 UI**：現有工作台在窄螢幕上的呈現方式（側欄收合、單欄顯示）可能整套要重新設計，分頁 bar 在小螢幕上要嘛捲動、要嘛做成下拉選單。
9. **Undo/redo 歷史的保存**：如果背景分頁的編輯器實例被銷毀重建（採條件渲染而非常駐），使用者切走又切回來會發現 undo history 消失，這對「打錯字想 ctrl+z」的體驗是退步。
10. **是否要持久化已開啟的分頁清單**：使用者重新整理整個瀏覽器頁面後，要不要記得「我剛剛開了哪幾篇」，這牽涉到要不要用 localStorage 存分頁清單，以及要在頁面載入時重新用這份清單去抓取對應內容。
11. **分頁數量上限與資源保護**：需不需要限制最多同時開幾個分頁，避免使用者不小心開了 20 個分頁拖垮瀏覽器分頁效能。
12. **既有拖曳排序功能與樹狀側欄的互動**：現有「作品與冊」側欄有拖曳排序（冊之間、故事之間），改成三層樹狀後，拖曳排序的互動範圍（能不能跨層拖、能不能拖進不同的冊）需要重新設計。
13. **搜尋功能**：如果分頁一多，需不需要一個「快速跳到某個分頁」或「搜尋已開啟分頁」的功能（類似 VS Code 的 Ctrl+P）。

## 需要你先決定的開放問題（做減法時優先看這裡）

- **範圍**：Story/Lore/Asset 三種都要支援多分頁，還是先只做 Story 一種（右欄多分頁機制先驗證單一內容類型，之後再擴充）？
- **樹狀側欄的深度**：要不要三層都做（含展開到個別故事/設定/資產），還是只做到「冊/分類/資產集」這層，個別項目維持現在「點進去才換路由」的行為？
- **編輯器常駐 vs 條件渲染**：要「切分頁真正無縫（游標/undo 都保留）」的常駐策略，還是接受「切分頁重新渲染、犧牲一點體感」的條件渲染策略？
- **背景分頁自動存檔**：要不要繼續跑，還是切走就暫停、切回來才恢復？
- **URL 策略**：要不要讓分頁狀態反映在網址上（可分享/可重新整理還原），還是只用 client state 管理？
- **AI 助理面板**：跟著目前作用中的分頁切換，還是每個分頁各自一份？
- **分頁數量上限**：要不要設一個上限（例如最多 8 個），超過要關掉最舊的還是直接擋。

## 工程難度

大：這不是一個功能開發，是編輯頁整個狀態模型的重構（自動存檔、離開警示、樂觀鎖三個既有機制的假設前提都要打掉重寫），加上一個全新的分頁管理層跟樹狀側欄元件。實際工作量高度取決於上面「需要你先決定的開放問題」怎麼答——如果全部選最簡化的選項（只做 Story、條件渲染、背景不自動存檔、URL 不反映分頁狀態、AI 助理跟著作用中分頁），範圍會小很多；如果全部選完整版，這會是這個專案目前為止規模最大的一次前端重構，等級上看得到跟「所見即所得編輯器全面重構」同一量級甚至更大。
