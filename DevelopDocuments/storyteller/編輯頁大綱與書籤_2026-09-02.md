# 編輯頁大綱與書籤（TOC + 書籤筆記合併規格）

> 這份文件取代原本分開的兩份規格草稿（`編輯頁TOC_2026-09-02.md`、`編輯頁書籤筆記_2026-09-02.md`）。使用者的立場很明確：TOC 跟書籤本質上是同一種東西——**一份依文件位置排列的索引，點了就跳過去**，差別只在於「標題」是從內容本身算出來的結構性項目，「書籤」是作者手動加的筆記型項目。兩者合併成同一個功能來規劃、同一個側欄面板呈現。

## 目的

- 編輯頁很長、章節很多時，快速跳到指定標題。
- 作者可以在任一段落加筆記型的書籤（「寫到這」「這裡要回頭改」），醒目標示＋快速定位＋回想起當初想做什麼事。
- 兩者共用同一份清單、同一個側欄面板、同一套跳轉機制，不是兩個各自獨立又長得很像的功能。

## 先聲明一個容易混淆的地方

repo 裡已經有一份 [`DevelopDocuments/storyteller/bookmark.md`](DevelopDocuments/storyteller/bookmark.md)，描述的是**讀者**在**故事閱讀頁**（已發布內容）逐行加書籤、搭配版本記錄與版本 diff 的功能。這份規格是**作者**在**編輯頁**做筆記，使用者、頁面都不同，先分開討論，不動舊文件。

## 為什麼書籤不用「註解」機制實作，但概念上是同一類東西

使用者一開始想到用「註解」來擴充書籤，理由很合理：**兩者都屬於「筆記＋醒目提示＋快速定位」這一類功能**，作者靠醒目的視覺提示回想起「這裡當初要做什麼」。這個概念判斷是對的——書籤在使用者體驗上，其實就是 TOC 的一種特殊項目（結構性標題之外，再加一種「作者手動標記」的項目類型）。

但實作機制上不建議直接用現有「註解」：

- 現有「註解」（comment）是**行內 mark**，掛在「選取的一段文字」上，2026-07-09 就從段落屬性改成這樣（[inlineCommentMark.ts:8-10](static_site/src/pages/storyteller/wysiwygCore/inlineCommentMark.ts:8)），必須先選字才能加，不適合「游標在這裡、想留個記號」的情境。
- 註解內容**直接序列化進故事內容本身**（同檔案 line 12），每次自動存檔、每個版本記錄都會一併存到這份筆記文字，沒辦法獨立查詢/列表化，也會讓故事內容底層字串多出使用者不想公開的雜訊。

結論：**概念上是同一類（筆記＋定位），呈現在同一份清單／同一個面板；但資料實作上分開**——標題是「從內容算出來的結構」，書籤是「作者額外持久化的資料」，兩種資料來源不同，很自然，不衝突（就像 TOC 本身也不需要把「標題」這件事存進另一張表，它就是內容的一部分）。

## 現況調查

- 標題本質上是「段落 + `headingLevel`（0-6）」，不是獨立的 heading node type（[markerParagraph.ts:60-90](static_site/src/pages/storyteller/wysiwygCore/markerParagraph.ts:60)）。
- 每個段落都有穩定的 `markerId`，設計註解裡明講「作為書籤功能的錨點」（同檔案 line 63）。
- **關鍵缺口**：`markerId` 目前是純內部 ProseMirror attribute，`renderHTML` 回傳 `{}`（[markerParagraph.ts:95-99](static_site/src/pages/storyteller/wysiwygCore/markerParagraph.ts:95)），完全沒有輸出到 DOM。這是「點清單項目→捲動到那裡」前必須先補的地基，標題跟書籤都需要它，只要做一次。
- 編輯區是一個 `overflow:auto` 的 `<Paper>` 容器，這次 session 才剛修過兩個「focus() 沒帶 preventScroll 導致編輯區跳回開頭」的 bug（commit `eabf2e3`／`26954a4`／`acd0a3f`）。跳轉時要用 `scrollIntoView` + ProseMirror 的 `setTextSelection`，**不要用 `.focus()` 定位**。
- 編輯頁已經有一組側欄 tab 切換機制（[StorytellerEditorSideTabs.tsx:9](static_site/src/pages/storyteller/StorytellerEditorSideTabs.tsx:9)：`StorytellerEditorSidePanel = "ai" | "agentic" | "history"`），切到某個 tab 時編輯區從 `xs=12` 縮成 `lg=7`（[StoryEditor.tsx:1413](static_site/src/pages/storyteller/StoryEditor.tsx:1413)）。新增一個 `"outline"` tab 掛在同一組機制上即可，不用另開新位置。

## 資料模型

**標題（結構性項目）**：不用存資料庫，每次存檔（手動/自動）時從內容重算一次，見下方「設計方向」。

**書籤（作者筆記項目）**：新表 `storyteller_writing_bookmarks`，比照現有 `StoryChat` 用 `story_id`/`lore_id` 二選一的慣例：

```
id          uint64 PK
story_id    *uint64  -- 跟 lore_id 二選一
lore_id     *uint64
user_id     uint64
marker_id   string   -- 對應段落的 markerId
note        *string  -- 可留空（單純標記這裡）
created_at
```

- Unique(`story_id`/`lore_id`, `user_id`, `marker_id`)——同一段落不重複加書籤。
- Hard delete（不需要保留歷史，比照舊 `bookmark.md` 的原則）。

## 後端 API（書籤 CRUD，標題不需要 API，前端算完就好）

- `GET/POST/DELETE /storyteller/projects/:project/stories/:story/bookmarks`（lore 版本同理）。

## 設計方向：合併呈現

1. **地基**：`markerId` 補上 `data-marker-id` 輸出到 DOM（一次性改動，標題跟書籤共用）。
2. **抽出標題清單**：`extractHeadingOutline(doc)`，跑一次 `doc.descendants(...)`，收集所有 `headingLevel > 0` 的段落，回傳 `{markerId, level, text, pos}[]`（`pos` 是文件內位置，用來跟書籤排序合併）。
3. **合併清單**：把「標題清單」跟「這篇故事/設定集的書籤清單」（API 抓回來，各自對應到一個 `markerId`，同樣需要知道目前文件內的 `pos` 才能排序——可以在 `extractHeadingOutline` 同一次 `descendants` 遍歷時，順便對照書籤的 `markerId` 找出它們目前的 `pos`）依 `pos` 排序、合併成一份清單。
4. **UI 呈現**（同一個面板、同一份清單，不用分頁籤切換）：
   - 標題項目：依 `headingLevel` 縮排顯示標題文字。
   - 書籤項目：書籤圖示 + 筆記內容（沒填筆記就顯示所在段落開頭幾個字當預覽），視覺上跟標題有區隔（例如較小字級/不同底色），但**排列順序是同一條時間軸/文件順序**，不是分開兩區塊。
   - 點擊任一項目：`document.querySelector('[data-marker-id="..."]')` 找到 DOM 節點 → `scrollIntoView({block:"start", behavior:"smooth"})` + `editor.commands.setTextSelection(pos)`。
5. **加書籤的觸發點**：游標所在段落的右鍵選單/工具列「加入書籤」，或段落左側 hover 出現書籤圖示。已加書籤的段落要有視覺提示（比照 `COMMENT_HIGHLIGHT_SX` 的做法，段落層級樣式標示，不用行內 mark）。

## 已定案

- **重新計算時機**：標題清單只要觸發存檔（手動或自動）就重算一次，不是每次 `onUpdate`。書籤清單則是開啟這個面板/存檔時重新打 API 抓最新的即可（書籤本來就是持久化資料，不需要跟編輯內容同步重算）。
- **面板位置**：新增一個 `"outline"` tab，掛在既有的 `StorytellerEditorSideTabs`（跟 AI 助理／編輯歷史同一組），標題跟書籤在同一份清單裡呈現，不用兩個分頁籤。

## User Story

- 一篇故事有 20 個章節標題，使用者想跳到「第十五章」：打開大綱面板，點一下，畫面捲到那個標題、游標也定位過去。
- 寫到一半要去忙別的事，先在游標段落點「加入書籤」記下「寫到這」；之後打開大綱面板，在標題清單間看到自己的書籤項目，一鍵跳回來。
- 校稿時想到某段設定怪怪的，加個書籤附註「這裡跟第三章設定衝突，之後回來改」，之後透過同一份清單逐一巡查，改完就把這筆書籤刪除。

## 常見 fail 應對

- 文件裡完全沒有 heading 也沒有書籤：面板顯示空狀態，不強迫使用者一定要用。
- 同名標題（例如兩個都叫「番外」）：用 `markerId` 定位，不是文字比對，不會點錯。
- 使用者刪除/合併了某個標題段落：`markerId` 消失，下次重算時自然從清單移除，不需要額外清理邏輯。
- 書籤指向的段落被整段刪除：`marker_id` 對應不到任何段落，該項目要顯示「找不到這個位置了，可能已被刪除」的提示，並提供直接刪除這筆書籤的按鈕（不自動清除，讓使用者自己確認）。
- 同一個段落重複加書籤：後端 unique 擋掉，或前端直接讓「加入書籤」變成「移除書籤」的切換按鈕。

## 待確認

- `note` 要不要限制字數？建議跟現有註解欄位規則對齊即可，不用另外設計。
- 書籤要不要分故事版本？我傾向不用分版本——筆記是「這個位置目前要注意」，版本更新後筆記如果還在同一段落就繼續有效，除非你覺得需要。

## 已確認（2026-09-03 討論）

- **`markerId` 外洩到公開輸出**：repo 內沒有任何地方拿這份 tiptap schema 呼叫 `generateHTML()`／`editor.getHTML()`（已 grep 確認），閱讀頁是獨立的 `StorytellerWysiwygMarkdown.tsx` 渲染，不吃這個 schema。`data-marker-id` 輸出到 DOM 不會外洩，不用擔心。
- **標題清單重算時機**：改成「內容即時變動就重算」，不等存檔——`extractHeadingOutline(doc)` 成本低（單純一次 `doc.descendants()`），存檔時重算反而會讓面板顯示落後於使用者剛打的內容，直接跟編輯內容同步反而更省事、也不會有「pos 過期導致跳錯位置」的邊界情況。
- **面板位置改成左側，不佔用右邊 dock**：
  - 現有右邊 dock（AI 助理／編輯歷史）是 `StoryWritingWorkspace` 裡 `xl` 斷點才 `position:fixed` 的獨立欄位，`xs`~`lg` 收合成上下堆疊；大綱／書籤不掛在這組 `StorytellerEditorSideTabs`，而是新增一組**左側**的收合／展開按鈕＋鏡像的左側 dock（結構比照右邊，不是常駐顯示）。
  - 左右兩側各自獨立收合，不互斥——`xs`~`lg` 窄螢幕允許左右兩個面板同時展開，各自收合成上下堆疊（跟現有右邊 dock 在窄螢幕的處理方式一致）。
- **LoreEditor 同步進度**：不分兩階段，StoryEditor 跟 LoreEditor 一次做完（比照 twins 慣例）。
