# 故事／設定集版本歷史 MCP 工具規格

## 背景

Story／Lore 的版本歷史在資料層／Service 層／前端 UI 都已經完整（`storyteller_story_versions`／`storyteller_lore_versions` 表，每次存檔存一筆完整快照）。`Service.StoryVersions`／`Service.StoryVersion`／`Service.LoreVersions`／`Service.LoreVersion`（`service/storyteller/storyteller.go:1510-1523`、`:2429-2444`）都已經寫好，前端 `StoryEditorHistoryPanel.tsx` 就是呼叫這幾個函式對應的 REST API。

唯獨 MCP tool 層只有 `storyteller_revert_story`／`storyteller_revert_lore`，沒有「列版本」「讀特定版本」。`storyteller_revert_story` 的 tool description 甚至老實寫著："There is currently no MCP tool that lists a story's version history"（`service/storyteller/tool_registry_story.go:280` 附近）——這份規格就是要補上這個缺口，讓 AI agent 也能在復原前先看看某個舊版本內容、或比對修改前後差異，不用使用者自己開網頁查「編輯歷史」再把內容貼給 agent。

## 目的

新增 4 個 MCP tool：

- `storyteller_list_story_versions`
- `storyteller_get_story_version`
- `storyteller_list_lore_versions`
- `storyteller_get_lore_version`

Story／Lore 兩邊行為必須一致（同一套邏輯，只是 target 不同），比照現有 `storyteller_revert_story`／`storyteller_revert_lore` 已經是對稱寫法的慣例。

## 資料來源：直接複用既有 Service 函式，不新增 repository/service 邏輯

- `storyteller_list_story_versions` → `Service.StoryVersions(userID, projectPublicID, storyPublicID)`
- `storyteller_get_story_version` → `Service.StoryVersion(userID, projectPublicID, storyPublicID, versionID)`
- `storyteller_list_lore_versions` → `Service.LoreVersions(userID, projectPublicID, lorePublicID)`
- `storyteller_get_lore_version` → `Service.LoreVersion(userID, projectPublicID, lorePublicID, versionID)`

這 4 個 Service 函式已經做好權限檢查（透過 `storyForUserProject`／`loreForUserProject` 確認呼叫者是該 project 的擁有者），MCP handler 不用重複驗證，比照 `storyteller_revert_story` 現有 handler 直接呼叫 Service 拿結果的寫法即可。

## Tool 定義

### `storyteller_list_story_versions`

- Input：`project_public_id`（必填）、`story_public_id`（必填）。
- 回傳：`Service.StoryVersions` 回傳的 `[]storytellerModel.StoryVersion` 陣列，直接序列化即可（`StoryVersion` 已經有完整 `json` tag）。**不要把 `Content` 整份塞進列表回應**——版本一多，內容全部塞進列表會讓單次 tool call 回應暴增；列表只需要 `id`/`title`/`summary`/`word_count`/`reverted_from_version_id`/`conflicted_with_version_id`/`created_at`，`content` 留給 `storyteller_get_story_version` 單獨取。比照 `storyteller_list_stories` 现有回傳只帶摘要欄位、`storyteller_get_story` 才回傳完整內容的既有分工模式。
- Description 需說明：「列出某個故事的版本歷史（不含正文內容，只有摘要資訊），若要讀取特定版本的完整內容請用 storyteller_get_story_version，若要復原到某個版本請用 storyteller_revert_story」。

### `storyteller_get_story_version`

- Input：`project_public_id`（必填）、`story_public_id`（必填）、`version_id`（必填，integer）。
- 回傳：`Service.StoryVersion` 回傳的完整 `StoryVersion`（含 `content`）。
- 邊界：`version_id` 不存在、或存在但不屬於這個 `story_public_id`（跨 story 亂填 version_id）時，`Service.StoryVersion` 內部應該已經會因為找不到符合 `story_id` 的 row 而回錯誤（`s.repo.StoryVersion(story.ID, versionID)` 這一步查詢天生就用 `story.ID` 做篩選）；MCP handler 不用額外判斷，直接把錯誤往上丟即可，跟現有其他 handler 錯誤處理風格一致。

### `storyteller_list_lore_versions` / `storyteller_get_lore_version`

同上，target 換成 lore，欄位對應 `LoreVersion`（型別定義應該跟 `StoryVersion` 平行，若欄位有出入以 `model/entity/storyteller/storyteller.go` 裡 `LoreVersion` 實際定義為準）。

## Tool Description 撰寫要求

- `storyteller_revert_story`／`storyteller_revert_lore` 現有 description 裡那句「There is currently no MCP tool that lists a story's version history」已經過時，這次要一併拿掉，改成指向新工具（例如：「target_version_id can come from storyteller_list_story_versions or storyteller_get_story」）。
- 新工具的 description 要讓 agent 看得懂三個工具的分工：list（摘要清單）→ get（單一版本完整內容）→ revert（復原）。

## 註冊方式

新工具加進 `storytellerStoryToolSpecs()`／`storytellerLoreToolSpecs()` 回傳的 slice 即可（`service/storyteller/tool_registry_story.go`／`tool_registry_lore.go`）。**不用手動把工具名稱加進任何清單**——`StorytellerToolRegistry()`（`service/storyteller/tool_registry.go`）已經改成直接照這幾個 provider function 的宣告順序全部收進去，新增的 spec 會自動被註冊，這是這個 repo 最近才做的重構，切記不要走回頭路手動維護名稱清單。

## 不做

- 不做版本間 diff／比對的 MCP tool（前端已經有 `StoryVersionDiff.tsx` 做這件事，AI agent 如果需要比對，可以自己呼叫兩次 `storyteller_get_story_version` 再自行比較文字，不用後端多做一個 diff 工具）。
- 不新增 repository／service 層函式，純粖包一層 MCP handler。
- 不動現有 REST API／前端 UI。

## 常見 fail 應對

- `story_public_id`／`lore_public_id` 不存在，或不屬於呼叫端有權限的 project：`storyForUserProject`／`loreForUserProject` 應該已經會回錯誤，直接往上丟。
- `version_id` 是別的 story/lore 的版本 id（跨目標亂填）：因為查詢天生用 `story.ID`／`lore.ID` 做篩選條件，會查不到、回錯誤，不會誤回到別人的版本內容。

## 工程難度

小：純粹是 4 個薄 MCP handler，複用既有已驗證過權限的 Service 函式，不新增任何 repository/service 邏輯。抓半天到一天等級。
