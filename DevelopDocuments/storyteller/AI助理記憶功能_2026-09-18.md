# AI 助理記憶功能提案

- 狀態：**規格草案，尚未拍板是否實作**，先列出來讓你挑戰
- 前置討論：本文彙整聊天中對 scope 分層、資料表欄位、chat 關聯設計的結論，未另存逐字記錄

## 背景與目的

AI 助理目前只在單一 story/lore 的 context 內運作，跨對話、跨故事沒有持久記憶。這個功能讓使用者手動觸發「整理成記憶」，把當下對話摘要成一條記錄存進記憶倉庫；同時開放 MCP 讀取，讓外部 client 也能拿記憶做分析。

**明確不做的事**：不做「專案層／全域層的助理聊天介面」。記憶分三層儲存，但讀取時是由現有的 story/lore 助理往上合併撈（story → project → global），助理本身不需要知道自己在哪一層執行。等哪天真要做專案儀表板等級的助理入口，是獨立的功能，屆時資料結構已經現成。

## 資料表設計：`storyteller_memories`

沿用 `storyteller_story_chats` 已有的 nullable FK 慣例（`*uint64`），soft delete 比照 index.md 的專案慣例。

| 欄位 | 型別 | 說明 |
|---|---|---|
| `id` | `uint64` PK | |
| `public_id` | `varchar(32)` NOT NULL，UNIQUE | upsert 用的穩定識別碼，比照 `lore_public_id` 的模式由呼叫端（MCP client／前端）指定或帶入，不外露內部 `id` |
| `memory_name` | `varchar(255)` NULL | 顯示用標題，可為空；為空時前端取 `content` 前幾十字當預設顯示。**不是 upsert key**，可隨時改名 |
| `user_id` | `uint64` NOT NULL | 建立者，稽核用。**不做查詢隔離**——project/story/lore 層級的記憶是該範圍協作者共用的池子，只有 global 記憶才真正依 user 分隔（見下方 scope 說明） |
| `project_id` | `uint64` NOT NULL，預設 `0` | `0` = global；非 0 = 綁定該專案。story/lore 層級的記憶也直接填入其所屬 project_id（story 建立後不會換 project，denormalize 沒有漂移風險，省一次 join） |
| `story_id` | `*uint64` NULL | 與 `lore_id` 互斥，**由應用層驗證**，不依賴 DB CHECK constraint（MySQL 版本可能不保證生效） |
| `lore_id` | `*uint64` NULL | 同上 |
| `chat_id` | `uint64` NOT NULL，預設 `0` | 指向 `storyteller_story_chats.id`。`0` = 非對話觸發（MCP 建立）。純粹是「這條記憶是哪次對話生成的」的回溯指標，跟下面的稽核欄位是兩件事，查詢 scope 不需要 join 這張表 |
| `provider_apikey_id` | `*uint64` NULL，FK `storyteller_provider_apikeys(id)` ON DELETE SET NULL | 稽核 + 費用估算用，MCP 呼叫時通常拿不到，允許空 |
| `model_name` | `varchar(255)` NULL | 同上，純記錄用途，**不能拿來當查詢/篩選條件**，換 key／換 model 仍要讀到同一批記憶 |
| `prompt_tokens` / `completion_tokens` | `int unsigned` NULL | 如果 `provider_apikey_id` 的目的是估費用，只記 key 不夠，還需要用量數字才算得出成本 |
| `content` | `text` NOT NULL | 記憶本文 |
| `status` | `enum('pending','in_progress','completed','failed')` 預設 `completed` | 比照 `storyteller_story_chats.status`，讓「整理記憶」這個動作可以走非同步、失敗可重試，不用另外設計一套狀態機 |
| `deleted_at` | `*time.Time` NULL | soft delete |
| `created_at` / `updated_at` | `time.Time` | |

### scope 組合語意

| project_id | story_id | lore_id | 意義 |
|---|---|---|---|
| `0` | NULL | NULL | global（該 user 跨專案共用） |
| `>0` | NULL | NULL | project-level（該專案協作者共用） |
| `>0` | 有值 | NULL | story-level |
| `>0` | NULL | 有值 | lore-level |

### 權限，不在這張表上處理

「誰能新增/編輯/刪除記憶」交給現有 RBAC（collaborator permission）機制判斷，不在 `storyteller_memories` 自己另外發明權限欄位或邏輯——比照現有 project owner / collaborator 的權限模型加一個對應權限位即可。

## User story

1. 使用者在 story 編輯頁跟 AI 助理對話一段後，按「存為記憶」→ 助理生成摘要草稿與建議 scope → 使用者確認/調整 scope → 寫入，`chat_id` 記錄來源對話。
2. 使用者之後在同一個 story（或掛同一 project 的其他 story）跟助理對話，助理自動合併撈取 story→project→global 記憶注入 context，不用重講一次。
3. 外部 MCP client 呼叫 `storyteller_list_memories`／`storyteller_search_memories` 讀取指定 scope 的記憶做分析；也可呼叫 `storyteller_upsert_memory` 帶 `memory_public_id` 建立或更新記憶。這類寫入 `chat_id`、`provider_apikey_id` 為空/0。
4. 專案協作者 B 看得到協作者 A 在同一個 project/story 建立的記憶（因為不依 user_id 做查詢隔離），但沒有維護權限的協作者不能編輯/刪除。

## 常見 fail 應對

- **story_id / lore_id 同時有值或同時為 NULL**：寫入時應用層直接拒絕，回傳明確錯誤，不要吃掉錯誤靜默存成 global。
- **`provider_apikey_id` 指向的 key 被刪除**：`ON DELETE SET NULL`，記憶本體不受影響，只是稽核欄位變空。
- **「整理記憶」呼叫 model 失敗**：`status='failed'`，比照現有 chat 的 pending/重送機制處理，不要留一條半成品的 `completed` 記憶。
- **MCP 呼叫沒有 project/story/lore 任何一個 scope 參數**：由呼叫端顯式指定，不做「猜測 scope」的自動推斷；沒帶就報錯，不要預設存成 global。
