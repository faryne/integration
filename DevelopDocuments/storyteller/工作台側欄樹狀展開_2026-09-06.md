# 工作台側欄樹狀展開規格

## 範圍縮減說明

`工作台多分頁編輯_2026-09-06.md` 那份完整規格暫緩，這次**只做左側欄的樹狀展開**：冊/設定集分類/資產集底下可以展開看到個別故事/設定/資產，點擊後**維持現有行為**（換路由到該項目的編輯頁，不開新分頁）。多分頁機制不在這次範圍內。

## 追加決定（2026-09-06 上線後回頭檢討）：拿掉資產集這層展開

第一版（Codex 實作，commit `29e9b6d`）把 Story／Lore／Asset 三層都做了展開。上線後回頭看，**決定拿掉資產集這層展開**，只保留 Story（冊 > 故事）跟 Lore（分類 > 設定）兩層。

理由：資產本質上要靠**縮圖**辨識，不是靠標題文字——故事/設定的標題是作者自己取的、有意義的識別依據，但資產的標題常常就是上傳時的原始檔名（例如 `IMG_1234.png`），純文字列表在窄側欄裡沒辦法讓使用者「看標題就知道是哪張圖」，展開了也還是得點進資產集列表頁看縮圖網格才能確認是哪張圖，等於多一層沒什麼用的中介步驟。拿掉這層同時也順便消掉先前資產展開用「大 `page_size=500` 沿用分頁 API」帶來的邊界情況（單一資產集超過 500 筆會被截斷）。

**要移除的部分**：
- 資產集節點（`ProjectWorkspaceSidebarTree.tsx` 裡的 `SidebarCollectionRow`，`section === "assets"` 的分支）不再顯示展開箭頭／不再可展開，維持原本「點資產集本身換路由到列表頁看縮圖網格」的行為（這是修改前、樹狀展開功能上線前的原始行為，回退到這個狀態即可）。
- `ProjectWorkspaceSidebarTreeChildren.tsx` 裡處理資產子節點清單的邏輯（用 `useStorytellerAssets` 帶 `pageSize=500` 抓全部那段）整段移除，不要留著死代碼。
- Story／Lore 這兩層的展開**完全不受影響，維持現狀**，這次只精準拿掉 Asset 這一種類型的展開能力。

## 現況（沿用 `工作台多分頁編輯_2026-09-06.md` 的調查結果）

- 側欄目前兩層：區塊（作品與冊/設定集/資產集）> 收藏集（`ProjectWorkspacePreviewComponents.tsx:66-172` `WorkspaceSidebar`），`SidebarGroup` 用 `Collapse` 做收合。
- 故事清單一次抓齊全（`useStorytellerStories`，無分頁）；設定/資產本身是**依收藏集分頁抓取**（一頁 20-24 筆），不是一次性清單。
- 現有標題截斷慣例：`noWrap` + 父層 `sx={{ minWidth: 0 }}`（flexbox 的標準截斷寫法，讓 `text-overflow: ellipsis` 生效），沒有搭配 hover tooltip 顯示完整文字（`ProjectWorkspacePreviewComponents.tsx:748-770` 的頁面標題就是這樣處理，冊/設定分類名稱同樣模式）。這次第三層維持同樣慣例，不額外加 tooltip，除非你想要更好的可讀性再加。

## 問題 1：標題過長怎麼顯示

沿用現有 `noWrap`（單行省略號截斷）+ 父層 `minWidth: 0` 的既有慣例，**不換行、不做多行截斷**（`WebkitLineClamp` 那種多行省略在側欄這種窄版面沒有意義，一行內容夠長時兩行也還是會被切掉，徒增高度不確定性，不好對齊樹狀縮排的視覺節奏）。

第三層縮排後可用寬度比第二層更窄，長標題被截斷的機率更高，這裡有兩個選項：

- **維持現況（跟現有二層一樣，純截斷不做其他事）**：使用者要看到完整標題，就要點進去讓標題出現在編輯頁上方。
- **加 Tooltip**：`hover` 時彈出完整標題文字。這是現有慣例沒有的東西，屬於這次順便補的小加分項——工程成本很低（MUI `Tooltip` 包一層），但要注意手機版沒有 hover，Tooltip 在觸控裝置上幫助有限。

建議：直接做 Tooltip（成本低、對桌面版使用者有實際幫助，觸控裝置沒有 hover 也不會變得更差，純粹是錦上添花），除非你覺得沒必要。

## 問題 2：展開時的 loading 顯示

因為故事清單是一次抓齊全的（沒有分頁 API），冊底下展開故事**不需要額外的網路請求跟 loading 狀態**——資料已經在記憶體裡，展開只是切換 UI 顯示，是同步的。

設定集分類／資產集底下的個別項目不是一次抓齊全，是分頁 API。這裡有兩條路：

- **選項 A：展開時另外呼叫一支「該分類下全部項目（不分頁）」的輕量清單 API**（只回 id/title，不用完整內容），第一次展開時顯示 loading（skeleton 或轉圈），資料回來後常駐在記憶體裡，之後收合再展開不用重新抓。
- **選項 B：展開時用現有分頁 API 抓第一頁，捲動到底才載入下一頁**（側欄本身要做無限捲動），沒有一次性清單 API 的開發成本，但側欄的樹狀節點如果本身在一個已經有捲軸的側欄容器裡再嵌一層捲動，UX 上容易讓使用者搞不清楚捲的是哪一層。

建議選 A：新增一支不分頁的輕量清單端點（只回 id/title/sort，不用資產的 metadata 或設定的內容摘要），對後端來說是很小的改動（比照現有 `list_lores`/`list_assets` 拿掉分頁參數的簡化版本），能避免側欄疊兩層捲軸的體驗問題。Loading 狀態比照現有 `WorkspacePane`（`ProjectWorkspacePreviewComponents.tsx:776-779`）的 `CircularProgress` 寫法，展開節點內顯示一個小的轉圈（不要用整頁 loading，只在該節點展開的位置顯示）。

## 已修復：行動版工作台列表顯示不完全（跟這次功能無關，順手一併修掉）

**根因**：`StoryRow`/`LoreRow`（`ProjectWorkspacePreviewRows.tsx`）外層 `<Stack direction="row">` 沒有 `flexWrap`，窄螢幕下標題以外的元素（icon、狀態 Chip、`actions` 那組 Switch+IconButton）加起來的最小寬度會超過視窗寬度，又因為外層容器是 `overflow: "auto"` 不是 `hidden`，內容不是被裁掉而是被推出視窗要橫向捲動才看得到——體感等同「顯示不完全」。不是 `WorkspaceChrome.tsx` 外殼佔用寬度的問題，`xs` 斷點下右欄本來就拿到全部可用寬度。

**修法**：`StoryRow`/`LoreRow` 的外層 `Stack` 加上 `flexWrap="wrap" useFlexGap`，讓 Chip/操作按鈕在窄螢幕自然換到第二行，跟專案裡其他地方處理類似橫向擠壓問題的既有慣例一致（`ProjectWorkspacePreviewActions.tsx` 的 actions 區塊、側欄色系選單都是這樣處理）。已用行動版模擬視窗（375px）實測：換行後 `scrollWidth` 等於 `viewport width`，沒有橫向溢出，桌面版因為空間夠不會觸發換行，不受影響。
