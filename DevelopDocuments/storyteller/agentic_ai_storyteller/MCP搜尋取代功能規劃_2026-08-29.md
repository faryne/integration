# MCP 故事/設定集 content 搜尋取代功能規劃（2026-08-29，2026-08-29 定案修訂）

## 背景／目標

使用者提出的原始需求：多篇故事/設定集裡有共通字眼要批次替換（例如「LuxOris」→「LUXORIS」），逐篇整份覆寫送出太麻煩，需要一個 MCP 工具直接對內容做搜尋取代。這是給 `/mcp` 端點（PAT 認證，Codex／Grok Builds 等外部工具用）的新工具，不是給站內「AI 助理」agentic 對話用的。

## 已定案的決定

- **RE2（Go 標準庫 `regexp`），不用第三方 PCRE 相容套件**——見下方「RE2 vs PCRE」說明。
- **不做 `dry_run`**，直接執行、直接寫入。安全網只有「事後可以用既有的 `storyteller_revert_story`/`storyteller_revert_lore` 退回」，這是使用者知情後的選擇，不再多爭論。
- **工具維持單篇（一次呼叫處理一個 story 或 lore）**，多篇文章的批次交給呼叫端（Codex 等）自己分次呼叫，不在工具內部做迴圈。
- **不卡 content 長度**，10 個字跟一萬個字一視同仁，不加任何長度門檻。
- **圖片說明（`Pages[].Description`）也算搜尋取代的目標範圍**——`content_type=image` 的故事不再整個排除，改成對每一頁的 `Description` 做搜尋取代（細節見下方）。

## RE2 vs PCRE 差在哪，為什麼直接用 RE2 沒問題

Go 標準庫的 `regexp` 套件是 **RE2** 引擎，跟 PCRE（Perl-Compatible Regular Expressions）不是同一種實作方式：

- **RE2**：用有限自動機（類似 Thompson NFA）比對，數學上保證**線性時間**，不可能發生「卡死」——不管 pattern 多複雜、輸入多長，時間跟輸入長度成正比，天花板可預期。代價是犧牲了一些需要「回溯」才能做到的語法。
- **PCRE**：用回溯（backtracking）比對，語法能力比較強（下面列的都支援），但某些 pattern 碰上特定輸入會觸發**指數級**時間（俗稱 catastrophic backtracking，例如 `(a+)+$` 這種巢狀量詞碰到一長串不匹配的輸入），這就是 ReDoS 攻擊的原理——外部输入的 pattern 有機會讓伺服器那個 request 直接卡死。

RE2 缺的語法：
- **Backreference**：pattern 裡引用前面已經比對到的 group，例如 `(\w+)\s+\1` 找「重複的單字」。
- **Lookahead/lookbehind**：`(?=...)`／`(?!...)`／`(?<=...)`／`(?<!...)` 這種「檢查但不吃掉字元」的零寬斷言。
- 更進階的 possessive quantifier、atomic group、recursive pattern 完全用不到，一般文字取代不會碰到。

RE2 有的、日常搜尋取代夠用的語法：字元集 `[...]`、交替 `|`、量詞 `*+?{n,m}`、capture group（取代字串可以用 `$1`／`${name}` 引用）、非捕獲群組 `(?:...)`、錨點 `^$`、單字邊界 `\b`、行內旗標 `(?i)`（不分大小寫）／`(?s)`（`.` 吃換行）／`(?m)`（多行模式）。

**針對「取代」這個情境，缺 lookahead 通常有替代寫法**：例如想「只替換後面接著空白的 LuxOris」，PCRE 會寫 `LuxOris(?=\s)`，RE2 沒有 lookahead，但可以改成 pattern `LuxOris(\s)`、取代字串 `LUXORIS$1`——把後面那個字元「抓進 group、在取代字串裡塞回去」，效果一樣，只是要多想一步。

**結論**：直接用 RE2，不用選第三方套件——查過現有 backend 完全沒有處理過外部輸入正規式的先例，RE2 天生沒有 ReDoS 風險，不用另外設計逾時防護，維護成本最低。

## 圖片說明也算搜尋取代目標——設計調整

原本規劃是 `content_type=image` 的故事直接排除（因為 `content` 存的是 `{"pages":[...]}` 這種 JSON，不是純文字，見 `StoryImageContent`，[storyteller.go:821-825](../../../model/entity/storyteller/storyteller.go)）。使用者確認圖片說明也要能搜尋取代，所以改成：

- **`content_type=text`**：直接對 `content`（純文字）做搜尋取代，跟原規劃一樣。
- **`content_type=image`**：解析 `content` 的 JSON，對**每一頁的 `Description` 欄位**分別做搜尋取代（不是對整份 JSON 字串做文字取代——那樣會有比對到 JSON 結構本身字元、破壞資料格式的風險），取代完把 `Pages` 陣列重新組回 JSON、存檔。
- 兩種類型的比對次數要分開算清楚在回應裡（例如 `content_type=text` 回一個總比對數；`content_type=image` 回「總比對數」＋「影響了幾頁」），讓呼叫端知道實際改了哪裡。

## 最終規格

- **新 MCP 工具**：`storyteller_search_replace_story`／`storyteller_search_replace_lore`（兩個獨立工具，比照現有 story／lore 工具都分開兩支的慣例）。
- **輸入參數**：
  - `project_public_id`（必填）
  - `story_public_id` 或 `lore_public_id`（必填，依工具而定）
  - `search`（必填，字串）
  - `replace`（必填，字串；`is_regex=true` 時支援 `$1` 之類的 capture group 引用）
  - `is_regex`（選填，boolean，預設 `false`——避免單純字串取代時，字串裡剛好有正規式特殊字元被誤解析；`false` 時內部用 `regexp.QuoteMeta` 跳脫成字面比對）
- **行為**：
  1. 讀出故事/設定集。
  2. `is_regex=false` 時把 `search` 用 `regexp.QuoteMeta` 跳脫；`is_regex=true` 時直接用 RE2 語法編譯，編譯失敗回明確錯誤訊息（附失敗原因）。
  3. `content_type=text`：對 `content` 做 `ReplaceAll`，算比對次數。
  4. `content_type=image`：對每一頁的 `Description` 分別做 `ReplaceAll`，累計總比對次數與受影響頁數，重組 `Pages` 存回 JSON。
  5. 比對到 0 次：回報 `match_count: 0`，不寫入、不建新版本（避免版本歷史留空紀錄）。
  6. 比對到 ≥1 次：直接執行取代並存檔，走既有的 `UpdateStory`/`UpdateLore` 路徑（沿用既有的建版本行為，改壞了可以用既有的 revert 工具退回），回傳新的 `content`／`version_id`，比照 `storyteller_upsert_story` 現有的回應組法。

## 預期影響檔案

- `service/mcp/storyteller_tools.go`：新工具的 MCP 層封裝（`RegisterTool`+`InputSchema`+`Handler`）。
- `service/storyteller/tool_registry_story.go`／`tool_registry_lore.go`：實際的搜尋取代邏輯（比照其他工具的慣例放在這層）。
- 不用動 `service/storyteller/storyteller.go` 的 `UpdateStory`/`UpdateLore`——直接呼叫現有方法存檔即可，不需要新增 service 方法。
- 不用動站內 AI 助理（`agentic_query.go`、前端 `StorytellerAgenticPanel.tsx` 等）——這是純 MCP 工具，跟站內對話功能無關。

## 補充：搜尋索引不用額外處理

`UpdateStory` 本身已經會自動呼叫 `syncStorySearchIndex()`（[storyteller.go:920](../../../service/storyteller/storyteller.go)）把改完的內容同步進 Elasticsearch，新工具只要照規格走既有的 `UpdateStory` 存檔路徑就會免費拿到，不用額外寫 reindex 邏輯。順帶查到 `UpdateLore` 目前完全沒有接搜尋索引（設定集本來就搜不到）——這是既有缺口，跟這次的新工具無關，使用者確認先不管、不排進這次範圍。
