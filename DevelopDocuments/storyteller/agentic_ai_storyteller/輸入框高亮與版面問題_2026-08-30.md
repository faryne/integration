# AI 助理輸入框高亮／版面問題（2026-08-30 討論）

使用者回報 4 個問題，經過查證程式碼＋跟 Codex 討論後的結論。這份文件只記錄分析結果與建議方向，**不要主動實作**，等使用者明確下指示才整理成正式需求規格丟給 Codex。

## 現況架構（背景知識）

輸入框的語法高亮是經典的「透明 `<textarea>` 疊在鏡射文字的 `<div>` 上」技巧，不是 `contenteditable`：
- 真正的 `<textarea>`（`StorytellerAgenticPanel.tsx:2010-2033` 附近）設 `color: transparent`、`caretColor: text.primary`——原生游標是真的、由瀏覽器畫，只有字看不到。
- `StorytellerPromptHighlightOverlay.tsx:27-115` 是絕對定位疊在上面、`pointerEvents: none` 的鏡射 `<div>`，透過 `useLayoutEffect` + `ResizeObserver` 同步位置/捲動/字型，用 `segmentStorytellerAgentPromptForHighlight` 把 `@story` 這類 token 上色。
- **這個 overlay 本身沒有 bug**，它不管理任何游標/選取狀態，純粹是視覺同步層。

## 問題 1＋2：選了 @story／@lore 候選後，游標跑掉／文字沒插對地方

**根因（已查證）**：`insertStoryMention`／`insertLoreMention`（`storytellerAgentEditing.ts:13-37`）：
1. regex 錨定在**整個字串最尾端**（`$`），不是游標實際位置——游標不在文字最後面時比對失敗，退化成直接把 token 加到字串最後面。
2. 呼叫端（`StorytellerAgenticPanel.tsx:2176-2205`）點候選時只 `setPrompt(...)`，**完全沒有 restore focus／selection**——同檔案的 `applyStorytellerAgentText`（`:78-108`）已經有正確做法可以參考：`requestAnimationFrame` 裡 `target.focus()` + `target.setSelectionRange(...)`，這兩個 mention 函式的呼叫端沒有比照做。

**建議方向（Codex 補充，比我原本想的更完整）**：
- 不要只是多帶一個游標數字修一半，應該把 mention 編輯改成「range operation」：輸入 `(value, selectionStart, selectionEnd, kind, title)`，回傳 `{ value, selectionStart, selectionEnd }`。邏輯是找**游標前方最近、且游標落在其 query 範圍內**的 partial token（例如使用者正在打 `@story:某段` 這一段）去替換；找不到符合的 partial token 才退回在目前 selection/cursor 位置插入，不是無條件比對字串結尾。
- 有一個額外的真實陷阱：點候選按鈕的當下，`<textarea>` 可能已經先 `blur()` 掉了（滑鼠點到按鈕的瞬間）——要嘛在候選按鈕上用 `onMouseDown.preventDefault()` 避免搶走 focus，要嘛維護一個 `promptSelectionRef` 記住點擊前的游標位置，跨過 blur 之後在 `requestAnimationFrame` 裡用記住的位置 restore。
- **不建議把整個高亮機制換掉**（例如換 `contenteditable` 或現成的 rich text editor）——現有的 bug 是選取／range 邏輯沒做完整，不是 overlay 技術本身有問題；overlay 只是純視覺同步層，IME／游標／貼上都還是交給原生 `<textarea>` 處理，對「少量 token 高亮」這種需求是合理、低成本的方案，換掉是殺雞用牛刀，還會引入新的相容性問題（IME 組字、貼上格式化等）。

## 問題 3：`/` 指令沒有比照 `@story` 做語法高亮

**現況（已查證）**：slash command 解析（`^/(\S+)`，只認字串開頭）跟高亮 token 系統（`matchHighlightTokenAt`，`storytellerAgentReferences.ts:72-133`，只認 `@thisStory`／`@thisLore`／`@story:[...]`／`@lore:[...]`，可以出現在任意位置）完全獨立，沒有共用邏輯。

**建議方向（Codex 意見，跟我原本設想的不同，值得採納）**：**不要**把 slash command 硬塞進 `matchHighlightTokenAt` 這套「任意位置掃描」的架構——兩者語法生命週期不一樣（`@story` 是行內任意位置的引用 token，slash command 是「整個訊息模式」的開頭 prefix，語意層級不同，硬塞同一套掃描邏輯會很彆扭）。比較乾淨的做法是**維持兩套獨立 parser，只在渲染時合併 segment**：先跑一個「只認字串開頭」的 slash command segmenter，命中就標成 command segment；剩下的文字才丟給既有的 `segmentStorytellerAgentPromptForHighlight` 做 `@story` 這類的高亮，兩者結果串起來顯示。

## 問題 4：AI 助理面板整體高度想要跟輸入區高度「一致」

**現況（已查證）**：`StorytellerAgenticPanel.tsx:1750, 1843-1856, 1971` 附近——`lg` 斷點外層 `Stack` 釘死 `height/maxHeight: 720`，訊息列表 `minHeight:{xs:360,lg:0}`／`maxHeight:{xs:520,lg:480}`，輸入區是自動高度（沒有 flex）。`TextField` 用 MUI 內建 `minRows={3} maxRows={8}` 自動長高，底下還有好幾排按鈕/chip 也會換行貢獻高度。結果：`lg` 斷點下輸入區長高會把訊息列表擠壓到接近 0（總高度釘死在 720，但訊息列表可能被壓縮到很小）；`xs` 斷點完全沒有固定高度，面板跟著內容無限長高，不會擠壓但也談不上「一致」。

**這句需求本身有點模糊，需要使用者進一步確認**：「整體高度跟輸入區高度一致」比較像是在表達「不希望輸入框長高時把對話列表擠壞」＋「面板高度不要跳來跳去看起來很怪」，但確切想要哪一種版面關係還不確定。Codex 建議直接問清楚：**想固定的是整個 panel 的高度，還是輸入區本身的高度上限？**

**如果要動，具體版面建議（Codex 提供，供之後參考）**：
- `lg` 斷點改用 CSS Grid 明確切三列：`grid-template-rows: auto minmax(240px, 1fr) auto`（標題／訊息列表／輸入區），面板高度固定或用 viewport-aware 的值，例如 `height: min(720px, calc(100vh - 32px))`，不要只釘死一個常數。
- 輸入區設一個高度上限，超過之後**內部自己捲動**，不再把整個 composer 撐高——這樣輸入框長高不會反過來擠壓訊息列表。
- 訊息列表給合理的 `minHeight`（不要是 `lg: 0`），保證不會被壓到看不到內容。
- **不建議只靠現有的 flex 架構再補幾個 `maxHeight` 修修補補**，因為 chips／autocomplete 按鈕的換行也是高度來源之一，零散的 flex 調整很容易顧此失彼。
- 手機（`xs`）維持現在的自然流動或改成 viewport cap 就好，強行套用固定 720px 在小螢幕上通常更難用，不建議跨斷點套用同一種高度策略。
