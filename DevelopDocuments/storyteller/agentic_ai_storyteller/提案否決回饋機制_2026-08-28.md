# 提案（Proposal）否決回饋機制（2026-08-28 討論）

## 問題

Agent 提出寫入提案（AgentProposal）後，使用者按「套用方案」／「否決」／都不選，這個決定完全不會進到下一輪對話的 context 裡——AI 在同一個 chat 串的後續回合完全不知道使用者做了什麼。

現況資料流：
- 提案存在獨立表 `storyteller_agent_proposals`，跟 `storyteller_story_chat_messages`（歷史記憶來源）分開。
- `agenticQueryHistoryMessages`（`service/storyteller/agentic_query.go:157`）重組歷史時，每個 chat 嚴格要求剛好 1 則 user + 1 則 assistant，不容許多插一則。
- `ApplyAgentProposal`／`RejectAgentProposal`（`service/storyteller/agent_proposal.go:139-232`）只更新 `AgentProposal.Status`，不碰 `StoryChatMessage`。

## 三種情境各自的結論

- **套用（含使用者滿意）**：不用做任何事。套用之後故事內容已經真的被改了，下一輪 AI 用工具查資料時看到的就是新內容，狀態是「活的」，不需要額外告知 AI。
- **都不選（pending）**：不用做任何事。使用者可以直接繼續正常對話，不需要提醒 AI「還有一個沒回應的提案」。
- **否決（含「75% 滿意、25% 想改」這種部分否決）**：兩者本質上是同一種情境（否決＋帶著具體意見），**不要拆成兩條流程**，都走同一套「否決 dialog」處理，讓使用者自己用白話描述要整段重寫還是只改某部分，交給 AI 自己判斷語意——不特別做選取範圍 UI（那是加值項，先不做，太陽春的文字框描述夠不夠用，等實際用過再說要不要加）。

## 否決流程設計（結論：應該是純前端功能，不用動 backend）

查過 `AgenticQueryRequest.ReplyContent`（`model/entity/storyteller/storyteller.go:1021`，JSON tag `reply_content`）本來就是通用的請求欄位，「回覆」功能已經在用同一套機制把「被回覆訊息的完整內容」塞給下一輪對話（不進 chat history 的嚴格 user/assistant 配對，是每次呼叫當下組進 prompt 用完即拋，但會存進 metadata 供之後重送用）。否決流程可以直接借用這套，完全不用碰 `agenticQueryHistoryMessages` 的配對邏輯。

流程：
1. 使用者在提案卡（`static_site/src/pages/storyteller/StorytellerAgenticProposalCard.tsx`）按「否決」→ 跳一個**只有一個文字框**的 dialog，placeholder 類似「哪裡要改？也可以直接說『整段重寫』」。不做全盤/部分重寫的選項切換，只給一個開放式文字框（可以加一顆「整段重寫」快捷按鈕，點了直接帶預設文字，純粹是輸入捷徑，不是另一套資料流）。
2. 送出時做兩件事：
   - 照舊呼叫既有的 `RejectAgentProposal`，把提案標記否決。
   - 組一段跟「回覆」功能一樣格式的引用內容（`buildStorytellerAgentReplyReferenceContent` 的 fence 格式，`static_site/src/pages/storyteller/storytellerAgentReferences.ts:354`），把**提案原本的 tool 名稱＋Arguments**（AI 當初想寫入的實際內容，已經存在 proposal 的 Arguments 裡）包進去，當作 `reply_content` 送出一則新的 agentic query，`user_prompt` 就是使用者剛打的意見。
3. 全部走既有的 `runAgentic()` 呼叫路徑，跟平常送訊息、回覆訊息完全同一套，只是引用的對象從「一則舊訊息」換成「一個提案」。

Arguments 是任意 JSON（不同工具長得不一樣，改故事內容/改設定集/改冊名都可能是提案），最簡單的做法是原封不動 `JSON.stringify` 塞進引用區塊，不特別為每種工具客製格式化文字。

## 預期影響檔案

- `static_site/src/pages/storyteller/StorytellerAgenticProposalCard.tsx`：加否決 dialog + 送出邏輯。
- `static_site/src/pages/storyteller/storytellerAgentReferences.ts`：可能需要一個組「提案引用文字」的 helper（跟 `buildStorytellerAgentReplyReferenceContent` 類似，或直接沿用）。
- 目前判斷不需要動 backend（`service/storyteller/agentic_query.go`、`agent_proposal.go`、DB schema 都不用改），因為 `reply_content` 欄位跟 `RejectAgentProposal` API 都已經存在。實際動工時如果發現需要動 backend，要先想清楚為什麼現有機制不夠用。

## 還沒決定、動工前要再確認的細節

- Dialog 的確切文案／有沒有要加「整段重寫」快捷按鈕。
- 否決後送出的這輪對話，畫面上要不要用某種方式標示「這是針對被否決的提案而發」（例如像「回覆」訊息那樣帶一行 blockquote 摘要），還是就當一則普通的使用者訊息處理。
- 如果一次有多個提案（同一輪或跨輪），否決其中一個時，引用內容只包那一個提案，不用管其他提案的狀態。
