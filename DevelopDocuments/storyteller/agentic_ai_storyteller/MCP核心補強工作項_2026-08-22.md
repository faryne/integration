## 工作項

- [ ] **1.（Codex）新增 `storyteller_revert_story` MCP 工具**
  - What：包一層 MCP 工具呼叫既有 `Service.RevertStory(userID, projectPublicID, storyPublicID, targetVersionID, source)`（[storyteller.go:907](../../../service/storyteller/storyteller.go)）。
  - Why：這個 service 方法已經存在、已經被網頁版「編輯歷史」面板在用（[route/storyteller.go:83](../../../route/storyteller.go)），但完全沒有曝露成 MCP 工具，AAS／任何 MCP client 目前沒有任何辦法退回歷史版本，是整套「整份覆寫 + diff 確認 + revert 安全網」流程缺的最後一塊。
  - Where：新工具加在 `service/mcp/storyteller_tools.go`，緊接在 `storyteller_upsert_story`（[storyteller_tools.go:591](../../../service/mcp/storyteller_tools.go)）附近，方便閱讀時上下對照。
  - How：照 `storyteller_upsert_story` 的既定寫法（`RegisterTool` + `objectSchema` + `Handler`）：
    - `InputSchema`：`project_public_id`（必填）、`story_public_id`（必填）、`target_version_id`（必填，integer，對應 `storyteller_get_story` 或版本列表回傳的 version_id）。
    - `source` 固定傳 `"mcp"`（沿用網頁版 `"web_manual"` 的先例，AAS 之後如果要細分來源可以再議，這輪先用同一個字串）。
    - 回傳沿用 `storyteller_upsert_story` 現有的 `jsonTextResult(storytellerStoryDetail{...})` 組法（包含新的 `LatestContent`/`VersionID`），讓呼叫端 revert 完立刻拿到最新內容，不用再多呼叫一次 `storyteller_get_story`。
    - 目前沒有「取得故事版本列表」的 MCP 工具可以查 `target_version_id`——這是已知限制，先在 `Description` 裡註明「version_id 目前只能透過 storyteller_get_story 拿到目前這一版的，或是使用者自己在網頁版『編輯歷史』查」，不在這輪額外補查詢工具（範圍控制，之後真的需要再開）。

- [ ] **3.（Claude 自己做）新增 `MoveStory` service 方法**
  - What：新增一個只動 `ParentID`（冊歸屬）、完全不碰 title/summary/status/content 的輕量 service 方法，簽名比照 `MoveLore`（[lore_collection.go:166](../../../service/storyteller/lore_collection.go)）：`MoveStory(userID uint64, projectPublicID, storyPublicID string, volumePublicID *string) (*storytellerModel.Story, error)`（實際簽名細節可能微調，例如是否需要獨立的 `StoryMoveRequest` struct 對齊 `LoreMoveRequest` 的寫法）。
  - Why：目前唯一能改故事 `ParentID` 的路徑是 `UpdateStory`（整份覆寫語意，[storyteller.go:807](../../../service/storyteller/storyteller.go)），這對只是想「搬到另一冊」的呼叫端來說，被迫要連 title/content 一起重新送出，一個沒注意就可能把內容覆寫掉。這是唯一違反「story／lore／asset 三者搬移能力應該對稱」原則的地方，補齊後 agent 呼叫「純搬移」才安全。
  - Where：`service/storyteller/storyteller.go`（或視檔案大小考慮跟 `MoveLore` 一樣移到獨立檔案，例如比照 `lore_collection.go` 開一個 `story_volume.go`——如果 `storyteller.go` 已經逼近 500 行警戒線就順手拆，沒有的話不用刻意拆）。內部要重用既有的 `resolveVolumeParent(projectID, parentID)`（`UpdateStory` 已經在用，[storyteller.go:835](../../../service/storyteller/storyteller.go)），沿用同一套「只能指向 `is_volume=true` 的故事」驗證邏輯，不要重寫一份。
  - How：讀出故事 → 呼叫 `resolveVolumeParent` 解析目標冊（含「傳空字串/nil＝移出冊」語意）→ 只更新 `story.ParentID` → 存檔（不建立新版本，因為內容沒變——這點要跟 `UpdateStory` 的行為對照確認：`UpdateStory` 改冊隸屬時有沒有連帶建立新版本？如果有，`MoveStory` 也要一致，不要行為不對稱）。做完後補一個小測試比照 `lore_test.go` 的風格。

- [ ] **4.（Codex）`storyteller_upsert_story` 補上 `volume_public_id` 參數**
  - What：`storytellerUpsertStoryArguments`（[storyteller_tools.go:245](../../../service/mcp/storyteller_tools.go)）、`InputSchema`（[storyteller_tools.go:602](../../../service/mcp/storyteller_tools.go)）都補上 `volume_public_id`，Handler 組 `StoryRequest{}` 時對應設定 `ParentID`。
  - Why：`StoryRequest.ParentID`（[storyteller.go:719-721](../../../model/entity/storyteller/storyteller.go)）後端本來就支援，網頁版也在用，但 MCP 完全沒曝露，導致 MCP 建立/更新的故事永遠是「不分冊」。
  - Where：`service/mcp/storyteller_tools.go`。
  - How：**關鍵是語意要對齊 `StoryRequest.ParentID *string` 的「nil＝不動、有值（含空字串）才處理」規則**——不能因為 MCP 的 JSON schema 沒有天然的「欄位存在但是空字串」vs「欄位完全沒傳」區分方式（Go 的 `map[string]interface{}` 解析可以區分，`decodeArguments` 目前怎麼處理要先確認）就簡化成「空字串一律當作不處理」，那樣會沒辦法透過 MCP 把故事移出冊。建議：`volume_public_id` 型別用 `*string`（Go 端），呼叫端沒傳這個 key 時是 `nil`（維持原冊隸屬），傳了空字串 `""` 時明確代表「移出冊」，傳了非空字串就是目標冊的 `public_id`。`InputSchema` 的 `Description` 要把這個規則講清楚（省略＝不變更目前冊隸屬；空字串＝移出冊；否則＝目標冊 public_id），照抄 `base_version_id` 那種「optional 但語意重要」的寫法。

- [ ] **5.（Codex，但要等 Item 3 完成）新增 `storyteller_move_story` MCP 工具**
  - What：包一層 MCP 工具呼叫 Item 3 新增的 `MoveStory` service 方法。
  - Why：跟 `storyteller_move_lore`／`storyteller_move_asset` 對稱，給 agent 一個「純搬移、不會不小心動到內容」的安全入口，這是這輪工作最初的動機。
  - Where：`service/mcp/storyteller_tools.go`，緊接在 `storyteller_upsert_story` 附近（跟 Item 4 放一起方便對照）。
  - How：完全比照 `storyteller_move_lore`（[storyteller_tools.go:1340](../../../service/mcp/storyteller_tools.go)）的寫法：`InputSchema` 只要 `project_public_id`／`story_public_id`／`volume_public_id`（空字串＝移出冊），Handler 呼叫 Item 3 的 `MoveStory`，回傳沿用 `toStorytellerStorySummary`。

## 驗證方式

- `go build ./...`、既有 Go 測試（`go test ./service/storyteller/...`、`go test ./service/mcp/...`）全部要過。
- 用 dev-only 假登入機制（`ENABLE_DEV_AUTH_BYPASS`）+ 本機 `/mcp` endpoint 手動跑過每個新工具至少一次成功案例，包含 Item 4 的「省略／空字串／目標冊」三種 `volume_public_id` 情境都要各測一次，確認語意如上面寫的一樣。
- 測試資料用完要清掉（軟刪除即可）。
