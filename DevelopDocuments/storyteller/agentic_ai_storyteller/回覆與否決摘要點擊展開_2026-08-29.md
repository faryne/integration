# 回覆／否決提案摘要點擊展開原始內容（2026-08-29 討論，2026-08-30 第二次改方向）

## 問題

「AI 助理」對話裡有兩種會在使用者訊息前面帶一行 blockquote 摘要的情境：

- **回覆**：`> 回覆 {speaker}：{摘要}`（`storytellerAgentReferences.ts` 的 `buildStorytellerAgentReplyQuote`）。
- **否決提案**：`> 否決提案 #N：{動作}（{內容摘要}）`（`buildStorytellerAgentProposalRejectionQuote`，2026-08-29 新增）。

現況兩者都只是純文字，直接併入訊息的 `instruction`／`content` 本身送出存檔，`<StorytellerMarkdown>` 渲染出來就是一段靜態的引言框，沒有互動性。使用者想要點這段摘要能看到完整的原始內容。

## 方向（已改過一次，這是最終定案）

原本討論的方向是「點擊後捲動到／跳轉到原始訊息」（類似 IM 的回覆機制），但發現有更簡單的做法：**點擊後直接在原地展開完整內容，不用跳轉**。

改方向的關鍵原因：這兩種摘要對應的完整原始內容，其實已經存在**該則使用者訊息自己的 `metadata` 欄位**裡——`reply_content`（回覆的完整內容、否決提案的 tool_name+arguments）本來就會被 `agenticQueryUserMessageMetadata`（`service/storyteller/agentic_query.go:814`）存進發送當下那則使用者訊息的 metadata，是為了「重送」功能存的，不是新資料。前端型別 `StorytellerStoryChatMessage.metadata?: string`（`static_site/src/types/storyteller.ts:502`）也已經把這個欄位整包透出來了。

這代表「展開」完全不需要：
- 不用在 DOM 裡找、捲動到別則訊息（分頁、還沒載入的舊訊息都不是問題，原本「跳轉」方案最大的限制）。
- 不用編碼「訊息 id／提案 index」之類的關聯資訊到假連結裡。
- 不用動 `StorytellerMarkdown.tsx` 這個 skill／agentic 共用的元件，不會牽動到 skill 模式。

## 實作方向

1. 點擊 blockquote 摘要那一行 → 解析**當前這則訊息自己的** `metadata` JSON，取出 `reply_content`。
2. 用 `<Collapse>`（MUI，這個檔案已經在用）之類的元件在原地展開/收合顯示完整內容，不用捲動或跳轉。
3. 剛送出、還沒經過 refetch 的樂觀更新訊息（前端 state 裡已經知道當下組的 `reply_content` 是什麼，不用等歷史記錄重新載入）也要能展開——這部分呼叫端本來就有這個值，直接帶著走即可。

## 預期影響檔案

- `static_site/src/pages/storyteller/StorytellerAgenticPanel.tsx`：訊息渲染邏輯加上「解析 metadata → 可展開/收合」，範圍幾乎全部在這裡（或視情況抽成一個小元件）。
- 大概率不用動 `storytellerAgentReferences.ts`（quote 產生邏輯不變）、不用動 `StorytellerMarkdown.tsx`、不用動 backend。

## 2026-08-29 版本的實作現況（已完成，Codex 實作＋Claude review 通過）

上面「實作方向」那節描述的版本**已經做完**：`StorytellerAgenticPanel.tsx` 新增 `parseAgenticReplyContent()` 直接讀 `metadata.reply_content`（避開 `parseAgenticMetadata()` 在 `steps` 空陣列時把資料一起丟掉的陷阱）、`PanelMessage` 的 agentic 分支加 `replyContent` 欄位、歷史記錄轉換與樂觀更新兩條路徑都補齊。這個版本**把完整原文複製一份存進新訊息自己的 `metadata`**。

## 2026-08-30 第二次改方向：不要複製完整內容，改存參照

Review 完後跟使用者確認實作細節，發現「複製完整內容存進 metadata」這個做法其實不是這次新做的決定，是沿用既有「回覆」/「重送」機制本來就有的存法，只是這次順便把它顯示出來才被注意到。重新評估後**決定改掉這個底層存法**，不是只有「點擊展開」這個 UI 行為要調整。

**問題**：`reply_content` 最多可以到 60000 字（`agenticQueryReplyContentMaxRunes`，`service/storyteller/agentic_query.go:130`），每次回覆都整份複製貼上一次進新訊息的 metadata，是純粹的資料重複——原始內容本來就已經完整存在別的地方（一般訊息的 `content` 欄位、或提案的 `arguments` 欄位），沒有必要再複製一份。

**決定**：`reply_content` 身兼兩職，要分開處理：

1. **送出當下**（同一輪）：前端組請求時，`reply_content` 這個request 參數**維持不變**——送出當下前端本來就已經知道被回覆訊息的完整內容（能點「回覆」的訊息一定已經顯示在畫面上），照樣把完整內容放進這次請求的 `reply_content`，讓 backend 組進這一輪的 prompt 餵給 AI，這件事的行為完全不用改。
2. **送出之後要持久化的部分**（存進新訊息的 metadata，供之後重送／點擊展開使用）：**改成只存一個參照＋一段短摘要**，不要整份複製：
   - 「回覆」情境：存**被回覆訊息的 `message.id`**＋既有的 60 字摘要（`buildStorytellerAgentReplyQuote` 已經在產生的摘要，不用新做）。之後不管是重送還是點擊展開，都用這個 id 回頭查那則訊息自己的 `content` 欄位取得完整內容，不用另外多存一份。
   - 「否決提案」情境：本質上**天生就不需要複製**——提案的完整內容（`tool_name`／`arguments`）本來就永久存在 `storyteller_agent_proposals` 表（`model/entity/storyteller/storyteller.go:574-585`，有自己的 `PublicID`），現有的套用/否決 API 也已經是用 `proposal.public_id` 查詢（見 `StorytellerAgenticProposalCard.tsx` 的 `reject.mutate(proposal.public_id, ...)`）。存參照就是存這個既有的 `public_id`，不用另外設計。
3. **重送**：現有的 `agenticQueryReplyContentFromMetadata`（`service/storyteller/agentic_query.go:829`）是直接從 metadata 讀出複製好的字串重建 prompt；改完之後要改成「用 metadata 存的 id/public_id 回頭查原始訊息或提案的內容」再重建，行為結果一樣（重送時 AI 收到的 prompt 內容不變），只是資料來源從「複製的快照」變成「即時查詢」。

## 預期影響檔案（更新）

- **Backend**：
  - `agenticQueryUserMessageMetadata`（`service/storyteller/agentic_query.go:814`）：存進 metadata 的內容從「完整 `reply_content` 字串」改成「參照 id/public_id ＋摘要」。
  - `agenticQueryReplyContentFromMetadata`（`service/storyteller/agentic_query.go:829`）：從「直接讀字串」改成「用參照查回原始內容」。
  - 新增（或確認既有是否夠用）一支查詢：依 `message.id` 取得單則歷史訊息的 `content`，給重送跟點擊展開共用；授權檢查要確認這則訊息屬於使用者自己的故事/設定集。
- **前端**：
  - `StorytellerAgenticPanel.tsx`：點擊展開從「已經有資料直接秀」改成「點了才打 API 抓」，要處理 loading／抓不到的容錯狀態。
  - 送出當下組請求的邏輯（`runAgentic()` 等）不用改，前端本來就有完整內容可以放進這次請求的 `reply_content`。
