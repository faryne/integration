# Skill 模式改用唯讀工具呼叫規劃（2026-08-31 提出，2026-08-31 定案）

規格已定案（含 Codex 審視意見），準備排時間交給 Codex 實作。

## 背景／問題

單輪 skill（`/rewrite`／`/expand`／`/translate`／`/custom`）目前完全沒有工具呼叫能力，是一次 `provider.Generate()` 打完就結束（`runAgent`/`RunLoreAgent`，[storyteller.go:570-641](../../../service/storyteller/storyteller.go)）。使用者用 `@story:[...]`／`@thisStory` 引用其他故事/設定集時，前端必須把引用到的**完整內容**串起來塞進 `full_content`（`buildStorytellerAgentReferenceContent`），因為 AI 沒有其他管道能拿到這些內容。這代表：

- 多引用幾篇長故事容易撞到 60000 字上限（`skillFullContentMaxCharacters`/`agentRunFullContentMaxRunes`），雖然前端已經有主動擋（超過直接鎖送出鈕、不會是送出後才碰壁），但體驗上就是「多選幾篇故事就用不了」。
- 就算沒撞到上限，也是每次都把引用故事的全文塞進 request，不管這次改寫實際上用不用得到那麼多內容，直接吃 token。

Agentic 多輪對話（`/Agent 名稱`、預設問答）不受這個限制——`@` 引用送出時完全不展開，AI 透過既有的唯讀 MCP 工具（`storyteller_get_story` 等）自己去查，這個決定是之前就定案的（見 Phase 文件）。

## 討論過程（含我自己一開始想錯的地方，如實記錄）

一開始討論「/rewrite 乾脆也用 agentic 模式」時，我提出了三個反對理由，後來被一一戳破：

1. ~~「agentic 模式輸出格式不夠乾淨，會夾雜對話語氣」~~——**不成立**。輸出格式嚴不嚴謹是 system prompt 設計的事，跟底層用哪個執行機制無關；只要這次呼叫不給任何寫入工具，AI 沒有機會觸發提案，回應就是純文字。
2. ~~「agentic 的寫入要走提案確認 UI，會讓 skill 變重」~~——**不成立**，理由同上：不給寫入工具，這個問題根本不會發生，前端渲染邏輯本來就是照訊息的 `mode` 決定要顯示提案卡片還是複製/貼到末尾按鈕，跟底層執行機制無關。
3. ~~「用 agentic 執行會套用到目前選的 Agent 人設，汙染改寫結果」~~——**不成立**。人設要不要套用是「組 system prompt 時的選擇」，skill 呼叫本來就已經是 `ignore_agent_persona: true` 固定行為，這條規則不管底層用哪個執行機制都能一樣套用，不是 agentic 特有的限制。

最後定案的方向，不是「整個 skill 改成 agentic 多輪對話」，而是更精準的一點：**skill 呼叫改成走 `RunAgentLoop`，但只給唯讀工具，完全不給寫入工具**，藉此解決「多引用就爆字數」的根本問題，同時保留 skill 現有的所有保證（輸出乾淨、UI 不變、人設中立）。

## 三條路徑的最終樣貌（確認前端只需要處理兩種渲染）

改動完成後系統會有三條執行路徑：

1. **正常提案**：`runAgentic` 多輪對話，AI 可能呼叫寫入工具，走提案卡片 UI（既有的，不受這次改動影響）。
2. **Skill／走 loop（有 `@` 引用時）**：呼叫 `RunAgentLoop`＋唯讀工具，AI 自己查引用內容。
3. **Skill／單次呼叫（沒有 `@` 引用，或 provider 是 Gemini 時）**：維持現在的 `provider.Generate()` 直接呼叫，不帶任何 tools。

**路徑 2 跟 3 對前端來說是同一種渲染**——決定要不要顯示提案卡片是看訊息的 `mode`（skill 的幾個 mode vs. 一般 agentic 問答），不是看後端內部走哪條路徑執行；`AgentRunResponse` 回應格式兩條路徑完全一樣。「有沒有 `@` 引用 → 決定要不要進 loop」純粹是後端內部實作細節，前端跟使用者完全無感，不需要改動任何前端渲染邏輯。

## Codex 審視意見（已採納，補進下方技術方向）

Codex 審視後認為方向站得住腳，但原本「現有 UI 與輸出格式保證不受影響」這句要降級成「wire format 可以不變，但語意與錯誤路徑要補齊」——抓到幾個實作時必須處理、不是可有可無的坑：

1. **Context 要注入使用者身分**：agentic 那邊呼叫工具前會把 `userID`／`source` 塞進 context（`WithStorytellerUserID`／`WithStorytellerSource`，見 [agentic_query.go:336](../../../service/storyteller/agentic_query.go)），工具處理常式依賴這個才查得到資料。`runAgent`/`RunLoreAgent` 目前完全沒有這段，接上 loop 前必須先補。
2. **Gemini 不支援 tools**：`AIProviderRequest.Tools` 非空時 Gemini provider 直接回 `ErrAIProviderUnsupported`（[ai_provider.go:690](../../../service/storyteller/ai_provider.go)）。現在用 Gemini 跑 `/rewrite` 完全正常，如果無條件都帶 tools，Gemini 這個 provider 會直接壞掉——**這正是「只在有 `@` 引用時才進 loop」這個分流判斷的直接理由**：沒有引用、或 provider 是 Gemini 時，走原本的單次呼叫，兩個問題一次解決，不用另外為 Gemini 寫特殊分支。
3. **`FinishReason` 會遺失**：`AgentLoopResult` 目前沒有這個欄位，但現有 skill 回應跟 metadata 都有記錄。要嘛讓 `AgentLoopResult` 保存最後一輪 provider response 的 finish reason，要嘛明確調整 skill 的 metadata/API 不再承諾這個欄位——實作時要挑一個，不能放著不管。
4. **`storyteller_list_projects` 不能無腦丟進工具集**：這個工具的 schema 沒有 `project_public_id`，被 `ScopeToolsToProject` 包住後，只要 AI 呼叫它就一定被擋（見 [agent_scope_test.go:29](../../../service/storyteller/agent_scope_test.go)），白白浪費一輪 step。Skill 的唯讀工具集要用 `ReadOnlyStorytellerTools()` 排除掉這個工具再傳進去。
5. **`full_content` 的 prompt 文案要跟著整理**：現在寫死「Current chapter full content」，但前端實際塞的是引用內容 bundle，語意早就有點混用（見 [storyteller.go:3209](../../../service/storyteller/storyteller.go)），改動時要一併釐清成「這是使用者目前正在編輯、還沒存檔的內容」跟「這是可以叫工具查的其他引用」兩種不同語意。

## 提議的技術方向（含 Codex 建議調整後的版本）

- `runAgent`/`RunLoreAgent`（story／lore 各一支，建議抽一個共用 helper，story/lore 只負責載入各自的 target 跟傳 kind/public_id/title，避免兩邊各自維護、之後其中一邊改了漏改另一邊）：
  - **沒有 `@` 引用，或 provider 是 Gemini**：維持現在直接呼叫 `provider.Generate(ctx, AIProviderRequest{...})`，不帶 tools，行為完全不變。
  - **有 `@` 引用且 provider 支援 tools**：改呼叫 `RunAgentLoop(ctx, AgentLoopRequest{..., Tools: ...})`。
- 進 loop 前補齊 context 注入（`WithStorytellerUserID`／`WithStorytellerSource`），比照 agentic query 的既有做法。
- `Tools` 帶**唯讀工具**（`ReadOnlyStorytellerTools()`，[agent_scope.go:46](../../../service/storyteller/agent_scope.go)，排除 `storyteller_list_projects`），並透過 `ScopeToolsToProject(tools, projectPublicID)`（[agent_scope.go:24](../../../service/storyteller/agent_scope.go)）限制在這次呼叫對應的 project 範圍內——**絕對不能帶任何寫入/刪除工具**，這是保留「skill 呼叫不需要提案確認」這個保證的關鍵，不是可以之後再補的細節。
- `AgentLoopRequest.History` 留空（skill 本來就是無狀態單輪，不用接歷史對話）。
- 走 loop 的路徑，結果從 `AIProviderResponse{Result, Usage, RawBody}` 改成讀 `AgentLoopResult{FinalText, Usage, RawResponses}`——`Usage` 是整輪（可能含工具呼叫中間輪次）加總後的總量，直接拿來寫 usage log／price snapshot 即可，不用重新設計（跟 agentic query 現有做法一樣，同一次 loop 都是同一個 provider/model，價格模型不變）。`RawResponses` 是陣列（每輪一筆）。`FinishReason` 依上面 Codex 意見那條處理。既有的 `buildAgentRunChat`/`buildLoreAgentRunChat`/`buildAgentUsageLog` 這幾個組資料的函式要跟著調整欄位來源。
- **system prompt 要補上專案/故事上下文**：目前 `buildAgentRunPrompts` 完全沒有告訴 AI 目前是哪個 project/story，因為以前不需要（沒有工具可呼叫）。要比照 agentic 那邊 `agenticQuerySystemPrompt` 的做法，把 `project_public_id`、目前這篇故事/設定集的 `public_id`／標題寫進 system prompt，AI 才知道呼叫 `storyteller_get_story` 時要填什麼參數。同時把 `full_content`/`selected_content` 的 prompt 文案整理清楚（見上方 Codex 意見第 5 點）。
- `MaxSteps`／`MaxDuration` 用比 agentic 更保守的預設值（agentic 現在是 8 分鐘、8 步，skill 應該維持「快速」的體感），實際數字實作時再定。
- **`ErrAgentLoopMaxStepsExceeded` 這類新錯誤要轉成使用者看得懂的中文訊息**，並明確決定「超過步數上限、但已經有部分結果」這種情況要不要存、算不算完成。

## 已確認不用處理的部分

- **`selected_content`／目前開著的故事內容，不能改成叫 AI 自己查，要繼續直接塞 prompt**：使用者正在編輯、還沒存檔的最新內容，工具查資料庫只會拿到「已存檔」的版本（`storyteller_get_story` 回 `story.LatestContent`），查不到未存檔的編輯內容。只有「額外引用的『其他』故事/設定集」才改成叫 AI 自己查。

## 已知的既有限制（這次不處理，但要知道）

- `@story:[標題]` 靠標題比對本來就有重名歧義的既有問題（前端跟後端都是用 title map 解析，重名會覆蓋），工具化之後這個歧義會更依賴模型自己判斷準不準，不是這次改動造成的新問題，但值得知道。

## 影響檔案（初步評估，實作時再確認）

- `service/storyteller/storyteller.go`：`runAgent`／`RunLoreAgent`（抽共用 helper，改成依「有沒有 `@` 引用／provider 是否支援 tools」分流呼叫單次 `Generate()` 或 `RunAgentLoop`）、`buildAgentRunPrompts`（補上 project/story 上下文、整理 full_content/selected_content 文案）、`buildAgentRunChat`／`buildLoreAgentRunChat`（改讀 `AgentLoopResult`）、`agentRunOutputMetadata`（可能要記錄工具呼叫次數之類的除錯資訊）。
- `service/storyteller/agent_run_test.go`／`ai_provider_test.go`：既有測試大量假設「一次 `provider.Generate()` 呼叫」，需要大幅調整或新增針對 loop 版本的測試（含至少一個「真的呼叫了唯讀工具」的案例）——工具 handler 內部是直接打真實 repo（`NewService()`），不是像 `runAgent` 那樣用假 repo 注入，測試設計需要另外想辦法（例如注入工具 spec 而不是直接拿 registry 真工具）。
- 前端不用動——`selected_content`／`full_content` 這兩個既有欄位語意不變，只是後端不再要求前端把所有引用內容都塞好塞滿；`referenceContent`／`payloadError` 那套 60000 字檢查之後可能要重新評估要不要放寬或拿掉（引用的其他故事不再強制展開）。
