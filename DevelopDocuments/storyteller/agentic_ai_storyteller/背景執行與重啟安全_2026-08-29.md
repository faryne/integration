# Agentic 對話改背景執行＋重啟安全（2026-08-29 討論）

## 起因

之前確認過：`RunStoryAgenticQuery`／`RunLoreAgenticQuery` 目前是**完全同步阻塞**的呼叫鏈（前端 HTTP request → Fiber controller → `RunAgentLoop` → 每一輪直接 `http.Client{Timeout: N}.Do(req)` 卡在原地等），沒有用 goroutine 背景處理。如果 client 端（我們自己對 provider 那個 `http.Client`）逾時斷線，provider 那邊就算已經生成完、甚至正在生成，我們這邊都拿不回來——四家 provider 裡 OpenAI（Responses API background mode）、Grok（Deferred Chat Completions）、Gemini（Interactions API `background: true`）都有官方的「送出→拿 id→之後 poll」機制可以解決這個問題，但 **Anthropic（Claude）沒有**，只有 streaming（一樣要保持連線）跟 Batches API（24 小時等級的批次，不適合即時對話）。

## 決定的方向

不靠各家 provider 自己的 async 機制（四家不一致，Claude 還沒有），改成**我們自己的 backend 用 goroutine 背景跑**：

1. HTTP handler 收到 agentic query 請求後，落地存檔（沿用既有 `CreateInProgressChatWithUserMessage`，chat 狀態設成 `in_progress`），然後用 `go RunAgentLoop(...)` 丟到背景執行，**立刻回應前端**（帶 `chat_id`，不用等 AI 回完）。
2. 前端固定每 N 秒 `fetchMessage`（輪詢），直到這個 `chat_id` 的狀態變成 `completed`（或失敗轉 `pending`，沿用既有 resend 機制）。
3. **不用另外設計去重機制**——每則訊息在 DB 本來就有自己的 `id`／`chat_id`（`StoryChatMessageOutput`，`model/entity/storyteller/storyteller.go:1085-1097`），前端也已經有 `chat_id` 對齊去重的邏輯（`StorytellerAgenticPanel.tsx` 的 `liveChatIds`／`dedupedSkillHistoryMessages`，是稍早 resend 機制那次順便做的），輪詢抓回來的訊息直接套用同一套即可。

## 重啟安全（今天討論定案的部分）

**問題**：`main.go` 現有的重啟機制（`gracefulRestart`，`main.go:191`）：

```go
shutdownAllSettings(runtime)   // Fiber ShutdownWithTimeout(30s)，只等「進行中的 HTTP 請求」
syscall.Exec(path, args, env)  // 原地整個 process image 換掉
```

`syscall.Exec` 是**整個記憶體空間原地替換**，換句話說：呼叫成功的瞬間，舊 process 裡所有還在跑的 goroutine 全部消失，沒有任何殘留執行的可能，沒有折衷空間。而且 `ShutdownWithTimeout` 現在只認得到「還沒回應完的 HTTP 請求」——一旦 handler 已經回應給前端（因為改成背景執行了），這個背景 goroutine 就完全脫離 Fiber 的生命週期追蹤範圍，`ShutdownWithTimeout` 不知道它的存在，重啟時會被 `syscall.Exec` 直接砍掉，等於繞了一圈又回到「跟斷線一樣報銷」的老問題。

**決定**：**老實等全部背景 routine 跑完，不設等待上限**（不是「等 30-60 秒、超過就強制重啟」那種折衷做法）。做法是加一層自己的追蹤：一個 `sync.WaitGroup`（或等價機制）——背景 agent loop 開始時 `Add(1)`，結束時 `defer Done()`；`shutdownAllSettings`／`gracefulRestart` 在呼叫 `syscall.Exec` 之前，加一段 `Wait()`，不設 timeout，就是老實等到底。

**順便決定**：這個追蹤機制**不是只給 agentic 對話專用**，之後要視重要性讓某些 crontab 排程任務也掛進同一套「重啟前必須等它跑完」的追蹤，不要各自重新發明一套。

## 還沒決定、動工前要想清楚的細節

1. **追蹤機制的介面長什麼樣**：可能是一個全域的 `BackgroundWork` 之類的東西，提供類似 `Track(name string) (done func())` 的 API，agent loop 派工跟之後要掛進來的 crontab 任務都呼叫同一個介面註冊，不要各自用自己的 `sync.WaitGroup`（不然重啟邏輯要一個一個等，維護起來很分散）。
2. **重啟訊號進來後，還要不要接受新的背景派工**：如果重啟開始 drain 之後還一直有新的 agentic 請求／新的 crontab 觸發進來繼續 `Add()`，drain 可能永遠等不完——大概率要在收到重啟訊號的當下就切一個「draining」旗標，新請求要嘛排隊等下一個 process 起來再處理，要嘛直接拒絕，這塊要設計清楚。
3. **背景 goroutine 用的 context 不能是 HTTP request 的 context**：handler 一旦提前回應，request context 會被取消，`go RunAgentLoop(ctx, ...)` 如果傳的還是 request 的 ctx，AI 呼叫會立刻被取消。要用一個跟 server 生命週期綁在一起、不受單一 request 影響的 context（例如掛在 app 啟動時建立的長壽命 context 上，配合上面的 drain 機制在真正要關機時才取消它）。
4. **前端輪詢的頻率／端點**：是新開一個「只查這個 chat_id 狀態」的輕量端點，還是沿用現有的歷史訊息列表端點整個重抓——效能上前者比較好，但要多開一支 API；後者不用新增後端程式碼，但每次輪詢都重抓一整頁歷史訊息，浪費頻寬。
5. **現有的 `pending`／`in_progress`／`completed` 狀態機、resend 機制，跟新的輪詢模式要怎麼接起來**——理論上骨架已經是為這個情境設計的（今天稍早才確認過），但實際串接時要重新過一次現有邏輯，確認沒有假設「一定是同步呼叫」的地方。

## 待辦

範圍明顯比「否決回饋機制」「用量估算」這幾個今天做的東西大很多，牽動 HTTP handler 回應時機、`main.go` 關機流程、前端輪詢邏輯，屬於要先過一輪完整規格再動工的等級。使用者明確下指示後才整理成正式需求規格，**目前不要主動實作**。
