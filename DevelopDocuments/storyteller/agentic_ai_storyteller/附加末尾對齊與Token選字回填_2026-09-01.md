# 附加末尾按鈕對齊、Token 數與選取文字重整後消失修正（2026-09-01）

## 背景

實測「選字觸發 AI 指令」跟後續的 skill 改用唯讀工具呼叫合併進主線後的成果時，發現三個問題：

1. 「附加末尾」按鈕只出現在 skill 模式的訊息泡泡（`/rewrite` 等指令的結果），agentic 對話模式的訊息泡泡（一般問答、`@thisStory` 引用對話、對 skill 結果按「回覆」但沒帶 `/` 前綴產生的延伸對話）完全沒有這顆按鈕。這是因為兩種模式各自用不同元件渲染訊息泡泡，功能沒對齊。
2. 訊息泡泡下方的 token 數 chip，重新整理頁面後就消失——不管是 skill 模式還是 agentic 模式都一樣。原因是後端其實有把 usage 存進 DB，只是 skill 模式讀不回來、agentic 模式後端根本沒存進訊息 metadata。
3. 選字觸發 AI 指令送出後，選取的原文完全沒有留下痕跡：畫面上的訊息泡泡只顯示使用者輸入的「額外需求」，DB 裡也只存了選取字數，沒存實際內容。

使用者裁示：**第 1 點直接把「附加末尾」按鈕在兩種模式下都做出來，不要再用「是不是 skill 模式」這種特殊條件去分流**——目前程式碼裡已經因為疊加太多特殊條件變得難以維護，這次不要再加新的特殊條件，而是把功能拉齊。第 2、3 點一併處理。

## 現況程式碼位置（施工前的事實，供對照，不是要保留的設計）

- Skill 模式訊息泡泡：`static_site/src/pages/storyteller/StorytellerAgentPanel.tsx`
  - `canApply = !isUser && message.content.trim() !== ""`（第 268 行），不看 `isCurrentResult`。
  - `{canApply && (...)}` 區塊（約第 317～370 行）固定渲染「附加末尾」（`onApplyText(message.content, "append", null)`）、「複製」、「回覆」（`enableInsert`/`enableReplace` 控制的「插入游標」「取代選取」是另外兩個更精細的動作，這次不用管）。
- Agentic 模式訊息泡泡：`static_site/src/pages/storyteller/StorytellerAgenticPanel.tsx`
  - 同名的 `canApply`（約第 615 行）判斷邏輯幾乎一樣：`!isUser && !message.isLoading && message.content.trim() !== ""`。
  - `{canApply && onApplyText && (...)}` 區塊（約第 745～775 行）目前只渲染「複製」「回覆」，缺「附加末尾」。
  - `onApplyText` prop 型別（約第 808 行）已經是 `(content, mode, selection) => void`，跟 skill 模式共用同一個 `applyAgentText` handler（見 `StoryEditor.tsx:1516`／`LoreEditor.tsx:1230` 的呼叫點），該 handler 本來就支援 `"append"`，agentic 這邊只是沒接上按鈕，**不需要新增或修改 handler 本身**。

- Skill 模式 token 顯示：
  - 後端 `agentRunOutputMetadata`（`service/storyteller/storyteller.go:3444` 附近）已經把 `usage`（`input_tokens`/`output_tokens`/`total_tokens`）存進 assistant 訊息的 `metadata` JSON。
  - 前端 `skillHistoryMessages`（`StorytellerAgenticPanel.tsx` 約 1252 行附近，從 DB 歷史重建 skill 訊息的地方）目前只解析 `mode`（見 `parseMessageMode`），完全沒解析 `usage`，所以歷史訊息的 `usage` 欄位永遠是 `undefined`。只有剛送出、還留在記憶體裡的 `skillResult`（約 1282 行）才帶得到 `usage`，一重整頁面就沒了。

- Agentic 模式 token 顯示：
  - 後端 `agenticQueryOutputMetadata`（`service/storyteller/agentic_query.go:1456` 附近）目前只存 `mode`/`step_count`/`steps`，**完全沒有存 usage**。usage 只寫進另一張獨立的 `AgentUsageLog` 表（`buildAgenticQueryUsageLog`），不是掛在這則訊息本身，所以歷史重建（`agenticPanelMessageFromChatRow`，約 1216 行）根本無從讀起。只有剛收到的即時回應（`StorytellerAgenticPanel.tsx:1672` 附近的 `response.usage`）能顯示。

- 選取文字沒留下痕跡：
  - 前端 `runSkill()`（`StorytellerAgenticPanel.tsx:1517` 附近）送出時，optimistic 訊息泡泡內容寫死成 `instruction.trim()`（第 1525 行），完全沒有把 `selectionAgentTarget.selectedText` 併入顯示。
  - 後端 `agentRunInputMetadata`（`service/storyteller/storyteller.go:3435` 附近）只存 `selected_content_length`（一個數字），沒存實際選取內容，所以就算前端想在重新整理後補顯示，DB 也沒有資料可查。

## 這次要做的事

### 1. 「附加末尾」按鈕在 skill／agentic 兩種訊息泡泡都要出現，且用同一套判斷邏輯

- 目標：拿掉「這是 skill 模式訊息才給附加末尾」這種依模式分流的特殊條件。兩邊訊息只要滿足「不是使用者發的、有內容、有 `onApplyText` 可用」就一律顯示「附加末尾」。
- 具體做法（不強制，Codex 可依現有程式風格調整，但方向不能偏）：
  - 在 `StorytellerAgenticPanel.tsx` 的 agentic 訊息泡泡 `canApply && onApplyText` 區塊內，比照 skill 模式加上：
    ```tsx
    <Button
      {...storytellerChatActionButtonProps}
      onClick={() => onApplyText(message.content, "append", null)}
    >
      附加末尾
    </Button>
    ```
    放在「複製」之前或之後皆可，跟 skill 模式的按鈕順序（附加末尾／複製／回覆）保持一致即可。
  - 如果評估後發現兩個檔案裡這段「附加末尾／複製／回覆」按鈕列的程式碼已經幾乎一模一樣，值得抽成共用元件，可以視情況做（`canApply` 的判斷條件目前兩邊已經幾乎相同，只差 `!message.isLoading` 這個 agentic 特有的檢查——skill 模式沒有 `isLoading` 訊息，保留這個差異即可，不用為了統一硬改語意）。抽不抽共用元件由 Codex 自行判斷，不是硬性要求，但**兩邊「附加末尾」的行為必須完全一致**：都是 `onApplyText(message.content, "append", null)`，不要有任何模式相關的例外或條件。
  - `isCurrentResult`／`resultSelection` 這兩個目前只跟「取代選取」「插入游標」兩個更精細動作有關，不在這次調整範圍內，agentic 模式不需要新增這兩個功能，只補「附加末尾」。

### 2. Token 數重整頁面後不能消失（skill／agentic 都要修）

- Skill 模式：
  - 在前端新增一個共用的 `parseMessageUsage(metadata?: string)` 之類的 helper（可以放在 `parseMessageMode` 附近），從 `metadata` JSON 解析出 `usage.total_tokens`（格式跟後端 `agentRunOutputMetadata` 一致：`{"finish_reason":"...","usage":{"input_tokens":N,"output_tokens":N,"total_tokens":N}}`）。
  - `skillHistoryMessages` 組 skill 訊息物件時（約 1252 行 `return { kind: "skill", ... }` 那段），補上 `usage: parseMessageUsage(message.metadata)`。
- Agentic 模式：
  - 後端 `agenticQueryOutputMetadata`（`service/storyteller/agentic_query.go:1456`）目前只寫 `mode`/`step_count`/`steps`，這次要比照 skill 模式的 `agentRunOutputMetadata` 一併寫入 `usage`（來源是同一個 function 裡已經有的 `output.Usage`，型別是 `*AIProviderUsage`，換算成 `input_tokens`/`output_tokens`/`total_tokens` 三個欄位，`output.Usage` 為 `nil` 時就不要輸出 `usage` 欄位，跟 skill 模式那邊 `usage == nil` 的處理方式一致）。
  - 前端 `agenticPanelMessageFromChatRow`（約 1216 行）比照上面同一個 `parseMessageUsage` helper，補上 `usage: parseMessageUsage(message.metadata)`。
  - 這兩種模式的 metadata JSON 結構如果本來就长得一样（都是 `{"...","usage":{"input_tokens":N,"output_tokens":N,"total_tokens":N}}`），**共用同一個 `parseMessageUsage` helper**，不要各寫一份。
  - 後端這處修改記得同步更新／新增對應的 Go test（`agentic_query_test.go` 應該已經有測 `agenticQueryOutputMetadata` 或類似輸出格式的地方，照現有慣例補一個「usage 非 nil 時 metadata 帶 usage 欄位、usage 為 nil 時不帶」的案例）。

### 3. 選字觸發 AI 指令的原文，送出後要能在畫面上留下痕跡

- 現況：只有「額外需求」文字被送進訊息泡泡與 DB，選取的原文完全遺失（DB 只存字數）。
- 這次要做：讓使用者事後（含重新整理頁面）還能看到「當初是針對哪段文字」。具體作法：
  - 後端 `AgentRunRequest.SelectedContent` 本來就有送到後端（`model/entity/storyteller/storyteller.go`），只是 `agentRunInputMetadata` 沒存下來。這次改成把 `SelectedContent` 本身（或至少一個可以還原顯示的預覽片段，例如前 200 字）存進 user 訊息的 `metadata`，欄位命名可以是 `selected_content_preview` 或直接存 `selected_content`（是否要整段存要考慮訊息大小；建議用跟前端 `truncateStorytellerSelectionPreview` 相同或相近的截斷長度，避免 metadata 過度肥大）。
  - 前端 `runSkill()` 送出時的 optimistic 訊息泡泡內容（`StorytellerAgenticPanel.tsx:1525` 附近），以及重新整理後從歷史重建 skill 訊息時（`skillHistoryMessages` 那段解析 `message.metadata` 的地方），都要能把這段選取文字用跟 composer 送出前一致的 blockquote 樣式（`borderLeft` + 斜體，不加「選取文字：」字樣，比照這次選字觸發 UX 既有的 blockquote 風格）顯示在訊息泡泡內容的最前面（或指令內容上方），讓使用者事後看得出這則指令當初是針對哪段文字下的。
  - 這一點如果實作起來發現會牽動訊息渲染結構較多（例如泡泡內容目前是純文字 `content` 欄位，要嘛把 blockquote 併進 `content` 一起存、要嘛額外用 metadata 欄位在渲染時組合），由 Codex 評估後選一種做法，但**兩個時間點（剛送出的 optimistic 泡泡、重新整理後從 DB 重建的泡泡）呈現的內容要一致**，不能一個有 blockquote 一個沒有。

## 驗收重點

- 手動測試：對一段選取文字跑 `/expand` 或其他 skill，確認：
  1. 送出後的訊息泡泡（不重整）跟重新整理頁面後的訊息泡泡，都能看到「附加末尾」按鈕，點擊行為一致。
  2. token 數 chip 重新整理後仍然顯示，數字跟剛收到時一致。
  3. 訊息泡泡裡看得出當初選取的原文（blockquote 樣式），reload 前後一致。
- 再測一輪 agentic 對話（例如用 `@thisStory` 或直接問答，不帶任何 slash 指令），確認：
  1. AI 回覆的訊息泡泡也出現「附加末尾」，點擊後內容真的被附加到編輯區末尾。
  2. token 數 chip reload 後仍然顯示。
- 兩種模式都要跑 `go build ./...`、`go vet ./...`、相關 package 的 `go test`，以及前端 `NODE_USE_SYSTEM_CA=0 npx tsc -b`（注意：純 `npx tsc -b` 在這台機器上會因為 keychain 問題直接壞掉，一定要加這個環境變數，不是真的型別錯誤）。
