# 程式碼區塊語法高亮規格

## 背景

編輯頁程式碼區塊規格（`編輯頁程式碼區塊_2026-09-04.md`）v1 刻意不做語法高亮，理由是「先不引入額外套件，等真的有需求再加」。現在要補上，這份文件只處理高亮這一件事，不重複前一份文件已經定案的資料模型/序列化格式/建立入口/收縮展開——那些完全不受影響。

## 目的

- 程式碼區塊顯示時依語言上色（關鍵字/字串/註解/數字等），編輯區跟閱讀頁都要有。
- 不改動任何儲存格式——高亮純粹是「同一份純文字內容，多算一層 token 資訊拿來上色」，`⟦markerId⟧`／GFM fence／MCP 那邊完全不用動。

## 技術選型：`lowlight`（不是 highlight.js 直接用、不是 Prism、不是 Shiki）

**結論：用 `lowlight`**（highlight.js 的 tokenizer 包成 [hast](https://github.com/syntax-tree/hast) AST 的版本），理由要解釋一下，因為這題不能只看「哪個套件比較潮」：

- **編輯區的內容是可編輯的 contenteditable，不是靜態 HTML**，不能像閱讀頁那樣直接塞一段 highlight.js 產生的 HTML 字串進去（那樣會整個蓋掉 ProseMirror 自己在管理的 DOM，游標／選取／IME 組字全部會壞掉）。可編輯區塊要做語法上色，業界唯一可靠的做法是 **ProseMirror decoration**：不改動文件本身的文字節點，另外疊一層「這段範圍套用這個 CSS class」的裝飾層，游標／編輯行為完全不受影響。
- decoration 需要「token 的起訖位置」，highlight.js 原本只吐得出一段 HTML 字串（`{value: "<span class=\"hljs-keyword\">func</span> ..."}`），沒有位置資訊，沒辦法直接拿來算 decoration 範圍。`lowlight` 把同一套 highlight.js 文法跑出來的結果包成有位置資訊的 AST（hast tree），這正是 **Tiptap 官方自己的 `@tiptap/extension-code-block-lowlight` 用的套件**——不是我們自己發明一套新做法，是抄業界（包括 Tiptap 自己）已經驗證過的標準組合。
- 閱讀頁是靜態渲染，不需要 decoration，但**同一份 lowlight AST 可以直接轉成巢狀的 `<span>` JSX**（AST 節點本身就是巢狀結構，遞迴渲染即可）——編輯區跟閱讀頁共用同一次 tokenize 結果，不用維護兩套高亮邏輯，跟這個 repo 一貫「一份實作兩邊共用」的原則一致。
- Prism（`refractor`）走同樣的 AST-based 路線也可以，兩者技術上半斤八兩；選 `lowlight` 純粹因為它是 Tiptap 官方擴充用的那個，社群案例/踩雷紀錄更多，出問題比較好查。
- Shiki 用真正的 TextMate 文法、上色品質最好，但預設是非同步（要等 WASM 載入才能 tokenize），拿來做「使用者正在打字」的即時 decoration 體驗會卡頓；而且我們的語言清單只有 15 種常見語言，用不到 Shiki 那種「精準到跟 VS Code 一模一樣」的等級，這裡不需要為了上色精緻度犧牲輸入流暢度。

## 語言範圍：只註冊 15 種（2026-09-05 確認擴充）

`static_site/src/pages/storyteller/wysiwygCore/storytellerCodeBlockView.tsx` 原本的語言 autocomplete 清單是 go/typescript/javascript/python/json/bash/yaml/sql/html/css，這次加 5 個：**ruby（含 RoR，Rails 程式碼語法上還是 ruby，不用另外開 RoR 專屬文法）、perl、rust、php、xml**，總共 15 種。`lowlight` 預設會註冊 190+ 種語言文法，全部打包會讓 bundle size 爆炸——**只手動 `lowlight.register()` 這 15 種**，其餘一律當純文字（沒有 token 資訊，直接原樣顯示，不報錯）。

這 5 個新語言也要同步加進 `STORYTELLER_CODE_BLOCK_LANGUAGES`（autocomplete 建議清單），不然使用者/AI 選不到、要自己手打語言名稱才用得到高亮。

語言標籤欄位本來就是自由輸入＋這 10 個當 autocomplete 建議，不是嚴格枚舉（見上一份規格）——所以使用者/AI 填了清單外的語言字串完全合法，只是那種情況下沒有高亮，跟其他不支援的語法一樣「原樣顯示、不出錯」。

## 編輯區實作：ProseMirror decoration plugin

在 `storytellerCodeBlock.tsx` 的 `addProseMirrorPlugins()` 裡新增一個 decoration plugin（`markerParagraph.ts:553-568` 已經有 `addProseMirrorPlugins` 的寫法可以參考，這裡不是 `appendTransaction` 改文件內容，是 `props.decorations` 疊一層顯示用的裝飾）：

- 對每個 `storytellerCodeBlock` node：取出 `node.attrs.language` 跟 `node.textContent`，如果語言有註冊就跑 `lowlight.highlight(language, text)` 拿到 hast AST，把 AST 的每個有 `className` 的節點轉成 `Decoration.inline(from, to, { class: tokenClassName })`。
- **效能**：每個 code block 各自 tokenize，不要整份文件重算——decoration plugin 的 state 用 `DecorationSet.map()` 增量套用文件變動，只有真的落在某個 code block 範圍內的變更才重新 tokenize 那一個區塊，其他區塊的 decoration 照抄舊的。這是這類 plugin 的標準寫法，不是這份規格自創的最佳化。
- token 的 CSS class 沿用 highlight.js 的慣例命名（`hljs-keyword`、`hljs-string`、`hljs-comment`...），這樣可以直接套用任何一份現成的 highlight.js 主題 CSS，不用自己重新設計一套 class 命名。

## 閱讀頁實作：同一份 AST 轉 JSX

`StorytellerWysiwygMarkdown.tsx` 現在的 code block 分支（`StorytellerWysiwygMarkdown.tsx:376-388` 左右）直接把 `content` 當純文字塞進 `<StorytellerCodeBlockFrame>`。改成：語言有註冊的話先跑 `lowlight.highlight()`，把回傳的 hast AST 遞迴轉成巢狀 `<span className={...}>`（AST 節點是 text 就直接輸出文字，是 element 就包一層 span 再遞迴 children），沒註冊或呼叫失敗就照舊輸出純文字——不能讓「這個語言沒有文法」變成整個區塊掛掉。

## 主題色彩：固定跟著 layout 既有的亮/暗模式，不跟 11 組強調色連動（2026-09-05 確認）

這個 app 除了亮/暗模式，還有一整組強調色系統（黃銅/青銅/孔雀石／...）。**語法高亮顏色只跟 layout 既有的 `theme.palette.mode`（亮/暗）綁死，不特別為 11 組強調色各自調色**——layout 是 dark 的時候，程式碼區塊固定顯示暗色系高亮；layout 是 light 的時候固定顯示亮色系高亮，中間不會因為強調色系統切換（黃銅／墨黑／銀白...）而跟著換高亮配色。理由：
- 程式碼區塊本來就用中性的 `action.hover` 當背景（不受強調色影響），高亮色沿用同一個「中性」定位，視覺上不會因為使用者換了強調色系統就顯得突兀或撞色。
- 幫 11 組強調色分別調一套語法配色，工程成本高、報酬低（使用者不會因為「程式碼區塊的高亮色沒有跟著孔雀石色系走」而在意）。

具體做法：挑一組亮色模式跟一組暗色模式的 highlight.js 主題（傾向 GitHub 亮色／GitHub Dark，這是最多人眼熟的組合，沒有特別意見的話就用這個），把兩份主題的 CSS 規則轉成跟這個 repo 慣用的 `sx` object 寫法（跟現有 `STORYTELLER_CODE_BLOCK_SX` 合併管理），用 `theme.palette.mode` 切換，不要另外載入兩份完整的主題 CSS 檔案（只挑會用到的那 15 種語言實際吐得出來的 token class 對應規則就好，其餘不用）。

## 常見 fail 應對

- 語言欄位是空字串／未註冊語言：不高亮，純文字原樣顯示，跟現在行為一致。
- `lowlight.highlight()` 丟例外（理論上不太會，但外部輸入不能完全信任）：整段 try/catch，失敗就退回純文字顯示，不能讓一個 code block 拖垮整個編輯器/閱讀頁。
- 使用者在編輯區把語言從「已註冊」改成「未註冊」（或反過來）：decoration 要跟著這次 attribute 變更重新計算，不能沿用舊的 token 樣式殘留在畫面上。
- 超長程式碼區塊（前一份規格的收縮/展開功能）：收縮時只顯示前面幾行，但 decoration 是對整份文字算的，收縮/展開純粹是 CSS `max-height`，不影響 tokenize 範圍，兩個功能不衝突，不用特別處理。

## 已確認（2026-09-05）

1. **語言擴充到 15 種**：原本 10 種＋ruby（含 RoR）／perl／rust／php／xml。
2. **主題切換機制**：固定跟著 layout 既有的 `theme.palette.mode` 切換（dark 版面＝暗色高亮、light 版面＝亮色高亮），不跟 11 組強調色連動；具體配色沿用 GitHub 亮色／GitHub Dark 這組最眼熟的組合。
3. **複製按鈕維持純文字**：複製的是 `content`（純文字字串），不含任何高亮 HTML/token 標記，跟現在行為一致，不用改。
