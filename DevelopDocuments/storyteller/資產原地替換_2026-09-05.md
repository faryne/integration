# 資產原地替換（Replace Asset）規格

## 背景

`資產集.md` 定案的資料模型裡，`storyteller_assets` 的 `public_id` 跟 `s3_key` 是同一列固定綁死的欄位，沒有版本概念。目前 `storyteller_update_asset` 只能改 `title`/`alt_text`/`description`/`metadata`，換檔案本體只能靠「重新上傳→拿到新 public_id→回頭改所有引用處」。

當同一張圖被多處引用（故事/設定集 markdown 內 `steamloom-asset://` 或圖像作品頁）時，事後發現圖片有問題要換掉，現有流程很痛：得找出所有引用處逐一改 public_id。這份規格只處理「原地替換底層檔案，public_id 不變」這一件事，**不做 `asset_version` 歷史記錄**（規模過大，見 `資產集.md` 延後項目；之後真的要做「復原到舊版」再回頭補）。

## 目的

- 新增一個「替換檔案」操作：same `public_id`，S3 key 換成新上傳的檔案，所有既有引用（markdown asset URI、圖像作品頁）自動生效，不用改任何引用處。
- 舊檔案直接視為廢棄，不保留歷史版本、不可復原。

## 資料模型：不新增表

沿用 `storyteller_assets` 既有欄位，`UPDATE` 時直接覆蓋：

- `s3_key`
- `mime_type`
- `file_ext`
- `file_size`
- `metadata`（例如 image 的 `width`/`height` 要重新量測寫入，舊的數值不能留著）
- `updated_at`

`public_id`、`id`、`project_id`、`collection_id`、`title`/`alt_text`/`description` 全部不變。

## 上傳流程（比照現有 presign/confirm，兩段式）

1. `storyteller_presign_asset_replace(asset_public_id, mime_type, filename, size)`
   - service 層先用 `asset_public_id` 查出既有 asset，確認屬於呼叫端有權限的 project（沿用 `PresignAssetUpload` 既有的權限檢查邏輯）。
   - mime type 必須跟原本 `asset_type` 相容（image 只能換成 image，之後才會有 audio/video 的分類限制）。
   - 產生**新的**隨機 S3 key（沿用 `randomAssetKey`），回傳 `upload_url` + 這個 pending key（可用既有 presign 的 pending/draft token 機制，不用另開一套）。
2. 前端 PUT 檔案到 S3。
3. `storyteller_confirm_asset_replace(asset_public_id, pending_key)`
   - `HeadObject` 驗證檔案真的存在、量測實際 size/content-type。
   - 用 asset 現有的 `s3_key` 記下舊 key，`UPDATE storyteller_assets` 覆蓋 `s3_key`/`mime_type`/`file_ext`/`file_size`/`metadata`/`updated_at`。
   - **刪除舊的 S3 object**（呼叫端確認新檔案 head 成功後才刪舊檔，避免刪了才發現新檔案有問題）。
   - 回傳更新後的 asset metadata（`public_id` 不變）。

沒有走 `CreateAsset`，全程不產生新的 `storyteller_assets` row、不影響 `storyteller_asset_references`（引用表記的是 `asset_id`，天生不變）。

## MCP 介面

新增兩個 tool，命名比照現有 asset upload pair：

- `storyteller_presign_asset_replace`：輸入 `asset_public_id`、`mime_type`、`filename`、`size`；輸出 presigned PUT URL + pending key。
- `storyteller_confirm_asset_replace`：輸入 `asset_public_id`、pending key；完成替換，回傳更新後 asset metadata。

Tool 描述要清楚寫明：**這是不可逆操作，舊檔案會被永久刪除，沒有版本歷史**，避免呼叫端誤用成「加一個版本」的語意。

## 前端

`StorytellerAssetManager.tsx` 資產卡片選單新增「取代檔案」入口：

- 點擊後跳出檔案選擇器，走 presign → PUT → confirm 三步（複用既有上傳 UI 元件邏輯）。
- confirm 成功後需要重新整理該卡片的縮圖/預覽（**簽名 URL 快取要一併失效**，見下方「快取」小節），並顯示成功 SNACK。
- confirm 前顯示一次 confirm dialog，文案明講「此操作無法復原，所有引用此資產的地方都會立即換成新檔案」，避免使用者手滑。

## 快取失效

- CloudFront 簽名 URL：目前簽名 URL 是即時簽發、不落地快取（見 `資產集.md` 現況判斷），所以 replace 後下一次簽名自然拿到新內容，**後端這層不用額外處理**。
- 瀏覽器/CDN 邊的 HTTP cache：若 CloudFront distribution 或瀏覽器對同一個 S3 key 有 cache-control，理論上不會撞到，因為新內容用的是新 S3 key（`s3_key` 整個換掉，不是覆蓋同一個 key 的內容）——**這點很重要**：replace 不是「用同一個 S3 key 覆蓋內容」，而是「原子性地把 asset row 指向新 key」，天生避開了 S3/CDN 對同一個 key 的快取問題。
- 前端本地：confirm 成功後手動 invalidate 該 asset 的預覽 URL 快取（若有做 client-side cache），或直接重新呼叫 `storyteller_get_asset` 拿新的簽名 URL。

## 權限與邊界

- 沿用現有 asset 權限檢查：只有 asset 所屬 project 的擁有者可以替換。
- 若 asset 已經 soft delete（`is_deleted=true`），不允許替換，回錯誤（該用建立新 asset）。
- mime type 分類必須跟原 `asset_type` 一致，不允許把圖片 asset 換成音訊檔案（第一版仍只開放 image）。

## 常見 fail 應對

- confirm 時新檔案 `HeadObject` 失敗（前端 PUT 沒成功）：直接回錯誤，不動既有 `s3_key`，舊檔案原封不動保留、不刪除。
- confirm 成功但刪除舊 S3 object 失敗（S3 暫時性錯誤）：不擋這次替換成功（asset 已經指向新檔案），但要記 log／或丟進既有的清理機制補刪，避免累積孤兒檔案；這不是本次規格要解的問題，沿用現有系統若有的清理排程即可，若沒有就先接受孤兒檔案存在，之後再處理。
- 替換時 asset 正在被其他請求讀取（簽名 URL 已經簽出去給某個正在載入的頁面）：可接受的競態——沒有鎖，短暫視窗內可能拿到舊內容或新內容其中一個完整版本，不會拿到「新舊混雜」的損毀資料，因為 S3 object 本身是不可變的（替換是「換指標」不是「改內容」）。

## 不做

- `asset_version` 歷史表、版本清單 UI、回復到舊版本。
- 檔案內容 hash／去重。
- audio/video 的替換（跟隨現有 asset 系統，第一版仍只開放 image）。

## 工程難度

小到中：沿用既有 presign/confirm 管線與權限檢查，主要新增兩個 handler（service 層各約一個函式）、兩個 MCP tool、前端一個選單入口 + confirm dialog。抓 1-2 個工作天等級。
