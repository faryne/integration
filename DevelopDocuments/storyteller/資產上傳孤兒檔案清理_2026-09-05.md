# 資產上傳孤兒檔案清理規格

## 背景

Presigned PUT 網址本身管不住檔案大小／類型，實際檢查是在 confirm 那一步用 `HeadObject` 事後驗證（`service/storyteller/asset.go` 的 `ConfirmAssetUpload`/`ConfirmAssetReplace`，`service/storyteller/upload.go` 的 `validateImagePageSizes`）。但目前**檢查失敗只會擋下這次操作（回錯誤、不寫 DB），完全不會刪除已經上傳到 S3 的檔案**——這個檔案就變成孤兒，永遠留在 bucket 裡。

另一種孤兒情境：使用者/agent 拿到 presigned URL 之後**根本沒有走到 confirm 這一步**（瀏覽器關掉、上傳中斷、agent 半途放棄），這種情況下檔案可能上傳成功也可能沒上傳，但完全沒有東西會去檢查、清理它。

這份規格處理兩件事，兩個都要做：

1. **驗證失敗時主動刪除**：confirm 檢查不過關時，順手刪掉剛上傳的檔案，不要留著。
2. **逾時未確認的殘留檔案清理**：presign 之後一段時間沒有被 confirm，視為放棄的上傳，由 S3 Lifecycle Rule 自動清掉。

## 技術限制：S3 Lifecycle 最小粒度是「天」，改用 1 天當過期時間

**S3 Lifecycle 過期規則的最小粒度是「天」**，沒辦法設定 15 分鐘這種等級的過期時間。確認過（2026-09-05）不需要堅持 15 分鐘，改用 **1 天**當過期時間，直接用 S3 原生的 Lifecycle Rule，不用自己維護排程/追蹤表：

- Presign 產生新 key 時，用 `PutObjectInput.Tagging` 幫這個 PUT 請求打上 `storyteller-pending=true` 這個 tag（這個 tag 是簽在 presigned URL 的查詢字串裡，前端不用額外做任何事，PUT 上傳時這個 tag 就會跟著生效）。
- Bucket 上設定一條 Lifecycle Rule：篩選條件是 tag `storyteller-pending=true`，`Expiration` 設 1 天——凡是打了這個 tag、超過 1 天還留著的物件，S3 會自動刪除，完全不用自己的程式碼介入。
- Confirm 成功時，呼叫 `DeleteObjectTagging` 把這個 tag 拿掉——物件不再符合 Lifecycle Rule 的篩選條件，永久保留，不會被誤刪。

這個做法完全不用新增資料表、不用新的 cron job、不用追蹤 pending 狀態——「有沒有被 confirm」直接體現在「tag 還在不在」，S3 自己會在期限到的時候處理，比維護一張 pending 表 + 排程簡單很多。

**唯一要注意**：Lifecycle Rule 是 bucket 設定，不是應用程式碼，需要在 AWS 上（Console/CLI/CloudFormation）額外設定一次，這份規格只涵蓋「程式碼要做的部分」（打 tag／清 tag），Lifecycle Rule 本身怎麼設定會附上參考設定，實際套用由你自己執行（跟這個 repo 一貫的「不碰部署」分工一致）。

## 第一部分：Confirm 驗證失敗時主動刪除

### `ConfirmAssetUpload`（`service/storyteller/asset.go:202`）

目前的失敗點：
- `HeadObject` 讀取失敗（理論上少見，檔案根本沒上傳成功，S3 上也沒東西可刪，維持現狀直接回錯誤）。
- `head.ContentType` 跟 presign 當下宣告的不一致 → 回錯誤，**新增：刪除該 key**。
- `head.ContentLength > maxAssetImageSizeBytes` → 回錯誤，**新增：刪除該 key**。
- `fillImageSizeMetadata` 失敗（例如檔案根本不是合法圖片，量尺寸失敗）→ 回錯誤，**新增：刪除該 key**。

因為這個階段完全還沒有任何 `storyteller_assets` row 指向這個 key（`CreateAsset` 還沒被呼叫），刪除是安全的，不會動到任何既有資料。

### `ConfirmAssetReplace`（`service/storyteller/asset.go:290`）

同樣邏輯，但要小心：**這裡絕對不能刪錯 key**。`ConfirmAssetReplace` 檢查的是「新上傳、還沒生效」的 pending key，不是 asset 現有的 `oldKey`——驗證失敗時只刪 `input.PendingKey` 這個新檔案，`asset.S3Key`（舊檔案，此時仍是生效中的檔案）完全不能動。失敗點跟上面一樣（HeadObject 失敗不刪、content-type 不符/超過大小/量尺寸失敗才刪剛上傳的 pending key）。

### `validateImagePageSizes`（`service/storyteller/upload.go:113`）

這是舊版圖像故事頁（`content_type=image`）的批次檢查，一次驗證多個 key。目前是「其中一個超標就整批回錯誤」，這個批次語意不變（改成部分成功需要動到上層 `syncImageStoryAssetReferences`/`asset_reference.go` 的呼叫邏輯，屬於更大的改動，這次不做）。**只加一件事**：迴圈檢查到某個 key 超過大小上限時，先呼叫 `DeleteObject` 刪掉那個超標的 key，再回錯誤。其餘沒超標的 key 不動（雖然這次故事還是存不成功，但至少不會因為這次失敗又添一批孤兒檔案；沒被引用成功的 key 本來就會在下一輪「逾時清理」機制裡被掃到，見第二部分）。

### 共用刪除邏輯

三個地方（`ConfirmAssetUpload`/`ConfirmAssetReplace`/`validateImagePageSizes`）刪除失敗（S3 暫時性錯誤）都比照現有 `ConfirmAssetReplace` 刪舊檔的寫法：**記一筆 warning log，不讓刪除失敗擋住原本要回的錯誤**（呼叫端在意的是「這次操作失敗了」，刪除只是盡力而為的清理，不是這次操作是否成功的判斷依據）。

## 第二部分：Lifecycle Tag 過期清理

### Presign 時打 pending tag

`PresignAssetUpload`（每個 file）跟 `PresignAssetReplace` 在組 `PutObjectInput` 時多帶一個欄位：

```go
Tagging: aws.String("storyteller-pending=true"),
```

`PresignImageUpload`（舊版圖像故事頁）**這次一併加上同樣的 tag**——這個做法不需要額外的 confirm 節點或追蹤表，純粹是「打 tag → 之後有人清掉 tag 就留著，沒人清掉 tag 就讓 S3 自己過期」，跟有沒有明確的 confirm 步驟無關，所以舊版圖像故事頁這次也能一起處理，不用像第一部分那樣排除在外。

### 對應的清 tag 時機

- `ConfirmAssetUpload`／`ConfirmAssetReplace` 成功建立/更新 asset 之後：對該 key 呼叫 `DeleteObjectTagging`，移除 `storyteller-pending` tag。
- `validateImagePageSizes` 通過驗證、故事真正存檔成功後：對 `content.Pages` 裡每個引用到的 key 呼叫 `DeleteObjectTagging`。這一步要放在 `CreateStory`/`UpdateStory` 真正寫入 DB 成功之後才做（存檔失敗的話 tag 應該繼續留著，讓它照原本的過期時間被清掉，不要提早清 tag 導致存檔失敗的圖片變成真正的永久孤兒）。
- 清 tag 失敗（S3 暫時性錯誤）：比照第一部分，記 warning log，不擋主流程；最壞情況是這個檔案的 tag 沒清掉，1 天後被 Lifecycle Rule 誤刪，但這是已經確認能接受的風險（跟你確認過可以接受 1 天為單位）。

### S3 Bucket Lifecycle Rule（需要在 AWS 端另外設定，不是這次程式碼異動的一部分）

Bucket 上設定一條 Lifecycle Rule，篩選條件是 tag `storyteller-pending=true`，`Expiration` 設 1 天。CloudFormation 片段可以參考：

```yaml
LifecycleConfiguration:
  Rules:
    - Id: storyteller-pending-asset-expiration
      Status: Enabled
      TagFilters:
        - Key: storyteller-pending
          Value: "true"
      ExpirationInDays: 1
```

這一步是 bucket 設定變更，不是應用程式碼部署，照這個 repo 一貫的分工，套用到實際 AWS 資源由你自己執行（Console 手動加規則，或併入既有 CloudFormation/CDK stack），這份規格與後續 Codex 實作只負責程式碼裡打 tag／清 tag 的部分。

## 邊界與例外

- Presign 核發了但使用者最終沒有真的 PUT 檔案上去：根本沒有物件存在，Lifecycle Rule 自然無事可做，不用特殊處理。
- 兩個請求對同一個 key 前後 confirm 兩次（極端競態）：第二次 confirm 會因為 `AssetByS3Key` 已經有記錄而走現有的「回傳既有 asset」分支（`ConfirmAssetUpload` 現有邏輯），不會重複清 tag；`DeleteObjectTagging` 本身也是幂等操作，重複呼叫不會出錯。
- 使用者存檔存到一半、`storyteller-pending` tag 已經被清掉，但後續某個原因整批操作又失敗回滾：這種情況這份規格不處理（現有程式碼本來就沒有這種跨步驟的交易回滾機制），維持現況風險等級不變。

## 不做

- 不改 `validateImagePageSizes` 的「整批失敗」語意。
- 不做資料表／排程追蹤（改用 S3 原生 tag + Lifecycle Rule，見上）。
- 不做清 tag 失敗的重試機制。
- 不由這次程式碼異動去套用 Lifecycle Rule 到實際 bucket（AWS 端設定，由你自己執行）。

## 工程難度

小：三個 presign 呼叫點各加一個 `Tagging` 欄位，三個「成功後」的位置各加一次 `DeleteObjectTagging`。不用新表、不用新 cron job。抓半天等級，另外你自己要花時間去 AWS 端套用 Lifecycle Rule。

## 工作項目 Checklist

- [ ] `PresignAssetUpload`：`PutObjectInput` 加 `Tagging: "storyteller-pending=true"`。
- [ ] `PresignAssetReplace`：同上。
- [ ] `PresignImageUpload`（`service/storyteller/upload.go`）：同上。
- [ ] `ConfirmAssetUpload`：成功建立 asset 後對該 key 呼叫 `DeleteObjectTagging`（失敗記 log 不擋成功回傳）。
- [ ] `ConfirmAssetReplace`：成功更新 asset 後對 `input.PendingKey` 呼叫 `DeleteObjectTagging`（絕對不要對 `oldKey` 動任何 tag 操作，那個 key 已經被刪除了）。
- [ ] `asset_reference.go`/`storyteller.go`：`validateImagePageSizes` 通過且故事存檔成功後，對所有引用到的 key 呼叫 `DeleteObjectTagging`。
- [ ] `ConfirmAssetUpload`/`ConfirmAssetReplace`：第一部分規格的「驗證失敗刪除該 key」邏輯照做（刪除物件本身即可，物件都刪了 tag 自然不用管）。
- [ ] `validateImagePageSizes`：第一部分規格的「超標的 key 主動刪除」邏輯照做。
- [ ] 提供 AWS Lifecycle Rule 設定片段（CloudFormation 或說明文字）給你參考，實際套用你自行執行。
- [ ] 驗收：`ConfirmAssetUpload` 帶一個超過大小上限的 key，回錯誤後該 key 在 S3 上已被刪除。
- [ ] 驗收：`ConfirmAssetReplace` 驗證失敗時，asset 原本的 `s3_key`（舊檔案）完全不受影響，只有 pending key 被刪。
- [ ] 驗收：正常 confirm/存檔成功的 key，`storyteller-pending` tag 已被移除（可用 `GetObjectTagging` 檢查）。
- [ ] 驗收：Lifecycle Rule 套用後（需要你自己在 AWS 端設定），放著不 confirm 的 key 隔天會自動消失（這項驗收依賴 AWS 端設定完成，程式碼這邊測不到，只能測「tag 有沒有被正確打上/清除」）。
