# 所見即所得編輯器

## 目的

為了提供 Storyteller 一個更直覺且易於使用的編輯體驗，我們需要開發了一個所見即所得編輯器。

這個 markdown 編輯器預定會使用在故事/設定集編輯頁面中。

這個所見即所得的編輯器除了支援 markdown 語法的即時編輯即時預覽功能外，還會包含一些簡單的編輯功能，讓作家們在編寫作品時能夠更加方便。

目前是希望比照 Notion 的編輯器為大方向搭配 Storyteller 的需求進行開發。

## 功能

### 語法白名單

即時編輯及即時預覽支援的樣式如下（此部分為白名單，只有在格式名單中被允許的才可以使用。且未來不排除會新增新的自訂 markdown 格式）：

| 樣式 | 語法 | 備註 |
| --- | --- | --- |
| 粗體 | `**文字**` 或 `__文字__` | 兩種寫法視為同義，皆解析為粗體 |
| 斜體 | `*文字*` | 僅此寫法；單一底線 `_文字_` 不在白名單內 |
| 底線 | `++文字++` | 因 `__` 已配給粗體使用，改用此寫法 |
| 下標 | `~文字~` | 單波浪號 |
| 上標 | `^文字^` | 單插入號 |
| 置左 / 置中 / 置右 | `⟦markerId align="left/center/right"⟧內容⟦/markerId⟧` | marker 上的屬性，不是獨立語法，見下方「段落標記」章節 |

以上語法定案先照此執行，但**白名單規則需實作為一組獨立的變數／常數（設定檔）**，不可寫死在解析邏輯裡，以保留未來新增／調整語法的彈性。

### 語法解析規則
- 編輯器與故事閱讀頁**共用同一套解析器、同一份白名單規則**，不會有兩套邏輯並存的情況。
- 不接受任何 HTML 內容。使用者貼上的內容一律清洗成純文字（去除所有 HTML 標籤與樣式），不嘗試將原始格式轉換或保留成白名單內的樣式，貼上後格式跑掉是可接受的結果。
- **非白名單語法一律略過解析、以純文字顯示**。也就是說即使內容中出現通用 Markdown 語法（例如標題 `#`、清單、連結、表格、程式碼區塊等），只要不在白名單中，就不會被特殊渲染，會直接以原始字元顯示——編輯器與閱讀頁的顯示結果一致。
  - 這代表舊文章中若使用了白名單以外的 Markdown 語法，在新解析器上線後會「變成純文字顯示」，屬於已知且接受的行為。

## 簡單的編輯功能

（如未述明，都是以段落為單位進行操作。且這些操作都不會反應在故事閱讀頁中）
- 以段落為單位加入註解。**每個段落最多只能有一組註解**（不是通用文書處理軟體，不支援單段多則註解）。

### 段落標記（paragraph marker）設計

為了讓註解能穩定掛在段落上，每個段落會附加一個隱藏 marker 作為錨點。設計上需要注意：

- **遷移範圍：全量處理 `story` / `lore` / `story_version` / `lore_version` 四張表**。現階段資料量小，一次跑完可接受，不需要為了降低風險而縮小範圍。
  - 執行遷移的期間**需要暫時關閉存檔功能**（含 autosave），避免遷移腳本改寫內容的同時，使用者端還在背景送出舊格式（無 marker）的存檔請求，兩邊互相覆蓋造成資料不一致。目前存檔路徑只有 autosave 這一種，等同遷移期間編輯器要暫時進入唯讀狀態，需要有個明確、短暫的維護窗口。
- **這不只是一次性遷移，而是需要編輯器內建的持續行為**：舊資料回填只解決存量問題，新建立的段落在 Tiptap 裡也要能即時被賦予 marker，這件事要做在編輯器的序列化邏輯裡，不是遷移腳本能一次解決的。
- **marker 的產生時機**：使用者按下 Enter（分割出新段落）時，由編輯器自動產生一組唯一 id。實作上建議把 id 放在 ProseMirror 的 **paragraph node attribute**（例如 `markerId`），而不是直接把它當成一段可以被使用者選取/誤刪的行內文字——node attribute 才能保證「這是段落的屬性，不是段落的內容」。
- **序列化格式：不建議直接用 HTML `<span id="...">`**。原提案（`<span id="markerId">內容</span>`）本質上就是把 HTML 存進 markdown 字串裡，但我們才剛定過「不接受任何 HTML 內容」這條規則——即使是系統產生、使用者不可編輯，也會讓這條規則出現一個要特別解釋的例外，且容易和「貼上時清洗所有 HTML 標籤」的邏輯打架（清洗邏輯如果不夠精準，可能把系統自己產生的 marker span 也一併洗掉）。建議改用一個不會被誤認成 HTML、也不在白名單語法範圍內的自訂記號包住段落（例如 `⟦markerId⟧內容⟦/markerId⟧`，實際符號可再挑），效果跟 span 一樣（解析器辨識、渲染時濾掉、DB 內仍保留），但不會跟「無 HTML」規則衝突。
- **段落分割/合併時 marker 的歸屬要有規則**，否則掛在段落上的註解會跟著迷路：
  - 分割（Enter 把一段拆成兩段）：建議游標前半段沿用原本的 marker（連同它掛的註解），游標後半段拿一個全新的 marker，註解不隨後半段複製過去（後半段視為新段落，沒有註解）。
  - 合併（Backspace 把兩段併成一段）：建議保留在前、位置較早的段落的 marker（連同它的註解），被併入的段落的 marker 跟註解直接作廢。

### 一行＝一個段落（定案，整合閱讀端時發現的重要限制）

實作整合閱讀頁（`Reader.tsx`）跟版本 diff 時發現：**故事閱讀頁已經有一套「書籤」功能是上線的**，`line_index`（書籤存的是第幾行）、`line_preview` 都是直接對 `content.split("\n")` 這個陣列的位置定位；版本 diff（`buildCustomLineDiff`）也是同樣邏輯，單純逐行比對兩個版本 `content.split("\n")` 的陣列。這兩個既有功能都假設「一行＝一個獨立單位」，且完全靠陣列位置對應，不是靠內容比對。

這代表 marker 機制不能自己發明一套「段落」的分法（原本設計是空行分隔的區塊），**段落的定義必須直接等於「一行」**，且段落之間**必須用單一 `\n` 分隔（不能是空行）**——這樣舊資料做 marker 遷移時，只要把「原本的每一行」直接包上 marker（陣列的長度、每個位置對應的內容都不變），既有書籤的 `line_index` 跟版本 diff 的逐行比對就完全不用調整，遷移工作本身也單純很多（純粹是「幫每一行加東西」，不是「重新切段落」）。

因為這個限制，原本設計對齊用「行首前綴＋多行區塊」（`::: center\n...\n:::`）行不通——那會把一個段落拆成三行，破壞「一行＝一個段落」。**後來定案：對齊跟 marker 一樣，直接當成 marker 開始標記上的屬性**，不是另外一套語法（見下一節），從根本上避開這個問題，也不需要為了對齊另外發明前綴規則。

標題還是維持行首的 `#` 前綴（沿用大家熟悉的 CommonMark 慣例），因為它本來就只佔一行，沒有這個限制要處理。

### 段落元素的屬性：align 跟 comment（定案，取代原本另開資料表存註解的提案）

**align（對齊）、comment（註解）都不是獨立語法，是 marker 開始標記上的屬性**，直接跟段落內容存在同一行字串裡：

```
⟦markerId align="center" comment="逃脫後的註解文字"⟧段落內容⟦/markerId⟧
```

固定順序是 `align` 在前、`comment` 在後；兩者都可以省略（省略 `align` 代表置左、省略 `comment` 代表沒有註解）。沒有任何屬性時就是最原始的樣子：`⟦markerId⟧內容⟦/markerId⟧`。

- **為什麼不用獨立資料表存註解**：孤兒註解問題直接靠結構解決——註解文字跟段落內容綁在同一個字串片段裡，段落被刪除/合併掉的時候，內嵌在裡面的註解自然一起消失，不需要另外一張表、也不需要 cascade delete 邏輯去同步。上面「合併時被併入段落的 marker 跟註解一起作廢」已經是這個機制的自然結果。
- **為什麼對齊也用同一套機制**：align 遇到的問題（不能佔用多行）跟原本評估另開語法要解決的問題本質相同，與其為每個新屬性各自發明一套前綴語法，不如統一用「marker 屬性」這個容器，天生活在同一行裡，完全不會跟「一行＝一個段落」衝突，未來如果還要加其他段落層級的中繼資料（不確定會有什麼，但這個容器可以直接擴充），也是同一套做法。
- **字元跳脫要仔細處理**：註解文字可能包含雙引號、反斜線等字元，內嵌進屬性字串時需要跳脫（例如 `"` → `\"`、`\` → `\\`），解析時要能正確還原，不能用天真的「找下一個 `"` 當結尾」，要能正確跳過跳脫過的引號。align 因為值是固定的三選一（`left`/`center`/`right`），不需要跳脫。
- **只支援一組 comment 屬性、一則註解**，不需要考慮多則註解或其他複雜情境。
- **段落元素本身要能整包被 diff／閱讀頁解析器辨識並濾掉，不用管裡面包了什麼屬性**：只要「段落元素」這個語法單位本身被當成一個不透明的整體來處理（辨識開始/結束標記、把裡面的段落內容抽出來，其餘一律丟棄），未來不管在這個屬性裡擴充什麼欄位，都不需要額外修改 diff 或閱讀頁的解析邏輯——這也是段落元素被設計成「純粹給作家編輯用的機制，讀者不需要在意」的原因。

## 版本歷史與 Diff 的關聯

針對「marker 是否讓序列化/diff 變好處理」：

- **對註解錨定確實有幫助**，這是 marker 存在的主要目的。
- **既有的逐行 diff（`buildCustomLineDiff`，`content.split("\n")` 逐位置比對）完全不用改**：因為「一行＝一個段落」已經跟它假設的資料形狀一致，不需要像原本設想的那樣改成「以段落 ID 對齊」。
- **已實作**：`wysiwygDemo/parser.ts` 匯出 `stripMarkerForDiffContent()`，在丟進 `buildCustomLineDiff` 之前先把每一行的段落元素（marker 開始/結束標記，含 align／comment 等屬性）濾掉，只留標題前綴跟段落內容本身。`StoryVersionDiff.tsx`、`StoryDiffCompare.tsx` 的內容比對都已經套用這個函式——單純加/改/刪一則註解或調整對齊，不會被誤判成「內容變了」，使用者也不會在畫面上看到 `⟦uuid⟧...⟦/uuid⟧` 這種內部語法。
- **marker 穩定性在這裡是硬要求**：目前存檔是「每次 autosave 不論內容是否變化都新增一筆版本」，如果 marker 在沒有實質編輯的情況下也被重新產生，diff 畫面會在使用者什麼都沒做的情況下也顯示「每段都變了」，是比現在更糟的雜訊來源。

## 技術選型

- 底層編輯器引擎採用 **Tiptap（ProseMirror）**。原因：
  - 與本文件規格（白名單樣式、自訂區塊語法、無 HTML）的擴充模式契合度高。
  - 目前生態圈中對 CJK 輸入法（注音／拼音組字）相容性口碑相對成熟，是重寫既有 textarea 編輯器時風險最低的起點。
- 現行編輯器（`react-markdown-editor-lite`）是純 textarea，IME 完全交給瀏覽器原生處理，換成 Tiptap 之後這項「原生正確性」不再是既有保證，需要實測驗證。
- 下一步：先做一版初步實作（spike），驗證重點包含：
  - 中文組字（注音／拼音）輸入時的游標與候選字視窗行為，尤其是組字範圍跨到粗體／底線等 inline 樣式邊界時是否正常。
  - 組字中途按退格、快速切換候選字等邊界情境。
  - 若實測發現 Tiptap 有無法接受的 CJK 問題，才回頭評估其他候選（如 Lexical）。
