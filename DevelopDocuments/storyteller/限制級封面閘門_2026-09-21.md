# 限制級專案的封面閘門

> 狀態：規格已與使用者確認方向（2026-09-21），待 Grok 實作。branch：`fix/restricted-cover-gate`

## 問題

專案封面（`cover_url`，見 `專案封面圖_2026-09-21.md`）現在會出現在專案卡片（首頁、我的追蹤、作者頁、搜尋）與閱讀頁。**限制級（`rating = restricted`）專案的封面沒有年齡閘門**：任何人（含爬蟲）從列表 API 就拿得到簽名 URL。閱讀頁雖然把封面放在年齡確認閘門內，但 API 回應本身已經把 URL 給出去了，等於外洩。

## 目標

限制級專案的封面，在**尚未確認滿 18 歲**的讀者面前，後端就不要輸出（`cover_url` 與 `cover_asset_public_id` 都省略）；**讀者按下「我已滿 18 歲」、有了確認 cookie 之後，封面恢復顯示**。專案擁有者不受影響，永遠看得到自己的封面。

## 現況（已查證）

- 年齡確認記在**瀏覽器 cookie** `nekomaid_r18_confirmed=1`（`static_site/src/helpers/ageConfirmation.ts`：`setAgeConfirmed()` 寫 cookie 並派發 `window` 事件 `faryne:age-confirmed`，`useAgeConfirmed()` 讀取）。
- 正式站網站與 API 同網域（`VITE_API_BASE="https://faryne.dev/api-integration"`），cookie 會自動隨請求帶到後端；**本機開發是跨埠**（網站 `localhost:5174` → API `localhost:8080`），fetch/axios 沒開 `credentials`、後端 CORS 也沒開 `AllowCredentials`（`main.go` 的 `cors.New` 只設 `ExposeHeaders`），所以本機讀不到 cookie。
- 因此**前端要額外把「已確認年齡」用請求標頭 `X-Age-Confirmed: 1` 帶給後端**（值取自 cookie，前端讀得到），後端兩者任一成立就視為已確認。這是讀者自我聲明的輕量閘門，與現有前端閘門同等信任，不是安全邊界；不要為此開 `AllowCredentials`（`AllowOrigins` 是萬用字元，開了也不能用）。既有的自訂標頭 `X-Encrypt-Key` 已能通過預檢，新增標頭同理。

封面輸出收斂點（後端）：
- 所有專案輸出：`service/storyteller/storyteller.go` 的 `finalizeProjectOutputsWithFollowers` → `attachProjectCovers`（[project_cover.go](../../service/storyteller/project_cover.go)）。
- 搜尋依專案分組：`service/storyteller/search.go` 約 257 行的 `signedCoversByProjectPublicID`。
- 呼叫端：`PublicProjects`、`PublicProject`（有可選 viewerID）、`SharedProject`、`PublicUserProjects`、`PublicFavoriteProjects`、`FavoriteProjects`（登入者的追蹤）、搜尋，以及**擁有者流程**（`Projects`、`Project`、`CreateProject`／`UpdateProject` 等，`includeDraftStories=true` 的那些）。

## 設計

### 規則

專案輸出時，滿足以下**全部**條件才省略封面：
1. 專案 `rating == restricted`；
2. 請求者**不是**該專案擁有者；
3. 請求者**未確認年齡**（既沒有 cookie `nekomaid_r18_confirmed=1`，也沒有標頭 `X-Age-Confirmed: 1`）。

省略 = 輸出中 `cover_url` 與 `cover_asset_public_id` 都不帶（比照無封面）。**其餘欄位不變**。

### 後端接法（建議，最小改動）

- controller 新增一個小 helper（放 `controller/storyteller/` 新檔即可），從請求判斷 `ageConfirmed`：cookie 或標頭任一成立。
- 讓 `Service` 帶一個 `ageConfirmed` 狀態（例如 `NewService().WithAgeConfirmed(bool)`，或等價作法），公開路由的 controller 都要設定它。**預設值 `false`（最安全）**——MCP 與其他呼叫端沒特別設定時，非擁有者流程就是隱藏。
- 擁有者流程（工作台專案列表／詳情／更新等）**永遠不隱藏**：不論 cookie。`PublicProject` 在 `isOwner` 時也不隱藏。
- 在 `attachProjectCovers` 與 `signedCoversByProjectPublicID` 套用上述規則。**擁有者判斷**：這兩處目前不知道「請求者是誰」，請用最小的方式讓它知道（例如 `finalizeProjectOutputs` 已有 `includeProfileIDs`＝擁有者視圖的旗標可參考；`PublicProject` 另外用 `isOwner`）；請自行讀程式決定，**不要**為此大改函式簽名到處傳參。
- 隱藏時**不要簽名／不要查資產**（省成本）。

### 前端

- API client（找共用的 axios／fetch 封裝，`static_site/src/apis/`）：當 cookie 已確認年齡時，**所有請求**帶標頭 `X-Age-Confirmed: 1`（讀取請用 `ageConfirmation.ts` 現有的 `hasConfirmedCookie` 邏輯，必要時把它 export 出來；不要重複實作 cookie 解析）。
- 使用者按下「我已滿 18 歲」（`setAgeConfirmed` 觸發 `faryne:age-confirmed` 事件）後，**已載入的專案資料要重抓**，封面才會恢復：在合適的位置監聽該事件，對 React Query 中所有 storyteller 專案相關的 query（公開專案列表、專案詳情／閱讀頁、作者頁、追蹤列表、搜尋…）做 `invalidateQueries`（找出實際的 query key 慣例；寧可多 invalidate 幾類，也不要漏掉閱讀頁與首頁）。
- 前端既有的年齡閘門行為不變；閱讀頁把封面放在閘門內的作法保留。

### 不做

- 不改資料表、不加 migration；不改擁有者行為；不做 IP／帳號層級的年齡驗證；不動 `cover_asset_public_id` 在擁有者編輯頁的行為。

## 驗證（務必實測）

本機沒有真的 S3 檔，可用這個技巧造出能載入的封面：在本機 DB 的 `storyteller_assets` 插入一筆 image 資產，`s3_key` 指向已存在於 CDN 的真實物件（本機簽名用的是同一組 CDN key pair）。**`s3_key` 在本機有唯一限制，每筆資產要用不同的 key**，可用：`steamloom/assets/2026/09/21/d5acc358b0295c8e`、`steamloom/assets/2026/09/21/56d2d92612bebf0a`。插入欄位參考：`public_id,user_id,project_id,asset_type,mime_type,file_ext,file_size,s3_key,original_filename,title,alt_text`（`user_id` 用 dev 測試帳號的 storyteller user id，先呼叫 `POST /storyteller/auth/dev-session` 取得）。再用 `PUT /storyteller/projects/:project` 帶 `cover_asset_public_id` 設封面。

至少驗證下列情境（用 curl 對 API 驗，再用瀏覽器驗前端）：
1. 一般專案：匿名讀者與列表都看得到封面（行為不變）。
2. 限制級專案、**匿名、無 cookie／標頭**：`/storyteller/projects/public`、`/storyteller/story/:project`、`/storyteller/user/:username`、搜尋分組結果都**沒有** `cover_url` 與 `cover_asset_public_id`；其餘欄位照常。
3. 同一限制級專案，**帶 `X-Age-Confirmed: 1`（或 `Cookie: nekomaid_r18_confirmed=1`）**：封面出現。
4. 限制級專案的**擁有者**（登入 dev session）：工作台 `GET /storyteller/projects`、`GET /storyteller/projects/:project` 與編輯頁**永遠有封面**，不論標頭。
5. 瀏覽器：未確認時首頁卡片與閱讀頁沒有限制級專案封面；按下「我已滿 18 歲」後**不重新整理頁面**封面就出現。清 cookie（`document.cookie="nekomaid_r18_confirmed=; Max-Age=0; path=/"`）重整後又隱藏。
6. `go build ./...`、`go vet`、`gofmt -l`（無輸出）、`go test ./service/storyteller/ ./service/mcp/...`、`cd static_site && npx tsc -b` 全部通過。
7. **測完清掉測試專案、測試資產與 cookie**（測試資產 `DELETE FROM storyteller_asset_references WHERE target_type='project_cover'` 與 `storyteller_assets` 對應列）。

## 常見 fail

- 只隱藏前端顯示、API 仍輸出 `cover_url` → 這正是要修的洩漏，必須在後端省略。
- 擁有者也被隱藏（工作台看不到自己的封面）→ 擁有者流程要豁免，情境 4 會測。
- 本機跨埠讀不到 cookie，誤以為功能壞了 → 用標頭方案；不要開 `AllowCredentials`。
- 按下確認後封面不出現，要重新整理才有 → 沒有 invalidate query。
- 只改列表漏了搜尋分組（`signedCoversByProjectPublicID`）或閱讀頁 → 情境 2 逐一驗。
- 前端型別檢查用 `tsc -b`（不是 `tsc --noEmit -p .`）。
