# 圖片／漫畫創作展示 - 閱讀器 mockup

## 目的
- SteamLoom 除了文字故事外，計畫增加圖片／漫畫類型的創作展示，目標是「台版 Pixiv」。
- 這份文件記錄閱讀器介面的 mockup 討論結果，以及後續補上的後端資料結構方向（見「資料結構與後端方向」）。
- 產品排序：先做完圖片／漫畫展示，再處理作品搜尋功能（現有文字故事的搜尋也一併考慮，不要分開兩套）。

## 已定案的方向
- 閱讀模式只做兩種：**單頁**（一次顯示一頁，左右熱區翻頁）與**跨頁**（雙頁對開，日式由右至左順序，可切換翻頁方向）。
- **不做韓式長條漫畫（webtoon）**：長條漫畫是完全不同的內容型態（沒有「頁」的概念、滿版寬度、留白節奏），閱讀介面也要整套重做，UX 太複雜，先不考慮。如果之後真的要做，需要另外開一份規劃文件，不能沿用這份的單頁／跨頁介面。
- 閱讀器維持沉浸感：左右翻頁熱區預設不可見、滑過才浮現；作品資訊側欄可收合，收合後閱讀區吃滿寬度。
- 視覺上延續現有 SteamLoom 黃銅／深色系統（同一組 brass/copper 色碼、Rockwell 標題字、JetBrains Mono 儀表字），不另外發明一套視覺語言。
- **不做分鏡引導閱讀**（像 LINE 漫畫那種一格一格自動放大導覽）。頁面本身是創作者在外部軟體排好版、畫完整頁再上傳的完整圖片，閱讀器不需要知道頁面內部的分鏡座標，也不會做這種需要額外標記分鏡 metadata 的導覽功能。
- **行動裝置手勢採業界通用規則，不自創新手勢**：左右滑動＝翻頁（方向對應跨頁模式的翻頁方向設定）、雙指縮放／雙擊放大＋放大後單指平移、單擊畫面中央＝切換工具列顯示／隱藏（呼應桌機版左右熱區預設隱藏的沉浸感原則）。
- **資訊卡不做留言與閱覽數**，先比照現有文字故事閱讀頁已有的欄位：作者、分級、標籤、收藏、評分、上一話／下一話。留言／閱覽數這兩個文字故事現在也沒有，之後如果要做，會當成橫跨文字與圖像兩種內容類型的獨立功能一起規劃，不會只掛在漫畫閱讀器上單獨做。

## 資料結構與後端方向（已定案）

跟「分冊」功能共用能共用的部分，用減法策略處理圖像內容，不整個另起爐灶：

- **`Project.content_type` 只是「預設顯示 layout」的偏好，不是內容類型鎖**：這個欄位建立後仍可自由修改，純粹決定專案首頁預設優先攤開哪種畫面（文字故事列表 or 圖像作品列表）。**同一個專案未來可以同時擁有文字故事的冊，也有圖像作品的話**——不會因為選了「文字故事」就不能再上傳圖片，反之亦然。這點是討論 mockup 時修正過的方向，原本設計誤把它當成專案層級唯一、不可變的內容類型鎖，後來發現插畫向小說、漫畫番外這類「一個專案混搭兩種內容」的情境很常見，才改成現在的純顯示偏好語意。
- **真正決定某個冊底下裝的是文字故事還是圖像作品，不看 `Project.content_type`，要看冊自己底下實際掛的子項目**：文字故事的子項目是 `storyteller_stories` 的一般故事列，圖像作品的子項目未來會是 `storyteller_image_pages` 的頁面列，兩者是兩張不同的表。「建立故事」這個入口屆時要分成「建立文字故事」／「上傳圖像作品」兩個獨立動作，不能只在建立專案當下選一次定生死。
- **⚠️ 待實作定案：冊本身要不要有明確的內容類型欄位**：一種做法是完全不加欄位，靠「查詢時看這個冊底下實際掛在 `storyteller_stories` 還是 `storyteller_image_pages`」反推類型；另一種做法是在冊（`is_volume=true` 的 Story）上也加一個跟 `Project.content_type`同樣語意的欄位，第一次掛子項目時鎖定，避免同一個冊底下意外混進兩種子項目。這點還沒定案，等真的動工圖像功能時再決定，目前只確定「Project 層級不鎖」這件事。
- **冊（`is_volume=true` 的 Story）原封不動沿用**，圖像作品裡冊的角色是「話」——一個可獨立管理（重新命名／刪除／拖曳排序）的容器，跟文字故事的冊是同一張表、同一套機制。**畫面顯示文字依內容類型從「冊」換成「話」**，純顯示層，不影響資料結構。
- **不做「冊 > 話 > 頁」三層真結構，只做「冊(=話) > 頁」兩層**：真三層需要在冊底下再蓋一層一樣的容器機制（CRUD、拖曳排序、UI 鑽層瀏覽），等於把分冊那整輪工程再往下重做一次，工程量不是線性增加。如果讀者介面需要「第幾話」這種分段標記，用頁面上的一個標籤欄位（例如 `chapter_label`）處理即可，不建成可獨立管理的實體。
- **頁面是全新的精簡表**（暫定 `storyteller_image_pages`），不塞進 `storyteller_stories`：只留 `parent_id`（指向冊）、`sort`、`image_key`、時間戳記，拿掉 `title`／`summary`／`status`／`word_count`／`latest_content` 這些純文字才需要的欄位。上傳一部 10 頁的漫畫＝寫入 10 列，`parent_id` 都指向同一個「話」。存檔時要驗證 `parent_id` 指向的冊跟這頁屬於同一個 `project_id`，避免把頁面掛到別的專案的冊底下（不再用 `Project.content_type` 判斷能不能掛，改成看冊本身能不能收圖像子項目，見上一點的待定案內容）。
- **⚠️ 冊的「非空不能刪除」檢查要跟著改，不然會誤刪有內容的話**：現有 `VolumeChildrenCount`（見分冊.md）只查 `storyteller_stories`，圖片頁存在 `storyteller_image_pages`，不在這個查詢範圍內。因為現在不再靠 `Project.content_type` 分流查詢，實作時這個檢查要兩張表都查、非空判斷用兩者總和，不能漏掉，否則一個裝滿圖片頁的「話」會被誤判成空的、允許直接刪除。
- **`ProjectDetail.tsx`（工作台管理頁）／閱讀頁的故事列表、TOC 要能同時列出文字故事的冊與圖像作品的話**，各自依自己的子項目類型渲染查詢，不是整頁只認一種、也不是靠 `Project.content_type` 決定要不要顯示——它只用來決定預設優先攤開哪個分頁／區塊。目前冊卡片顯示的「幾篇」數量、拖曳排序邏輯都是直接查文字故事表算出來的，之後要嘛同一頁對兩種內容類型分開查詢與渲染、要嘛圖像作品另外做一個平行頁面，範圍比單純換掉編輯器大，動工前先意識到這點。
- **圖片傳遞走 CloudFront 簽名 Cookie**，不是逐張圖片各自簽名 URL，適合「一次讀一堆頁面」的場景，一次簽發、閱讀階段內都有效，前端不用每張圖重算簽名網址。要老實承認限制：這只能擋掉順手盜連／爬蟲批次下載，擋不住使用者直接截圖——Pixiv／Fantia 這些前輩也一樣擋不住，先不追求做到完全防盜。
- **上傳流程**：前端直接用 presigned PUT 把圖片傳去 S3（不繞後端伺服器），支援一次整批上傳、之後抽換單頁、之後再新增頁面。
- **單頁版本歷史**：新增一張版本表（暫定 `storyteller_image_page_versions`），每次抽換某一頁的圖片都寫一筆記錄，設計原則是「編輯記錄永久保留、實際圖檔數量有上限」：
  - **編輯記錄（M）不設上限**：誰、何時抽換過這一頁，永久保留，即使圖檔後來被清掉，記錄本身還在。
  - **實際圖檔（N）有上限，每一頁各自獨立計算、彼此不共用額度**：超過 N 個版本的舊圖檔會被清掉（S3 物件刪除、該筆記錄的 `image_key` 欄位清空），控制儲存成本（圖片比文字貴很多）。
  - **N 目前定為程式碼常數**，之後要調整直接改常數即可，不做成資料庫可設定值／不開放使用者自訂。
  - **版本比對只能對「兩邊都還留著圖檔」的版本做**，其中一邊的圖檔已被清掉的話，只能顯示「有過這次編輯，但圖片已不再保留」，不能真的並排比對。
  - **待確認（跟付費機制連動，目前不確定要不要做）**：之後可能想讓免費使用者的 N 比付費使用者低，藉此當作一種付費誘因。如果要做，代表 N 不能只是單一全站常數，要能依使用者方案查表決定——這點先記錄，等付費機制那份文件的方案設計更明確再回頭處理，不影響現在先用常數的做法。

## Mockup 內容
互動版 mockup：https://claude.ai/code/artifact/dad4a627-a5b7-4a1b-a2f8-65405d21fce9

版面組成：
- 頂部工具列：返回、作品標題＋話數選擇、單頁／跨頁切換、翻頁方向切換（跨頁模式才顯示）、縮放讀數、設定、資訊側欄開關。
- 閱讀主舞台：置中顯示分鏡頁面，左右熱區翻頁，底部頁碼讀數（例如 `012 / 240`）。
- 底部縮圖列：可點縮圖跳頁，上方有一條讀取進度飾條。
- 右側資訊卡：作者、分級（沿用現有 `普通級`／`輔導級`／`限制級` 顏色語意）、標籤、收藏、評分、上一話／下一話（原本 mockup 畫的留言／閱覽數已定案不做，見上方）。

頁面內容目前是佔位用的色塊分鏡，只用來驗證版面跟互動，不是美術提案；色塊本身的格線樣式純粹是佔位素材，跟正式的分鏡版型無關（分鏡排版是創作者外部工具的事，已定案不做引導式分鏡導覽）。

## 工作台建立流程 mockup（進行中，前端 mockup，尚未接後端）
- **`ProjectDetail.tsx` 新增獨立的「圖像與冊」分頁**，跟「故事與冊」分開（原本考慮塞進同一頁用區塊區隔，後來覺得圖像之後會有自己整套上傳／排序／版本歷史 UI，混在一起只會越來越亂，改成跟「設定集」一樣的獨立分頁）。分頁只是純顯示切換，不影響 `Project.content_type`（那個欄位維持前面章節定案的「預設顯示 layout 偏好」語意，不決定分頁看不看得到）。
- **「上傳圖像作品」入口**：`ImageEpisodeEditor.tsx`（路由 `project/:id/image/:episodeId`，比照故事編輯器用 `:episodeId === "new"` 代表建立），畫面包含話名稱欄位、拖曳／點擊批次選圖、縮圖網格（可拖曳重新排序、可個別移除）。
- **這階段全部用前端 mockup 頂著**（`storytellerImageEpisodeMock.ts`，localStorage 存話標題／頁數／封面縮圖），圖片不會真的上傳、也不會同步到其他裝置，畫面上有明顯的 mockup 提示文字。等 `storyteller_image_pages` 等後端資料結構定案動工時，把這個 mock 檔案換成真正的 API 呼叫即可，呼叫端介面不用大改。
