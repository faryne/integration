- 狀態：已實作並併入 main（`b9aff80`，未 push）；mockup 見 `discussion-board-mockup/`
- Branch：`feature/steamloom-discussion-board`

## 定案的決定

1. **討論串屬於專案，可錨定在某一話或某篇設定**（方案 2）。錨定的串同時出現在作品頁「討論」分頁與那一話／那篇設定的討論 modal，是同一份資料，不是同步。
2. **所有討論都是有標題的串**，沒有自動產生的「本話討論」。
3. **閱讀頁正文不加任何區塊**：只在閱讀工具列多一顆「討論」按鈕（帶串數），按了開 modal（手機全螢幕），列出錨定這一話／這篇設定的串，點一串原地展開全部留言。作品頁「討論」分頁用同一個列表元件，直接放在頁面上。
4. **沒有獨立的討論串頁**：分享、複製連結導到討論分頁並自動展開（`/discussions?thread=…`）。
5. **「關於」只在討論分頁發起時可選**（不指定／故事／設定）；從閱讀頁、設定頁的 modal 發起的串自動錨定在那裡。
6. **篩選**：全部／一般（沒有錨點）／故事（標出是哪一話）／設定（標出是哪篇設定）。排序：最新回覆（預設）／最新發起。
7. **誰能發言**：登入、本人有筆名、沒被作者封鎖（比照動態留言）。沒有筆名不能開串也不能留言。
8. **封鎖**：作者可封鎖留言者與發串者；封鎖記在作品的**所有署名身份**上，跟創作者動態共用封鎖名單（在動態封鎖的人，在討論版也不能發言，反之亦然）。被封鎖者仍可閱讀。
9. **作者身份切換**：作者（作品擁有者）開串、留言、回覆時可在**這部作品署名過的身份**間切換（例：有 A／B／C 三個筆名，作品署名 B、C，就只能選 B、C）。錨定某一話時預設該話的署名身份。
10. **編輯**：每個人都能編輯自己的串（標題＋內文）與留言；每次編輯把舊版本附加進 `edit_history`（v1 不顯示歷史），畫面在時間後標「已編輯」。已鎖定的串、被封鎖的人不能編輯。
11. **鎖定**：作者可鎖定串（按下先確認「所有人都無法再回覆」），鎖定後不能回覆也不能編輯；沒有置頂。
12. **刪除**：發串者或作者可刪整串（連同回覆都看不到），留言者或作者可刪留言（留佔位）。
13. **可見度**：公開與不公開（僅限連結）作品有討論版，不公開作品要帶分享 token（作者本人不用）；私人作品沒有。
14. **字數**：畫面不顯示字數，後端留寬鬆上限（標題 100、內文 10000、留言 5000）。
15. **通知**：v1 只留接口（`notifyDiscussion`）不發任何通知，之後再補。

## Schema（MySQL 5.7）

```sql
CREATE TABLE storyteller_discussion_threads (
  id, public_id, project_id,
  anchor_type VARCHAR(16) NOT NULL DEFAULT '',  -- '' 一般 / story / lore
  anchor_id BIGINT UNSIGNED NOT NULL DEFAULT 0,
  user_id, profile_id,                           -- 發串者身份
  title VARCHAR(191), body TEXT,
  edit_history JSON NULL, edited_at, locked_at,
  last_activity_at,                              -- 最新回覆排序
  is_deleted, deleted_at, created_at, updated_at
);
ALTER TABLE storyteller_comments ADD edit_history JSON NULL, ADD edited_at TIMESTAMP NULL;
```

- 回覆沿用 `storyteller_comments`（`target_type = discussion_thread`），刪除佔位、↪ 回覆 @、作者封鎖都跟動態同一套。
- `edit_history` 以 `JSON_ARRAY_APPEND` 附加 `{title, body, edited_at}`：單表 UPDATE 由左到右賦值，所以讀到的是更新前的舊值。

## API

```
GET    /storyteller/story/:project/discussions?filter=&sort=&anchor_story=&anchor_lore=&page=&share=   公開
GET    /storyteller/discussions/:thread?share=                                                        公開（展開一串）
POST   /storyteller/story/:project/discussions?share=     {title, body, anchor_story?, anchor_lore?, as?}
PUT    /storyteller/discussions/:thread                    {title, body}
DELETE /storyteller/discussions/:thread
PUT/DELETE /storyteller/discussions/:thread/lock
POST   /storyteller/discussions/:thread/block              封鎖發串者
POST   /storyteller/discussions/:thread/comments?share=    {body, parent?, reply_to?, as?}
PUT    /storyteller/comments/:comment                      {body}（只開放討論版留言）
DELETE /storyteller/comments/:comment、POST /storyteller/comments/:comment/block   沿用，依留言所在地方判斷權限
```

- 列表與詳情回 `viewer: {state, as[]}`：`state` 為 ok／login／pen_name／blocked，`as` 是可用身份（作者＝作品署名身份，讀者＝本人）。
- 錯誤碼新增 409005（已鎖定）；其餘沿用動態的 403001／403002／409004／429001。
- 寫入路由全部進稽核 registry（`discussion.*`、`comment.update`、`author.block` 多一條路由）。

## 前端

- 閱讀頁：`StorytellerReaderToolbar` 多一個 `discussionButton` 插槽；`Reader.tsx` 只加串接，討論相關邏輯都在 `pages/storyteller/readerDiscussion.ts`（組 context：防劇透判斷、錨點名稱與連結）與 `components/storyteller/discussion/*`。
- 作品首頁：`ReaderWorkLanding` 多一個「討論」分頁（`/discussions`），分享連結也有（`/share/:token/discussions`）。
- 防劇透：錨定的話讀者沒讀完、或錨定的設定還被設定防劇透閘門鎖著時，討論分頁的標題摺成「尚未讀完的內容」，展開先看到閘門（先去讀／直接看）。閱讀頁 modal 裡不擋（讀者人就在那一話）。作者本人不擋。
- 共用元件：留言串從動態抽出來成 `components/storyteller/comments/`（`CommentThreadView`、`CommentItem`、`CommentBox`），動態與討論版同一個畫面，各自只接自己的 API；`PostTextInput` 的字數上限改選填（討論版不顯示字數）。

## 實作備註

1. **時間一律由 Go 帶入**：連線用的是本地時間、MySQL `NOW()` 是 UTC，混用差 8 小時。第一版「最新回覆」排序因此錯亂，討論版的 `last_activity_at`／`edited_at`／`locked_at` 都改成 Go 的 `time.Now()`。既有程式碼（例如 `first_published_at`、`notified_at`）也有混用 `NOW()`，目前只用來判斷有無、沒有拿來排序，沒有動。
2. **封鎖寫在作品所有署名身份**：作品的署名身份在作品頁本來就公開是同一位作者，封鎖全部不會多洩漏筆名關係。解除封鎖要在封鎖名單各身份分別解除。
3. **錨點即時檢查**：錨定的話下架、設定轉草稿或刪除後，列表的錨點顯示「已下架」，不給連結。
4. **閱讀頁按鈕的數字**是錨定這一話／這篇設定的串數，0 時不顯示。

## 已知 Bug 記錄

### MySQL `NOW()` 與 Go 寫入的時間不同時區

- **現象**：討論版「最新回覆」排序錯亂——有新回覆的串沒有排到最前面。
- **Root cause**：連線字串 `loc=Local`，gorm 用 Go 的本地時間（本機 +08）寫入 `created_at`／`updated_at`；但部分 SQL 用 MySQL 的 `NOW()`，而本機 MySQL 的 `time_zone` 是 SYSTEM（UTC），兩者差 8 小時。
- **解法**：討論版先改成全部由 Go 帶入時間；之後在 `fix/steamloom-mysql-now-timezone` 掃 steamloom 全部 repository，把剩下 6 處 `NOW()` 一起改掉：AI 助理卡住對話的判斷（`agenticChatStaleCutoff()`，原本本機要多等 8 小時才回收）、`first_published_at`、`read_at`、通知 `locked_at`、動態 `pinned_at`／`notified_at`。後 5 個欄位目前只判斷有沒有值，沒有實際影響，改掉是為了一致。
- **只有本機會發生**：正式環境主機與 MySQL 都是 +08（2026-10-08 確認：主機 `CST`、`SELECT now()` 為台灣時間），Go 寫入與 `NOW()` 一致。本機 Docker 的 MySQL 原本是 UTC，Mac 是 +08，才差 8 小時。
- **本機環境**：`docker-compose.yml` 的 mysql 加上 `--default-time-zone=+08:00`，跟正式環境一致；`updated_at ... ON UPDATE CURRENT_TIMESTAMP` 由 DB 自動寫入的時間也因此對齊，不用改程式。副作用：本機改設定前寫入的 TIMESTAMP 讀出來會晚 8 小時（MySQL 以 UTC 儲存、依時區換算），開發資料不處理。
- **狀態**：已修（分支 `fix/steamloom-mysql-now-timezone`：程式改由 Go 帶入時間＋本機 MySQL 時區）。
