# 編輯頁程式碼區塊（Code Block）規格

## 目的

- 故事/設定集編輯頁支援插入程式碼區塊：多行、等寬字體、不套用行內格式（粗體/顏色/底線等），可選標註語言。
- 為「Storyteller 拿來當 SDD 規格庫」的構想鋪路（見 memory `project_storyteller_sdd_repurpose_idea`）：規格文件常常要塞 API schema、介面定義、範例 payload，沒有 code block 幾乎不能用。
- MCP／AI agent 也要能可靠地寫入這個語法，不能只有網頁編輯器用得到。

## 現況調查（跟 table／list 對照，決定 code block 該像哪一個）

編輯器裡「段落以外的結構」目前有兩種實作模式，決定 code block 該仿照哪一種是這份規格最關鍵的一步：

**模式一：blockKind（quote／bullet／number／hr）**——扁平段落屬性，不是獨立 node type。每一行仍然是一個 `paragraph` node，只是多了 `blockKind` attribute；連續同 blockKind 的段落在編輯區用 CSS（`data-block-kind` 選擇器）視覺分組，並沒有真的巢狀 DOM；閱讀頁（`StorytellerWysiwygMarkdown.tsx`，純 React 渲染沒有 schema 限制）才輸出真正巢狀的 `<blockquote>`/`<ul>`/`<ol>`。序列化是「行首前綴」（`> `、`- `、`1. `、`---`）。這個模式的前提是「每一行本質上還是一個獨立段落，只是外觀分組」——完全不適合 code block，因為程式碼的多行內容必須當一個不可分割的整體，行內也不能有粗體/顏色這些 mark。

**模式二：table（2026-08-14 改版）**——真正的巢狀 ProseMirror node type（`storytellerTable > tableRow > tableCell`，見 `wysiwygCore/storytellerTable.ts`），用 `@tiptap/pm/tables` 的機制實作，有自己的 commands（插入/加減列/加減欄/刪除整個表格）跟一個獨立的浮動 `StorytellerWysiwygTableMenu`（bubble menu，只在游標在表格內才出現）。序列化是「每一列一個 bracket marker」：`⟦table tableId="..." rowId="..."⟧| cell | cell |⟦/table⟧`，同一個 `tableId` 的連續列在解析時會被合併成一個真正的巢狀 doc node（不是像 blockKind 那樣純粹靠 CSS 分組）。插入表格走共用的 command registry（`commands.ts` 的 `"insert"` group），因此右鍵選單／斜線選單會自動出現這個選項，不用個別接線。

**結論：code block 應該比照 table 的模式二（真正的 node type），不是 blockKind。** 理由：
- 多行內容要當一個整體（不能被 Enter 拆成多個獨立段落）
- 不能有行內格式（粗體/顏色/底線等 mark），跟一般段落的 schema 不一樣
- 需要「語言標籤」這種只有整個區塊才有意義的屬性，不是逐行的

## 資料模型

**新 ProseMirror node type**：`storytellerCodeBlock`
- `group: "block"`
- `content: "text*"`（純文字，不允許任何 inline mark——跟 table cell 目前允許 inline mark 不一樣，程式碼不該被套用粗體/顏色）
- `attrs: { markerId: string | null, language: string | null }`
- `code: true`（沿用 ProseMirror 慣例，讓拼字檢查等功能跳過這個節點）

**markerId 是必要的（已定案）**：跟段落一樣需要穩定的錨點，否則編輯頁的書籤功能無法對這個區塊運作。這代表 markerId 的「backfill」機制要延伸到這個新 node type，前後端都要處理：

- **前端**：`markerParagraph.ts` 現有的 `appendTransaction` 自動補 id 邏輯目前只掃 `paragraph` type 的節點；要擴充成同時掃 `storytellerCodeBlock`（或抽成一個共用的「幫任何有 markerId attr 但值是 null 的節點補 id」邏輯，兩種節點共用同一份，不要複製兩份）。
- **後端**：`backfillStoryMarkerIds`（`storyteller.go`）目前逐行處理，假設每一行都是段落。Code block 用 GFM fence 語法橫跨多行，不能逐行套用同一招；後端要先掃出 fence 區塊的起訖範圍，把整個區塊當一個單位補 id（見下方序列化格式的 `id` 屬性設計）。
- 書籤資料模型（`storyteller_writing_bookmarks` 表）不用改，`marker_id` 欄位本來就是通用字串，code block 的 markerId 存進去就跟段落的書籤一樣運作；大綱面板（`StorytellerEditorOutlinePanel.tsx`）合併清單時，code block 本身不是標題，不會出現在「標題」那組，但可以被加書籤、出現在「書籤」那組（書籤預覽文字用程式碼開頭幾個字，比照現有段落書籤的 `previewText` 邏輯）。

**是否要有 markerId（給書籤/大綱用）？** 待確認——見下方「待確認」。

## 序列化格式：直接用 GFM 慣用的三個反引號 fence，不發明新語法

跟 table 不同，這裡**不**建議發明新的 bracket marker 語法，直接用大家都熟悉的 GFM fenced code block，只在開頭 fence 那一行、語言後面加一個 `id` 屬性來承載 markerId（跟段落用內嵌 marker 包住不同，這裡用「fence 屬性」而不是「整段包一層 bracket marker」，才不會讓整段程式碼內容被額外的標記符號污染）：

```
```go id="a1b2c3"
func main() {
	fmt.Println("hello")
}
```
```

`id` 屬性可以省略（AI／使用者新建區塊時通常不會自己填），沒有的話比照段落的 backfill 機制，存檔時後端補一個新的並改寫那一行 fence。

理由（直接對應你要求的第一點「MCP 必須可套用」）：
- AI agent 對三個反引號 fence 的語法已經是直覺反應，不需要在 `storytellerContentSyntaxHint` 裡教它任何新東西就能正確使用——這正是這幾天一直在處理的「AI 沒被明確教過某個標記語法，容易漏保留/漏用」問題的根本解法：**能用大家已經知道的語法，就不要自創**。`id="..."` 這個屬性雖然是這個 app 自己加的，但寫法跟 Pandoc/一些 markdown 方言的 fence 屬性語法（`{#id}` 這類）神似，AI 大概率能猜對「這是這個區塊的 id，編輯時要保留」，加上 hint 裡明講一句就更保險。
- 對比 table 當初必須自創 bracket marker，是因為「表格」在這個 app 的既有 markdown 子集裡沒有原生語法可用（原本連 pipe table 都不支援對齊/多行儲存格）；code block 沒有這個限制，GFM fence 加一個屬性就夠用，不用整段包 marker。

**解析行為**：`parser.ts` 目前逐行解析（每行都會被 `serializeParagraph` 包一層 `⟦markerId⟧...⟦/markerId⟧`）。三個反引號 fence 之間的內容**不能**被這套逐行段落解析器處理，需要在逐行解析之前先掃一次、把 fence 之間的內容整段抓出來，比照 table 用 `tableId` 把連續列合併成一個 node 的做法（`paragraphsToDoc` 那段），只是這裡改成「偵測開始 fence／收集到結束 fence 為止」的狀態機，不是靠共同 id 分組。

**已知限制（先不處理，比照這個 repo 一貫的務實简化原則）**：
- 不處理巢狀 fence——如果程式碼內容本身包含獨立一行的三個反引號，會被誤判為結束 fence。GFM 標準做法是允許開頭 fence 用更多反引號（4 個以上）來跳脫，這裡先不做，等真的有人遇到再加。
- 貼上外部已經是 fenced code block 格式的文字，不會自動辨識轉成 code block node（跟 table 目前的行為一致，也是要走斜線指令／右鍵才會建立）。

## 編輯器 UI/UX

- **建立方式**：
  1. 輸入規則：跟 GFM 慣例一致，打 ` ``` ` 加語言（可留空）再按 Enter，直接轉成 code block，游標進到區塊裡。
  2. 斜線指令 `/code`（或 `/程式碼`）。
  3. 右鍵選單「插入程式碼區塊」。
  這三者的後兩個都走共用的 command registry（`commands.ts` 的 `"insert"` group），跟 table／插入圖片同一組機制，右鍵選單跟斜線選單會自動同步出現，不用個別接線——這是你要求「比照 table/list」在**入口**層面最直接的體現。
- **不放進底部工具列**：跟 table 一致，工具列（`StorytellerWysiwygToolbar.tsx`）只放「整份文件」層級的操作，block 層級操作一律走 bubble menu／右鍵／斜線選單。
- **區塊內編輯手感**：
  - Enter＝插入換行（留在區塊內），不是分段或跳出——這跟目前所有段落型 block 完全不同，是 code block 存在的意義。
  - Tab／Shift-Tab：先不做縮排快捷鍵，維持瀏覽器原生 Tab（跳出區塊），避免佔用鍵盤焦點跳轉；有需要再加。
  - 游標在區塊最前面按 Backspace：比照多數編輯器慣例，跳出/合併回上一段（沿用 ProseMirror 預設 `joinBackward`，不用像段落 marker 那樣特別處理）。
- **語言標籤 UI**：純文字輸入框（不做嚴格枚舉），搭配常用語言 autocomplete（go/typescript/javascript/python/json/bash/yaml/sql/html/css 這類常見選項，純前端提示用，不限制輸入值）。不做語法驗證，用來標記＋給 reading page 顯示用。
- **不做語法高亮**（詳見下方閱讀頁一節的理由），所以不需要引入 highlight.js/shiki 之類的套件，v1 純樣式框即可。
- **區塊右上角保留一塊自訂按鈕區**（已定案）：語言標籤旁邊固定一塊可以擺按鈕的區域，用陣列組態表示，每個按鈕是 `{ icon, label, onClick: (content: string) => void }`（`content` 是目前這個 code block 的純文字內容）——這樣之後要加其他按鈕（例如「在 AI 助理裡問這段程式碼」之類）不用改動 code block 元件本身，只要在組態陣列加一筆。首批只放一顆「複製」按鈕（`onClick` 呼叫 `navigator.clipboard.writeText(content)`，複製成功給個短暫的視覺回饋，比照多數程式碼平台的「複製後圖示變勾勾」手感）。

## 閱讀頁顯示（會不會突兀？）

**結論：不會突兀，甚至是讀者最熟悉的呈現方式之一。** 純文字 `<pre><code>` 搭配等寬字體＋淺灰／深灰底色框，是幾乎所有內容平台（GitHub、部落格、Notion、Medium）呈現程式碼的標準做法，讀者對這個視覺語言的辨識度非常高，比大部分自訂樣式更不突兀。

- `StorytellerWysiwygMarkdown.tsx` 加一個新分支，輸出 `<pre><code class="language-xxx">內容</code></pre>`，語言標籤（如果有填）用小字顯示在區塊左上/右上角，同一個右上角自訂按鈕區塊（「複製」按鈕）在閱讀頁也要有——讀者一樣會想複製程式碼，這個元件（含按鈕組態）應該是編輯區跟閱讀頁共用同一份呈現邏輯，不要各刻一份。
- **不加語法高亮**：v1 先不引入額外套件（highlight.js/shiki 都會增加 bundle size 跟渲染成本），純等寬字體＋底色框已經足夠可讀；等真的有使用者反映需要再加，不預先做。
- 樣式併入既有的 `BLOCK_GROUP_SX`（跟 blockquote/table 同一份樣式定義集中管理）。

## MCP／AI agent 那端要改的

`storytellerContentSyntaxHint`（`service/storyteller/tool_registry_types.go`）補一句：

> code block: standard GFM triple-backtick fences with an optional language tag, e.g. \`\`\`go ... \`\`\`. No inline styling or bracket markers inside a code block — treat its content as literal text.

因為用的是 GFM 標準語法，這句補充其實只是「確認一下這個子集也支援它」，不需要像 table 那樣寫一大段規則說明——這正是選擇標準語法而不是自創 bracket marker 的紅利。

## User Story

- 使用者在故事裡想貼一段對話框裡角色寫的程式（世界觀需要），打 ` ``` ` 建立區塊、貼上程式碼，內文正常顯示等寬字體，讀者一看就知道這是程式碼片段。
- 使用者把 Storyteller 當成規格庫使用，一篇「API 設計規格」文件裡插入好幾個 JSON 範例 payload、Go struct 定義，透過 MCP 讓 coding agent 讀取，agent 不需要被特別教就知道怎麼正確處理這個語法。
- AI 助理／agentic 對話中使用者要求「幫我把這段虛擬程式碼加上語法標籤」，AI 直接改 `language` attribute，不會動到程式碼內容本身。

## 常見 fail 應對

- 沒有指定語言：允許留空，reading page 不顯示語言標籤即可，不強制。
- 程式碼區塊整個是空的：允許，當成占位區塊，使用者之後再填。
- 使用者刪除整個 code block：整個 node 一起消失，不留殘餘 marker。
- 程式碼內容本身包含獨立一行三個反引號：已知限制，會被誤判為區塊結束（見上方「已知限制」）。
- 貼上已經是 fenced code block 格式的外部文字：不會自動辨識，維持純文字貼上（跟 table 現行行為一致）。

## 已定案（2026-09-04 確認）

1. **markerId 必要**——見上方資料模型一節，前後端 backfill 都要延伸支援這個新 node type。
2. **語言標籤**：純文字輸入＋常用語言 autocomplete，不做嚴格枚舉限制。
3. **右上角自訂按鈕區**：陣列組態 `{ icon, label, onClick: (content: string) => void }[]`，首批只放「複製」，之後要加其他按鈕只改組態、不用動元件本身；編輯區跟閱讀頁共用同一份呈現邏輯。
