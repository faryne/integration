# 行內程式碼（inline code）語法支援規格

## 背景：為什麼會漏掉這個功能

[StorytellerMarkdownSyntaxDrawer.tsx:33](../../static_site/src/pages/storyteller/StorytellerMarkdownSyntaxDrawer.tsx#L33) 的語法說明面板裡教使用者可以用單一反引號 `` `inline code` `` 打行內程式碼，但實際上編輯器從來沒實作這個功能——打反引號只會留在文字裡，不會變成任何樣式。

回頭查證後，根因是：

- [wysiwygCore/extensions.ts:33-37](../../static_site/src/pages/storyteller/wysiwygCore/extensions.ts#L33) 的 schema 是**白名單制**——所有 TipTap extension 都是明確列在陣列裡才會生效，沒列進去的語法（`#` 標題、`- ` 清單等）打了就原地留在段落文字裡。行內樣式目前只有 Bold／Italic／Underline／Strike／Subscript／Superscript／顏色／連結／腳注／註解，從來沒有把 TipTap 內建的 `Code` mark extension 排進這份清單。
- Fenced code block（```` ``` ````）有做，是因為它從一開始就被當成獨立的**區塊節點**（`StorytellerCodeBlock`），跟表格、資產圖片一樣是設計時就明確列入待辦的功能；inline code 只是一個跟 Bold/Italic 同等級的**行內 mark**，卻沒被同步排進 [whitelist.ts](../../static_site/src/pages/storyteller/wysiwygCore/whitelist.ts) 的 `MARK_SYNTAX_WHITELIST`。
- [StorytellerMarkdownSyntaxDrawer.tsx](../../static_site/src/pages/storyteller/StorytellerMarkdownSyntaxDrawer.tsx) 那條說明只有一次 commit（2026-06-29），內容像是照一般 markdown 語法小抄的既定印象直接寫的（`` `inline code` `` + fenced code block 通常會一起出現在任何 markdown 教學裡），沒有回頭對照 `extensions.ts`／`whitelist.ts` 的實際白名單去驗證。

結論：**不是 bug 修復，是把當初漏列的一個 mark 補進既有的白名單架構**。整個 mark 的解析／匯出／渲染都是「加一筆到集中設定 + 幾個 `Record<MarkName, …>`」的模式，TypeScript 會在漏改的地方直接編譯錯誤（下面會列出哪些是編譯期強制、哪些不是）。

## 現況架構（跟這次改動有關的部分）

Mark 的定義是單一事實來源模式，一個 mark 要正常运作，需要改到下面這些地方（`MarkName` 是聯合型別，新增值後 TS 會在所有 `Record<MarkName, …>` 的地方報缺漏，等於編譯器幫忙抓改動範圍）：

1. **`whitelist.ts`**：`MarkName` 型別、`MARK_SYNTAX_WHITELIST`（delimiter／canonical 寫法）——唯一事實來源，`PARSE_DELIMITERS` 是從這裡自動 flatMap 出來的，不用手動維護第二份。
2. **`markInputRules.ts`**：像 `CustomItalic`/`CustomStrike` 一樣，用共用的 `delimiterInputRegex`/`delimiterPasteRegex` 幫 TipTap 的 `Code` extension 補上打字時自動觸發、貼上時自動辨識的 input/paste rule（官方 `Code` extension 本身沒有 input rule）。
3. **`extensions.ts`**：把 `CustomCode` 加進 `createWysiwygCoreExtensions()` 回傳的陣列，schema 才會真的認得這個 mark。
4. **`parser.ts`**：`findNextToken`/`parseInline` 是通用邏輯，理論上不用改——`PARSE_DELIMITERS` 多一筆就會被掃到。但這裡有個**語意問題需要先決定**，見下面「問題 1」。
5. **`serializer.ts`**：`MARK_NESTING_ORDER_OUTER_TO_INNER` 陣列（ProseMirror doc → 內部字串）要決定 `code` 排在哪一層——`CANONICAL_DELIMITER` 是從 `MARK_SYNTAX_WHITELIST` 自動 derive 的，不用手動加。
6. **`exportMarkdown.ts`**：`EXPORT_MARK_ORDER_OUTER_TO_INNER` 陣列 + `EXPORT_MARK_WRAPPERS`（`Record<MarkName, [string, string]>`，這個是編譯期強制，漏改會直接 TS 報錯）——輸出標準 markdown 時要用反引號包。
7. **`StorytellerWysiwygMarkdown.tsx`**：`MARK_TAG`（`Record<MarkName, keyof JSX.IntrinsicElements>`，同樣編譯期強制）——渲染成 `<code>` tag，閱讀頁／預覽/公開頁共用同一份渲染邏輯，改這裡就全部生效。
8. **`commands.ts`**：`MARK_COMMANDS` 陣列加一筆 `id: "code"` 的 command（`toggleCode()`／`isActive("code")`），工具列的 bubble menu（[StorytellerWysiwygBubbleMenu.tsx](../../static_site/src/pages/storyteller/StorytellerWysiwygBubbleMenu.tsx)）是泛用迴圈跑這份清單渲染按鈕，不用另外改 UI 元件。
9. **`package.json`**：需要新增 `@tiptap/extension-code` 依賴（目前沒裝，Bold/Italic/Underline/Strike/Subscript/Superscript 都各自是獨立套件，`Code` 也是獨立套件，同一套官方 extension 家族）。

## 問題 1：inline code 的內容要不要允許巢狀其他 mark

這是這次真正需要先決定的設計問題，不是照抄現有模式就能解決。

**現有架構的行為**：`parser.ts` 的 `parseInline()` 在處理 delimiter 時是**遞迴**解析內層文字的（[parser.ts:475-480](../../static_site/src/pages/storyteller/wysiwygCore/parser.ts#L475)）——`**這是*巢狀*粗體**` 這種寫法，粗體裡面的 `*巢狀*` 會被解析成斜體。這是刻意設計，讓 Bold/Italic/顏色/連結可以互相包。

**但 inline code 語意上通常要是「字面內容」**：幾乎所有 markdown 實作（CommonMark、GFM）都把反引號內的內容當純文字，`` `a * b` `` 裡的星號不會被解讀成斜體 delimiter，這樣使用者才能安心在行內程式碼裡打任何符號（`*`、`~`、`⟦`）而不用擔心被誤判成別的語法。如果照現有架構原封不動加一筆 `code` 到 `PARSE_DELIMITERS`，`` `text *bug* here` `` 會被解析成「code 包著一段斜體」，這跟使用者的直覺不符，也會讓「行內程式碼可以安全貼上任何字元」這個 code span 最基本的用途失效。

**兩個選項：**

- **選項 A（建議）：`code` 在 parser 裡特殊處理成不遞迴**——`findNextToken` 掃到 `` ` `` 開頭的 delimiter 時，若 `markName === "code"`，內層文字直接當一個純文字 run（`marks: [...外層既有 marks, "code"]`），不呼叫 `parseInline(innerRaw)`。實作上是 `parseInline` 裡 `token.kind === "delimiter"` 分支加一個 if 分岔，改動集中在一個函式裡，不影響其他 mark 的既有遞迴行為。副作用：`code` 內部理論上還是可能被外層 mark 包住（例如粗體包 code），只是 code 內部本身不會再解析出新的 mark／marker／圖片語法。
- **選項 B：跟其他 mark 一樣走通用遞迴邏輯**——改動量最小（`PARSE_DELIMITERS` 多一筆就完工，parser.ts 完全不用碰），但會出現上述「code 內容被誤解析」的問題，使用者打程式碼片段時要自己注意不能有星號/波浪號等符號，體驗上是個地雷。

**建議選 A**：inline code 的「內容原封不動、不怕被誤判」是這個功能存在的核心價值，選 B 等於做了一個不能安心用的半成品。改動範圍可控（一個 if 分岔），不影響其他六個 mark 現有行為。

## 問題 2：delimiter 字元 `` ` `` 有沒有衝突

沒有。現有白名單用掉的字元是 `**`／`__`（粗體）、`++`（底線）、`--`（刪除線）、`*`（斜體）、`~`（下標）、`^`（上標），反引號完全沒被用過，不用擔心跟既有語法搶字元。

## 問題 3：nesting order（跟其他 mark 疊加時的巢狀順序）要排哪裡

`serializer.ts` 的 `MARK_NESTING_ORDER_OUTER_TO_INNER` 跟 `exportMarkdown.ts` 的 `EXPORT_MARK_ORDER_OUTER_TO_INNER` 目前都是 `bold → underline → strike → italic → subscript → superscript`（由外而內）。

建議把 `code` 排在**最內層**（`superscript` 之後）：現實情境比較可能是「一段話裡插一個行內程式碼片段，前後文字剛好也是粗體」，而不是「程式碼片段本身還要有下標」；排最內層代表如果真的疊加了其他 mark，輸出會是 `` **`code`** ``（粗體包 code）而不是 `` `**code**` ``（code 包粗體語法字元，會因為選項 A 的不遞迴而被當純文字字面輸出，等於 code 內容裡真的印出兩個星號）——前者才是使用者期待的疊加結果。

## 問題 4：工具列圖示

`commands.ts` 已經 import 了 `CodeIcon`（給 `insert-code-block` 用）。Inline code command 建議用**同一個 `CodeIcon`**——它跟 `insert-code-block` 分屬不同 scope（`inline` vs `insert`），不會同時出現在同一個選單裡搶視覺辨識度（bubble menu 只顯示 `mark` group，slash 選單/右鍵選單才會顯示 `insert-code-block`），沒有必要為了行內版另外找一顆圖示增加維護負擔。

## 問題 5：需要新增測試嗎

現有 `wysiwygCore/*.test.ts` 沒有任何一個是專門測 Bold/Italic 等既有 mark 的 parser/exportMarkdown 行為（`codeBlock.test.ts` 測的是 fenced code block 這個獨立節點，不是行內 mark）。照現有慣例，這次也不用特別為 `code` mark 補測試——除非你想順便建立這塊的測試覆蓋，那是額外決定，不在這次範圍內。
