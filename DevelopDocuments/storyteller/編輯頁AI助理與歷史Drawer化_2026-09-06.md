# 編輯頁 AI 助理／編輯歷史改為 Drawer 規格

## 背景

`StoryEditor.tsx`／`LoreEditor.tsx`（雙胞胎，行為要一致）右側目前用 `StoryWritingWorkspace.tsx` 的固定 dock 顯示「AI 助理」跟「編輯歷史」，兩者互斥顯示（`StorytellerEditorSideTabs.tsx` 的 `ToggleButtonGroup`，單一 `sidePanel` state 控制）。現況：

- 只有 `xl` 斷點才是固定 380px 寬、`position: fixed` 的浮動欄；`xl` 以下（含 `lg`/手機）是 `position: static`，直接疊在編輯區下方，沒有摺疊/隱藏機制。**沒有 Drawer 雛形**。
- 380px 這個寬度對兩個面板的內容都偏窄：AI 助理的長 code block／工具參數字串要靠 ellipsis／捲動硬撐；編輯歷史目前內容只是版本清單表格，寬度問題不明顯（診斷細節見下）。

調查結果顯示這兩個面板在「資料保存」「串流狀態」「內容型態」三個維度上差異很大，**確認你的懷疑是對的：兩者不能套同一套 Drawer 化做法**，這份規格分開處理。

## 共通決定：兩者都改成 Drawer，沿用既有 Drawer 慣例

沿用 `StorytellerAssetUploadDrawer.tsx` 已經建立的慣例：`Drawer anchor="right"`，三段式結構（頂部標題列＋關閉鈕、中段 `flex:1, overflow:auto` 內容、底部固定 action bar），統一的 `requestClose()` 關閉入口。**寬度不套用資產上傳 Drawer 的 720px**，兩個面板各自評估（見下）。

`StorytellerEditorSideTabs.tsx` 的 `ToggleButtonGroup` 觸發方式不變（AI 助理／編輯歷史互斥），只是原本切到 `sidePanel !== null` 時是 dock 版面 reflow，改成觸發 Drawer 開啟；`sidePanel === null` 時 Drawer 關閉，編輯區拿回全部寬度（這正是 Drawer 化的核心動機：不開的時候不佔用任何空間）。

窄螢幕（現在 `xl` 以下疊在下方沒有摺疊機制）用 Drawer 後直接統一行為：所有斷點都是「點開才出現、蓋在內容上方」，不用再分斷點寫不同版面邏輯，這算是這次改動額外解決的一個既有問題。

## AI 助理面板（`StorytellerAgenticPanel.tsx`）

### 現況特性
- **不是 SSE，是 3 秒輪詢**（有 `chatStatus === "in_progress"` 的訊息時才啟動，元件 unmount 時清 timer）。
- 對話歷史走 React Query（後端持久化），本次 session 的即時訊息存在**元件內 local state** `liveMessages`。
- **目前互斥顯示本身就已經是 unmount/remount**（切到「編輯歷史」時，AI 助理元件被 React 整個卸載），所以 Drawer 化的「關閉時要不要 unmount」這個問題**不是新問題**，現況早就是每次切走再切回來 `liveMessages` 就會被清空、重新等歷史 query 撈回來（有 cache，通常很快，只是會有一瞬間「重新出現 loading」的體感）。
- 內容型態複雜：Markdown 回覆、可摺疊「工作軌跡」摘要（長字串目前用 ellipsis 截斷）、`<pre>` 引用區塊（`maxHeight:260, overflow:auto`）、`AgentProposal` 寫入提案卡片——這些在 380px 固定寬度下明顯擁擠。

### 這次要做的決定

1. **寬度**：比現有 380px 加寬，但不用到資產上傳 Drawer 的 720px（那是給圖片縮圖網格用的）。建議 480-560px 之間，讓 code block／工具軌跡摺疊區有喘息空間，同時不會在桌面版把編輯區擠得太窄（Drawer 是 overlay，不會真的壓縮編輯區寬度，但太寬會遮住太多正在編輯的內容）。
2. **關閉時的資料保存（比現況多一個選擇）**：
   - **選項 A（維持現況行為）**：Drawer 關閉＝卸載，`liveMessages` 清空，重開靠 React Query cache 補回歷史，體感上會有一瞬間 loading 閃爍。跟現在完全一樣，零改動成本。
   - **選項 B（順手修掉這個既有小毛病）**：Drawer 用 `keepMounted`（MUI Drawer 內建 prop），關閉時只是視覺隱藏，`liveMessages`／輪詢 timer 都不受影響，重開瞬間接續、沒有 loading 閃爍。這是這次順便可以修的既有 UX 小瑕疵，成本很低（一個 prop），建議做。
3. **串流中關閉的行為**：後端進度是持久化的（`chat_status`），前端關閉 Drawer **不會**中斷任何後端請求（跟資產上傳「關閉前要 flush 未存的 PUT/PATCH」完全不同性質，那邊是真的有進行中的網路請求會被切斷，這邊只是前端輪詢/顯示層）。所以**不需要**比照資產上傳 Drawer 那種「上傳中擋關閉」的保護機制——建議 AI 助理 Drawer 允許隨時關閉，不用額外攔截。
4. **AgentProposal 提案卡片**：跟著面板一起變寬，不用特別處理，卡片本身邏輯不變。

## 編輯歷史面板（`StoryEditorHistoryPanel.tsx`/`StoryEditHistory.tsx`）

### 現況特性
- 側欄裡顯示的**只是版本清單表格**（來源／時間／字數／回復按鈕／左右選版本 radio／比較按鈕／分頁），沒有 diff 內容。
- **Diff 已經是 Modal 呈現**（`StorytellerVersionCompareDialog.tsx`），選好左右版本按「比較」才開 dialog，側欄本身完全不顯示 diff——這代表編輯歷史面板本身的內容其實不重、寬度問題不像 AI 助理那麼明顯。
- 版本清單資料**目前是編輯頁一載入就無條件抓**（跟 `sidePanel` 開關狀態無關），而且這個 query 的 payload 已經包含完整 `content`（給 diff dialog 直接用，不用另外發請求）——**這個 query 本身不輕**，是「預先付出流量成本、換取開啟面板/開 diff 都是零延遲」的現況取捨。

### 這次要做的決定

1. **寬度**：可以比 AI 助理面板窄，抓 420-480px 就夠（表格＋分頁，不像對話內容那麼需要橫向空間）。
2. **資料抓取時機（現況多一個可以評估的選擇）**：
   - **選項 A（維持現況）**：編輯頁一載入就抓版本清單＋完整 content，不管使用者有沒有點開「編輯歷史」。維持現況零改動，缺點是這個 payload 每次進編輯頁都要付出，即使使用者從來不看編輯歷史。
   - **選項 B（改成 on-open 才抓）**：Drawer 真正打開時才觸發 `useStorytellerStoryVersions`，關閉後不強制卸載 query（React Query 本身有 cache，重開不重複打，除非資料過期）。好處是不看編輯歷史的使用者省一次不小的請求；代價是**第一次點開 Drawer 會有一個小 loading 等待**（現況因為預載所以零延遲）。
   - 建議選 B：現有「一律預載」的取捨在故事很長、版本很多的情況下，會讓**每一次打開編輯頁**都多付出一筆不小的流量，只為了「使用者也許會點開編輯歷史」這個不確定的假設；改成 on-open 才抓，換來的是使用者真的點開時多等一下 loading（可以接受，比照 AI 助理面板本身也是開啟才看到內容的體感一致）。
3. **Diff Dialog 的資料來源不受影響**：不論選 A 或 B，`StorytellerVersionCompareDialog.tsx` 用的都是同一個 `useStorytellerStoryVersions` query 的結果（已經含 `content`），改成 on-open 只是把「什麼時候觸發這個 query」往後移，dialog 本身邏輯完全不用改。
4. **不需要考慮串流/中斷問題**：這個面板完全是靜態清單，沒有任何持續中的請求需要顧慮關閉時機。

## 兩者的關鍵差異總結（呼應你的懷疑）

| | AI 助理 | 編輯歷史 |
|---|---|---|
| 內容型態 | 對話串流、複雜排版（code block/摺疊區/提案卡片） | 版本清單表格，diff 另開 Modal |
| 資料保存顧慮 | local state（`liveMessages`）＋輪詢 timer，收合會重置 | 純 React Query cache，沒有 local state 顧慮 |
| 關閉時機顧慮 | 要不要用 `keepMounted` 避免 loading 閃爍（體驗優化，非必要） | 要不要把預載改成 on-open（效能優化，非必要） |
| 建議寬度 | 480-560px（內容較重） | 420-480px（只是清單） |
| 關閉保護機制 | 不需要（後端進度跟前端請求無關） | 不需要（沒有進行中的請求） |

## 追加決定（2026-09-06 實作完成後回頭檢討）：行動版改成貼底部工具列的迷你面板，不用全螢幕 Drawer

第一版（Codex 實作，commit `5dec67a`）兩個面板都用 `Drawer`，寬度用 `{ xs: "100vw", sm: <寬度> }`——**行動版會整頁蓋掉編輯內容**。回頭檢討發現這對 AI 助理／編輯歷史這兩個「邊寫邊參照」的工具是體驗倒退：使用者開 AI 助理聊天或看編輯歷史時，完全看不到正在編輯的故事內容，比原本（Drawer 化之前）「疊在下方、滑一下還是同畫面」更封閉，多一次「關掉才能回去看文章」的動作。**資產上傳 Drawer 不受影響，維持現況全螢幕**——那是獨立任務（上傳完關掉），蓋滿螢幕沒有違和感。

### 現況調查（決定新設計前先查清楚）

底部工具列鏈：`StorytellerWysiwygEditor.tsx:1555` 的 `StorytellerWysiwygBottomBar`（含 status／格式化工具列／`StorytellerEditorSideTabs` 切換按鈕），是 flex column 裡最後一個子項（`flexShrink:0, zIndex:3`），**不是自己 `position:fixed`**；真正把整個工作台鎖進 viewport 的是 `WorkspaceChrome.tsx:70-74` 那層 `position:fixed; top; bottom:0; left:0; right:0` 外殼。桌面/行動版目前**沒有斷點差異邏輯**，差異只來自 `embedded` prop（工作台內嵌編輯才有底部列；`App.tsx` 獨立路由編輯頁沒有）。

### 新設計：手機斷點（`xs`，沿用 `ProjectWorkspacePreview.tsx:81` 現成的 `isMobile`/`md` 斷點判斷）改成貼底部工具列的迷你面板，`sm` 以上維持現有 Drawer 不變

- **定位**：在 `WorkspaceChrome.tsx` 已建立的 fixed 外殼內，新增一個 `position: fixed; left:0; right:0; bottom: <底部工具列實際高度，約 48-56px>` 的浮動區塊，貼齊工具列正上方。**不做整頁 Backdrop 遮罩**——編輯內容維持完全可見/可滑動，這正是要解決的問題（如果加遮罩會讓編輯內容變成「看得到但不能互動」，沒有真正解決「看不到內容」的抱怨）。
- **高度**：不要太高，抓一個固定上限（例如 `maxHeight: 45vh` 或直接抓 320-360px），內容超過就自己內部 `overflow: auto` 捲動，不要讓面板本身撐滿或推擠整個畫面。
- **AI 助理迷你面板內容**：顯示已送出的對話串（使用者訊息＋AI 回覆），沿用現有 `StorytellerAgenticPanel.tsx` 的訊息渲染邏輯，只是外框換成這個矮胖的迷你面板而不是全高 Drawer——訊息列表本身要在面板內自己捲動（`overflow:auto`），不是靠面板長高。長 code block／工具軌跡摘要在有限高度下更需要摺疊機制，沿用現有 ellipsis／`maxHeight` 慣例即可，不用另外重新設計。
- **編輯歷史迷你面板內容**：**只顯示** 新舊版本 radio（左右選版本）、每筆版本的修改時間、回復（revert）按鈕——不用完整表格（來源／字數等次要資訊在迷你面板裡先省略，維持面板矮）。**滑鼠移到修改時間上才用 Tooltip 顯示是誰修改的**（沿用現有工具提示慣例，不用常駐顯示這個次要資訊）。「比較」按鈕維持現況開 `StorytellerVersionCompareDialog.tsx`（Modal 不受這次改動影響，桌面/行動版都一樣）。
- **關閉方式**：比照現有 Drawer 的 `StorytellerEditorSideTabs` 切換行為——再點一次同一顆 toggle 按鈕就收起（`sidePanel` 設回 `null`），迷你面板本身也保留一個小的關閉按鈕（右上角一個 icon），跟現有 `StorytellerEditorSideDrawer` 的關閉互動一致，不用另外發明新手勢（例如下滑關閉），保持跟桌面版 Drawer 同一套心智模型。
### 追加決定（討論後定案）：不做兩個平行元件，同一個 `StorytellerEditorSideDrawer.tsx` 內部依斷點切換 `anchor`

原本考慮新增一個平行元件（`StorytellerEditorSideSheet.tsx`）處理行動版，跟現有 `StorytellerEditorSideDrawer.tsx` 各管一個斷點——討論後認為**這會變成兩套要一直保持同步的機制，長期維護成本高，也讓「桌面/行動版到底哪一套邏輯在跑」變成以後排查問題的額外心智負擔**。改成：

- **只有一個元件**（`StorytellerEditorSideDrawer.tsx`），內部用現成的斷點判斷（比照 `ProjectWorkspacePreview.tsx:81` 的 `isMobile`/`md` 用法）決定要傳給底層 MUI `Drawer` 的 `anchor`：
  - `sm` 以上：`anchor="right"`，維持現有寬度（AI 助理 520px／編輯歷史 460px）、滿版高度。
  - `xs`（手機）：`anchor="bottom"`，寬度改成滿版、**高度限制在上限**（例如 `maxHeight: "45vh"` 或 320-360px 固定值），不用整頁 Backdrop 遮罩（或用最淡的遮罩，確認底下編輯內容仍清楚可見）。
- 呼叫端（`StoryEditor.tsx`/`LoreEditor.tsx`）完全不用感知斷點差異，還是用同一組 props 呼叫同一個元件；斷點切換的判斷邏輯**封裝在 `StorytellerEditorSideDrawer.tsx` 內部**，這樣未來要調整行動版樣式（例如高度上限要不要改）只要動這一個檔案。
- 面板**內容**維持原本各自的設計：AI 助理照常顯示完整對話串（內部自行捲動）；編輯歷史在行動版沿用前面章節提到的精簡呈現（只顯示新舊版本 radio／修改時間／revert 按鈕，時間 hover 才顯示是誰修改），這是因應行動版高度有限做的內容層級取捨，跟「元件機制要不要拆兩套」是兩件獨立的事——這次只解決機制重複的問題，內容精簡與否維持原規劃不變。

### 資產上傳 Drawer 維持現況（不受這次追加決定影響）

`StorytellerAssetUploadDrawer.tsx` 行動版全螢幕 `100vw` 的行為不變——上傳是獨立任務、有明確「完成」出口，跟編輯頁「邊寫邊參照」的使用情境不同，不用套用同一套迷你面板設計。

## 追加決定二（實測發現「只改容器不改內容」不夠，這次要動內容層級）

行動版底部 anchor 落地後實測發現：`StorytellerAgenticPanel.tsx` 內部原本的排版（自己的標題列＋人設選單＋完整輸入框＋長 placeholder）整個塞進 45vh 的矮容器後，扣掉這些常駐元素幾乎沒有空間留給實際對話內容，等於「開了但看不到東西」，跟修這輪之前的抱怨換一種方式重演。**上一輪「不處理 AI 助理面板內部排版」的排除範圍這次撤銷**，確定要動內容層級才能真正解決問題。

### 1. 拿掉 `StorytellerAgenticPanel.tsx` 內部重複的標題列（`floatingDock` 模式下）

`StorytellerAgenticPanel.tsx:2078-2094` 目前不管 `presentation` 是什麼都會渲染自己的「`<SmartToyIcon/>` AI 助理」標題列——這在 `presentation="floatingDock"`（現在掛在 `StorytellerEditorSideDrawer` 裡）的情境下跟 Drawer 自己的標題列（同樣顯示「AI 助理」＋關閉 X）**完全重複**，白白吃掉一整行高度。改成：`floatingDock` 為真時，這個 icon+標題文字整段不渲染，只保留「未選擇人設」那顆切換按鈕（單獨一行或跟其他控制項並排，视覺上不要留一整行空白）。`presentation="inline"`（獨立頁面情境，沒有外層 Drawer 標題）維持現狀不變。

### 2. 輸入框收窄、精簡 placeholder（僅 mobile / 容器高度受限時）

`StorytellerAgenticPanel.tsx:2357-2388` 的輸入框目前預設多行、placeholder 是一整句完整範例（「例如：幫我把這段開頭改得更懸疑一點；或輸入 /rewrite 更懸疑一點 觸發單輪改寫。」）。行動版（沿用 `StorytellerEditorSideDrawer.tsx` 判斷的同一個 `isMobile` 斷點，這個判斷需要往上傳或用同一個 `useMediaQuery` 呼叫）：輸入框預設行數收窄（例如 1-2 行，聚焦後可以再展開），placeholder 縮短成精簡版本（例如「輸入需求…」），不要整句範例塞進窄空間。桌面版（`floatingDock` 寬版或 `inline`）維持現狀完整 placeholder 不變。

### 3. 底部工具列 icon 在行動版縮小

`StorytellerEditorSideTabs.tsx`（AI 助理／編輯歷史切換按鈕）＋ `StoryEditor.tsx:1556-1588`／`LoreEditor.tsx` 對應段落的「插入資產」`IconButton`／`StorytellerEditorOutlineToggle`：這些目前都是 `size="small"`／`fontSize="small"`，行動版還要再縮小一階（例如 icon `fontSize` 降到 `1rem`／`16px`，`IconButton`／`ToggleButton` 的 padding 也對應縮小，`sx={{ p: 0.5 }}` 之類），不做成文字標籤（維持圖示，只是縮小尺寸，不引入新的文字標籤翻譯負擔）。斷點判斷跟前面兩點用同一個 `isMobile` 依據，不要各自重新宣告一個相近但不完全一樣的斷點條件。

### 4. 編輯歷史拿掉「標題」欄（不分斷點，桌面/行動版都拿掉）

`StoryEditHistory.tsx:160`（表頭 `<TableCell>標題</TableCell>`）跟 `:205-243`（對應內容 `<TableCell><Typography fontWeight={800}>{item.title}</Typography>...</TableCell>`）**整欄移除，這次是全斷點統一拿掉，不是只有行動版才隱藏**——每個版本的標題通常等於當前故事標題（除非改過），單獨列一欄意義不大，拿掉之後桌面版表格也能少一欄更寬鬆，行動版更明顯受益。確認移除後 `TableRow` 的其餘欄位（版本號／來源／字數／建立時間／操作）跟表頭數量對得上，不要留下欄位錯位。

**決定**：這輪（機制＋已完成的精簡）先 merge 回主線，不整包 revert——桌面版體驗完整、行動版比 100vw 蓋滿畫面已經是改善，機制本身沒有問題。**AI 助理面板需要一次完整的重新設計**（不是修修補補），目標是讓它在窄版面下也能把訊息／工具軌跡／提案卡片這些內容合理配置，這是之後要另開一份規格處理的題目，不在這輪範圍內，也不因為這輪已經上線而降低優先度。
