# 創作者檔案（多重筆名）

> 狀態：規格已與使用者確認（2026-09-21），待交給 Grok 實作。branch：`feat/user-profile-pen-names`

## 目的

同一個帳號可以額外建立多個「筆名」，並指定給個別的 story（章節／話）作為署名。專案（Project）的作者呈現由底下 story 使用的署名推導，可顯示「A、B、C 共著」。**沒有特別建立筆名、或 story 沒指定筆名時，一律使用帳號（`storyteller_users`）本人的資料**——不強迫使用者建任何 profile。每個筆名視同一個作者：有自己的作者頁、可被單獨追蹤。公開介面不得洩漏多個筆名屬於同一帳號。

## 現況（2026-09-21 對照程式碼）

9/10 脫鉤後 `storyteller_users` 是帳號表，`id` 就是全站 user id（`storyteller_projects.user_id`、`author_favorites.user_id/author_user_id`、PAT 等都存它）。同一張表兼任公開身份：`pen_name`（全站 unique）、`bio`、`use_default_avatar`、`avatar_url`、`sns_links`；對應 Go entity 叫 **`UserProfile`**（表 `storyteller_users`）。

- 作者顯示：`authorOutput(project.UserID)`（[service/storyteller/storyteller.go](../../service/storyteller/storyteller.go)）→ Project 只有單一作者。
- 作者頁：`/storyteller/user/:username` → `UserProfileByPenName` → `PublicProjectsByUserID`。
- 追蹤：`author_favorites.author_user_id` 是帳號 id；`PublicAuthorSummary`／`AuthorFollowerCount` 以帳號 id 統計。
- 搜尋索引：`buildWorkDocument(project, story, authorPenName)` 是**以 story 為單位**建 doc，`author_pen_name` 由 `authorPenNameForIndex(project.UserID)` 取。
- 公開輸出 `UserProfileOutput.UserID` 目前直接給前端帳號 id，前端拿它當追蹤對象。

## 設計

### 身份模型

「作者身份」= 二選一：
- **本人身份**：帳號 `storyteller_users` 自己的 pen_name／bio／avatar／sns（不動，不搬遷）。
- **額外筆名**：新表 `storyteller_author_profiles` 的一筆，使用者自己建立。

命名：既有 `UserProfile` 已被帳號表佔用，新 entity 叫 **`AuthorProfile`**，避免混淆；帳號側不改名。

### 資料表

**`storyteller_author_profiles`**（新，只放「額外」筆名）：`id`、`user_id`（→ `storyteller_users.id`，擁有者，僅後端使用、不對外輸出）、`pen_name`、`bio`、`use_default_avatar`、`avatar_url`、`sns_links`、`deleted_at`／`created_at`／`updated_at`。

**`storyteller_story_profiles`**（新 pivot）：`id`、`story_id`、`profile_id`、`created_at`；unique `(story_id, profile_id)`。
- `profile_id = 0` 代表「本人身份」，所以可以表達「本人 + 筆名 B 共著同一話」。**不加 profile_id 的 FK**（0 不存在於 profile 表），由 service 驗證。
- 某 story 完全沒有 pivot 列 ＝ 等同只有 `[0]`（既有資料零遷移）。
- 驗證：`profile_id != 0` 者必須屬於該 story 所屬 Project 的擁有者帳號（不支援跨帳號共著）。

**`storyteller_author_favorites`**：新增 `author_profile_id BIGINT UNSIGNED NOT NULL DEFAULT 0`（0 = 追蹤本人身份，既有資料原封不動仍有效）；`user_id` 是追蹤者帳號，`author_user_id` 保留為被追蹤身份的所屬帳號。unique key 改 `(user_id, author_user_id, author_profile_id)`。

`storyteller_projects`、`storyteller_stories` 本身不動。舊欄位沒有要刪的，**不需要資料回填 migration**，只有 DDL。

### 語意決策

1. **Project 作者 = 底下 story 署名的聯集。** 輸出從單一 `author` 改為 `authors[]`（依署名 story 數多到少、同數依最早出現排序）。要批次解析（一次查出這批 project 的所有 story 署名），列表頁不可 N+1。只計算對該讀者可見的 story（比照既有 `PublicAuthorSummary` 的可見性規則）。
2. **公開輸出不含任何 id，身份一律用 `pen_name` 識別。** `pen_name` 在「帳號本人 pen_name ∪ 額外筆名 pen_name」範圍內全站唯一（DB 無法跨表 unique，`ensurePenNameAvailable` 兩表都要查；`validatePenName` 照用，因為它同時是 `/user/:username` 的 URL 片段）。追蹤 API 的 `:author` 由帳號 id 改為 pen_name。既有 `UserProfileOutput.UserID` 從公開輸出移除，只有「自己的帳號設定」回傳保留。
3. **作者頁 `/user/:username`**：`username` 先解析成「本人」或「某額外筆名」。該頁作品 = 至少有一話署名該身份的 Project；統計（作品數／故事數／話數／追蹤數）以「署名該身份的 story」為準；評分沿用 Project 層級，取「有署名該身份的 Project」的評分。本人身份的判定：story 有 `profile_id=0` 列或完全沒有 pivot 列。
4. **收藏頁只掛本人身份。** `/user/:username/favorites/projects|authors` 是帳號層級資料，只有本人身份的作者頁看得到；額外筆名的作者頁回空陣列、前端不顯示該分頁（否則兩個作者頁露出同一份收藏等於公開關聯）。`hide_favorite_*` 維持帳號層級。
5. **擁有者判斷**：既有 `viewerID == profile.ID` 類寫法，對額外筆名要改成比 `profile.UserID`（帳號）。自己追蹤自己：目標身份所屬帳號 == 追蹤者帳號 → 拒絕（含同帳號的其他筆名）。
6. **編輯**：編輯頁 story 中繼資料加署名多選（預設 = 本人）。Project 建立／編輯不選筆名。
7. **刪筆名**：仍有 story 署名該筆名時不可刪，須先改署名，不連動搬移。
8. **配額**：`service/storyteller/limits.go` 新增 `FreeMaxProfiles = 3`（額外筆名數），接進 `/storyteller/limits`，前端沿用最近「配額到頂主動擋建立」的做法。
9. **MCP／PAT**：PAT 維持帳號層級，不綁筆名。
   - story 相關工具（`storyteller_upsert_story`、`storyteller_patch_story`、`storyteller_upsert_image_story`）新增選填 `profiles: ["筆名", ...]`（傳 pen_name；傳帳號本人的 pen_name 代表本人身份；不填 = 建立時預設本人／更新時不動；空陣列 = 回到本人）。`patch_story` 可只傳 `profiles` 單獨改署名。這些工具與 `get_story` 的回傳都會帶 `authors[]` 供確認。
   - 筆名維護工具（`service/storyteller/tool_registry_profile.go`，**MCP-only**，不暴露給網頁 AI 助理面板）：`storyteller_list_profiles`（回傳本人 pen_name＋額外筆名＋上限）、`storyteller_create_profile`、`storyteller_update_profile`（以現有 pen_name 識別，可用 `new_pen_name` 改名，只更新有傳的欄位）、`storyteller_delete_profile`。MCP 端一律以 pen_name 識別，不暴露 id；帳號本人的筆名不能由 MCP 改，需到網頁「我的檔案」。
10. **搜尋索引**：`author_pen_name` 改為陣列（每話署名的 pen_name 們；沒署名 = 本人 pen_name）。mapping 已是 text + `.keyword` 子欄位，陣列可直接沿用 `author_pen_name.keyword` 查詢。story 改署名、筆名改名（額外筆名或本人）時，重建受影響 story 的索引——先確認現有「改 pen_name 是否重建索引」的行為，沒有就一併補。

### API 變動

- 新增（authenticated）：`GET/POST /storyteller/profiles`、`PUT/DELETE /storyteller/profiles/:profile`（額外筆名 CRUD；`:profile` 為擁有者自己看得到的 id，僅限本人操作，須檢查擁有者）。
- `GET/PUT /storyteller/user` 維持不變（仍是本人身份＋帳號設定），另回傳 `profiles[]`。
- story 的建立／更新 body 新增 `profile_ids: [0, 12]`（僅擁有者的管理端使用；公開輸出只有 pen_name）。
- `/authors/:author/favorite`、`/favorites/authors`、`PATCH /favorites/authors/:author/visibility`：`:author` = pen_name。
- 公開專案輸出：`author` → `authors[]`（見決策 1）。story 輸出附上該話署名 `authors[]`。

### 遷移

一支純 DDL migration（Up／Down 都寫）：建兩張新表＋`author_favorites` 加欄位換 unique key。無回填。

### 已知限制（刻意不做）

- 不支援跨帳號共著；不做全域「切換身份」；不提供「追蹤帳號底下所有筆名」。
- `fallbackAuthorName`（沒設 pen_name 時 fallback 成 Google 顯示名稱／email）維持現狀不動；公開頁露出 email 是既有隱私問題，另案處理。

### 常見 fail 與對策

- 漏改擁有者判斷（帳號 vs 額外筆名）→ `git grep -n "profile.ID\|AuthorUserID"` 逐一確認。
- 公開輸出殘留帳號 id 或 profile id → 逐一檢查每個 `*Output` 的 JSON，並在瀏覽器 devtools 實際看回應。
- Project 列表 N+1 → 署名一律批次查詢。
- pen_name 跨表撞名（兩表各自建立同名）→ 建立／改名時兩表都檢查；本人改名同理。
- story 改署名、筆名改名後搜尋仍顯示舊名 → 重建索引。
- 前端型別檢查用 `tsc -b`，不要用 `tsc --noEmit -p .`（project references 下不會真的檢查）。
