# 稽核功能提案（Audit Log）

- 狀態：**規格已定稿，尚未實作**（2026-09-27），待指派開發
- Branch：`feature/storyteller-audit`
- 範圍：先做 storyteller（steamloom），其他產品線不在這一輪

## 目標

使用者在 storyteller 做的每一個「會改變資料或安全狀態」的操作，以及所有透過 PAT（MCP／API）進行的讀取，不論成功或失敗，都留下一筆 append-only 稽核事件，事後可以查出：**誰、何時、從哪個入口（Web／API／MCP／排程）、用什麼憑證、從哪個 IP 與 User-Agent、對什麼、做了什麼、結果如何**。

稽核只做「事後追查」，不是版本快照，也不提供從稽核還原（沿用〈想要做的東西.md〉協作寫入章節已確認的方向）。

## 已確認

- **儲存**：MySQL 為 source of truth，保留近 **3 個月**；更早的資料匯出到 S3，以 Athena 查詢。封存匯出與 Athena 查詢**這一輪一起做**。不使用 S3 Vectors（理由見文末附錄）。
- **不做跨來源 join**：同一個稽核頁分成「近期（MySQL）」與「封存（Athena）」兩種查詢模式。
- **舊表**：`storyteller_project_audits` 已上 prod 但未使用，本輪只標示 Deprecated，RBAC 收尾時再以獨立 migration 清除。
- **寫入不綁業務交易**：業務 commit 後才送出稽核事件，由非同步 pipeline 寫入，失敗會 retry。
- **IP／User-Agent 要存**，**不做去識別化**，跟著稽核事件一起保存到封存期限（N 年）到期；入口（Web／API／MCP）必須分得出來。
- **Redis**：prod（EC2 自架）已於 2026-09-27 開啟 AOF。
- **Proxy**：backend 前面只有一台 nginx（設定在 `httpd_conf/nginx`），做法見「入口與身分識別」。
- **封存 bucket 開 Object Lock**（governance mode），做法見「冷熱分離」。
- **S3 封存保存 N 年後刪除**，N 可設定，**預設 7 年**（法遵與儲存成本考量），做法見「封存保存期限」。
- **社交與收藏也要記**（列為低重要度，查詢時預設收合）。
- **PAT 讀取要記**：MCP 與之後 API 的讀取都記；Web（session）的讀取不記。

## 記錄範圍

### 判斷原則

一個操作**要記**，只要符合下列任一條：

1. 改變了持久化資料（新增、修改、刪除、搬移、排序、回復版本、發佈、可見度切換）。
2. 改變了安全狀態（登入、登出、憑證建立或撤銷）。
3. 花了使用者的錢或額度（呼叫 AI provider）。
4. **透過 PAT（MCP／API）讀取資料**。
5. 上面四類操作**嘗試了但被拒絕或失敗**。

**不記**：Web（session）上的讀取、輪詢、搜尋，以及只影響介面暫存狀態的操作。

**為什麼 PAT 讀取要記、Web 讀取不記**：PAT 是長期有效的 token，操作者通常是外部程式或 AI 工具，使用者不一定在場；外洩後可以在任何地方直接呼叫。資料外洩最典型的樣子就是「只讀不寫」，如果不記讀取，就無法回答「這支 PAT 讀走了什麼」。Web 的讀取則是使用者本人在看自己的資料，量大且追查價值低。

### 粒度

- **一個使用者動作 = 一筆事件**。一次請求連帶改了多筆資料（例如重新排序 10 冊、刪除設定集連帶 soft delete 其下設定），記成**一筆**，受影響的數量與 ID 列表放在 summary。
- **MCP／API**：每一次 tool call 或 request 算一筆，**讀取與寫入都算**。讀取事件記目標與列表筆數，不記內容。
- **自動儲存**：每次存檔都記（本來就會產生一個版本），查詢介面再把同一人、同一目標、短時間內的連續更新合併顯示。
- **排程**：一次排程執行記一筆 `system` 事件（例如「清除 12 筆逾期記憶草稿」），不逐筆記。

### 一定要記的操作

| 類別 | action 範例 | 備註 |
|---|---|---|
| 專案 | `project.create`、`project.update`、`project.delete`、`project.visibility.change`、`project.share_token.regenerate` | `update` 記每個變動欄位的前後值 |
| 作品／冊 | `story.create`、`story.update`、`story.delete`、`story.move`、`story.revert`、`volume.*`、`volume.reorder` | 內文只記 version ID，不記全文 |
| 設定／設定集 | `lore.*`、`lore_collection.*`、`lore_chapter.*` | 同上 |
| 資產 | `asset.upload.confirm`、`asset.replace.confirm`、`asset.update`、`asset.move`、`asset.delete`、`asset_collection.*` | presign（產生上傳網址）不記，確認上傳才記 |
| AI 助理 | `agent.run`、`agent.resend`、`agent.proposal.apply`、`agent.proposal.reject` | 記 chat ID、provider、model、token 用量；不記 prompt 全文 |
| 梭梭記憶 | `memory.draft.generate`、`memory.confirm`、`memory.update`、`memory.delete`、`memory.draft.discard` | |
| 帳號與憑證 | `auth.login`、`auth.login.failed`、`auth.logout`、`pat.create`、`pat.revoke`、`provider_key.create`、`provider_key.update`、`provider_key.delete` | 憑證只記 public ID 或末四碼，不記本體 |
| 個人資料與設定 | `profile.update`、`author_profile.*`、`agent_skill.*`（自訂 Skill） | |
| 社交與收藏 | `favorite.add`、`favorite.remove`、`bookmark.*` | 低重要度，查詢時預設收合 |
| PAT 讀取（MCP／API） | `project.read`、`story.read`、`story.list`、`lore.read`、`asset.read`、`memory.list`、`memory.search` 等，對應每個讀取類 tool | 只在 `auth_method=pat` 時記；記目標、列表筆數，不記內容；低重要度，查詢時預設收合，可依 PAT 篩選 |
| 系統 | `system.memory_draft.cleanup`、`system.audit.export` 等排程 | `actor_type=system` |

### 不記的操作

| 類別 | 範例 | 理由 |
|---|---|---|
| Web 讀取 | 列表、詳情、預覽、閱讀頁（session 登入） | 使用者本人看自己的資料，量大、價值低 |
| AI 助理的唯讀工具 | 梭梭在對話中呼叫的 `get_*`／`list_*` | 對話本身已有 `agent.run` 紀錄 |
| 匿名閱讀 | 讀者閱讀公開或分享的作品 | 屬於流量統計，不是稽核 |
| 輪詢 | AI chat 狀態、記憶草稿狀態、封存查詢狀態 | 沒有副作用 |
| Web 搜尋 | 工作台搜尋 | 同 Web 讀取 |
| 準備動作 | presign 上傳／更換網址 | 沒有實際寫入，確認時才記 |
| 介面暫存 | 閱讀進度、面板開合、編輯器版面 | 屬於 UI 偏好，不是使用者資料 |

### Outcome 定義

| outcome | 意義 | 範例 |
|---|---|---|
| `success` | 操作完成並已 commit | |
| `denied` | 身分或權限檢查沒過 | 無效 PAT、存取別人的專案、登入失敗 |
| `failed` | 通過權限檢查，但操作本身失敗 | 驗證錯誤、衝突、provider 失敗、DB 錯誤 |

`denied`／`failed` 只記錯誤代碼與訊息類別，不記請求內容。

### 覆蓋率保證

- 所有 action 集中定義在一個 registry。
- 規則：`POST`／`PUT`／`PATCH`／`DELETE` 的 route 與**所有** MCP tool（含讀取類）**必須**對應到一個 action；Web 的 `GET` 不得改資料。例外（例如 presign 用 `POST` 但不記）必須在 registry 裡明確標示為 exempt。之後的公開 API 也適用「所有 endpoint 都要對應 action」。
- 開發環境啟動時比對 route／tool 清單與 registry，有未對應的就警告。

## 入口與身分識別

| 欄位 | 值 | 判斷方式 |
|---|---|---|
| `source` | `web` | 走 session 驗證的 `/storyteller/*` route |
| | `api` | 預留給未來以 PAT 呼叫的公開 REST API |
| | `mcp` | `/mcp` endpoint |
| | `cron` | 排程 |
| `auth_method` | `session`、`pat`、`none` | 由驗證 middleware 寫入 context |
| `credential_ref` | PAT 的 public ID | 只有 `auth_method=pat` 時有值 |
| `ip` | 用戶端 IP | 見下方注意事項 |
| `user_agent` | 截斷到 255 字 | MCP client 通常會帶自己的名稱，可分辨是哪個 AI 工具 |

AI 助理在 Web 上執行，入口仍是 `source=web`，由 action（`agent.*`）與 summary 裡的 chat ID 區分；外部 AI 透過 MCP 操作則是 `source=mcp`。

**取得用戶端 IP**：backend 只聽 `127.0.0.1`，前面唯一一層是 nginx。目前 Fiber 沒設定 proxy header，`ctx.IP()` 拿到的永遠是 `127.0.0.1`。

- **不用 `X-Forwarded-For`**：nginx 用的是 `$proxy_add_x_forwarded_for`，會把用戶端自己帶的值保留在前面、再接上真實 IP；Fiber 取 header 時拿的是第一個值，等於讓使用者自填 IP。
- **改用 `X-Real-IP`**：nginx 設成 `$remote_addr`，一律覆蓋用戶端帶來的值，無法偽造。Fiber 設定 `ProxyHeader: "X-Real-IP"`，並啟用 trusted proxy、只信任 loopback（`127.0.0.1`、`::1`），避免繞過 nginx 直連時被偽造。
- **nginx 要補設定**：`/api-integration/` 已經有 `X-Real-IP`，但 steamloom 的 `/mcp` 以及其他轉給 backend 的 location 沒有，要補上 `proxy_set_header X-Real-IP $remote_addr;`。

另外兩張輔助表：

- `storyteller_audit_exports`：每月匯出紀錄（月份、狀態、S3 key、筆數、checksum）。**MySQL 只刪除已確認匯出成功的月份。**
- `storyteller_audit_archive_queries`：封存查詢 job（使用者、條件、Athena execution ID、狀態）。前端只拿得到自己的 job，不能直接用 execution ID 查別人的結果。

## 寫入 pipeline（不綁業務交易，可 retry）

```text
service commit 成功
  → 組好事件（含前後值、context 裡的 actor／IP／UA）
  → XADD 到 Redis Stream `storyteller:audit:events`
        │
        ▼
audit writer（backend 內的背景 goroutine，consumer group）
  → XREADGROUP 批次取出（例如一次 100 筆）
  → INSERT IGNORE 批次寫入 MySQL
  → 成功就 XACK
  → 失敗不 ack，由 XAUTOCLAIM 重新認領 retry（指數退避）
  → 同一筆送達超過 N 次 → 移到 dead-letter stream，記 ERROR log
```

- **為什麼用 Redis Stream**：已經有 Redis；Stream 內建 pending list、送達次數與重新認領，不用自己寫 retry 狀態機；backend 重啟後尚未寫入的事件還在。
- **at-least-once**：同一筆可能送兩次，靠 `event_id` UNIQUE 加 `INSERT IGNORE` 去重。
- **前後值**：必須在 commit 前讀好，commit 成功後才送出事件；commit 失敗就改送 `failed` 事件，不會出現「沒發生的操作卻有 success 紀錄」。
- **Redis 寫不進去**：短暫 retry；仍失敗就直接寫 MySQL；再失敗就把完整事件 JSON 寫進 ERROR log（ELK 裡可以撈回來補寫）。
- **graceful shutdown**：沿用既有的 background work tracker，關機前把手上的批次處理完。
- **已接受的風險**：commit 成功後、送出事件前如果 process 剛好 crash，這一筆會遺失。這是「不綁交易」的代價；要完全不漏就得改用 transactional outbox（事件跟業務寫在同一個交易），這次先不做。

## 冷熱分離：MySQL 近 3 個月＋Athena 封存

| | 近期（預設） | 封存查詢 |
|---|---|---|
| 時間範圍 | 近 3 個月 | 3 個月以前 |
| 資料來源 | MySQL | S3（JSONL.gz）＋ Athena |
| 互動 | 即時列表、篩選、分頁 | 送出 → 背景執行 → 輪詢 → 顯示結果並可分頁 |
| 必要條件 | 無 | 必須指定月份範圍（控制掃描量與費用） |

- **切界規則**：查詢範圍只要包含 3 個月以前，介面就引導改用封存查詢，不自動拆成兩段合併。
- **月匯出**（排程）：每月月初把上個月匯出到 `s3://<bucket>/audit/year=YYYY/month=MM/part-NNNNN.jsonl.gz`。檔名固定，重跑會覆蓋，可以安全重試。完成後寫入 `storyteller_audit_exports` 並比對筆數。
- **清除**（排程）：只刪「超過 3 個月」而且「該月已確認匯出」的資料，所以最近 3 個月在兩邊都有，切界不會有空窗。
- **Athena**：
  - 用 partition projection，不需要 Glue crawler。
  - Workgroup 設定單次掃描上限，查詢結果放在另一個 bucket，並設 7 天過期。
  - 後端用 `ExecutionParameters` 帶參數，不拼接字串；`project_id`／`actor_user_id` 等條件由後端依登入者強制加上。
- **S3 bucket 與 Object Lock**：
  - Object Lock 本身**不另外收費**，費用只有儲存量；資料本來就要保存 N 年，所以不會因此多付錢。
  - 唯一的額外儲存：Object Lock 必須搭配 versioning，匯出重跑時覆蓋同一個檔名會留下舊版本，而且舊版本在保存期內刪不掉。只有匯出失敗重跑時才會發生，量很小。
  - 用 **governance mode**：有特定 IAM 權限的人仍可解除，萬一匯出錯誤還能清掉。不用 compliance mode，因為那種連 root 帳號都刪不掉，設錯就收不回來。
  - Storage class 用 **S3 Standard-IA**（或 Glacier Instant Retrieval）比 Standard 便宜，Athena 仍可直接查；**不要用 Glacier Flexible Retrieval 或 Deep Archive**，Athena 查不到。

### 封存保存期限（N 年後刪除）

保存期限由**應用程式設定**決定，backend 自己上鎖、到期自己刪除，而不是在 S3 console 另外設一套 lifecycle。這樣只有一個設定來源，刪除動作本身也會留下稽核紀錄，符合法遵需要。

| 設定（環境變數） | 預設 | 用途 |
|---|---|---|
| `AUDIT_HOT_RETENTION_MONTHS` | `3` | MySQL 保留月數 |
| `AUDIT_ARCHIVE_RETENTION_YEARS` | `7` | S3 封存保存年數 N |

流程：

1. **匯出時上鎖**：每個檔案上傳時帶 per-object retention，`retain-until` =「該月月底 + N 年」（governance mode）。在這個日期之前，沒有特殊權限的人（包含 backend 自己）都刪不掉。
2. **到期刪除**（每月排程）：找出「月底 + N 年」已經過去的月份，刪除該 prefix 下的**所有版本**（含匯出重跑留下的舊版本），確保真的從 S3 消失，不是只留一個 delete marker。
3. **刪除也要稽核**：每刪除一個月份，記一筆 `system.audit.archive.purge` 事件（月份、刪除的檔案數），並把 `storyteller_audit_exports` 該月狀態改成 `purged`、寫入 `purged_at`。匯出紀錄表本身很小，永久保留，之後可以證明「哪個月的資料在什麼時候依政策刪除」。
4. **Athena**：已刪除的月份查詢時直接回空結果；封存查詢介面依 `storyteller_audit_exports` 標示「此月份已超過保存期限並已刪除」。

**N 之後要改怎麼辦**：

- **延長**（例如 5 年改 7 年）：新匯出的檔案直接用新的 N。已存在的檔案用一次性維護指令延長 retention（governance mode 隨時可以延長）。
- **縮短**（例如 7 年改 5 年）：新匯出的檔案用新的 N。已存在的檔案維持原本的 retention，刪除排程會跳過還在鎖定期內的檔案，**不會自動提前刪除**。真的要提前刪，得用具備 `s3:BypassGovernanceRetention` 權限的帳號另外執行維護指令，這個權限不給 backend 平常使用的 IAM role。

**成本**：

- Standard-IA 每個檔案最少以 128KB、30 天計費；每月一個（或少數幾個）檔案的規模，這個限制可以忽略。
- 到期就刪，儲存量會穩定在「N 年份」的上限，不會無限增長。

**IAM 權限切分**：

- backend 平常用的 role：`s3:PutObject`、`s3:PutObjectRetention`、`s3:ListBucketVersions`、`s3:DeleteObjectVersion`、`s3:GetObject`，以及 Athena 查詢需要的權限。**沒有** `s3:BypassGovernanceRetention`，所以鎖定期內一定刪不掉。
- 另外一個只給維護用的 role 才有 bypass 權限。

## 查詢介面（需先出 mockup 確認）

- **專案稽核頁**（專案 owner 可見）：時間軸列表，可依操作者、類別、入口、結果、時間篩選，點進去看欄位差異；近期／封存兩種模式。
- **帳號活動頁**（本人可見）：登入、PAT、API key、個人資料等帳號層事件，含 IP 與 User-Agent。
- 協作者能不能看專案稽核，等 RBAC 讀取權限定案再說（事件可能洩漏他無權讀取的子資源名稱）。

## User stories

1. 專案 owner 發現設定被改了，想知道是誰、什麼時候、從 MCP 還是網頁改的，以及改之前的值。
2. 使用者懷疑 PAT 外洩，想看這支 PAT 最近從哪些 IP、用什麼工具**讀了哪些資料**、做過哪些修改。
3. 梭梭（AI 助理）套用了一個提案，使用者想回頭確認是哪一輪對話、改了哪篇。
4. 有人嘗試存取無權限的專案，owner 能看到被拒絕的紀錄。
5. 使用者想查半年前某篇故事是誰刪的，改用封存查詢找到紀錄。

## 常見失敗與應對

| 情境 | 應對 |
|---|---|
| Redis 暫時不可用 | 送出端 retry → 直接寫 MySQL → 寫 ERROR log，三層保底 |
| MySQL 寫入失敗 | 不 ack，retry；超過次數進 dead-letter，並記 ERROR log |
| 重複寫入 | `event_id` UNIQUE 加 `INSERT IGNORE` |
| 事件寫入延遲 | 通常只延遲數秒；查詢頁註明「最近幾秒的事件可能尚未出現」 |
| summary 誤帶敏感欄位 | allowlist；新欄位預設不記 |
| IP 被偽造 | 只讀 nginx 覆蓋過的 `X-Real-IP`，且只信任 loopback 來源 |
| 月匯出失敗或筆數不符 | 不刪 MySQL 資料，下次排程重試；記 ERROR log |
| Athena 查詢過大或逾時 | 強制月份範圍，workgroup 掃描上限；job 標示失敗並回報原因 |
| PAT 讀取事件量暴增（例如 AI 工具大量 `list_*`） | 第一版照實記錄；真的過量再改成「同一 PAT、同一目標、1 分鐘內合併一筆」並在 summary 記次數 |
| 到期刪除失敗 | 不改 `storyteller_audit_exports` 狀態，下次排程重試；記 ERROR log |
| 誤把 N 設太短 | 已上傳的檔案仍受原本的 retention 保護，不會被提前刪除 |
| 專案或使用者被刪 | 沒有 FK，紀錄保留；介面顯示「已刪除的專案／使用者」 |

## 預計影響檔案

- `migration/`：`storyteller_audit_events`、`storyteller_audit_exports`、`storyteller_audit_archive_queries`
- `model/entity/storyteller/`：audit entity、action registry 常數；`rbac.go` 內 `ProjectAudit*` 加上 Deprecated 註解
- `middleware/`：request context（request_id、source、auth_method、credential_ref、IP、UA）；`authsession`、`storytellerpat` 寫入 auth 資訊
- `main.go`：`ProxyHeader: "X-Real-IP"`＋只信任 loopback；啟動 audit writer
- `httpd_conf/nginx`：所有轉給 backend 的 location 補 `X-Real-IP`（部署由使用者處理）
- `config/`：`AUDIT_HOT_RETENTION_MONTHS`、`AUDIT_ARCHIVE_RETENTION_YEARS`、S3 bucket 與 Athena 相關設定
- `cronjobs.go`：月匯出、MySQL 清除、S3 到期刪除
- `repository/storyteller/`：audit 批次寫入、查詢、匯出紀錄、封存查詢 job
- `service/storyteller/`：`audit*.go`（事件組裝、Redis Stream producer／consumer、summary allowlist、Athena client），並在既有各寫入 service 補呼叫
- `service/mcp`：標記 `source=mcp`
- `controller/`、`route/`：稽核查詢 API（近期、封存 job 建立／輪詢／結果）
- `static_site/`：專案稽核頁、帳號活動頁（先出 mockup）
- 基礎設施（使用者自行處理）：S3 bucket（versioning＋Object Lock governance、Standard-IA）、Athena workgroup 與結果 bucket、IAM 權限

## 分階段

1. **P1**：資料表、request context、trusted proxy、Redis Stream pipeline、action registry；專案與內容類寫入（Web＋MCP），以及 MCP 讀取類 tool（在 tool registry 統一掛勾，只在 `auth_method=pat` 時記，AI 助理走同一批 tool 也不會誤記）。
2. **P2**：帳號與憑證、AI 助理、梭梭記憶、社交收藏、`denied`／`failed` 事件、排程事件。
3. **P3**：近期查詢 API 與前端頁面（先出 mockup）。
4. **P4**：月匯出（含 per-object retention）、MySQL 清除、S3 到期刪除、Athena 封存查詢與前端封存模式。

## 待決與延後事項

規格面已無待決項目。以下是刻意延後、不在這一輪處理的：

- **協作者能否查看專案稽核**：等 RBAC 讀取權限定案。
- **`storyteller_project_audits` 清除**：RBAC 收尾時另開 migration。
- **Transactional outbox**：目前接受「commit 後、送出事件前 crash 會漏一筆」；若之後要求零遺漏再改。
- **帳號刪除與稽核保存的關係**：刪除帳號功能尚未實作；屆時需決定該帳號的稽核紀錄（含 IP）是保存到 N 年期滿，還是提前匿名化。

## 附錄：為什麼不用 S3 Vectors 存稽核

| 需求 | 稽核的實際需要 | S3 Vectors 的行為 |
|---|---|---|
| 查詢方式 | 精確條件，依時間排序、分頁 | embedding 近似最近鄰（topK），沒有排序與 offset 分頁 |
| 完整性 | 一筆不漏 | 帶 filter 時結果可能少於 topK，不保證列全 |
| 寫入成本 | 每次操作寫一列 | 每筆都要先呼叫 embedding 模型，內容也會送到 embedding provider |

S3 Vectors 比較適合梭梭記憶／Lore 的語意檢索，另案評估。
