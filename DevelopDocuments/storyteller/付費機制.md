# 付費機制（初步調查與規劃）

## 目的

分冊功能上線後，故事跟冊已經是各自獨立、有身份（`public_id`）的內容單位，可以拿來當販售的最小單位。這份文件先整理金流商調查結果跟幾個核心問題的初步方向，細節（費率、拆帳比例的實際數字、退費政策文字）還沒定案。

**這份文件不是法律／稅務意見，金流商申請條件、費率、稅務規定都可能隨時間變動，實際申請與拆帳架構落地前務必直接跟金流商業務窗口、記帳士／會計師確認一次。**

## 你列的五個問題，先給初步方向

### 1. 金流商選擇

調查了台灣目前主流的幾家（綠界 ECPay、藍新 NewebPay、TapPay），重點發現：

- **個人（無公司行號）都能申請，但額度與功能有限**：
  - 綠界「個人會員」：信用卡＋非信用卡＋物流貨到付款的收款額度**共 30 萬／月**，免年費／設定費，身分驗證（身分證／居留證）約 2-3 個工作天。
  - 藍新「一般會員」只有提領／轉帳功能，要用到線上金流至少要到「進階會員」；「商務會員」才能到年費 $18,000＋保證金 $30,000 這個等級（明顯是給有一定規模的公司用的，個人不必考慮）。
  - 結論：**個人身份下，綠界的個人會員是目前最直接能用、成本最低的選擇。**

- **⚠️ 關鍵限制：海外信用卡（港澳中星的卡）綠界個人會員刷不了**——綠界已於 2023-01-01 起，停止對個人／商務會員開放海外信用卡交易，海外卡收單目前只開放給「特約會員」（通常要有公司/行號登記）。也就是說：**如果現在維持個人身份，實務上只能收台灣本地發卡的信用卡，港澳中星的用戶如果是用當地發卡行的卡，很可能刷不過。**這點直接衝擊你「目標用戶可能包含港澳中星」的設定，需要三選一：
  1. 先只做台灣本地市場，海外之後有量了再登記行號、升級特約會員解鎖海外收單。
  2. 現在就去登記個人工作室／行號，直接用能收海外卡的方案起步。
  3. 台灣本地用綠界／藍新個人會員，海外訂單另外接一個能收外卡的管道（例如 PayPal——個人也能申請商業帳戶，海外收款是強項，但費率通常比本地金流商高、且提現到台灣銀行帳戶會有換匯成本）。

- **拆帳／分潤（marketplace 那種「一筆錢自動分兩份」的功能）**：查到綠界有在推「創作者金流平台」，方向上是對的，但**沒有查到公開、明確的自動分潤 API 規格**，需要直接找綠界業務窗口問清楚實際支援到什麼程度（是自動即時分帳，還是本質上還是要平台自己批次撥款給創作者）。**保守起見，先假設要走「平台全額代收 → 自己批次撥款給創作者」這條路**（見下方「拆帳」小節），不要一開始就設計成依賴金流商自動分帳，免得那個功能查證後發現不到位、整個結帳流程要重做。

### 2. 租賃 vs 買斷

這件事**跟金流商本身關係不大，是你自己後端的存取權限邏輯**：不管租賃還是買斷，對金流商來說都只是「使用者付了一筆錢」的一次性交易（不需要訂閱／定期定額功能）。差別在於你自己資料庫裡怎麼記這筆購買：

- 一張「購買紀錄」表，記錄 `user_id`、購買的目標（`story_id` 或 `volume_id`）、購買類型（`rental` / `purchase`）、`expires_at`（買斷是 `NULL`，租賃故事填「付款時間 +3 天」、租賃冊填「+7 天」）。
- 判斷使用者能不能看某篇內容，就是查這張表有沒有一筆「未過期或永久」的紀錄。
- 好處：金流商只要能處理「一次性刷卡」就夠了，不用挑支援訂閱制的方案，選擇範圍變大很多。

### 3. 與創作者拆帳（平台抽成 ≤30%）

技術上不難（購買紀錄多記一個「這筆錢裡創作者拿多少、平台拿多少」的欄位），**但這裡有稅務上要注意的地方**：

- 查了「代收轉付」的規定：如果收款跟轉付之間**完全沒有差額**（單純幫忙轉手，一毛不留），可以不用另外開發票、也不列入自己的銷售額。但你這裡明確是要抽成（平台留一部分），**這就不是零差額的代收轉付了，平台抽走的那部分（≤30%）本質上是你的營業收入**，跟單純代收轉付的稅務處理不一樣。
- 換句話說：轉給創作者的那 70%+ 或許還能討論要不要走代收轉付邏輯處理，但**你自己抽成的那部分，八九不離十是要繳稅的所得**，達到一定規模可能會被要求辦理商業登記。這塊務必找記帳士確認一次，不要用「反正是幫創作者代收」當作可以完全不用管稅務的理由。
- 拆帳比例本身（平台不高於 30%）先記錄下來當產品邏輯的參數，之後跟創作者的合約條款要不要寫死在系統裡（例如允許未來針對不同創作者談不同比例）也是待確認事項。

### 4. 退費

還沒定案，但先列出租賃／買斷分開想的理由：

- **買斷**：通常要看使用者有沒有開始「消費」內容（例如已經讀超過一定比例、或已經下載/看過）。如果金流商本身有退款期限（多數是原路刷退，有些會限定在一定天數內才能退），你的退費政策不能超過金流商能實際執行退款的期限。
- **租賃**：因為本來就是短天期的存取權，是否要允許退費、退多少（是否按已使用天數比例退）需要另外設計規則，不建議照搬買斷的退費邏輯。
- 待確認：退費要不要有審核（客服人工判斷），還是符合條件（例如購買後 24 小時內、完全沒開始閱讀）就自動退。

### 5. 金流資料不能只限 `storyteller` 內

同意這個方向。實作上建議：

- 金流相關的資料表（購買紀錄、金流商 callback 記錄、退款記錄、對創作者的撥款紀錄）**不要建在 `storyteller_` 前綴底下**，另開一個共用的 domain（例如 `payment_` 前綴，或獨立成 `service/payment`、`repository/payment` 這種跟現有 `service/storyteller`、`service/auth` 平行的套件）。
- `storyteller` 這邊只需要存「這篇故事／這一冊賣多少錢、可不可以租」這種內容端的設定，實際的訂單／付款／撥款邏輯走共用金流模組，透過「這是哪個 domain 的哪個資源」這種通用欄位（例如 `product_type`、`product_id`）掛勾，不要讓金流模組直接寫死認識 `storyteller_stories`／`storyteller_lores` 這種表。這樣以後其他側專案要收費，直接接同一套金流模組就好。

## 延伸的付費模式：創作者包養與專案會籍

除了單篇故事／單冊的買斷／租賃，還在考慮兩種模式，性質跟上面完全不同，分開記錄：

### 創作者包養（訂閱制，掛在創作者身上）

跟單篇買斷/租賃是不同性質的東西——**包養是週期性訂閱（例如月費），沒有明確終點，取消才停止**，不是「付一次、到期就斷」。目前確認的方向跟 perk：

- **掛在「創作者」本人身上，不是掛在某個專案底下**——理由是故事系列不知道何時完結，讓讀者對單一專案開放式訂閱，時限模糊，不合理（這也是下面「會籍」要用固定期限、不做開放式訂閱的原因）。
- Perk（依你說的優先順序）：
  1. **新作品買斷／租賃打折**（優先做）
  2. 限定包養者閱讀作品（可能做）
  3. 新作優先看（不一定做）
- **跟創作者檔案（多重筆名）那份文件有依賴關係**：現在 storyteller 的「作者」就是 `user_id`，包養可以先直接掛在 `user_id` 上。但如果之後真的做了多重筆名，「包養一個人」還是「包養一個筆名身份」就要跟那份文件的決定同步——例如讀者包養的是「Faryne with Claude」這個 AI 共創身份，不代表也想看「Faryne」的個人創作，兩者若走不同筆名，包養的範圍語意就會不一樣。這裡先不用解決，等多重筆名定案了再回頭確認要不要遷移。
- 三個 perk 各自需要的實作方向：
  - **折扣**：結帳單篇買斷／租賃時，檢查使用者對該作品作者是否有有效包養，套用折扣百分比。
  - **限定包養者閱讀**：`Story`／`Lore`（或冊）需要一個「僅包養者可讀」的旗標，這跟「用錢解鎖付費牆」不一樣——標了這個旗標的內容，**不開放任何形式的單獨買斷／租賃**，只有有效包養才能看。
  - **新作優先看**：內容需要一個「正式公開時間」欄位，包養者可以在公開時間之前先看到已經寫完、但還沒對外公開的內容。
- 訂閱制需要金流商支援定期定額扣款，這是你要另外處理的收單規格範圍，這裡不重複。

### 參考業界前例：pixivFANBOX 與 Fantia

這兩個是同性質服務裡經營最久的兩家，剛好代表兩種不同哲學，對「限定包養者可讀的內容，到底要不要永久限定」這個問題很有參考價值：

- **pixivFANBOX**：支援者現在開始包養，**可以回溯看到這個創作者過去所有的限定內容**（不是只有訂閱之後才發的新文才看得到）。哲學是「你現在是支持者，就把整個倉庫打開給你」，早期內容不會另外拿出來賣。
- **Fantia**：走「月結」制——支援通常只涵蓋**當月**發的限定內容，過去的月份如果想看，創作者可以把它們包裝成「**バックナンバー（過期號）**」**另外單獨賣**，性質上就是一般的單篇購買，跟當月的訂閱權益脫鉤。除此之外 Fantia 本來就同時支援「訂閱方案」＋「單篇下載／商品購買」並存，不是只能二選一。

**這正好解答了前面「僅包養者可讀是永久限定、還是之後開放」的懸而未決**：Fantia 的做法（限定內容過了「當期」就自動變成可以單獨買斷的一般商品）技術上就是幫「僅包養者可讀」多加一個**「限定到期時間」欄位**——時間到了之前，只認包養；時間到了之後，自動變成可以走一般買斷／租賃的內容，不用另外寫特殊邏輯，判斷邏輯本身沒變，只是這個旗標從「永久 true」改成「到某個時間點前是 true」。我會建議採用 Fantia 這種「限時獨佔、之後開放」的做法，比照你原本文件裡「新作優先看」的精神是一致的（早看的人是用時間換取特權，而不是永久排除其他讀者），也比 FANBOX 的「永久只給包養者」更容易讓內容之後還能靠買斷/會籍持續變現。

另外兩家都是**多級距方案**（FANBOX 100~10,000 日圓、Fantia 從 100 日圓起，都是創作者自己訂價、訂多級），不是只有一種包養價格。你列的三個 perk（折扣／限定內容／搶先看）很適合直接對應成 2-3 個級距（例如低價位只有折扣、中價位加限定內容、高價位再加搶先看），而不是綁死一口價的單一方案——這樣也比較貼近你原本「折扣優先做、其他不一定」的優先順序，可以讓低價位先上，之後再逐步開放更高級距的 perk。

### 專案會籍（固定期限的「全讀通行證」，不是訂閱）

你提到的顧慮很合理：故事系列不知道什麼時候結束，讓讀者對單一專案開放式訂閱、不知道要付到什麼時候，體驗不好。你想到的方案是**固定期限（3 個月／6 個月／1 年）、一次性收費、期限內可以看這個專案底下的所有故事／冊**，到期後不自動續訂。

這個設計有個好消息：**技術上完全不需要新的付款機制**，跟現有「買斷／租賃」的資料模型（一次性收款 + `expires_at`）是同一套，只是多一種 `product_type = project`、期限選項變成月／年而不是天。金流商只要能處理單次刷卡就夠，不需要訂閱扣款支援，這點比包養簡單很多。

到期後預設直接失效，使用者要繼續看就重買一次；要不要加「自動續訂」的選項，先當成之後可以加的功能，不是第一版必要的。

### 存取判斷需要整合四種授權來源

有了包養跟會籍之後，判斷「這個使用者能不能看這篇故事／這一冊」要合併檢查：

1. 這篇／這冊本身有沒有被買斷（永久）
2. 這篇／這冊本身有沒有在租賃期限內
3. 使用者有沒有涵蓋這個專案、還在期限內的會籍
4. 這篇／這冊有沒有標「僅包養者可讀」，使用者對該作者有沒有有效包養

判斷順序：**先看內容有沒有標「僅包養者可讀」**——有的話只認第 4 種授權，1／2／3 都不適用（不能單獨買斷或租賃，也不算在會籍「全讀」的範圍內）；沒有標的話，再依序檢查 1／2／3，任一種有效就能看。

## 待確認事項（先列出來，之後陸續定案）

- 個人身份先上線只做台灣本地，還是現在就要處理海外收單（登記行號／改用 PayPal 等）？這個決定會影響整個金流商選型，優先順序最高。
- 拆帳的稅務／商業登記問題要不要先找記帳士諮詢過一輪，再往下設計金流模組的資料表？
- 拆帳比例要不要做成可設定（每個創作者可能不同），還是先寫死一個全站統一的比例？
- 撥款給創作者的頻率跟方式（月結？創作者自己申請提領？最低提領金額？）
- 退費的審核流程（人工／自動）與租賃內容的退費規則
- 買斷後内容如果之後被作者下架／刪除，已購買的讀者權益怎麼處理？
- 金流模組要不要現在就先抽出來（哪怕暫時只有 storyteller 一個呼叫端），還是先做在 storyteller 裡面、等真的有第二個呼叫端再抽？
- 包養要掛在帳號（`user_id`）還是掛在筆名身份？現在可以先掛帳號，但要記得跟創作者檔案（多重筆名）那份文件的決定同步
- 「僅包養者可讀」建議參考 Fantia 做法，改成「限時獨佔、時間到自動開放買斷／租賃」（見上方「參考業界前例」），而不是永久限定——但要不要真的採用、限時多久，還是你決定
- 包養要不要做成多級距方案（比照 FANBOX／Fantia，例如低價位只有折扣、中價位加限定內容、高價位再加搶先看），還是先做單一固定方案就好
- 會籍到期後要不要提供自動續訂？包養跟會籍能不能疊加折扣（例如同時包養某作者、又買了他某個專案的會籍）？
- 包養／會籍的退款規則跟單篇買斷／租賃是不是要分開設計（例如包養取消是否退當月剩餘天數）

## 影響範圍（初步預估，待細節定案後展開）

- **新的共用模組**：`service/payment`、`repository/payment`、`model/entity/payment`（暫定），獨立於 `storyteller`；包養的訂閱扣款週期管理也會在這個模組裡
- **storyteller 這邊**：
  - `Story`／`Lore`（或未來的冊）需要加上「可否販售／租賃價格／買斷價格」「僅包養者可讀」「正式公開時間（給搶先看用）」等設定欄位
  - `Project` 需要能設定會籍的期限選項與價格
  - 閱讀頁需要依「買斷／租賃／會籍／包養」四種授權來源綜合判斷內容是否可見（見上方「存取判斷」小節）
- **後端**：金流商 callback／webhook 處理、購買紀錄、撥款批次作業、包養的訂閱狀態同步（續訂/取消）
- **前端**：購買/租賃/會籍/包養的付費流程 UI、創作者後台的收益/撥款畫面、包養方案設定介面（折扣％、要不要開限定內容／搶先看）
