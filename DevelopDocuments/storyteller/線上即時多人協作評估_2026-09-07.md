# 線上即時多人協作：可行性評估（純評估，不預期實作）

## 定位

這份文件**不是實作規格**，是回答「這個功能到底有多大、會撞到哪些牆」的評估文件。使用者已經預期這個功能很可能不會做，這裡的目的是把理由攤開來看，而不是規劃怎麼做。

## 現況調查結論：五個各自獨立、疊加起來的架構性障礙

### 1. 擁有權模型——整個資料模型寫死「一個 project 一個 user」

`ProjectByPublicIDForUser`（`repository/storyteller/storyteller.go:108-113`）直接 `WHERE user_id = ? AND public_id = ?`，沒有 membership/角色 join table。`storyteller_projects` 表本身只有一個 `user_id` 欄位（`model/entity/storyteller/storyteller.go:155`），Story/Lore/Asset/Volume 等子資源也都各自帶 `user_id`（`:210, :276, :293, :334, :486`）。

這不是權限檢查層的小改動，是**整條資料模型的外鍵設計**都假設單一擁有者。要做多人協作，等於要：
- 新增 project membership/role 表（誰被邀請進這個 project、什麼角色）。
- 把**現有所有** repository 查詢裡的 `user_id = ?` 改成「user_id 在 project members 名單內」——這條件遍布整個 storyteller 套件的每一支查詢函式，改動面極廣、極容易漏改導致權限漏洞。

### 2. 版本紀錄——只記錄「哪個管道存的」，不記錄「誰存的」

`StoryVersion`/`LoreVersion`（`model/entity/storyteller/storyteller.go:460-478`、`:538-552`）都有 `Source string` 欄位，但語意是傳輸管道標記（`"web"`、`"mcp:token label"`），**不是操作者 user_id**。`CreateStory(userID, ..., source string)` 這類函式簽章雖然有傳入 `userID`，但這個值目前完全沒有落地存進版本紀錄表——結構裡沒有 `AuthorUserID` 這種欄位（唯一例外是 `Asset` 有 `AuthorUserID`，`model/entity/storyteller/storyteller.go:648`）。

**這直接對應到你提的問題「版本歷史中又是誰搞出這個版本的」——現在完全沒有這個資料，要做就要先補 migration 加欄位、改所有寫入路徑帶進 user_id。**

### 3. 自動存檔機制——純輪詢，沒有任何即時通道

`StoryEditor.tsx:638-695` 的自動存檔是**元件本地** `setInterval` 定時打 REST API，單向、沒有 WebSocket/SSE/long-polling，完全不知道「別人剛剛存了什麼」。

**這直接對應到你提的問題「有人開有人沒開、頻率不同」的尷尬**——目前的機制本來就是為「同一時間只有自己在編輯」設計的，多人協作情境下：
- A 存檔的當下，B 完全不會被通知，B 背景繼續打字，等 B 自己的計時器觸發存檔時才會撞見樂觀鎖衝突（見第 5 點，現有機制是 last-write-wins，不會真的擋下寫入，代表 A 的內容可能被 B 的自動存檔悄悄蓋掉，沒有人會發現）。
- 就算兩人存檔頻率調成一樣，只要不是同一秒觸發，也還是會有其中一份被蓋掉的窗口。
- 要做到「即時反應」，本質上需要拋棄「定時整篇覆蓋存檔」這個模型，換成即時同步每個字元/段落層級的變更（見第 5 點）。

**這個 repo 目前沒有任何即時推播的基礎設施先例**——`project_storyteller_sse_deferred.md` 記錄過 2026-08-24 曾評估 AI 助理面板要不要做 SSE 即時推播（`AgentLoopRequest` 加 `OnStep` callback），但因為「AI 助理等待體感」跟「`make restart` 中斷復原」這兩個不同的理由暫緩，**跟這次多人協作是不同題目，但要解決的底層技術問題是同一塊**：要嘛先把 SSE/WebSocket 這條路重新撿起來，要嘛整個從零開始評估。

### 4. AI 助理面板——對話跟提案完全沒有「誰在跟 AI 講話」這個概念

`AgentProposal`（`model/entity/storyteller/storyteller.go:591-602`）欄位只有 `ChatID/ToolCallID/ToolName/Arguments/Status`；`StoryChatMessage`（`:606-622`）欄位是 `ChatID/AgentID/Role/Content/Metadata`——這裡的 `AgentID` 是「AI agent 設定（選了哪個 provider/model）」的 id，**不是操作者的 user id**。整條 chat → message → proposal 的資料鏈路都掛在 story/project 底下、靠 project 的擁有者 user_id 間接推導，沒有「project 內好幾個不同使用者，各自跟 AI 開對話」的資料位置。

**這直接對應到你提的三個問題**：
- 「必須明確標示是誰打的對話」：`StoryChatMessage` 要加 `user_id`。
- 「套用提案的人又是誰」：`AgentProposal` 要加 `AppliedByUserID`（現在只有 `Status` 標記 applied/rejected，不知道是誰按的）。
- 「版本歷史中又是誰搞出這個版本的」：跟第 2 點是同一個缺口——AI 幫某個使用者代寫、套用後產生的版本，也要能追溯回「這是哪個使用者透過 AI 產生的版本」。

### 5. 樂觀鎖粒度——整篇文章一次鎖，不是段落/字元級

`UpdateStoryWithVersion`（`repository/storyteller/storyteller.go:1493-1533`）用單一 `base_version_id` 比對整個 Story/Lore 的 `LatestVersionID`，衝突判定與寫入單位都是「整份 content 字串」。註解裡明講設計哲學：**「永遠會寫入，不會因版本衝突拒絕寫入」**——也就是 last-write-wins + 事後標記衝突（`version_conflict` 旗標），這在「單人、多分頁，衝突機率低且使用者自己能處理」的情境下夠用，但多人「即時互相看到對方打字」的體驗，本質上需要換成 **OT（Operational Transformation）或 CRDT（Conflict-free Replicated Data Type）**這類段落甚至字元級的合併機制——這是完全不同等級的技術棧，不是在現有樂觀鎖上加參數就能達到，現有機制沒有可以直接擴展的粒度基礎。

## 你還沒明確決定、但會大幅影響工程量的開放問題

- **權限精細度**：「加入專案就能改任何故事/設定」還是「每篇故事/設定各自可調權限」——後者等於要在第 1 點的 membership 表之外，再加一層「member × story/lore」的細粒度授權矩陣，工程量再往上一階。
- **AI 助理的對話要不要也即時同步**：如果 A 跟 AI 對話產生的提案，B 要不要即時看到、能不能由 B 來套用/否決 A 開的提案——這是「多人協作」延伸出的另一個子問題，沒有現成答案。
- **要不要做 presence（誰在線上、游標在哪）**：這是即時協作使用者體感的核心期待（Google Docs 式的「看到別人的游標」），但這是 CRDT/OT 機制之外**另一層獨立的即時狀態同步需求**，做跟不做都要明確決定。

## 額外的風險/複雜點（調查時沒直接問到，但推演會遇到）

- **PAT／MCP 存取權的邊界重新定義**：現有 `ScopeToolsToProject`（`agent_scope.go`）跟 PAT 都是綁在單一 user 上，多人共享 project 後，MCP client（PAT）要能操作「別人擁有、自己被邀請進去」的 project，整條 PAT 驗證鏈也要跟著改。
- **踢除協作者的資料歸屬問題**：某使用者被踢出 project 後，他之前寫的版本歷史／AI 對話紀錄要保留還是連坐處理，需要明確規則。
- **既有單一擁有者資料的遷移**：現有所有 project 都是單一 user_id，導入 membership 機制需要一次性把「擁有者」轉成 membership 表裡的 owner 角色，屬於一次性 migration，要注意不能動到既有資料。
- **成本／基礎設施**：即時推播（WebSocket/SSE）與 CRDT 同步伺服器（如果選擇伺服器端合併）會增加常駐連線與運算成本，這對目前的部署規模（單一 process、無專門即時層）是新的維運面向。
- **審計/信任問題**：多人共享寫入權限後，「誰不小心刪掉了誰的內容」變成需要明確可追溯的問題，現有 soft-delete 機制夠不夠用、要不要做操作歷史日誌（不只版本歷史，還包含刪除/搬移這類非內容變更的操作記錄）。

## 技術選型方向（僅供之後參考，這次不展開）

如果之後真的要做，CRDT 這條路業界常見的選擇是 Yjs 或 Automerge（都有 JS 生態圈，能跟現有 Tiptap/ProseMirror 前端銜接——Tiptap 官方甚至有 Yjs collaboration extension，這點是唯一對現有技術棧友善的地方）；OT 則通常需要自己維護 transform 邏輯或依賴 ShareDB 這類框架，跟現有全手寫的後端風格落差較大。這只是點出方向，不是這次評估要下的決定。

## 結論

五個障礙點疊加起來看，這不是「加一個功能」，而是同時要動：**（a）授權/資料擁有權模型重寫、（b）版本歷史與 AI 對話 schema 補欄位、（c）從零建置即時推播基礎設施、（d）编辑衝突機制換成 OT/CRDT 技術棧、（e）上述所有既有查詢邏輯的地毯式改動**。這五塊彼此獨立又互相依賴，任何一塊沒做好都會讓其他塊的體驗打折扣（例如即時推播做了但衝突機制還是 last-write-wins，使用者還是會看到內容被覆蓋）。

**目前沒有任何一塊有現成的地基可以直接沿用**（連唯一調查過的 SSE 都是「評估過但暫緩」，不是「做好可以撿」）。如果真的要做，建議不要想著一次做完整個即時協作，而是先把「多人共享 project 的授權模型」這個最底層、影響面最廣的部分獨立出來做（哪怕暫時不做即時同步，先讓多人可以「輪流」編輯同一個 project 也是一個獨立可交付的里程碑），驗證這塊資料模型改動穩定之後，才考慮要不要疊加即時同步層——不要一次性設計五塊全部到位的完整方案，那樣風險跟不確定性都太高，符合你原本「規模很大、很可能不會做」的判斷。
