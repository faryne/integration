| --- | --- | --- |

# 介面：Dialog 與看板娘整合

## 現況與問題

- 部分 Dialog 過度依賴水平線、外框與區塊邊界切割資訊，Title、Content、Actions 容易各自像一層獨立區塊，畫面偏硬。
- Storyteller 同時存在一般 `ConfirmNameDialog`、工作台版 `WorkspaceConfirmNameDialog` 與各頁面自行拼裝的 MUI Dialog，視覺與 spacing 不完全一致。
- 看板娘素材、appearance 切換與 CDN helper 已經存在；如果只把梭梭加進舊 Dialog，會像額外貼上的裝飾，沒有真正融入資訊層級。

## 已確認方向

這次不是「所有 Dialog 都加看板娘」，而是重新建立 Storyteller Dialog 的共用視覺系統，再依用途決定是否顯示梭梭。

### 1. 重大決策型 Dialog

適用情境：

- 刪除專案、故事、設定集、資產。
- 放棄尚未儲存的內容。
- 變更公開狀態、分享網址等影響外部讀者的設定。
- 專案建立、發布或其他值得明確回饋的成功狀態。
- AI 提案將覆蓋、搬移或刪除現有內容。

設計原則：

- Desktop 採左右配置：左側放 96～128px 梭梭，右側放標題、說明、輸入與 actions。
- Mobile 改為上下配置：上方放 72～88px 梭梭，下方維持完整操作空間。
- `DialogTitle`、`DialogContent`、`DialogActions` 之間不畫水平線，改用留白與 spacing 表達層級。
- 梭梭所在區域可以使用非常淡的 appearance gradient，但不再加一圈區塊 border。
- 危險操作只讓確認按鈕、警告圖示與少量關鍵文字使用 error color，不把整個 Dialog 染紅。
- 需要輸入名稱的刪除確認仍保留，但文案只說一次，避免 description、label、helper text 重複表達同一件事。

Dialog 使用獨立狀態圖，不與既有通用 pose 混用：

| 語意 | Dialog state |
| --- | --- |
| 一般重要提醒 | `neutral` |
| 危險／刪除 | `danger` |
| 成功完成 | `success` |
| AI 或較長時間處理中 | `thinking` |

`error` 保留給真正執行失敗的狀態；不可逆操作使用冷靜制止的 `danger`，不再用困擾或線打結的失敗表情代替。

### 2. 一般操作型 Dialog

適用重新命名、建立分類、編輯書籤、插入連結／腳注、選擇冊別等高頻操作。

- 不放梭梭，避免角色過度曝光後失去提醒效果。
- 套用相同的圓角、陰影、padding、按鈕排列與 backdrop。
- 一樣以留白取代不必要的 Title／Content／Actions 分隔線。

### 3. 內容工具型 Dialog

適用版本比對、資產選擇器、長清單、歷史紀錄與表格。

- 不放梭梭，讓空間保留給內容本身。
- 可以保留 sticky header 下方或資料區邊界的一條結構線。
- 不讓 Title、Toolbar、Content、Footer 每一層都各有一條線。

## 共用元件規劃

新增 Storyteller 專用元件，不修改成全站看板娘版，避免影響 Storyteller 以外功能：

```tsx
<StorytellerDialog>...</StorytellerDialog>

<StorytellerMascotDialog
  tone="danger"
  state="danger"
  title="刪除這個專案？"
  description="刪除後將無法從工作台開啟。"
  actions={...}
/>
```

- `StorytellerDialog`：統一 Paper、Backdrop、spacing、responsive layout 與 actions。
- `StorytellerMascotDialog`：在基礎 Dialog 上增加角色區、tone 與 pose。
- 全站共用 `components/common/ConfirmNameDialog.tsx` 保持中性；Storyteller 以 wrapper 或專屬元件承接。
- 收斂 `ProjectWorkspacePreviewDialogStyles.ts` 與 `WorkspaceConfirmNameDialog` 的重複樣式。

## Mockup 與首批導入範圍

正式改現有頁面前，先用三種代表情境做可互動前端 mockup：

1. 刪除專案：梭梭＋輸入名稱確認。
2. 專案建立成功：梭梭＋「建立第一篇故事／回專案首頁」。
3. 一般重新命名：沒有梭梭的輕量 Dialog。

確認 Desktop、Mobile 與三套 appearance 後，再先導入：

- 專案刪除確認。
- 工作台未儲存變更提醒。
- 專案建立成功。

首批完成後再逐步替換其餘 Storyteller Dialog，不一次大改所有頁面。

## 驗收條件

- 三個代表情境可在 Desktop／Mobile 與 Nocturne、Ivory、Prism 下正確顯示、操作，沒有內容溢出。
- `danger`、`success`、`thinking`、`neutral` 各有 Dialog 專用 SD 圖；三套 appearance、三種尺寸皆可由 CDN 取得並具有透明背景。
- Major Dialog 不在 title、content、actions 之間畫水平線；內容工具只保留資料結構必要的分隔線。
- Mascot 只出現在重大決策、重要成功或長時間處理；重新命名等高頻操作不顯示角色。
- Desktop 使用左右配置、Mobile 使用上下配置，輸入與 actions 不因 mascot 被過度壓縮。
- 危險操作只用少量 error color；名稱確認未通過時 destructive action 維持 disabled。
- 正式元件符合 MUI Dialog 原有 focus trap、Escape、ARIA 與鍵盤操作行為。
- appearance 變更後圖片與 Dialog tone 同步更新，不需要重新載入頁面。

## 不做範圍

- 不修改 Storyteller 以外的全站共用 Dialog，也不一次替換全部既有 Dialog。
- 不讓一般操作型、內容工具型 Dialog 都出現梭梭。
- 不把 `error` 與 `danger` 合併成同一個狀態。
- 不在此階段加入 Live2D、角色動畫、語音或新的 appearance。
- 不重寫 MUI Dialog、theme provider 或全站 focus management。

# MCP：Project 工具

## 現況

目前已有：

- `storyteller_list_projects`
- `storyteller_get_project`

缺少建立與修改 Project metadata 的能力。

## `storyteller_create_project`（已確認加入）

### 工具定位

- 提供外部 Codex、Claude 或其他 MCP client 建立 Storyteller Project。
- 放入 `StorytellerMCPOnlyToolRegistry()`，不提供給站內編輯頁 AI Agent。
- 原因是建立專案時尚未有 `project_public_id`，無法套用站內 Agent 現有的 project scope 與 proposal 歸屬模型。

### Input schema

只有 `name` 必填：

```json
{
  "name": "新作品",
  "description": "作品簡介，可省略",
  "visibility": "private",
  "rating": "general",
  "content_type": "text",
  "tags": ["奇幻"]
}
```

欄位規則：

- `name`：必填。
- `description`：選填，預設空字串。
- `visibility`：選填，允許 `public`、`unlisted`、`private`，預設 `private`。
- `rating`：選填，允許 `general`、`guidance`、`restricted`，預設 `general`。
- `content_type`：選填，允許 `text`、`image`，預設 `text`。
- `tags`：選填，最多 12 個，每個最多 24 字。
- 不開放 `slug` 作為建立參數；沿用 `CreateProject` 依名稱產生並解決重複 slug 的既有行為。

### Output

回傳完整 project summary，至少包含 `public_id`、`name`、`slug`、`visibility`、`rating`。MCP client 取得 `public_id` 後，可以接著呼叫 `storyteller_upsert_story` 建立第一篇故事。

### 注意事項

- 這是非 destructive 的寫入，但重送同一請求會建立第二個專案；第一版接受此語意，之後若實際出現 retry 導致重複資料，再評估 `idempotency_key`。
- 測試必填名稱、預設值、自訂 enum、tags 限制與錯誤輸入。

## `storyteller_patch_project`（已確認加入）

### 工具定位

- 修改既有 Project 的名稱、描述、可見度、分級、內容類型、slug 或 tags。
- 放在共用 `StorytellerToolRegistry()`；站內 AI 呼叫時會被現有 proposal 機制攔截，外部 MCP 則直接執行。
- 必須帶 `project_public_id`，因此可沿用既有 project scope 驗證。

### 為何不用完整 `update_project`

目前 REST `ProjectRequest` 是完整欄位覆蓋。如果 Agent 只想把作品改成 private，卻沒有正確回傳 description、rating、content type 與 tags，可能用空值或預設值蓋掉既有資料。

`patch_project` 應採 optional fields：

1. 先讀取現有 Project。
2. 只合併本次有傳入的欄位。
3. 沿用現有 `UpdateProject` 的 normalize、validate、share token 與搜尋索引同步流程。

注意事項：

- `tags: []` 代表明確清空 tags；沒有 `tags` 才代表不修改，Go input 必須能區分兩種狀態。
- 修改 slug、visibility 會影響公開網址或分享方式，站內 AI 必須顯示為待確認 proposal。
- 回傳修改後的完整 Project，讓 Agent 不必再呼叫一次 `get_project`。

## `storyteller_delete_project`（暫緩）

- 目前 PAT 沒有 read／write／destructive scope，一把 PAT 可以取得全部 Storyteller MCP 工具。
- 刪除整個 Project 的 blast radius 明顯高於刪除單篇內容。
- 等 PAT scope、MCP tool annotations 或 destructive approval policy 補強後再評估。

## 驗收條件

- Storyteller MCP 的 `tools/list` 同時包含 `storyteller_create_project` 與 `storyteller_patch_project`。
- `create_project` 只有 `name` 必填；省略其他欄位時套用既有 `private`、`general`、`text` 預設值，slug 由 service 產生。
- `patch_project` 只更新有傳入的欄位；省略欄位保持原值，`tags: []` 明確清空標籤，完全沒有 patch 欄位時回傳錯誤。
- enum、name、slug、tags 數量與長度沿用既有 service validation，不在 MCP handler 建立第二套規則。
- 修改 visibility 時沿用既有 share token 行為，修改 metadata 後沿用搜尋索引同步。
- 回傳完整 Project summary，包含 `public_id`、`slug` 與 `content_type`。
- 使用者只能建立自己的 Project，且只能 patch 自己持有的 `project_public_id`。
- Storyteller 與 MCP service 的相關測試通過。

## 不做範圍

- 本階段不提供 `storyteller_delete_project`。
- 不新增 PAT read／write／destructive scopes，也不修改既有 PAT 資料模型。
- 不加入 `idempotency_key`、自動去重或同名 Project 合併。
- 不允許 `create_project` 指定 slug；仍由既有 service 產生。
- 不另外建立一套 MCP 專用 Project persistence 或 validation。

# AI 助理：看板娘口吻

## 建議方向（待確認）

將「梭梭作為產品 UI 的說話者」與「AI 生成內容的人設」分開處理。

### 固定使用梭梭語氣

- Loading、空狀態、錯誤、完成、重送提示等 UI 文案。
- 文案由前端固定維護，不消耗 token，也不會因模型而漂移。
- 語氣遵守既有梭梭設定：安靜、簡短但不是系統訊息腔，不賣萌、不搶使用者作品的主體性。

### 不應全域強制梭梭語氣

- `/rewrite`、`/expand`、`/translate`、`/continue` 產出的文字可能直接放進正文。
- 使用者自訂 Agent 已有自己的 `DefaultPrompt`，全域再疊一層梭梭人設會互相衝突。
- 一般詢問若沒有明確選擇 persona，應維持中性回答。

### 建議實作

- 增加可選的內建「梭梭」Agent preset，沿用既有 Agent／DefaultPrompt 機制。
- 使用者明確選擇梭梭或呼叫對應指令時，回答才帶梭梭語氣。
- Skill 類指令繼續使用 `ignore_agent_persona`，避免產出的正文被角色口吻污染。

# AI 助理：SSE

## 現況

- AI 工作已是背景執行，送出後立即取得 `chat_id`。
- 前端目前每三秒輪詢 chat 狀態。
- `AIProvider` 目前只有一次性 `Generate()`；OpenAI-compatible、Claude、Gemini、自架模型都沒有共用 streaming abstraction。

## 建議第一階段：執行狀態 SSE（待確認）

先推送工作生命週期，不做逐 token：

```text
chat.in_progress
provider.started
tool.started
tool.completed
proposal.created
chat.completed
chat.pending
```

- 完整答案仍以 DB 中完成的 assistant message 為準。
- 前端可以即時顯示正在讀取故事、設定集、執行工具或整理回答。
- 取代固定三秒 polling，同時保留斷線後重新查 DB 的 fallback。

技術注意事項：

- Production 若有多 instance，不能只用 process 內 channel；建議以 Redis Pub/Sub 傳遞事件。
- 原生 `EventSource` 不能自訂現有 session header；前端應使用 `fetch()`＋`ReadableStream` 解析 SSE，或改用短效 stream token。
- 支援 heartbeat、reconnect 與 `Last-Event-ID`；SSE 中斷不代表背景 AI 工作取消。
- `pending` 代表本輪失敗但可重送，不能跟仍在執行的 `in_progress` 混為一談。

## 第二階段：逐 token streaming（暫緩）

若要逐 token，需要同時處理：

- 為每家 provider 實作 streaming parser 並擴充 `AIProvider` abstraction。
- Agent tool-calling 多輪中，區分中間 tool event 與最終文字。
- 部分文字持久化、重新整理恢復、process 中斷收尾。
- token usage、raw provider response 與錯誤處理。

成本與風險明顯高於狀態 SSE，等第一階段實際使用後再決定。

## MCP 是否同步加入 SSE

建議目前不做。

- AI 回覆 SSE 與 MCP transport 是不同層次的問題。
- 現有 MCP 工具是有限時間內完成的 CRUD，沒有逐 token 回覆需求。
- Storyteller MCP server 也刻意不提供站內 AI Agent 功能。
- 未來若要支援更多標準 MCP client，再獨立升級成完整 Streamable HTTP、progress notification 或 OAuth，不與 AI SSE 共用 endpoint。

# 桌面版 App

## 目標

- 將完整工作台搬進桌面版 App。
- 編輯介面上方為編輯區，下方為需求輸入／AI 助理區。
- 可與 Claude、Codex 或其他外部 AI Agent 整合，提供 rewrite、expand、review 等工作流。

## 建議架構（待確認）

### Tauri 薄殼

- 沿用現有 Vite＋React SPA，不複製一套桌面前端。
- Tauri 只負責視窗、auto update、deep link、本機檔案、OS keychain 與未來的 Agent process bridge。
- 新增 runtime adapter 隔離 Web／Desktop 差異，避免頁面到處判斷 `isTauri`。
- 先維持遠端 Go API 與目前登入／資料模型，不在第一版做完整離線資料庫。

### 編輯器與 AI 配置

- 桌面 layout 使用可拖曳的上下 split pane。
- 上方保留現有 WYSIWYG editor 與工作台分頁。
- 下方重用 `StorytellerAgenticPanel`，不是另寫一套桌面 AI UI。
- 保存上下區域高度與面板開合狀態。

### 外部 Agent 整合順序

第一階段：

- 沿用 Storyteller MCP 作為內容讀寫邊界。
- 為 Claude／Codex 提供 Steamloom Skill／Plugin，封裝 rewrite、expand、檢查設定衝突等工作流。
- 所有修改仍經 Storyteller API、版本歷史與 proposal／確認機制。

第二階段才評估桌面 App 直接啟動本機 Agent：

- 不透過 shell 字串執行任意命令，只允許白名單 executable 與結構化參數。
- 處理 Claude／Codex 各自的登入、process lifecycle、JSONL／event protocol、權限詢問與取消。
- 清楚區分站內 AI provider 與使用者本機已登入的 Agent，避免金鑰與費用來源混淆。

## 主要風險

- BrowserRouter 在 Tauri protocol 下的 reload／deep link fallback。
- API CORS、cookie／session 與桌面 origin。
- macOS／Windows code signing、auto update 與發行流程。
- 關閉視窗時尚未儲存內容與背景 Agent 工作如何處理。
- 不能因為包成 App 就默認擁有任意 filesystem／shell 權限。

# 行動版 App

## 產品定位

第一階段只提供完整閱讀體驗，不搬完整工作台。手機不適合長篇編輯，但仍值得保留：

- 閱讀與閱讀設定。
- 書籤、閱讀進度與追蹤作品。
- 原生分享。
- 離線下載作品。
- 快速記下一則靈感／註記。
- 未來可評估非常輕量的小錯字修正，但不放完整 WYSIWYG 工作台。

## 建議實作順序（待確認）

### 第一階段：PWA

- 增加 Web App Manifest、icons、standalone display 與 service worker。
- 先快取 app shell 與公開靜態資產；登入後作品的離線資料不直接混進第一版。
- 保留目前 React codebase 與部署方式，先驗證手機閱讀、安裝與返回閱讀進度的需求。

### 第二階段：Capacitor

只有確定需要 App Store、push notification、原生分享、檔案系統或完整離線書庫時才包原生 App。

- 沿用既有 React build，原生層只處理裝置能力，不重新實作閱讀 UI。
- 離線作品需另行設計 IndexedDB／SQLite 儲存、版本更新、刪除與容量管理，不能只當成 service worker cache。

## 不建議項目

- 手機完整工作台與長篇 WYSIWYG 編輯。
- 第一版同時處理閱讀、離線同步、完整 AI 對話與原生上架。
- 為了共用桌面殼而強迫手機採用不適合的視窗與多面板 layout。

# 管理後台（提案草案，待確認）

## 定位與現況

先把「管理後台」定位為 SteamLoom／Storyteller 的平台營運入口，不是作者自己的工作台，也不是 faryne.dev／Galgame 管理頁的延伸。

- 現有 Storyteller 頁面與 API 主要以登入者自己的 `user_id` 查詢；沒有跨使用者的管理查詢、管理操作或管理審計紀錄。
- Storyteller 帳號已獨立於主站 `users`：登入身分落在 `storyteller_users`，session brand 是 `storyteller`。主站的 `users.is_admin` 與 Galgame 管理流程不能直接拿來當 Storyteller 管理權限。
- Project 有 `public`／`unlisted`／`private`，並含故事、設定、資產、AI 對話與 API key。已確認平台內部管理的 `read` 可跨所有 Project，不受 visibility 限制；但各資源的 `read` 與 API key 等敏感憑證仍須分開授權。

## 建議第一階段：可用但低風險的營運視圖

獨立 `/my/admin` 路由與後台 layout，延續 Storyteller appearance，但導覽、中文 breadcrumb 與頁面權限明確區隔作者工作台。先做四個區塊：

1. **總覽**：使用者、專案、公開作品、近期新增數量與基本 AI 用量統計。資料走聚合查詢，不靠前端載入全表計算。
2. **使用者查詢**：依 Storyteller user ID、筆名搜尋；只有具個資權限者可依電子郵件精確搜尋／檢視。只顯示營運必要欄位、帳號狀態與作品數，不顯示 Firebase token、PAT、provider API key。
3. **專案查詢**：依 public ID、擁有者、名稱、visibility、rating、建立時間篩選；列表顯示 metadata 與數量，有對應資源 `admin.*.read` 權限者可進一步檢視內容，包含 `private`／`unlisted` Project。
4. **管理紀錄**：查詢角色授予／撤銷與未來的管理操作；第一版即建立紀錄格式，避免管理動作上線後才補追溯能力。

列表採伺服器端分頁與排序；前端隱藏入口只是體驗，API 每次請求仍須重新授權。第一階段先不對使用者作品做任何跨帳號寫入。

## 候選平台內部管理 permission matrix（尚未定案）

以下是**管理後台**角色可取得的候選權限，與作者／協作者的 Project-scoped `project.read` 等 permission 分開命名、分開檢查；建議使用 `admin.<resource>.<action>`。此處列權限範圍，不代表第一階段就要實作所有刪除功能。

| 資源 | 候選 permission | 對照現況／待釐清 |
| --- | --- | --- |
| Project | `admin.project.read`、`admin.project.delete` | 管理刪除與作者自行刪除是不同動作；採可復原的 soft-delete，連帶隱藏子資源與搜尋結果的規則仍需定義。 |
| Story／Image（圖像作品） | `admin.story.read`、`admin.story.delete` | 圖像作品目前也是 Story；依 `content_type` 檢查，可讀取跨 Project 的故事內容與圖像頁面。 |
| Volume（冊） | `admin.volume.read`、`admin.volume.delete` | 冊目前也是 Story；依 `is_volume` 檢查，不能用 Story 權限繞過冊的刪除限制。 |
| Lore（設定） | `admin.lore.read`、`admin.lore.delete` | 與作者操作分開；刪除後的引用與公開顯示需定義。 |

已確認：平台角色的各項 `admin.<resource>.read` 可讀取**所有使用者、所有 Project** 的對應資源，不因 `private`／`unlisted` 受限；同一 `read` 同時涵蓋該資源的列表與詳情，不另外定義 `admin.*.list`。`admin.project.read` 只讀安全的 Project metadata，不包含 Story、Lore、Asset 等子資源內容；持有任一子資源的 `admin.*.read` 時，也可取得導覽所需的 Project 安全摘要，不必再額外勾選 `admin.project.read`。第一階段營運列表可先顯示 metadata，再由有對應 read 權限者進入內容；PAT、provider API key 等憑證不屬於上述 read。`delete` 採可復原 soft-delete、保留操作紀錄與復原途徑，並與「因檢舉暫時下架公開內容」分開；後者不應直接改寫作者的 visibility，也不應用刪除權代替。每次管理刪除都要獨立驗證權限、指定理由、確認對象，不借用作者 `user_id` 呼叫現有 owner-only API。

## 後續候選功能（須另行定案）

- **內容處置**：實作使用者檢舉入口、檢舉處理狀態、下架與恢復公開內容。`admin.report.update` 可處理檢舉流程，但檢舉狀態更新不應自動等於刪除／下架被檢舉內容。若要下架，處置狀態應獨立於作者設定的 `visibility`，保留原值與理由；公開閱讀 API、搜尋索引、分享連結、CDN／既有簽名 URL 的生效時間都要一起定義。
- **帳號處置**：停權、解除停權。必須同時處理既有 session、PAT／MCP、背景 AI 工作與作者仍能否匯出資料，不能只在前端藏按鈕。
- **營運設定**：例如 provider model 目錄或首頁推薦。先確認是否真有人工維護需求，再決定是否搬進後台。

## 建議實作邊界

- 新增 Storyteller 專用 `/storyteller/admin/*` API；`controller` 只處理輸入與回應，查詢／處置邏輯放 `service/storyteller`，跨使用者資料查詢放 `repository/storyteller`。不要讓管理員冒用作者 `user_id` 去呼叫現有 owner-only service。
- 管理 UI 在 `static_site/src/pages/storyteller/` 下獨立拆頁；先做可互動 mockup，確認列表資訊密度、手機降級方式及危險操作 dialog 後再實作。
- 查詢結果對不同 permission 做欄位裁切，尤其電子郵件、私人內容、AI 對話與密鑰；管理操作要有 actor、target、action、reason、時間與 request ID 的 append-only audit，避免把密鑰或全文寫進 log。

## 驗收條件（提案）

- 非管理員看不到後台入口，直接請求後台 API 仍被拒絕；有權限者只能看到自己角色允許的頁面與欄位。
- 使用者／專案搜尋支援分頁與篩選，查詢範圍可跨使用者，但不改動作者既有的 owner-only API 語意。
- `private`／`unlisted` 正文與原圖只向具對應 `admin.*.read` 權限者開放；PAT 與 provider API key 不因內容讀取權而外洩。
- 管理紀錄能追溯角色異動；若後續加入處置動作，每項都需記錄理由及處置前後狀態。
- 後續開放管理刪除時，只持有 `admin.project.read` 等讀取權的人不能刪除；刪除 Project、Story、冊、設定、設定集、資產集與資產的直接 API 請求，都只能由具對應 `admin.*.delete` 權限的人執行並留痕。
- 新頁面有中文 breadcrumb，API 錯誤有可讀的 snackbar；權限變更後不必重新登入就能阻擋後續請求。

## 不做範圍與待討論

- 第一階段不做管理刪除／批次刪除、直接修改他人正文、代登入作者帳號，也不把管理工具暴露到現有 PAT／MCP。
- 待確認後台最先要解決的是「營運查詢」、「內容審核」還是「帳號管理」；若目前只有一名管理者，四個唯讀區塊是否需要縮成更小的第一批。
- 待確認檢舉入口與下架／停權的操作流程，定案後才設計寫入 API；另須定義 `admin.report.delete` 是移除誤報／垃圾檢舉，還是另有用途，避免破壞處置證據。

# RBAC（Project 協作第一批已確認；管理後台另排）

## 已釐清的權限語意

每位登入的 Storyteller user 都隱含 `default_user` 角色，可操作自己帳號下的所有 Project。其他有效角色的權限與 `default_user` **取聯集**，不會取代原有權限；但額外授權只對角色指定的資源範圍生效。資料模型與權限命名區分 Project 協作及平台後台，兩種範圍不可互相推導權限；第一批只開放 Project 協作。

例：B 擁有 Project「Book 1」，建立該 Project 專用的 `Role A`，賦予 `story.update`，再把 A 加入此角色。`story.update` 有效包含同資源的 `story.read`，所以 A 仍能管理自己的 Project，也能在 Book 1 查看與修改 Story；A 不會因此取得 B 的其他 Project、Book 1 的設定／資產／API key 或平台後台權限。A 在協作專案列表可看見 Book 1 的安全摘要，不需額外勾 `project.read`。只要對 Book 1 取得有效讀取授權，`private`／`unlisted` 不會再阻擋 A 讀取該授權範圍內的內容。

Project 是目前的作品容器，Story 與冊都掛在 `storyteller_projects.id` 底下。第一版先以 Project 為 role 範圍；若日後要求「只准改 Book 1 的某一篇 Story」，再討論 Story 層級授權。

## 第一批交付邊界（已確認）

- 第一批要交付**可實際使用的 Project 協作**，不是只有 RBAC 資料表／授權函式：獲授權的 Project 應出現在 A 的專案列表，標示擁有者／協作身分；A 可進入既有工作台，對授權範圍內的 Project metadata 與 Story／圖像作品、冊、設定、設定集、資產集、資產執行下表對應的列表／詳情／建立／修改。實作時須逐條盤點 Web API 與 MCP tool，不得只讓入口列表可見，子資源卻仍被 owner-only 查詢擋住。
- 「先不做前端授權」指**不讓前端自行決定安全邊界，也不先做角色／成員的管理畫面**；不是完全不改前端。工作台至少須辨識 owner／collaborator、顯示後端提供的有效操作能力，對無權操作隱藏或停用入口，並維持 API 失敗時的可讀提示。後端對每次 Web／PAT／MCP 請求仍重新驗證有效角色、Project 歸屬與目標資源。
- 第一批需有 owner-only 的角色／permission／成員管理 API，供暫時透過 API 管理授權；可建立 Project role、設定權限、授予／撤銷成員與有效期。權限管理 UI 可後補；不能因沒有 UI 就把角色固定寫在資料庫或略過撤銷流程。
- 第一批提供 Project audit 的查詢 API，讓 owner 能檢視專案異動；協作者是否可讀完整 audit 仍須另定，不因持有 `project.read` 就自動開放。這不影響協作者已獲授權的編輯與 owner 事後追查覆寫。
- 既有 owner 的 `/projects` 列表、單一 Project 詳情及工作台操作保持原本回應與行為；協作資料使用安全摘要與有效操作能力，前端再合併顯示。不要把協作者直接套用含 `share_token`、未授權 Story／Volume 的現有 `ProjectOutput`。只要下列 permission 未授予，協作 Project 的 UI 與 API 都不得暗中開放該資源。
- `platform` role 的資料模型可預留，但第一批不交付管理後台查詢／刪除 API、管理 UI 或平台權限的 PAT／MCP 使用；這些依上節管理後台提案另排。既有未授權者與公開閱讀行為不變。

## 第一批 Project permission matrix（資源邊界仍須逐 API 核對）

依目前確認的範圍，先用 `resource.action` 表達第一批權限；具體 key 與 endpoint／MCP tool 對照由實作時列出，所有額外授權都只在該角色綁定的 Project 內生效。`read` 同時涵蓋該資源的列表與詳情，不為每種資源另增 `list` permission；各列表必須在資料查詢時依有效 Project role 與資源權限過濾。`create`／`update` 都有效包含**同一資源**的 `read`，由授權判斷推導，前端應顯示衍生後的能力，不必在 `role_permissions` 重複存一筆 read。

| 資源 | 第一批 permission | 對照現況／待釐清 |
| --- | --- | --- |
| Project | `project.read`、`project.update` | `read` 只提供 Project 安全摘要，不包含子資源內容；任何有效的 Project-scoped 權限也可取得該 Project 的安全摘要。`update` 先開放現有 Project 更新 API 可修改的全部欄位，不拆欄位級權限。 |
| Story／Image（圖像作品） | `story.create`、`story.read`、`story.update` | 圖像作品目前也是 `Story`，以 `content_type=image` 區分；先共用權限，若需要區分圖文編輯者再拆。圖像上傳／頁面替換與 Asset 權限的交界待定。 |
| Volume（冊） | `volume.create`、`volume.read`、`volume.update` | 冊目前也是 `Story`，以 `is_volume=true` 區分；授權時應依資料型態檢查，不能拿 `story.update` 更新冊。 |
| Lore（設定） | `lore.create`、`lore.read`、`lore.update` | 設定版本回復、搬移與 AI 提案是否屬 `update` 待定。 |
| Lore Collection（設定集） | `lore_collection.create`、`lore_collection.read`、`lore_collection.update` | 與 Asset Collection 權限分開；管理設定集不等於可修改其中的 Lore。 |
| Asset Collection（資產集） | `asset_collection.create`、`asset_collection.read`、`asset_collection.update` | 與 Lore Collection 權限分開；管理資產集不等於可修改其中的 Asset。 |
| Asset | `asset.create`、`asset.read`、`asset.update` | 上傳／確認可視為 `create`，更換檔案／metadata／搬移可視為 `update`；原始檔下載與圖像頁面的授權邊界待定。 |

已確認 Lore Collection 與 Asset Collection 必須拆成獨立權限，Collection 權限也不隱含其中 Lore／Asset 的內容權限。`project.read` 單獨授予時只能看 Project 安全摘要；持有 `story.read` 者可看該 Project 的摘要、Story 列表與詳情，但不能因此讀 Lore 或 Asset。即使只獲得子資源的 `create`／`update`，也可取得導覽用的 Project 安全摘要，並可讀取**同一種子資源**。未列出的 `delete`、Project 建立、角色／成員管理、AI 執行與提案套用、版本回復等操作，**不因上述 `create`／`update` 自動開放給協作者**；先維持 owner-only，之後逐項決定。列表、詳情、預覽與 MCP tool 也都要映射到相同權限，不能因 API 路徑不同而放行。

對一般使用者的協作授權，Project 的 visibility 僅影響未取得授權者的公開閱讀；已獲授權的 user／PAT 可依其 Project role 讀取授權範圍，不再受 `private`／`unlisted` 限制。現有 `ProjectOutput` 包含 `share_token` 及內嵌 Story／Volume 資料，不能直接當作「安全摘要」回傳；需另外定義裁切後的 DTO，排除分享 token、子資源內容與不屬於協作授權的欄位。

## 協作寫入與專案稽核（已確認方向）

- `project.update` 先直接涵蓋現有 `ProjectRequest` 可修改的全部欄位：名稱、slug、描述、visibility、rating、content type、tags；切換 visibility 所觸發的 share token 變動也沿用現有邏輯，不讓協作者直接指定 token。
- **不新增 ProjectVersion。**目前 `UpdateProject` 直接 `Save` 覆寫 `storyteller_projects`；新需求是 `project_audit`，記錄誰在何時對 Project 及其資源做了什麼，而不是保存每份 Project metadata 快照、提供版本回復。稽核只能協助追查事件，不能當成可還原的編輯歷史。
- Story／圖像作品與 Lore 已有版本寫入：若請求帶 `base_version_id`，版本落後時仍寫入新版本並標示衝突，不拒絕寫入；協作者第一版沿用此 Web 行為，不在這一輪做即時同步或自動合併。版本目前未記錄實際操作者 user ID，協作後至少需補上 actor 歸屬供追溯。
- **Project metadata 不做衝突偵測或標記。**多人同時修改時，後寫入者直接覆蓋前者；事後由使用者查 Project audit 了解誰在何時改了哪些欄位。Volume 更新雖會建立 StoryVersion，但目前未帶 `base_version_id` 做衝突判斷；Collection、Asset metadata 也沒有同樣的版本衝突機制，這些子資源的並行規則仍待定。

### Project audit 建議規格（細節待確認）

- 新增 `storyteller_project_audits`（實際命名待定）：至少記 `project_id`、`actor_user_id`、`source`（Web／MCP／管理後台等）、`action`、`target_type`／`target_id`、`occurred_at`、`request_id`。以 Project 及其 Story、圖像作品、冊、設定、設定集、資產集、資產、角色／成員的**異動事件**為主；是否連每次 read 都記錄另行決定。
- `project.update` 的 audit **必須**記每個實際變動欄位的安全前／後值，讓使用者查得出被覆蓋的內容；不儲存完整 Project 快照，也不提供從 audit 一鍵還原。Story／Lore 內容異動只記對應 version ID 與 actor，不把全文複製進 audit；share token、PAT、provider API key、原始檔等敏感值不入紀錄。[OWASP Logging Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html)也建議排除 token 與密鑰。
- 資料庫異動與 audit 寫入應在同一個 transaction，讀取修改前的 Project 列時須保證取得正確前值，避免同時修改時 audit 記錯差異；audit 採 append-only，後續更正要新增事件，而非改寫舊事件。初次導入不替既有 Project 偽造「過去誰做了什麼」；只從功能上線後開始記錄。
- Project 不新增 `revision`／`base_revision` 比較，也不回報 `version_conflict`；audit 只提供事後查詢，不會警告當下是否蓋掉別人的修改。第一批先讓 Project owner 查詢完整 audit；協作者的 audit 讀取權限須另定，因為事件可能包含其無權讀取的其他子資源資訊，不能直接因擁有 `project.read` 就顯示完整 Project audit。
- 現有 slug 查重以傳入的 `userID` 判斷；協作者修改 B 的 Project 時必須改用 **Project owner 的 user ID** 查重，不能拿操作者 A 的 ID。

## 建議資料模型（表名與欄位待定）

| 表 | 用途與主要欄位 |
| --- | --- |
| `storyteller_roles` | 可重用角色定義：`id`、`name`、`scope_type`（`project`／`platform`）、`project_id`（平台角色為 NULL）、`created_by_user_id`、狀態與建立／更新時間。`default_user` 可作為系統角色定義，但不必替每位 user 建立指派紀錄。 |
| `storyteller_permissions` | 穩定的 scope/action key 與說明，例如 `story.read`、`story.update`、`admin.users.read`；由程式碼／migration 定義可用 key，不讓角色建立者輸入任意字串。 |
| `storyteller_role_permissions` | `role_id`、`permission_id`；Project role 只能選 Project 可用的 permission，平台 role 只能選平台 permission。 |
| `storyteller_user_roles` | `role_id`、`user_id`、`starts_at`、`expires_at`、`granted_by_user_id`、`revoked_at`；一筆代表某人在指定期間取得該角色。 |
| `storyteller_project_audits` | Project 與子資源異動的 append-only 事件紀錄；記操作者、時間、動作、目標、來源及安全的變更摘要，不提供版本快照或還原。 |

起迄時間建議放在**使用者與角色的關係**，因為同一角色可能授予不同人不同期限；若整個角色本身需要停用，可另設狀態或 `disabled_at`。時間以 UTC 儲存，判定為 `starts_at <= now AND (expires_at IS NULL OR now < expires_at) AND revoked_at IS NULL`。若允許同一人重複獲授同角色，需定義是否可有重疊有效區間與續期行為。

## 授權判斷與現有系統銜接

- Session 或 PAT 先確認操作者是 A；對目標 Story 查出所屬 Project。若 Project owner 是 A，套用 `default_user`；否則只合併 A 在**該 Project** 目前有效角色的 permission。平台後台 API 只看 `platform` role，不因擁有 Project 而放行。每次請求都在後端檢查 action 與目標資源，預設拒絕。[OWASP Authorization Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)也強調角色之外仍須檢查請求與物件的關係。
- 現有 `ProjectByPublicIDForUser` 與多數 service／repository 查詢寫死 `project.user_id = user_id`。只新增四張表不會讓 A 真正讀寫 B 的 Book 1；需要盤點並逐條改成「owner 或有效協作授權」，且同時檢查 Story、冊、資產等子資源確實屬於目標 Project，不能只改一個入口。修改後仍須保留 owner fast path 與既有 owner API 契約；協作列表與詳情使用不洩漏額外資料的 DTO。
- MCP 應與 Web 共用 Project 授權判斷：A 的 PAT 在角色生效期間可依 Book 1 的 permission 執行對應工具，角色到期／撤銷後立即失效；不要把 role 複製進 token。**平台管理權限是否可由 PAT/MCP 使用仍待另定**，不隨 Project 協作權限自動開放。
- 建立／修改角色、調整 permission、加入／移除成員都由 Book 1 owner（或另有明確管理授權者）執行，並留下 actor、target、Project、變更前後及時間的審計紀錄；不能讓持有 `story.update` 的人順便修改角色、刪除 Project 或查看 B 的 provider API key。
- 平台角色可共用上述表，但 `scope_type=platform`，例如 `platform_owner`／`content_moderator`／`support_reader`；候選權限見上方管理後台矩陣。角色與權限的對應、首位 owner bootstrap、最後 owner 防鎖死與個資欄位裁切仍須另外定義，不借用主站 `users.is_admin`。

## 驗收條件（提案）

- A 無額外角色時只能操作自己的 Project；被授予 Book 1 的 `story.update` 後，有效權限同時包含 `story.read`，Web／MCP 都能存取 Book 1 的對應 Story，但不能操作 B 的 Book 2 或 Book 1 未授權的設定／資產／管理功能。
- 只有 `project.read` 時可列出 Book 1 並讀安全摘要，但無法列出 Story；只有 `story.read` 時可列出 Book 1 及其 Story，無須另勾 `project.read`，但仍不能列出 Lore／Asset。Project／子資源列表不顯示未授權內容。
- A 的專案列表能同時顯示自己的與獲授權的 Project，明確區分擁有者／協作者；進入 Book 1 工作台後，授權的列表、詳情、建立與修改在 Web 可用，未授權的操作不顯示或停用，即使繞過前端直接呼叫 API／MCP 也會被拒絕。授權變更後重新取回能力，不以舊的前端狀態放行。
- Book 1 即使設為 `private`／`unlisted`，A 仍可讀取已授權的內容；一般未獲授權者則維持原本 visibility 規則。平台管理角色的對應 read 權限可跨所有 Project 讀取。
- A 的自身 Project 權限在取得或失去 `Role A` 後均不受影響；角色未開始、已到期或撤銷時，舊 session／PAT 也不得繼續使用協作權限。
- 直接改 Project／Story ID、把其他 Project 的 Story ID 塞進 Book 1 API、或經由不同 endpoint／MCP tool 執行同一動作，都不能繞過授權。
- 角色、permission 與成員異動可追溯；service 層有授權測試，涵蓋 owner、協作者、無權限者、時間邊界及撤銷情境。
- Project owner 可透過 API 查詢上線後的 Project audit，看到 `project.update` 實際變動欄位的前後值與操作者；協作者不能僅憑 `project.read` 取得完整 audit。
- 協作者更新 Story／圖像作品／Lore 時，比照現有 Web 寫入新版本；有 `base_version_id` 且落後時仍儲存並標示衝突。開放 `project.update` 前先建立 Project audit；多人同時改 Project metadata 時直接以最後寫入為準，不回報衝突，事後可查實際變動欄位與操作者，但不能從 audit 一鍵回復舊版。

## 不做範圍與待討論

- 這是**共享 Project 的授權基礎**，不等於多人即時協作。同步編輯、游標 presence、衝突合併與 AI 對話歸屬仍屬獨立課題；現有版本寫入是 last-write-wins，詳見[線上即時多人協作評估](線上即時多人協作評估_2026-09-07.md)。
- 第一版建議不做逐篇 Story 的 role scope、任意巢狀角色、跨 Project 的協作角色、自訂 permission key 或 PAT 的平台管理權限。
- 第一批不做角色／成員管理 UI，也不把前端 capability 顯示當成授權機制；但要做協作專案列表與現有工作台的最低限度適配，不能把整個協作體驗延到下一批。
- 待確認一個 Project 能否建立多個自訂角色、同一人能否同時加入多個角色。
- **已確認：角色／成員管理（建立角色、設定權限、授予／撤銷成員）第一批不可委託，永遠 owner-only。** 協作者不論被授予什麼 resource permission（`story.update` 等），都無法建立角色或授予／撤銷其他人的角色——這條路徑本身不存在，不是「有權限但被擋」。`storyteller_user_roles.granted_by_user_id`／`revoked_by_user_id` 純粹是稽核欄位，記錄實際執行動作的人；因為呼叫端已經是 owner-only，這兩欄在第一批只會是 owner 的 user_id，不代表委託機制。之後若要開放委託，需要新增獨立的 `role.manage` 這類 permission 並重新定案，不是靠現有 resource permission 自動涵蓋。
- 第一版不做 Project metadata 版本快照、歷史還原或衝突標記；待確認 Project audit 的查詢權限，以及目前未支援衝突標記的 Volume、Collection、Asset metadata 應補齊還是先接受 last-write-wins。
- 待確認上表各權限的精確邊界，尤其圖像作品與 Asset、版本回復與 AI 操作；不能因名稱相近就讓一項 permission 暗中包含另一項。
