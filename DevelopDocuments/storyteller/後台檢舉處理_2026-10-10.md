## 範圍

這輪只做「平台權限的地基＋檢舉處理」，不做提案裡的總覽、使用者查詢、專案查詢。

## 平台權限（沿用既有 RBAC 表）

- `storyteller_permissions` 新增 `scope_type=platform` 的 key（命名沿用提案的 `admin.<resource>.<action>`）：

  | key | 用途 |
  |---|---|
  | `admin.report.read` | 看檢舉列表與被檢舉內容 |
  | `admin.report.update` | 結案／駁回檢舉（隱含 `read`，沿用既有 `derivePermissions` 規則） |
  | `admin.comment.delete` | 以站方身分移除留言 |
  | `admin.author_post.delete` | 移除動態 |
  | `admin.discussion_thread.delete` | 移除討論串 |
  | `admin.story.delete` | 移除單話（冊不在範圍內） |
  | `admin.lore.delete` | 移除設定 |
  | `admin.project.delete` | 移除整部作品 |
  | `admin.author_profile.delete` | 移除額外筆名（連帶該筆名的動態、討論串、留言） |
  | `admin.user.ban` | 停權帳號（見「創作者處置」） |

- **為什麼是 `admin.<resource>.<action>`**：跟既有 project 權限（`story.update`）同一個語序；同資源的權限排在一起，權限矩陣、角色編輯畫面都是一列一個資源；「`update` ⇒ 同資源 `read`」的推導規則也以資源為單位。平台權限前面多了 `admin.`，推導時要先去掉前綴，且**不能**沿用 project 的「持有子資源權限 ⇒ `project.read`」規則，所以另寫一支 `derivePlatformPermissions`。

- **bootstrap（migration）**：建立 platform role `admin`（`project_id` NULL），授予上列全部權限；把**主站 `users.id = 1`** 對應的帳號加入此 role。`storyteller_user_roles.user_id` 存的是 `storyteller_users.id`，所以用 `SELECT id FROM storyteller_users WHERE user_id = 1` 取得，不寫死（找不到就不插入）。
- **授權判斷**：新增 `EffectivePlatformPermissionKeys(userID)`（只看 `scope_type=platform`、走 primary），service 端每支後台方法都各自檢查需要的 key，預設拒絕（403）。不因擁有作品而放行，也不讀主站 `users.is_admin`。
- **只開放 session**：後台 API 掛在 session 驗證群組 `/storyteller/admin/*`，PAT／MCP／OAuth 一律不能用。
- `GET /storyteller/admin/me` 回傳目前有效的平台權限；前端有任一權限才顯示「管理後台」入口（入口隱藏只是體驗，API 仍每次檢查）。

## 檢舉處理

### 列表以「被檢舉的對象」聚合

同一則留言被 10 個人檢舉，列表只出現一列；處理是對「對象」做，一次結掉它底下所有待處理的檢舉。

- `GET /storyteller/admin/reports?status=pending|resolved|dismissed&target_type=&page=`（`admin.report.read`）
  - 每列：對象種類、對象摘要（名稱／內文摘要、擁有者筆名、目前是否已刪除與 `delete_reason`）、待處理數／總數、各原因次數、最後被檢舉時間。
  - **排序**：待處理數多的排前面（被越多人檢舉越優先），同數再依最後被檢舉時間新到舊；伺服器端分頁。
- `GET /storyteller/admin/reports/:targetType/:targetID`（`admin.report.read`）
  - 對象完整內容（留言／動態／討論串給全文；故事／設定／作品給標題與前台連結）＋這個對象的所有檢舉（原因、補充說明、檢舉者筆名、時間、狀態、處理者）。
  - 後台 API 直接用內部 `target_id`（只給管理員，不對外）。

### 處置動作

| 動作 | API | 權限 | 效果 |
|---|---|---|---|
| 移除內容 | `POST .../:targetType/:targetID/remove` `{reason_key}` | `admin.report.update` ＋ 對應的 `admin.<type>.delete` | 先寫 `delete_reason` 再 soft delete，連帶處理跟作者刪除相同的副作用（搜尋索引、資產引用、冊異動事件）；該對象所有 pending 檢舉改 `resolved`、記 `handled_by_user_id／handled_at`；通知擁有者 |
| 駁回 | `POST .../:targetType/:targetID/dismiss` | `admin.report.update` | 所有 pending 檢舉改 `dismissed`，內容不動 |

- 移除理由可選任何未停用、適用此對象的理由（含內部專用的 `tos_violation`），預設帶「被檢舉最多次的原因」。
- 對象已被作者自行刪除：動作按鈕改成「結案」（只結案、不覆寫 `delete_reason`），畫面標「作者已自行刪除」。
- 作者刪除流程與站方移除共用同一組內部刪除 helper（抽出 `deleteStoryRecord` 等），差別只在權限檢查與 `delete_reason`，不借用作者 `user_id` 呼叫 owner-only 方法。
- **本輪不做**：復原（soft delete 本身可由 DB 復原，UI 另排）。

### 創作者處置

創作者以筆名被檢舉，後端存成 `user`（帳號本人身份）或 `author_profile`（額外筆名），兩者處置不同：

| 對象 | 動作 | 效果 |
|---|---|---|
| 額外筆名（`author_profile`） | 移除筆名（`admin.author_profile.delete`） | 沿用作者自己刪筆名的流程：該筆名的動態、討論串、留言一併 soft delete，全部寫入同一個 `delete_reason`；帳號本人與其他筆名不受影響 |
| 帳號本人（`user`） | 停權帳號（`admin.user.ban`） | 見下 |

**停權帳號** = `storyteller_users.is_deleted=1`＋`delete_reason`，並且：

1. **立即擋下所有入口**：Firebase 登入（`UpsertFirebaseUser` 遇到已停權帳號回錯誤，不發 session）、既有 session（storyteller 登入群組多一層「帳號是否有效」檢查，PK 查詢）、PAT／OAuth／MCP（`storytellerbearer` 驗證後同一個檢查）。session 存在 Redis 但沒有依使用者建索引，所以採「每次請求檢查」而不是逐一刪 session，效果一樣是下一個請求就失效。
2. **停權當下不動任何內容**：作品、筆名、動態、討論串、留言都維持原狀（個別違規內容走各自的檢舉移除）。這樣誤停權時只要改回帳號狀態就好。
3. **排程清除**：每日 job 找出停權超過 `bannedAccountPurgeAfter`（常數，預設 6 個月）的帳號，把其下仍未刪除的作品、額外筆名、動態、討論串、留言以停權理由 soft delete，並移除搜尋索引。job 冪等（只動仍未刪除的），不另加欄位記錄是否處理過；邏輯放 service，`main.go` cronjob 區只負責呼叫。
4. **確認 dialog 要輸入筆名才能按停權**。
5. **不發站內通知**（停權後登不進來看不到）；email 通知跟著 Email 通道（目前暫緩）另排，維持在 TODO。

### 通知被處置者

- **檢舉人不會收到任何通知**（結案、駁回都不通知）：避免檢舉人拿結果去跟被檢舉人爭論，也不透露處置細節。之後要做「你的檢舉已處理」再另排。
- 在 `NotificationKinds` 註冊表新增 `moderation.removed`（Category `general`、新 View `moderation`；目前通知沒有個別關閉的設定，不用另外處理強制送達）。
- payload 帶對象種類、對象名稱快照與 `delete_reason`（slug）；前端用 `moderationReasonLabel` 顯示「你的留言已由站方移除，原因：廣告、洗版」。後端寫入的 Title／Body 只放不含原因的通用文字（給推播或不認得 kind 的前端用），避免後端再維護一份理由中文對照。
- 刪除帳號寄 email 跟著帳號處置一起另排。

### 稽核

- 在 `audit_registry.go` 登錄 `admin.report.remove`、`admin.report.dismiss`（High），由既有 `WebSuccess` middleware 記錄 actor、target、理由與 request ID；順便補登 `report.create`（Low）。

## User Story

- 管理員打開「管理後台」→ 待處理列表看到「F 的留言」被檢舉 3 次（廣告、洗版 ×3）→ 點進去看全文與三則檢舉 → 移除內容（預設理由「廣告、洗版」）→ 確認 → 前台該留言變成「此留言已由站方移除，原因：廣告、洗版」；F 收到通知；三則檢舉變已結案。
- 管理員判斷誤報 → 駁回 → 檢舉移到「已駁回」，內容不動。
- 非管理員直接打 `/storyteller/admin/reports` → 403；前端沒有入口，手打網址看到「沒有權限」。

## 常見失敗與應對

| 情境 | 應對 |
|---|---|
| 沒有任何平台權限 | API 403；前端頁面顯示沒有權限、不打其他 API |
| 有 `report.update` 但沒有該類型的 `delete` | 移除 403；前端不顯示「移除內容」，仍可駁回 |
| 兩位管理員同時處理同一對象 | 結案以 `status = pending` 為條件更新，後到的人移除時對象已刪除 → 只結案剩餘 pending；駁回時沒有 pending → 回成功不報錯 |
| 對象已被作者刪除 | 移除只結案、不覆寫原因 |
| 理由不適用該對象或已停用 | 400 |
| 冊被檢舉（理論上前台不會發生） | 移除回 400「冊不能直接移除」 |
| 角色被撤銷 | 每次請求都查 primary，下一個請求立即失效，不用重新登入 |
| 管理員停權自己 | 400，不能處置自己的帳號 |
| 停權後原本登入中的分頁 | 下一個 API 回 403「帳號已停用」，前端清 session 回首頁 |

## 實作筆記

- **權限判斷**：`service/storyteller/admin_auth.go`（`requirePlatform`、`derivePlatformPermissions`）。後台每支 service 方法第一行就檢查，controller 不判斷。
- **帳號停權檢查**：`middleware/storytelleraccount`（session 群組）＋`storytellerbearer`（PAT／OAuth／MCP）＋`UpsertFirebaseUser`（登入）。停權回 401 `401201`，前端沿用既有「401 → 重建 session → 失敗就清 session」流程。停權＝`is_deleted=1` 且 `delete_reason` 不為空；本人刪帳號（理由為空）不受影響。
- **刪除 helper**：`deleteProjectRecord`／`deleteStoryRecord`／`deleteLoreRecord` 由作者刪除與站方移除共用；`DeleteAuthorProfile` 多了 `reason` 參數（本人刪除傳 nil）。
- **排程**：`cronjobs.go` 的 `storyteller-purge-banned-accounts`（每日 04:40），常數在 `admin_ban_purge.go`。手動執行：`go run . -cmd storyteller-purge-banned-accounts`。
- **前端**：`layouts/StorytellerAdminLayout.tsx`、`pages/storyteller/admin/reports/`；通知新 view `moderation`。
- **已知限制**：額外筆名被站方移除時，若仍有故事署名這個筆名，署名會變成找不到身份（作者自己刪筆名會先擋下，站方不擋）。
