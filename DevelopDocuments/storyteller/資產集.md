# Storyteller 資產集規劃

## 目的

讓使用者可以在 storyteller 內管理可重複引用的媒體資源。第一階段建議先支援**圖像資產**，並讓圖像作品頁上傳的圖片自動進入資產集；故事、設定集或其他作品頁可透過資產 id 內嵌引用同一份媒體。

這個功能的核心不是「多一個上傳按鈕」，而是把目前散落在圖像作品頁 JSON 內的 S3 key 提升成正式 domain：可查詢、可插入、可簽名讀取、可追蹤引用，也能避免誤刪仍在使用中的檔案。

## 建議範圍

第一版只開放 `image/*`，包含 `jpeg`、`png`、`webp`、`gif`。資料模型可以預留 `asset_type`，但前端與後端驗證先不開 audio/video，避免第一版就踩到轉碼、縮圖、串流、range request、檔案大小與成本控管。

資產歸屬以 `project_id` 為主，資產只能在同一個專案內引用，不支援跨專案共用。`user_id` 仍建議保留成 owner 快照，方便查詢「我的資產」與做權限過濾；真正的內容邊界則以 project 為準。

## 現況判斷

目前圖像作品頁已經有基本上傳與讀取管線：

- `service/storyteller/upload.go`：產生 S3 presigned PUT URL，限制圖片 mime 與檔案大小。
- `service/storyteller/cloudfront.go`：把 S3 object key 轉成 CloudFront 簽名 URL。
- `Story.LatestContent`：`content_type=image` 時存 `StoryImageContent` JSON，頁面直接記錄 S3 key。
- 閱讀頁 API：讀取圖像作品頁時即時簽 URL，不把簽名結果落地。

因此第一版不需要重做儲存層與 CDN 管線，主要工程在「新增資產資料表與引用關係，並把現有 image page 上傳流程接進去」。

## 資料模型方向

### `storyteller_asset_collections`

資產集底下需要 collection，避免資產一多變成單一平鋪列表。Collection 是專案內的整理容器，不是媒體資產本身；第一版先做單層 collection，不做無限樹狀目錄。

建議欄位：

- `id`
- `public_id`
- `project_id`：必填，collection 只能管理同一個專案底下的資產。
- `name`
- `sort`
- `is_deleted`
- `deleted_at`
- `created_at`
- `updated_at`

索引建議：

- `UNIQUE KEY public_id`
- `KEY project_sort (project_id, is_deleted, sort, id)`

若之後真的需要多層目錄，再在 `storyteller_asset_collections` 加 `parent_id`；不要把 folder 塞進 `storyteller_assets`，避免資產表同時承載「媒體檔案」與「目錄」兩種不同生命週期。

### `storyteller_assets`

建議欄位：

- `id`
- `public_id`
- `user_id`
- `project_id`：必填，資產只能在同一個專案內使用。
- `collection_id`：可為 `NULL`，代表未分類。
- `asset_type`：第一版只接受 `image`，未來可擴充 `audio`、`video`。
- `mime_type`
- `file_ext`
- `file_size`
- `metadata`：JSON，存不同媒體類型各自需要的資訊，例如 image 的 `width` / `height`，未來 audio/video 的 `duration_seconds`、`poster_asset_id`、`codec` 等。
- `s3_key`
- `original_filename`
- `title`
- `alt_text`
- `description`
- `is_deleted`
- `deleted_at`
- `created_at`
- `updated_at`

索引建議：

- `UNIQUE KEY public_id`
- `KEY user_project_type (user_id, project_id, asset_type, is_deleted, created_at)`
- `KEY collection_type (collection_id, asset_type, is_deleted, created_at)`
- `KEY project_type (project_id, asset_type, is_deleted, created_at)`
- `KEY s3_key (s3_key)`

`metadata` 使用 JSON 可以避免為了不同媒體類型一直加 nullable 欄位。MySQL 5.7 的 JSON 欄位可用來保存結構，但不要在第一版依賴複雜 JSON 查詢；列表排序與篩選仍以一般欄位為主，`metadata` 偏向顯示與播放器需要的補充資料。

### `storyteller_asset_references`

用來記錄哪些內容引用了哪些資產，避免誤刪與方便日後做引用清單。

建議欄位：

- `id`
- `asset_id`
- `target_type`：例如 `story`、`lore`、`image_story_page`。
- `target_id`
- `target_version_id`：可為 `NULL`；文字故事／設定集若要追版本可填。
- `reference_key`：例如 markdown token、image page id，方便 debug。
- `created_at`
- `updated_at`

第一版可以只維護「最新內容」的引用狀態，不急著把所有歷史版本引用都完整正規化。版本內容本身已經保存原始 markdown / JSON，之後要回溯仍有資料可解析。

## 引用格式

故事與設定集的 markdown 建議使用自訂 URI：

```markdown
![替代文字](steamloom-asset://assetPublicId)
```

優點：

- 編輯內容不直接暴露 S3 key 或短效簽名 URL。
- render 時可以依觀看者權限即時轉成 CloudFront 簽名 URL。
- 未來同一套 parser 可以支援 `audio` / `video`，不需要改既有內容格式。

圖像作品頁第一版可以保留目前 `StoryImagePage.key`，但新增 `asset_id` 或 `asset_public_id`。新資料以 asset 為準，`key` 可暫時保留做相容與遷移緩衝。

## 權限原則

管理端：

- 使用者只能看到自己的資產。
- 專案工作台只顯示目前 project 底下的資產。
- 建立或更新引用時，service 層必須檢查 asset 與 story/lore/image page 屬於同一個 project，避免跨專案引用。
- 刪除資產前必須檢查引用數；仍被最新內容引用時不允許刪除，或只能做「隱藏／停用」。

公開閱讀端：

- 不提供任意 asset lookup 公開 API。
- 公開故事／圖像作品頁只回傳該內容實際引用到的資產簽名 URL。
- 私人或草稿內容只有作者本人預覽時可以拿到簽名 URL。

## 上傳流程

第一版建議調整為：

1. 前端向後端要求 presigned PUT URL，帶 `project_id`、`collection_id`、`mime_type`、`filename`、`size`。
2. 後端驗證權限與檔案類型，產生隨機 S3 key，回傳 `upload_url` 與暫存 token 或 asset draft 資訊。
3. 前端直接 PUT 到 S3。
4. 前端呼叫 confirm API，後端 `HeadObject` 驗證實際大小與 content type，建立 `storyteller_assets` row，並把寬高等補充資訊寫入 `metadata`。
5. 圖像作品頁使用這批 asset 組成頁面 JSON；故事／設定集則透過插入器放進 markdown。

現有圖像作品頁上傳可先包成「上傳完成後自動建立 asset，再把 asset id 寫入 page JSON」。這樣使用者在圖像作品頁上傳的圖片會自然出現在資產集中。

## MCP 介面

資產集要進現有 storyteller MCP 機制，沿用 `/storyteller-mcp`、`storytellerpat`、`service/mcp/storyteller_tools.go` 的 tool 註冊方式，不另開一套 MCP endpoint。MCP 呼叫端拿到的權限跟 PAT 綁定的使用者一致，所有 asset tool 都必須帶 `project_public_id`，並在 service 層確認該 project 屬於目前使用者。

建議新增工具：

- `storyteller_list_assets`：列出某 project 的資產，支援 `collection_id`、`asset_type`、keyword、page/page_size。`collection_id` 空值代表全部，`__uncategorized__` 代表未分類。
- `storyteller_get_asset`：取得單筆 asset metadata 與作者可用的簽名預覽 URL。
- `storyteller_presign_asset_upload`：取得資產上傳用 presigned PUT URL，取代未來資產化流程中的圖像專用 presign。
- `storyteller_confirm_asset_upload`：檔案 PUT 完成後建立 asset row，並回傳 `asset_public_id`。
- `storyteller_update_asset`：更新 title、alt_text、description、metadata。
- `storyteller_delete_asset`：soft delete；若仍被最新內容引用，回傳錯誤。
- `storyteller_list_asset_collections`：列出某 project 的資產 collections。
- `storyteller_create_asset_collection`：建立 collection。
- `storyteller_update_asset_collection`：重新命名或調整排序。
- `storyteller_delete_asset_collection`：刪除 collection；底下仍有資產時不允許刪除，避免誤搬資料。
- `storyteller_move_asset`：把資產移到指定 collection，或移回未分類。

既有工具調整：

- `storyteller_upsert_story` / `storyteller_upsert_lore`：允許內容包含 `steamloom-asset://assetPublicId`，寫入時更新 asset references，並檢查所有 asset 都屬於同一個 project。
- `storyteller_get_story` / `storyteller_get_lore`：內容仍回原始 asset URI，不把簽名 URL 寫回內容；需要預覽資產時用 `storyteller_get_asset`。
- `storyteller_upsert_image_story`：新增支援 page 帶 `asset_public_id`。舊的 `key` 仍保留相容，但新資料以 asset 為準。
- `storyteller_presign_image_upload`：短期保留，避免破壞現有 MCP client；長期可在描述裡標註建議改用 asset upload flow。

MCP 不提供匿名讀取工具，也不提供「只用 asset public id 任意簽 URL」的公開能力；簽名預覽 URL 只給通過 PAT 的作者管理用途。

## 工程難度

### Image-only MVP：中等

可利用既有 S3 presign 與 CloudFront 簽名邏輯，主要是補資料表、CRUD、引用解析、前端選擇器與既有圖像作品頁整合。以目前 codebase 估算，若 UI 不做太華麗，大約是 3-6 個工作天等級。

### Image + Audio + Video：中高到高

audio/video 會多出播放相容性、檔案大小、縮圖、duration metadata、可能的轉碼與串流問題。若沒有外部媒體處理服務，第一版直接做完整影音資產會把 scope 拉大很多，建議等 image asset 穩定後再開。
