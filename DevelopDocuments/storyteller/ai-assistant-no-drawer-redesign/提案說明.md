# Storyteller AI 助理 No-Drawer 提案

日期：2026-09-11

## 結論

如果完全拋棄 Drawer，我建議不要再找另一個容器收納完整聊天室，而是把 AI 拆回作者真正會做的三種工作：

1. **在文字旁下指令**：選字後直接出現 inline command toolbar。
2. **在原文旁討論**：回覆以不寫入文章內容的 inline thread 錨定在段落後方。
3. **用完整工作區審稿**：修改提案切換為 Review mode，佔用主編輯區呈現 diff。

AI 不再是一個要「打開、進去聊天、關掉」的地方，而是編輯器的一組協作能力。

## 這輪收斂後的三項決定

### 文件內不會同時鋪滿所有 AI thread

`thread` 是一次針對同一 anchor 的完整討論，不是每一則 AI 回覆都插一張卡。顯示規則固定為：

- 整份文件同時只展開一個 active thread。
- 同一 anchor 再次「問 AI」時接在原 thread，不新增另一塊。
- 非 active thread 收成稿紙 gutter 的 `✦` 小錨點，不佔文章高度。
- 有 pending proposal 的錨點加 badge，優先巡覽。
- 已套用／未採用且沒有新訊息的 thread 預設隱藏，可由頂部 `AI 討論` 找回。

因此討論多不會讓編輯區無限制變長；畫面上只有作者正在處理的那一組內容。

### `/` 選單新增單一「AI 協作」區塊

建議在既有 slash menu 最前方加入一個 `AI 協作` group，但只放一項：

```text
✦ 問 AI
  針對目前段落提問或修改
```

選取後關閉 slash menu，打開共用 command bar。它不把 `/ai` 寫進故事內容，也不是另一個 content block；只是 editor command。若當下有 selection，scope 用 selection；只有 caret 時，scope 用目前 paragraph／block。

不要在 slash menu 再列 `/rewrite`、`/expand`、`/translate`。那些是送出後端的執行模式，不需要成為三個不同入口。

### 選字與右鍵浮動選單只留「問 AI」

建議移除 `改寫`、`擴寫`、`翻譯` 等平行 AI action，只留一個 `✦ 問 AI`。開啟 command bar 後，再提供 `改寫／擴寫／縮短／調整語氣` preset chips；點擊只是預填 prompt，作者仍可補充要求。

這樣可以避免三套選單各維護一份 AI 功能，也避免「直接擴寫」在沒有看清 scope、Agent 與 context 時立刻送出。

入口與預設 scope 統一如下：

| 入口 | 預設 scope |
| --- | --- |
| 選取文字後「問 AI」 | selection + 前後段落 |
| 右鍵段落「問 AI」 | 目前 paragraph／block |
| 編輯器輸入 `/` →「問 AI」 | caret 所在 paragraph／block |
| 底部工具列 `✦ AI` | 目前故事／設定集 |

四個入口最後都進同一顆 command bar；差別只有一開始替作者帶入哪個 scope。

## 為什麼比 Drawer 更適合 storyteller

Drawer 最大的結構問題，不是 520px 太窄或手機 45vh 太矮，而是它把「原文」與「AI 對話」分成兩個互相競爭的視窗：

- 作者必須在文章與聊天之間反覆對照。
- selection、reply、context 被抽離原本位置，只能靠引用摘要辨認。
- 長回覆、工具軌跡、提案、composer 都搶同一條垂直空間。
- 手機不論右側 Drawer 或 bottom sheet，都會遮到文章或壓縮聊天。

No-Drawer 版本讓討論回到它所針對的段落，review 則取得完整畫面。每種任務使用適合自己的空間，不要求一個容器同時解決全部問題。

## 核心互動

### 1. 選字後直接操作

選取段落時，在選區上方顯示：

- `✦ 問 AI`
- `改寫`
- `擴寫`
- 更多指令

`改寫`、`擴寫` 仍可轉為既有 `/rewrite`、`/expand`，不需要更動後端 mode。一般問答與更多需求則打開編輯器底部中央的 command bar。

沒有選字時，底部工具列的 `✦ AI` 可開啟同一個 command bar，作用範圍預設為目前故事。

### 2. Command bar 只負責送出

command bar 不承擔歷史訊息，只包含：

- 這一輪的 context chips
- prompt input
- Agent／model 摘要
- send

送出後立即關閉；背景執行狀態顯示在原文錨點與底部 AI 按鈕，不讓輸入容器常駐佔位。

### 3. AI 回覆錨定在原文

回覆以 editor decoration／portal 的方式插在目標段落後，不成為實際故事內容：

```text
原文段落

✦ Mira · 回覆這一段
  回覆內容……
  ▸ 參考內容／工作軌跡
  修改提案

下一段原文
```

好處：

- 不需要引用「你剛才選的是哪一段」。
- 作者可直接看前後文，判斷 AI 是否理解錯誤。
- 同一章可以有多個獨立 thread，不會全部混成一條聊天歷史。
- thread 可收合成一條帶狀標記，不干擾長時間寫作。

資料層仍可沿用現有 chat／message，只需在 metadata 或獨立欄位保存 anchor marker id。若第一版不改 schema，也能先把同一 session 的 thread anchor 留在 local state；重開後回到章節層級 thread。

### 4. 修改提案切換到 Review mode

點擊 `進入 Review mode` 後，不開 Dialog，也不開 Drawer；主編輯區切成審稿工作區：

- 頂部：提案名稱、目前第幾項、返回寫作
- 次列：故事、作用範圍、base version、變更量
- 桌面：原文／提案左右並排
- 手機：原文／提案 tab 切換
- 底部：不採用、風險說明、套用

Review mode 使用完整主畫面，長篇 diff、code block、圖片與多 section 才有足夠空間。套用後回到原錨點，inline thread 顯示 `已套用`，文章立即更新並保留版本復原入口。

### 5. 找回散落的 thread

頂部工具列顯示 `AI 討論 2`：

- 點擊後跳到最近未處理的 thread。
- 再點依文件順序巡覽下一個。
- 沒有待處理項目時跳到最近一則。

不另外做全高 thread 列表；真的需要跨章節搜尋時，放進獨立的專案 activity 頁，而不是把 Drawer 搬回來。

## 桌面配置

- 文章始終維持原本最大寬度，不因 AI 開關改變換行。
- inline toolbar 貼選區出現，失焦後消失。
- thread 可暫時超出稿紙左右 padding，但仍留在稿紙範圍內。
- command bar 浮在底部工具列上方、對齊主編輯區中央。
- Review mode 替換主內容，不影響左側章節樹與頂部 breadcrumb。

## 手機配置

手機不再需要 Drawer、bottom sheet 或固定 45vh：

- selection toolbar 精簡為 `問 AI／改寫／擴寫`。
- command bar 貼底部工具列上方，送出後立即消失。
- inline thread 直接進入文章 flow，可收合。
- Review mode 佔主內容，原文／提案以 tab 切換。
- 返回寫作後 scroll 回原 anchor。

這會讓手機在任何時間只有一個主要閱讀面，不需要文章與 AI 面板互搶高度。

## 與現有能力的對應

| 現有能力 | No-Drawer 呈現 |
| --- | --- |
| selection trigger | 選區上方 inline toolbar |
| 一般 agentic query | command bar → inline thread |
| `/rewrite`、`/expand` | inline quick actions／slash menu |
| reply reference | thread 內「繼續問」，天然承接同一 anchor |
| Agent／model override | command bar metadata popover |
| tool steps | thread 內收合的工作軌跡 |
| proposals | thread 內摘要卡 → Review mode |
| apply／reject | Review mode footer |
| usage | 工作軌跡 metadata |
| chat history | 文件內 thread；跨章節另走專案 activity |

## 建議元件切分

- `StorytellerSelectionAIBar`
- `StorytellerAICommandBar`
- `StorytellerInlineAIThread`
- `StorytellerInlineAIThreadAnchor`
- `StorytellerAIProposalSummary`
- `StorytellerAIReviewWorkspace`
- `StorytellerAIThreadNavigator`

其中 thread 應透過 editor plugin／decoration 呈現，不要直接塞入 ProseMirror document，避免 AI UI 被序列化進故事 Markdown。

## 主要代價與風險

### 1. 實作成本高於改 Drawer

需要處理 anchor marker、editor decoration、重新載入後定位、段落刪除或合併後的 orphan thread。這不是單純搬 JSX。

### 2. 多 thread 可能讓文章變長

必須預設一次只展開目前 active thread，其他收合成窄列；離開章節前記住展開狀態沒有必要。

### 3. 全域問題沒有自然錨點

針對整篇故事的問題固定錨在標題下方，或歸類為 chapter thread。不要為了這個例外重新引入側欄。

### 4. Anchor 失效要有降級策略

marker 被刪除時，thread 不應消失。建議移到章節標題下方並標示「原段落已不存在」，讓作者決定刪除 thread 或重新指定位置。

## 建議導入順序

1. 先做 selection toolbar + command bar，仍把回覆送回現有 Drawer，驗證輸入入口。
2. 加入 session 內 inline thread，不做跨 reload anchor。
3. 導入持久化 anchor 與 thread navigator。
4. 把 proposal diff 改成 Review mode。
5. 最後移除 Drawer 與相關 mobile bottom sheet 邏輯。

這個順序可以逐步驗證，不必在一次改版裡同時承擔 editor plugin、chat history 與 review workspace 的全部風險。

## Mockup 操作

- 選區上方：`問 AI`、`改寫`、`擴寫`
- 底部工具列：`✦ AI`
- inline thread：收合／展開工作軌跡
- 提案：進入 Review mode
- Review mode：桌面左右 diff、手機 tab diff、套用並回到文章
- 頂部 `AI 討論 2`：跳回錨定 thread
- 桌面／手機與深／淺色切換
