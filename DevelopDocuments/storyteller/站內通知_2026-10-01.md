# 站內通知（In-app Notifications）

- 狀態：已實作（2026-10-01），在 `feature/storyteller-notifications` 分支，尚未併入 main；mockup 見 `notification-mockup/`
- Branch：`feature/storyteller-notifications`
- 範圍：只做 storyteller（steamloom），收件人用 storyteller 使用者 id（與 `storyteller_author_favorites.user_id` 同一套）
- 前置關係：之後的留言、作者動態（公告／預告／活動）、Web Push 都疊在這一層上面

## 目標

1. 一個**通用的通知寫入入口**，任何功能在業務寫入成功後呼叫一次就能送出通知，不用自己管收件人去重、聚合、已讀狀態。
2. v1 接兩類來源：
   - **內容更新**：追蹤的作者／收藏的作品有新話公開、新作品公開
   - **安全**：新的 OAuth 應用程式取得授權、新建 Personal Access Token
3. 前端：頂欄鈴鐺加未讀數，點開看最近通知，另有完整通知頁。

## 不做（這一輪）

- Web Push、email 摘要（之後疊在同一張表上，由派送層讀取）
- SSE／WebSocket 即時推播（沿用既有決策：暫緩），改用輪詢
- 依通知類型個別關閉的偏好設定（v1 視「追蹤／收藏」為同意接收；設定頁等真的有人嫌吵再做）
- 留言、作者動態本身
- 梭梭記憶草稿、稽核月匯出等其他來源（已確認不需要）

## User Stories

| # | 角色 | 情境 | 期望 |
|---|---|---|---|
| U1 | 讀者 | 追蹤的作者發了新的一話 | 鈴鐺出現未讀數；點開通知看到這次更新了哪幾話，再從內容頁進 Reader |
| U2 | 讀者 | 收藏的作品一次公開整冊 10 話 | 只收到**一則**「《作品》更新了 10 話」，不是 10 則 |
| U3 | 讀者 | 作者把私密作品改成公開 | 收到「作者發表了新作品《作品》」一則 |
| U4 | 讀者 | 作者把某話改回草稿再改回完成 | 不會被通知第二次 |
| U5 | 讀者 | 同時追蹤作者又收藏作品 | 同一次更新只收到一則 |
| U6 | 讀者 | 點了通知，但那一話已經被下架／刪除 | Reader 走既有 404／無權限畫面，通知標成已讀，不壞頁 |
| U7 | 作者 | 自己發新話 | 自己不會收到通知 |
| U8 | 讀者 | 一鍵全部標為已讀；刪掉單則通知 | 刪除走 confirm dialog，soft delete |
| U9 | 使用者 | 有新的 OAuth 應用程式連上帳號、或建立了新的 PAT | 收到安全通知，含入口／IP／裝置；不是本人操作就能一鍵到管理頁撤銷 |
| U10 | 使用者 | 想留下某則通知（之後可能是粉絲的支持信） | 按「鎖定」，鎖定的通知不會被 180 天保留期清掉；有數量上限 |
| U11 | 使用者 | 通知快到保留期限 | 頁面上看得到保留期說明，快到期的通知會標「N 天後清除」 |

## 核心設計：「新話公開」怎麼偵測

### 為什麼不在每個寫入點 hook

一話「對讀者可見」的條件是：**專案 `visibility = public` 且 話 `status = completed` 且（沒分冊或所屬冊 `status = completed`）且未刪除**。會讓這個條件從否變成是的入口很多：

- 新建 story（`normalizeStoryRequest` 預設 status 就是 `completed`）
- story 草稿→完成、冊草稿→完成（一次放出整冊）
- story 從草稿冊搬進已完成的冊
- 專案 private／unlisted → public（一次放出整部）
- PAT／MCP upsert、之後單機版 publish

逐點 hook 一定會漏，而且「草稿↔完成來回切」的去重得分散在各處處理。

### 做法：排程掃描 + `first_published_at`

1. `storyteller_stories` 新增 `first_published_at DATETIME NULL`。
2. 排程每 5 分鐘跑一次：找出「目前符合可見條件且 `first_published_at IS NULL`」的話 → 寫入 `first_published_at = NOW()` → 依專案聚合後派送通知。
3. `first_published_at` 只寫一次，之後怎麼切狀態都不會再通知（U4）。
4. 所有入口（含之後的單機 publish）都自動涵蓋，不用改既有寫入程式。
5. 5 分鐘延遲順便當緩衝：作者手滑發佈、馬上改回草稿，就不會發出通知（因為掃描當下不可見）。

代價：通知最多晚 5 分鐘。對「新話更新」這類通知可以接受。

### 收件人

對每個「本輪新公開的話」：

- 追蹤該話任一署名身份的讀者：`storyteller_story_profiles`（沒有列 = profile 0）× `storyteller_author_favorites (author_user_id, author_profile_id)`
- 收藏該作品的讀者：`storyteller_project_rankings.is_favorite = 1`
- 排除作者本人（`project.user_id`）
- 依 `(收件人, 專案)` 去重聚合（U2、U5）

### 通知文案的身份

通知只帶**這一話的署名筆名**（`AuthorIdentityOutput`），不帶帳號 id，避免多筆名被串起來。

## 安全通知

| kind | 觸發點 | 內容 | 連結 |
|---|---|---|---|
| `security.oauth.authorized` | `storytelleroauth.exchangeCode` 成功、**首次**建立 grant 時（同一個 grant refresh 不再發） | 應用程式名稱、時間、IP、User-Agent 摘要 | 帳號與安全 › OAuth 授權 |
| `security.pat.created` | `CreatePersonalAccessToken` 成功後 | PAT 名稱、token 前綴、到期日、IP、User-Agent 摘要 | 開發者 › Personal Access Token |

- 收件人是帳號本人，**不排除操作者本人**：安全通知的用意就是「如果不是你做的」。
- 每則各自獨立，不聚合（`group_key` = `kind:{grant/pat public_id}`）。
- IP／User-Agent 從既有的 audit request context 取，不另外解析。
- 文案固定附一句「不是你本人操作？立刻撤銷」，按鈕直接連到對應管理頁。

## Schema

```sql
-- 新話首次公開時間；只寫一次，作為去重依據
ALTER TABLE storyteller_stories ADD COLUMN first_published_at DATETIME NULL;

CREATE TABLE storyteller_notifications (
  id           BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  public_id    VARCHAR(32)  NOT NULL,
  user_id      BIGINT UNSIGNED NOT NULL,          -- 收件人
  kind         VARCHAR(64)  NOT NULL,             -- 例：story.published、project.published
  group_key    VARCHAR(191) NOT NULL,             -- 去重鍵，同收件人同 key 只會有一筆
  project_id   BIGINT UNSIGNED NULL,              -- 方便之後依專案靜音／清除
  payload      JSON NOT NULL,                     -- 顯示用快照：project/story public_id、標題、筆名、話數
  read_at      DATETIME NULL,
  locked_at    DATETIME NULL,                     -- 使用者鎖定的時間；非 NULL 就不會被保留期清除
  is_deleted   TINYINT(1) NOT NULL DEFAULT 0,
  deleted_at   DATETIME NULL,
  created_at   DATETIME NOT NULL,
  UNIQUE KEY uk_user_group (user_id, group_key),
  KEY idx_user_list (user_id, is_deleted, id),
  KEY idx_user_unread (user_id, read_at),
  KEY idx_user_locked (user_id, locked_at),
  KEY idx_purge (locked_at, created_at)
);
```

- `payload` 快照內容依 kind 而定，要足夠渲染內容頁、不用再 join：
  - `story.published`：專案 public_id／名稱、署名筆名、更新的話清單（public_id、標題、字數），清單最多存 50 筆，另存總數，超過的部分顯示「以及其他 N 話」
  - `project.published`：專案 public_id／名稱、簡介、tags、分級、當下話數與字數
  - `security.*`：client 名稱／授權範圍或 PAT 名稱／前綴／到期日，加上時間、入口、IP、User-Agent
- `payload` 存**快照**而不是每次 join：作品改名或被刪除時舊通知照樣能顯示，連結點下去由 Reader 判斷權限（U6）。
- 前端依 `kind` 組文案，不在 DB 存整句文字，之後改字不用動資料。
- `group_key` 範例：`story.published:{project_public_id}:{batch_id}`。重複寫入用 `INSERT IGNORE`，排程重跑或 crash 後重做都不會重複發。

## 通用寫入入口

```go
// service/storytellernotify
// Notify 只能在業務寫入成功後呼叫；以 group_key 冪等，重送安全。
func (s *Service) Notify(inputs []NotificationInput) error
```

- 直接批次寫 MySQL，不走 Redis stream。量級還小，audit 那套 retry／dead stream 先不用搬過來。
- 之後的留言、作者動態都呼叫這一支。

## 新增通知類型的方式

一律呼叫 `storytellernotify.Service.Notify([]Input)`，不用寫新的寫入方法：

1. **所有類型都必填 `title`／`body`**（`Notify` 會擋空白值）：純文字、保留換行，**不解析 markdown**。有專屬畫面的類型也要填一份文字摘要（例如新話通知會自動填「鴉羽 的《霧都旅館》更新了 3 話」），前端遇到不認識的 kind、之後若做推播都靠這份文字。
2. **`link` 選填**：站內路徑（`/` 開頭）或 `http(s)://` 外部網址都可以，外部網址會另開分頁；`javascript:` 等其他協定前端不顯示按鈕（避免點了直接執行程式碼）。沒填就只顯示標題與內文。只有內部人員會寫這個欄位，所以不限制網域。
3. **簡單類型**（公告、提醒）：`Kind` 取新名字（例如 `system.announcement`），只填通用欄位即可，**前端不用改**。
4. **需要專屬畫面的類型**：`NotificationPayload` 加欄位，前端在 `storytellerNotificationUI.ts` 的 `notificationHeadline` 和 `StorytellerNotificationDetail.tsx` 的 `NotificationBody` 各加一個分支。之後粉絲來信這種使用者撰寫的長內容若要 markdown，走這條、用既有的 `StorytellerMarkdown` 渲染，不改通用欄位。
5. `GroupKey` 決定冪等範圍：同一收件人同一 key 只會留一筆，重送安全。
6. 業務寫入成功後才呼叫；跟業務寫入必須同一個交易的（例如發佈掃描），改用 `NewRows` 產生資料列，自己放進交易。

## 前端

- **頂欄鈴鐺**（StorytellerShell）：未讀 badge。分頁可見時每 60 秒輪詢 `unread-count`，切回分頁、換路由時也會更新。
- **鈴鐺 popover**（桌機）：最近 10 則、「全部標為已讀」、「查看全部」。手機版點鈴鐺直接進通知頁。
- **點通知＝打開內容，不直接跳走**：
  - 路由 `/storyteller/notifications/:public_id`，打開即標為已讀。
  - 內容區夠寬時，左右分欄：左邊列表、右邊內容。不夠寬時（手機、平板、縮小的視窗，用 container query 判斷），改成「列表 → 內容」切換，內容頁上方有「‹ 返回通知」。
  - popover 點通知會導到通知頁並打開那一則。
  - 各 kind 的內容頁：
    - 新話：這次更新的每一話（標題、字數、閱讀連結），加上「從第 N 話開始讀」「前往作品首頁」。
    - 新作品：封面、簡介、tags、話數與字數，加上「從第 1 話開始讀」「前往作品首頁」。
    - 安全：完整資訊（應用程式或 Token、時間、範圍、入口、IP、裝置）、「不是你本人操作？」警告，以及前往撤銷或刪除的按鈕（導到管理頁，不在通知裡直接撤銷）。
  - 內容頁底部顯示「N 天後自動清除」或「已鎖定」。
  - 代價：讀新話要多點一下（先開通知，再按閱讀）。之後社群功能的粉絲來信、留言回覆這種長內容，本來就需要內容頁。
- **通知頁** `/storyteller/notifications`：麵包屑「Steamloom › 我的工作台 › 通知」、全部／未讀／已鎖定切換、無限捲動、單則刪除（confirm dialog）。
- **保留期提示**：通知頁頂端固定一條說明「通知會在 180 天後自動清除；鎖定的通知會永久保留（已鎖定 3 / 50）」。距離清除剩 14 天內的通知，標上「N 天後清除」。
- **鎖定按鈕**：每則通知右側有鎖頭按鈕，鎖定後帶「已鎖定」標記。達上限時按鈕仍可按，按下後跳 snack「已達鎖定上限 50 則，請先解除其他通知的鎖定」。
- API 失敗一律跳 snack。
- 實作前會先出 mockup 給你看。

## 稽核

- 標已讀、全部已讀屬於介面狀態，不記（依稽核規格「介面暫存」）。
- 刪除、鎖定、解除鎖定記 `notification.delete`、`notification.lock`、`notification.unlock`，屬低重要度（同收藏）。
- 排程每次執行記一筆 `system.notification.fanout`（新公開幾話、送出幾則）。
- 保留期清除記 `system.notification.purge`。

## 保留期

- **建立超過 180 天且未鎖定**的通知由排程每日 hard delete（含 soft delete 過的）。這是保留期清理，不是使用者刪除，所以不受 soft delete 規範限制。
- 以建立時間計算、不論是否已讀：原本草稿寫「已讀且超過 180 天」，但這樣從不打開的帳號未讀通知會無限累積。
- **鎖定上限 50 則**（設定值 `STORYTELLER_NOTIFICATION_LOCK_LIMIT`，預設 50）。上限只擋「新增鎖定」，日後調低上限也不會解除既有的鎖定。

## 常見失敗與應對

| 情境 | 應對 |
|---|---|
| 上線當下所有已公開的話都還沒有 `first_published_at`，第一輪掃描會對全站讀者狂發通知 | migration 內 backfill：目前符合可見條件的話一律設 `first_published_at = created_at` |
| 排程寫完 `first_published_at` 後派送失敗 | 同一個 transaction 寫 `first_published_at` 和通知；失敗整批 rollback，下一輪重做（`group_key` 冪等） |
| 兩台機器同時跑排程 | 不另外加 Redis 鎖：同一個交易裡用 `UPDATE ... WHERE id IN ? AND first_published_at IS NULL` 認領，affected 筆數不足代表別的執行先寫掉了，整批 rollback、交給下一輪（見實作備註 2） |
| 熱門作者粉絲多，一次 fan-out 太大 | 收件人分批 insert（每批 500）；目前量級不會遇到，先記著 |
| 專案公開→私密→公開 | 話的 `first_published_at` 已存在，不會重發；「新作品公開」由「這個專案先前有沒有任何話公開過」判斷，不需要 `projects.first_published_at`（見實作備註 1） |
| 作品被刪除或轉私密，通知還在 | 保留通知，點下去由 Reader 決定能不能看；不主動清掉通知（避免洩漏「它曾經存在」以外的資訊） |
| 使用者鎖定的時候剛好碰上清除排程 | 清除用 `WHERE locked_at IS NULL AND created_at < ?` 一次刪，鎖定要求先到就不會被刪；後到則回 404，前端跳 snack |
| 兩個分頁同時鎖定，衝破上限 | 鎖定用 `UPDATE ... JOIN (SELECT COUNT(*) ...) WHERE locked < limit` 的條件式更新，不先查再寫；子查詢是一致性讀，真的同一瞬間併發仍可能多鎖 1 則，可接受 |
| R18 作品 | 收件人本來就主動追蹤過，照常通知；通知列表沿用作品卡既有的分級標示 |

## 實作備註（跟草稿不同的地方）

1. **「新作品公開」不另外加欄位**：作者頁本來就是「有可見的話才算出現」，所以把「這個專案先前沒有任何話的 `first_published_at` 有值」（含已刪除的話）視為新作品。專案轉公開、新專案第一話完成都會自然落到這條，少一個 `projects.first_published_at` 欄位和對應的回填。
2. **排程不加 Redis 鎖**：認領與派送在同一個交易裡，認領用條件式 UPDATE，重跑或兩台同時跑都只會有一方成功；`group_key` 的 `INSERT IGNORE` 是第二道保險。
3. **`Story` struct 不加 `first_published_at`**：既有程式有對 `Story` 做 `Save()` 的路徑，欄位放進 struct 會把排程剛寫的值蓋回 NULL，所以只由排程用原生 UPDATE 寫入。
4. **OAuth 安全通知的 IP／User-Agent 取自按「允許」當下**：`/oauth/token` 是應用程式的伺服器在呼叫，那裡的 IP 不是使用者的。授權碼（Redis）多存一份 `origin`，grant 建立時拿來發通知。
5. **payload 多存 `project_slug`**：前端標準閱讀網址是 `work/{public_id}-{slug}/...`。Reader 只看 public_id，slug 之後改了也不影響。
6. **安全通知失敗不影響主流程**：建立 PAT／授權成功後才發，發送失敗只記 ERROR log。
