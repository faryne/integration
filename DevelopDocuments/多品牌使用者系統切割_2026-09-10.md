# 多品牌使用者系統切割規劃

## 背景

原始需求：讓 Storyteller（steamloom.works）跟主站 `users` 表脫鉤，並換一個獨立 Firebase 專案讓登入彈窗顯示「SteamLoom」品牌，而不是現在共用的名稱。

討論過程中發現這其實是「多品牌」議題——目前 faryne.dev 這個 monorepo 底下至少還有 galgame.tv、neko.maid.tw 兩個品牌，也可能面臨同樣的「要不要切開共用 `users` 表」的問題，因此把設計拉高一層，先確認三個品牌的現況，再決定這一輪實際要做的範圍。

## 三個品牌現況（2026-09-10 盤點）

| 品牌 | 使用者相關現況 | 這次要不要動 |
|---|---|---|
| storyteller（steamloom.works） | 已有 `storyteller_users` profile 表，透過 `user_id` 外鍵掛在 `users` 下（[migration/20260623123000-create_storyteller_users.sql:14-15](../migration/20260623123000-create_storyteller_users.sql)），沒有直接 SQL JOIN，是 Go 層在 3 個 fallback 函式裡回頭查 `users` 拿 email/display_name/photo_url（見下方「現況細節」） | **這一輪要做**：已經有 profile 表的形狀，只是要斷開 FK、補欄位、換一條登入路徑，是小工程 |
| galgame.tv | 目前**沒有**自己的 profile 表，直接吃 `users` 表的欄位（email/display_name/photo_url 等），跟主站是同一套使用者資料，沒有中間層 | **這一輪不動**。要切開的話，得先設計並生出一張 `galgame_users`（或類似名稱）的 profile 表、寫 migration、把現有 `users` 資料 backfill 過去——這是跟 storyteller 完全不同量級的獨立工程，混在這一輪只會讓範圍失控。留給未來單獨開一份規格 |
| neko.maid.tw | 目前完全沒有任何 user 功能 | 談不上「切割」，純粹記一條原則：**未來 nekomaid 要加 user 功能時，一開始就直接走本次設計的 `CreateSessionFor` + 自己的 profile 表**，不要先掛 `users` 再回頭切（呼應既有 [新產品線路徑要早用 helper] 的做法：一開始就用對的架構，不要等有需要才回頭改寫死的東西） |

## 現況細節（storyteller ↔ users 耦合點）

- `storyteller_users` 沒有直接 SQL JOIN `users`，是 Go 層在 3 個地方回頭查（[service/storyteller/storyteller.go:3128](../service/storyteller/storyteller.go)「gravatarURL」、[:3141](../service/storyteller/storyteller.go)「fallbackAuthorName」、[:3155](../service/storyteller/storyteller.go)「loginAvatarURL」），各自 fallback 到 `users` 的 email/display_name/photo_url。
- 登入（[service/auth/session.go:32](../service/auth/session.go) `CreateSession`）目前只碰 `users` 表，跟 `storyteller_users`完全脫鉤——`firebase_uid` 只存在 `users`。
- Firebase 專案：前端/後端目前四個品牌（main/galgame/nekomaid/steamloom）共用同一個 Firebase 專案 `faryne-integration`（[static_site/.env](../static_site/.env)、[config/index.go:25](../config/index.go)），但 build 系統本身已經是「每個品牌各自 build+deploy」（[makefile:14-36](../makefile) 四個獨立 target），換 Firebase 專案不需要在前端加 runtime 判斷，只要讓 `build-frontend-steamloom` 那個 target 多帶一組專屬 `VITE_FIREBASE_*` 即可。後端沒有用 Admin SDK，是自刻 JWT 驗簽（[service/auth/firebase_token.go:48](../service/auth/firebase_token.go)），只比對單一 `FIREBASE_PROJECT_ID`，改成比對一份合法清單即可支援多專案。

## 這一輪的設計決定

### 1. `CreateSessionFor`：用 func type 參數取代寫死的 upsert 邏輯

不用 optional callback（沒傳就走預設），因為一旦有多個品牌，「預設行為」這個概念本身就不成立——包括主站現有登入也該是明確傳入的一個變體，跟 storyteller／未來 galgame 平等並列，不是隱含的 fallback。也不用單一 method 的 interface（Go 慣例上這種情況直接用 func type 就好，不用多包一層外殼）。

```go
type UpsertFirebaseUserFunc func(*auth.FirebaseToken) (*modelAuth.User, error)

func CreateSessionFor(idToken string, upsert UpsertFirebaseUserFunc) (*modelAuth.SessionResponse, error) {
	verified, err := VerifyFirebaseIDToken(idToken)
	if err != nil {
		return nil, err
	}
	user, err := upsert(verified)
	if err != nil {
		return nil, err
	}
	return issueSession(user)
}
```

- 主站現有登入：把 `CreateSession` 現在的 upsert 邏輯（[service/auth/session.go:38-43](../service/auth/session.go)）原封不動搬成一個 `UpsertFirebaseUserFunc` 變體。
- storyteller：新的 upsert 函式改查/寫 `storyteller_users`，回傳前轉成 `*modelAuth.User` 形狀（`Id` 借用 `storyteller_users.id`）。這個轉接函式不算「一系列新方法」，純粹是 struct 轉接，`issueSession`/`RedisSession`/`UserResponse` 完全不用動、可以直接共用。
- galgame：現在還是直接用 `users`，所以它的 upsert 函式**現在**跟主站那個完全一樣；等它未來真的生出自己的 profile 表，只需要換掉這個 func，`CreateSessionFor` 本身不用再動。

### 2. `RedisSession` 加 `Brand` 欄位，防止跨品牌 session 被誤判成別人

**風險**：`storyteller_users.id` 跟 `users.id` 都是各自從 1 開始的 auto-increment，數字大概率會撞號。一旦 storyteller 的 session 的 `UserId` 開始代表 `storyteller_users.id`，如果同一把 `X-Encrypt-Key` 被拿去打其他品牌的 API（debug 工具複製貼上、以後哪個共用元件寫錯、或未來 galgame 也切開後 id 空間各自獨立），對方的程式碼會拿這個數字當自己的 `users.id`/`galgame_users.id` 去查——大概率查到一個完全不相關的真實使用者，回傳/修改到他的資料，是資料外洩等級的問題。瀏覽器層面因為 localStorage 是 per-origin 隔離，不會「自動幫你登入別的品牌」，但後端本身沒有任何機制擋這件事，不能只靠「反正 domain 隔離應該不會發生」這種脆弱假設。

**修法**：

- [model/entity/auth/session.go:18-23](../model/entity/auth/session.go) 的 `RedisSession` 加一個欄位：`Brand string \`json:"brand"\``（值如 `"main"`／`"storyteller"`／`"galgame"`）。
- `issueSession`／`CreateSessionFor` 簽發 session 時打上對應品牌標記（`CreateSessionFor` 可以多一個 `brand string` 參數，或者直接讓每個品牌自己的 wrapper 函式決定）。
- [middleware/authsession/authsession.go:19](../middleware/authsession/authsession.go) 的 `New()` 改成接受一個 `expectedBrand string` 參數，查到 session 後多一行檢查：`if session.Brand != expectedBrand { return output.Unauthorized(...) }`。各品牌的 route group 呼叫時各自傳入自己的 brand（例如 storyteller 那邊改成 `authsession.New("storyteller")`）。
- 主站現有的呼叫點（目前 `authsession.New()` 沒帶參數的地方）改傳 `"main"`，是唯一需要回頭補的既有呼叫點，數量不多。

這樣不管將來哪個品牌各自有獨立 id 空間，同一把 key 只能在對的品牌底下生效，從根本排除「跨品牌認錯人」，不是靠 domain 隔離的偶然安全感。

### 3. `storyteller_users` 補欄位、拔 FK

- 新 migration：拔掉 [migration/20260623123000-create_storyteller_users.sql:14-15](../migration/20260623123000-create_storyteller_users.sql) 的 `FOREIGN KEY (user_id) REFERENCES users(id)`；`storyteller_users` 新增 `firebase_uid`（唯一索引）、`email`、`display_name`、`photo_url` 欄位。
- 既有 `storyteller_users` row 的這些新欄位，用一次性遷移腳本從 `users`（透過現有 `user_id` 外鍵關聯）backfill 過去，backfill 完才能真正切斷依賴。
- [model/entity/storyteller/storyteller.go:659-678](../model/entity/storyteller/storyteller.go) 的 `UserProfile` struct 加對應欄位。
- 改掉 `gravatarURL`/`fallbackAuthorName`/`loginAvatarURL` 三個函式（[service/storyteller/storyteller.go:3128-3161](../service/storyteller/storyteller.go)），讀自己表的欄位，不再呼叫 `authRepo.NewUserRepository().UserByID(...)`。

### 4. Firebase 專案分離（SteamLoom 品牌）

- Firebase Console 開一個新專案，Google OAuth consent screen 的 Public-facing name 設成「SteamLoom」（純 console 操作，不是 code）。
- [makefile:32-36](../makefile) 的 `build-frontend-steamloom` 內建時多帶一組 `VITE_FIREBASE_*` 環境變數，覆蓋 [static_site/.env](../static_site/.env) 的預設值。
- [config/index.go:25](../config/index.go) 的 `FirebaseProjectID` 改成清單（例如逗號分隔或 slice），[service/auth/firebase_token.go:49-52,73-78](../service/auth/firebase_token.go) 的比對邏輯從「等於單一值」改成「存在於合法清單中」。
