## 2. 帳號（2026-11-05 定案：Firebase＋使用者登入時順便搬家）

### 2.1 背景與決策

- 舊資料（`users_v2`，2016 年版）：用**帳號**登入（不是 email）；密碼在 Laravel 版程式是 `hash_hmac('md5', <CloudFront 私鑰 PEM 內容>, 密碼)`（密碼當 HMAC 鑰匙），更早期可能是單純 md5，使用者也不確定。2013 年版的 Google 登入（`users` 表）跟 `users_v2`／收藏無關，不處理。
- Firebase 的 HMAC_MD5 匯入是「固定鑰匙算密碼」，跟舊格式相反，**無法整批匯入**；舊站又用帳號登入。所以**不做一次性匯入**，舊會員第一次登入時由後端順便搬進 Firebase。
- Firebase 專案：使用者既有、給 neko.maid.tw 的**免費（Spark）專案**；開 Email/Password 登入。重設密碼信每天 150 封的上限不用在意（舊會員很久沒用了）。
- 不需要 SES：驗證信、重設密碼信都由 Firebase 寄。

### 2.2 登入：單一表單「帳號或 Email＋密碼」（2026-11-05 改：原本分兩個分頁，整合成一套）

註冊、登入、忘記密碼**全部由後端呼叫 Firebase**（Identity Toolkit REST API＋Web API Key，不需要管理者金鑰），前端不載入 Firebase 登入 SDK。
`POST /nekomaid/auth/login`（`login`、`password`，加上例外時才帶的 `new_password`／`new_email`）：

1. `login` 對得到 `users_v2.username`（未刪除）→ 當成帳號：
   - 已搬過（`firebase_uid` 有值）→ 用該帳號的 email `accounts:signInWithPassword` → 成功發 session
   - 還沒搬 → 走「舊帳號搬家」（下面）
   - 已合併的帳號 → 密碼驗證通過才回「已合併到 ○○ 帳號」
2. 否則當成 email：`signInWithPassword` 成功 → 依 `firebase_uid` 找使用者發 session；失敗 → 找「還沒搬、email 相同」的舊帳號，有就走「舊帳號搬家」（舊會員也能用 email＋舊密碼登入）
   - 同 email 有多個還沒搬的舊帳號 → 拿密碼逐一比對，**對得上的那個就是目前帳號**，其他的併進來；剛好多個都對得上時取 id 最小（最早註冊）的
   - 都對不上 → 再比對「已合併」的帳號，對得上就回「已合併到 ○○ 帳號」
3. 都不成立 → 一律回「帳號或密碼錯誤」（不透露帳號或 email 是否存在）

**舊帳號搬家**：驗舊密碼，依序試 HMAC-MD5（PEM 原始內容／去掉結尾換行）→ 單純 md5，log 記下命中哪一種 → `accounts:signUp`（email＋這次輸入的密碼）→ 綁 `firebase_uid`、清空 `userpass` → `accounts:sendOobCode`（VERIFY_EMAIL）寄驗證信 → 發 session。**同 email 的其他舊帳號這時還不合併**，等 email 驗證成功才合併（見 §2.5）。

**註冊** `POST /nekomaid/auth/register`（email、密碼）：email 對得到還沒搬的舊帳號 → 不建新帳號，回特定錯誤請他用舊密碼登入或重設密碼；否則 `signUp` → 新增 `users_v2`（`username`、`userpass` 都是空字串）→ 寄驗證信 → 發 session。

**因為 Firebase 帳號只會由後端建立**，不會有「別人搶先用這個 email 註冊、綁走舊收藏」的情況，所以不需要「email 未驗證不綁定」的規則。驗證信另有用途：證明信箱主人（合併的前提）與清除垃圾帳號（§2.5）。

### 2.3 搬家時的例外狀況

| 情況 | 處理 |
|---|---|
| 舊密碼不到 6 字，Firebase 拒收（`WEAK_PASSWORD`） | 回特定錯誤，前端請使用者設新密碼後連同 `new_password` 重送（舊密碼仍要先驗過） |
| 舊 email 格式錯或空白（`INVALID_EMAIL`） | 回特定錯誤，前端請使用者填新 email 後連同 `new_email` 重送 |
| 新 email 已被別的帳號使用（`EMAIL_EXISTS`） | 請使用者換一個 email |
| 同 email 的帳號其實是不同人（例如大家都填 `test@test.com`） | 合併只在 email 驗證成功時做（§2.5），收不到信的人併不走別人的帳號 |
| 被拿來猜密碼 | **我們自己的限流要比 Firebase 嚴**（依使用者 IP、依帳號）：所有登入都從伺服器打 Firebase，Firebase 看到的是同一個伺服器 IP，被它擋下會讓所有人都登不進去 |

### 2.4 忘記密碼

- `POST /nekomaid/auth/password-reset`（email）：
  - 對得到還沒搬的舊帳號 → 先 `signUp`（隨機密碼）並綁 `firebase_uid`，再 `accounts:sendOobCode`（PASSWORD_RESET）
  - 其他 → 直接 `sendOobCode`
  - 不論 email 存不存在，回應都一樣（不能拿來查帳號）
- 重設信裡的連結到 Firebase 的頁面設新密碼，之後一樣用登入表單登入。

### 2.5 Email 驗證、合併與清除（2026-11-05 定案）

- **寄驗證信的時機**：舊會員搬家、新會員註冊的當下（後端手上剛好有 idToken，用 `accounts:sendOobCode` VERIFY_EMAIL）；還沒驗證的人**每次登入自動重寄**，同帳號 24 小時最多一次。不做「重寄」按鈕。
- **驗證連結**：Firebase 後台把信件動作網址改成 neko.maid.tw 自己的頁面（`/auth/action`），後端用 oobCode 呼叫 `accounts:update` 確認，記下 `email_verified_at`。重設密碼信也走同一頁（`accounts:resetPassword`）。不這樣做，我們要等使用者下次登入才知道他驗證了，排程會誤刪。
- **合併在驗證成功時才做**：同 email（不分大小寫、去空白）的其他舊帳號，`users_fav_*` 併入（重複略過）、soft delete 並記 `merged_into_id`、`userpass` 保留（之後用它登入時驗得過密碼才告知「已合併到 ○○」）。驗證得了信箱＝這個信箱底下的帳號都歸他；亂填的 email（如 `test@test.com`）沒人驗證得了，就不會被誰併走。
- **待刪除與清除**（2026-11-05 使用者定案：**不分新舊帳號**，寄過驗證信的都適用）：
  - 驗證信寄出超過 **24 小時**仍未驗證 → 待刪除（不另存狀態：`verification_sent_at` 早於 24 小時前且 `email_verified_at` 為空）。舊會員搬家後沒驗證也一樣。
  - 每天一次排程，分批把待刪除帳號 soft delete；Firebase 帳號不刪（刪除需要管理者金鑰，閒置帳號也不收費）。
  - 待刪除或已清除的帳號，本人用正確密碼回來登入 → 恢復、重新給 24 小時並重寄驗證信（Firebase 帳號還在，不恢復的話這個 email 既不能註冊也不能登入）。
  - 還沒驗證時帳號照常可用，頁面頂端提示「請在 24 小時內到信箱點驗證連結，否則帳號會被刪除」。
- **一直沒回來登入的舊帳號永遠保留**：它們沒有 Firebase 帳號、從沒寄過驗證信（`verification_sent_at` 為空），不會符合待刪除條件，不需要另外標記新舊。
- 已知後果：舊會員的 email 若早已失效（格式正確但收不到信），搬家後 24 小時會被清除；之後用正確密碼登入會恢復，但驗證信仍寄到同一個失效信箱。要解決得另外做「修改 email」，不在本次範圍。
- 被合併的帳號不受影響：合併只在驗證成功時發生，沒驗證就不會合併，同 email 的其他舊帳號原樣保留。

## 3. 禁抓名單

### 3.1 現況問題

- `CheckForbidden` 只比對 `site + author_id`，`artwork_id` 欄位完全沒用到 → **無法只禁單一作品**。
- 只有「抓取」與「作品詳情頁」會檢查；**搜尋列表、RSS、MCP 搜尋沒有過濾**，禁抓前就抓進來的作品在列表上可能還看得到（`is_proceed`／`finish_time` 這組原本設計給「自動刪索引」的欄位，Go 版沒有接）。

### 3.2 `artwork_forbidden` 升級（P1）

- MyISAM latin1 → InnoDB utf8mb4；加 `id` PK。
- `artwork_id = ''` 表示整個畫師；有值表示單一作品。
- 舊資料轉換規則（prod 實際資料確認後定案）：有畫師、沒作品 → 整個畫師；有畫師、有作品 → 單一作品；沒畫師、有作品 → 單一作品（畫師從 artwork_main 反查，查不到留空）；兩欄都空 → 略過。
- 新增欄位：`source enum('admin','submission')`、`submission_id NULL`、`note varchar(255)`、`created_by NULL`、`is_deleted`、`deleted_at`、`created_at`、`updated_at`；保留 `is_proceed`／`finish_time` 給下架 job 用。
- `CheckForbidden(site, authorID, artworkID)`：`is_deleted = 0 AND site = ? AND author_id = ? AND (artwork_id = '' OR artwork_id = ?)`。

### 3.3 同步 job（P1）

> 2026-11-04 使用者決定：**禁抓只把資料從 ES 拉掉，不刪原圖（S3）、不動 MySQL**；解除時再把 artwork_main 的資料同步回 ES。

- `main.go` cronjob `nekomaid-forbidden-sync` 每 5 分鐘：撈 `is_proceed = 0` 的列（新增、復原、解除都會把它歸零）
  - 生效中（`is_deleted = 0`）：查出該畫師（或作品）的 ES 文件、用 `_source` 精確比對後依 `_id` 刪除
  - 已解除（`is_deleted = 1`）：把 artwork_main 中 `is_deleted = -1` 的作品重新索引；同畫師還有其他生效中禁抓的作品跳過
  - 完成後標記 `is_proceed = 1`；以 `updated_at` 比對，處理期間被管理者改過狀態的列不會被誤標
- 只在 production 執行。
- ES 有、artwork_main 沒有的舊文件，被拉掉後解除時無法回補。

### 3.4 整合後台（P1）

路徑 `faryne.dev/backend_admin/nekomaid/*`，沿用 `BrandMain` ＋ `is_admin`（同 galgame／AV）。

- 禁抓名單：列表（site／畫師 ID／暱稱搜尋）、新增（畫師或單一作品，貼網址自動解析）、移除（confirm → soft delete）、顯示下架 job 狀態。
- 申請審核（P4 才有資料）：pending 置頂 → 核准（建立 forbidden 列，`source = submission`）／駁回（填理由）。

### 3.5 版權申告（2026-11-04 改為從作品頁送出，併入第一階段）

- 入口（2026-11-05 改）：作品頁**麵包屑**上畫師名稱與作品名稱旁各一個小旗子，「難以名狀的抓圖器 / 站台 / 畫師 ⚑ / 作品 ⚑」。畫師旁＝整個畫師、作品旁＝只有這件作品，範圍由入口決定，對話框不再讓人選。原本放在資訊面板按鈕列，作者第一時間找不到。
- 範圍**最大到畫師**；`artwork_forbidden_submissions.artwork_id` 空字串＝整個畫師。
- 欄位：聯絡 email、說明皆**選填**（2026-11-04 使用者決定；有填 email 才檢查格式，說明最多 2000 字）＋ honeypot；不需登入；IP 每小時 5 件。
- **送出一律記錄 IP**，用來防止惡意大量申告：後台列表顯示 IP，以及同一 IP 的申告件數（超過 1 件時標紅，點了可以依 IP 篩選，`?ip=`）；申請人的查詢頁不會回傳 IP。
- 處理結果公開（2026-11-05 使用者定案）：
  - `/copyright-claim`：所有申告的處理結果（審核中／已核准／已駁回，駁回才顯示理由），可依狀態篩選。
  - `/copyright-claim/:hash`：同一 IP 送出的所有申告；送出後的對話框給這個連結。
  - **一律不顯示 email、IP、說明**（repository 只選公開欄位，不靠前端隱藏）。
  - 站內連結依目標「**現在**是否禁抓中」（API 的 `is_forbidden`）決定：禁抓中只顯示文字（站內頁會 404），解除後恢復連結。不看申告本身的狀態，因為同畫師別人的申告被核准、或核准後又解除，都會改變能不能連。
  - `:hash` = `HMAC-SHA256(NEKOMAID_IP_HASH_SECRET, IP)` 的前 32 個 hex 字元，存在 `ip_hash` 欄位。不能用單純雜湊：IPv4 只有 43 億種，公開的 hash 可被暴力反推回 IP。沒設鑰匙時一律拒收申告（500）；換鑰匙會讓既有查詢網址全部失效。
  - 共用 IP（公司、電信 NAT）的人會看到彼此的申告，但內容本來就跟公開列表一樣，不會多洩漏資訊。
  - 格式不對或查不到的 hash 一律回空列表。
- 後台「Nekomaid → 版權申告」：待審／已核准／已駁回；核准（備註選填）→ 寫進禁抓名單（`source = submission`）→ 同步 job 開始拉掉 ES；駁回理由必填、申請人看得到。目標已被禁時核准視為完成。
- API：`POST /nekomaid/forbidden-submissions`、`GET /nekomaid/forbidden-submissions`（公開列表）、`GET /nekomaid/forbidden-submissions/:hash`；`GET /admin/nekomaid/forbidden-submissions`、`PUT .../:id/approve`、`PUT .../:id/reject`。
- mockup：`DevelopDocuments/nekomaid/copyright-claim-mockup/`、`DevelopDocuments/nekomaid/forbidden-admin-mockup/`。

## 6. User stories ＋ 常見 fail 應對

| 情境 | 預期 / 應對 |
|---|---|
| 舊會員用帳號（或 email）＋舊密碼登入 | 驗舊雜湊（多種格式）→ 合併同 email 帳號 → 後端代為註冊 Firebase → 之後同一個表單直接由 Firebase 驗 |
| 舊會員忘記密碼 | 後端先代建 Firebase 帳號並綁定，再寄 Firebase 重設信；回應不透露 email 是否存在 |
| `users_v2` 有重複 email | 以登入的那個帳號為主，其他同 email 帳號的追蹤併入、soft delete 並記 `merged_into_id` |
| 舊雜湊格式都對不上 | 登入失敗，請使用者走忘記密碼；log 會記下各格式命中次數 |
| 有人想用別人的舊 email 註冊新帳號 | 註冊時 email 對得到還沒搬的舊帳號就不建新帳號，請他用舊密碼登入或重設密碼（重設信只會寄到本人信箱） |
| faryne.dev 的 session 被拿去打 nekomaid API | brand 不符 → 401 |
| 畫師申請下架，管理者核准 | 5 分鐘內 job 刪 ES＋S3；搜尋、RSS、MCP 同步消失 |
| 本機誤跑下架 job | `IsProduction` 保護，不動 prod ES／S3 |
| 同一畫師重複申請／禁抓列已存在 | 核准時若已有有效列直接標記完成；soft delete 過的列改回 `is_deleted = 0` 而非新增（unique key 不會撞） |
| 有人惡意大量送申請 | IP 限流＋honeypot；全部要人工核准，不會自動生效 |
| 收藏的作品後來被禁抓 | 收藏列保留，列表不顯示 |
| `/nekomaid/me` 被當成 `site = me` 的搜尋 | 路由順序：`me` 群組先註冊 |
