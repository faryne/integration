# neko.maid.tw 使用者系統＋禁抓名單 規格草稿（2026-11-04）

> 狀態：**草稿，待使用者確認後才動工**。範圍：帳號（註冊／登入／忘記密碼）、收藏＋使用者頁、`artwork_forbidden` 後台＋畫師自助申請。

## 0. 結論先講

| 區塊 | 做法 | 規模 |
|---|---|---|
| 帳號 | **獨立 Firebase 專案 `nekomaid`（Email/Password）**，舊 `users_v2` md5 雜湊用 `firebase auth:import --hash-algo=MD5` 匯入；後端只做 idToken → session（`CreateSessionFor` + 新 brand `nekomaid`） | 中 |
| 收藏＋使用者頁 | 沿用 `users_fav_authors` / `users_fav_artworks`（`user_id` 對 `users_v2.id` 不動），加收藏 toggle API＋`/me` 頁 | 中 |
| 禁抓名單 | `artwork_forbidden` 升級（InnoDB、soft delete、支援單一作品）＋作品頁版權申告＋**同步 job**（只動 ES：禁抓拉掉、解除回補）＋整合後台 | 中～大 |
| DB 整理 | nekomaid DB 目前 repo 內**沒有任何 migration**，要先補 migration 目錄；沒在用的舊表一併 DROP | 小 |

整體確實大，建議拆 4 個 branch 依序做：**P0 DB 整理 → P1 禁抓後台＋下架 job → P2 帳號 → P3 收藏＋使用者頁 → P4 前台禁抓申請**。
禁抓排在帳號前面，因為它跟帳號完全獨立，而且是目前唯一「對外有風險」的缺口（見 §3.1）。

## 1. 前置：nekomaid DB 的 migration（P0）

- 現況：`migration/` 只管主站 DB；nekomaid 走 `NEKOMAID_DSN`（`artworks` DB，prod 為 MySQL 5.7.33），沒有 migration 紀錄。
- 做法：新增 `migration/nekomaid/` ＋ `migration/nekomaid.yml`（環境名同主站 `localhost` / `development` / `master`），Makefile 加 `mig-up-nekomaid` / `mig-down-nekomaid`。第一支 migration 不重建既有表，只做下面的 ALTER／CREATE。
- 舊表清理（Go 端完全沒引用，舊 PHP 只留參考）：
  - DROP：`artwork_downloads`、`artwork_main_utf8mb4`、`artwork_stats_raw`、`artwork_stats_rows`、`artworks_indexed`、`moe_artworks_list`、`supports`、`users`（舊 Google 登入）、`users_login`（舊 session 紀錄，已由 Redis 取代）
  - 保留：`artwork_main`、`artwork_authors`、`artwork_forbidden`、`users_v2`、`users_fav_*`
  - DROP 獨立一支 migration，`down` 不還原（備份就是 2026-11-04 這份 dump）。

## 2. 帳號（P2）

### 2.1 為什麼選 Firebase 不自刻

- 寄信（驗證、重設密碼）Firebase 包了；我們自己的 SES 寄信管道目前是暫緩狀態，自刻等於要先把它做起來。
- 不用自己存密碼、做暴力破解防護；舊 md5 雜湊在使用者**第一次成功登入後由 Firebase 自動升級**成 scrypt。
- 跟 SteamLoom 同一套架構：`CreateSessionFor(idToken, brand, upsert)` ＋依品牌挑 Firebase 專案，已驗證過可行。

### 2.2 設計

- 新 brand：`service/auth/brand.go` 加 `BrandNekomaid = "nekomaid"`；`users_v2.id` 跟主站 `users.id` 會撞號，靠 session brand 檢查擋跨品牌誤用（同 SteamLoom 理由）。
- Firebase 專案：`NEKOMAID_FIREBASE_PROJECT_ID`（後端驗 token）、`VITE_NEKOMAID_FIREBASE_*`（前端依 `isNekomaidSite()` 挑）。
- 前端：註冊／登入／忘記密碼直接呼叫 Firebase JS SDK（`createUserWithEmailAndPassword` / `signInWithEmailAndPassword` / `sendPasswordResetEmail`），拿 idToken 打 `POST /nekomaid/auth/session` 換 session；登出打 `DELETE`。
- 註冊時寄驗證信，但**不擋登入**（收藏這種低風險功能沒必要卡）。
- `users_v2` 調整：
  - 轉 InnoDB utf8mb4；加 `firebase_uid varchar(128) NULL UNIQUE`、`updated_at`、`is_deleted`、`deleted_at`；`email` 加 index。
  - `id` 不動 → `users_fav_*` 不用搬資料。
- upsert 邏輯（`service/nekomaid/user.go`）：`firebase_uid` 找得到 → 用；找不到 → 用 email 找 `firebase_uid IS NULL` 的舊帳號綁定；都沒有 → 新增（`userpass` 留空字串）。
- 本機測試：`CreateDevSessionFor(BrandNekomaid, ...)` 接既有 dev bypass。
- **刪帳號不在本次範圍**（跟 SteamLoom 一樣先不做）。

### 2.3 舊帳號匯入（一次性）

1. `go run . -cmd nekomaid-export-firebase-users > users.json`：`localId = "nk-<id>"`、`email`、`displayName = username`、`passwordHash = base64(hex decode(userpass))`。
2. 先挑**一個自己的測試帳號**匯入驗證 `--rounds` 參數（MD5 無鹽要確認是 `0` 還是 `1`），確定能用舊密碼登入才整批。
3. `firebase auth:import users.json --hash-algo=MD5 --rounds=<驗證後的值> --project <nekomaid>`。
4. 匯入確認後，`users_v2.userpass` 全部清空（無鹽 md5 留在 DB 只是負債）。

## 3. 禁抓名單

### 3.1 現況問題

- `CheckForbidden` 只比對 `site + author_id`，`artwork_id` 欄位完全沒用到 → **無法只禁單一作品**。
- 只有「抓取」與「作品詳情頁」會檢查；**搜尋列表、RSS、MCP 搜尋沒有過濾**，禁抓前就抓進來的作品在列表上可能還看得到（`is_proceed`／`finish_time` 這組原本設計給「自動刪索引」的欄位，Go 版沒有接）。

### 3.2 `artwork_forbidden` 升級（P1）

- MyISAM latin1 → InnoDB utf8mb4；加 `id` PK。
- `artwork_id = ''` 表示整個畫師；有值表示單一作品（既有資料要先確認 author-level 那些列 `artwork_id` 存的是什麼，見 §7）。
- 新增欄位：`source enum('admin','submission')`、`submission_id NULL`、`note varchar(255)`、`created_by NULL`、`is_deleted`、`deleted_at`、`created_at`、`updated_at`；保留 `is_proceed`／`finish_time` 給下架 job 用。
- `CheckForbidden(site, authorID, artworkID)`：`is_deleted = 0 AND site = ? AND author_id = ? AND (artwork_id = '' OR artwork_id = ?)`。

### 3.3 同步 job（P1）

> 2026-11-04 使用者決定：**禁抓只把資料從 ES 拉掉，不刪原圖（S3）、不動 MySQL**；解除時再把 artwork_main 的資料同步回 ES。

- `main.go` cronjob `nekomaid-forbidden-sync` 每 5 分鐘：撈 `is_proceed = 0` 的列（新增、復原、解除都會把它歸零）
  - 生效中（`is_deleted = 0`）：查出該畫師（或作品）的 ES 文件、用 `_source` 精確比對後依 `_id` 刪除
  - 已解除（`is_deleted = 1`）：把 artwork_main 中 `is_deleted = -1` 的作品重新索引；同畫師還有其他生效中禁抓的作品跳過
  - 完成後標記 `is_proceed = 1`；以 `updated_at` 比對，處理期間被管理者改過狀態的列不會被誤標
- 只在 production 執行。
- ES 有、artwork_main 沒有的舊文件，被拉掉後解除時無法回補。

### 3.4 整合後台（P1）

路徑 `faryne.dev/backend_admin/nekomaid/*`，沿用 `BrandMain` ＋ `is_admin`（同 galgame／AV）。

- 禁抓名單：列表（site／畫師 ID／暱稱搜尋）、新增（畫師或單一作品，貼網址自動解析）、移除（confirm → soft delete）、顯示下架 job 狀態。
- 申請審核（P4 才有資料）：pending 置頂 → 核准（建立 forbidden 列，`source = submission`）／駁回（填理由）。

### 3.5 版權申告（2026-11-04 改為從作品頁送出，併入第一階段）

- 入口：作品頁資訊面板的按鈕列最後一個「⚑ 版權申告」文字按鈕，點開對話框。
- 範圍**最大到畫師**：只有這件作品／這位畫師的所有作品（二選一）；`artwork_forbidden_submissions.artwork_id` 空字串＝整個畫師。
- 欄位：聯絡 email、說明皆**選填**（2026-11-04 使用者決定；有填 email 才檢查格式，說明最多 2000 字）＋ honeypot；不需登入；IP 每小時 5 件。
- **送出一律記錄 IP**，用來防止惡意大量申告：後台列表顯示 IP，以及同一 IP 的申告件數（超過 1 件時標紅，點了可以依 IP 篩選，`?ip=`）；申請人的查詢頁不會回傳 IP。
- 送出後給查詢連結 `/copyright-claim/:token`（審核中／已核准／已駁回＋駁回理由）。
- 後台「Nekomaid → 版權申告」：待審／已核准／已駁回；核准（備註選填）→ 寫進禁抓名單（`source = submission`）→ 同步 job 開始拉掉 ES；駁回理由必填、申請人看得到。目標已被禁時核准視為完成。
- API：`POST /nekomaid/forbidden-submissions`、`GET /nekomaid/forbidden-submissions/:token`；`GET /admin/nekomaid/forbidden-submissions`、`PUT .../:id/approve`、`PUT .../:id/reject`。
- mockup：`DevelopDocuments/nekomaid/copyright-claim-mockup/`、`DevelopDocuments/nekomaid/forbidden-admin-mockup/`。

## 4. 收藏＋使用者頁（P3）

### 4.1 資料表

- `users_fav_authors` / `users_fav_artworks`：轉 InnoDB utf8mb4；`author_id` 從 `varchar(10)` 放寬到 `varchar(15)`（pixiv 畫師 ID 已到 9 位數，跟 `artwork_main` 對齊）。
- 取消收藏 = 實體刪除（toggle 性質，沒有回復需求）。
- `users_fav_tags`：**本次不做 UI**，表保留。

### 4.2 API（全部掛 `authsession.New(BrandNekomaid)`）

| Method | Path | 用途 |
|---|---|---|
| GET | `/nekomaid/me/favorites/keys` | 一次回所有收藏 key，前端拿來畫愛心狀態 |
| GET | `/nekomaid/me/favorites/authors?page=` | 畫師列表＋每人最新 4 張縮圖 |
| GET | `/nekomaid/me/favorites/artworks?page=` | 作品列表（ES ids 批次查） |
| PUT / DELETE | `/nekomaid/me/favorites/authors/:site/:authorId` | 收藏／取消 |
| PUT / DELETE | `/nekomaid/me/favorites/artworks/:site/:authorId/:artworkId` | 收藏／取消 |

- ⚠️ `/nekomaid/:site` 會吃掉 `/nekomaid/me`，`me` 群組必須註冊在 `g.Get("/:site")` **之前**。
- ⚠️ **禁抓會影響追蹤**（2026-11-04 使用者確認）：被禁抓的畫師／作品，使用者的追蹤列表、`/favorites/keys`、畫師最新縮圖都要過濾掉（不顯示也不報錯）；收藏列本身保留，解除禁抓後自動恢復顯示。判斷一律走 `ForbiddenRepository.IsForbidden` 同一套規則（整個畫師或單一作品），列表查詢時批次比對，別逐筆查。

## 6. User stories ＋ 常見 fail 應對

| 情境 | 預期 / 應對 |
|---|---|
| 舊會員用舊密碼登入 | Firebase 用 MD5 驗過 → 自動升級雜湊；upsert 用 email 綁回原 `users_v2.id`，收藏都在 |
| 舊會員忘記密碼 | Firebase 寄重設信，與新會員流程相同 |
| `users_v2` 有重複 email／空 email | 匯入會失敗或撞號 → 匯入前先查（§7），重複的保留最舊的 id、其餘收藏併入 |
| 舊雜湊不是純 32 碼 hex md5 | 該筆無法匯入 → export 指令略過並列出，這些人走忘記密碼 |
| 匯入時 `--rounds` 設錯 | 全部人登不進去 → 一定先用單一測試帳號驗證 |
| faryne.dev 的 session 被拿去打 nekomaid API | brand 不符 → 401 |
| 畫師申請下架，管理者核准 | 5 分鐘內 job 刪 ES＋S3；搜尋、RSS、MCP 同步消失 |
| 本機誤跑下架 job | `IsProduction` 保護，不動 prod ES／S3 |
| 同一畫師重複申請／禁抓列已存在 | 核准時若已有有效列直接標記完成；soft delete 過的列改回 `is_deleted = 0` 而非新增（unique key 不會撞） |
| 有人惡意大量送申請 | IP 限流＋honeypot；全部要人工核准，不會自動生效 |
| 收藏的作品後來被禁抓 | 收藏列保留，列表不顯示 |
| `/nekomaid/me` 被當成 `site = me` 的搜尋 | 路由順序：`me` 群組先註冊 |
