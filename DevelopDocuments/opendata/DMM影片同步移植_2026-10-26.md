# DMM 影片同步移植到 Go（取代 PHP＋logstash）

> 狀態：已實作（2026-10-26，branch `feat/dmm-video-sync-go`）。上線後要關掉 PHP 排程與 logstash pipeline（見〈上線切換〉）。

## 目標

- 把 `php7-version` 的 `dmm:daily`（TG 通知）、`dmm:daily-published`（寫 DB），以及 logstash 的 `dmmvideo` pipeline（DB → ES）全部改由 Go 處理。
- 繼續寫入原本的 `lab_jp.dmm` 表（Go 的 `enum.DBWalolita`）和 ES 的 `dmmvideos`。文件格式和 `_id` 都沿用舊規則，既有的 53 萬筆不用搬。

## 舊流程與問題

| 元件 | 做什麼 | 問題 |
|---|---|---|
| `dmm:daily`（10:00） | 抓當天清單第 1 頁，前 10 筆發到 TG（Markdown） | 標題含 `[ ] _ *` 時整則會送失敗 |
| `dmm:daily-published`（03:50） | 抓前一天全部頁數，`updateOrCreate` 寫進 `dmm` | — |
| logstash `dmmvideo` | `SELECT id AS vid, info FROM dmm WHERE id >= :sql_last_value`，每小時 25 分執行，`document_id => %{vid}` | **只追 id 最大值**：舊作品被 update 後永遠不會再進 ES，回補 DB 也補不到 ES |

## 新流程

- **`av-dmm-video-sync`**（`50 3 * * *`）：抓前一天全部頁數 → 整頁 upsert 進 `dmm`（以 `no` 為唯一鍵）→ 依 `no` 查回 id → 逐筆用 `index` 寫入 ES（`_id` = `dmm.id`，存在就覆蓋）。
  - 回補：`-cmd av-dmm-video-sync -dayFrom 2026-01-15 -dayTo 2026-03-21`（區間含頭尾）。
- **`av-dmm-video-notify`**（`0 10 * * *`）：**先同步當天的作品，同步完才**把當天清單前 10 筆用 HTML parse mode 發到 TG（`TG_BOT_TOKEN`／`TG_CHAT_ID`），外部文字一律 `html.EscapeString`。（2026-10-27 調整：原本只發通知，當天的片要等隔天 03:50 的前一天同步才進 ES，通知裡的片在網站上查不到。）
  - 同步約 1 分鐘，通知會比 10:00 晚一點；同步失敗仍照常發通知（失敗另有 TG 告警）。
  - 03:50 的前一天同步維持不變，用來補 DMM 當天稍晚才上架的作品；同步是覆寫，重跑不會重複。
  - 文字之後再用 `sendMediaGroup` 發這 10 筆的封面相簿（直式 `ps.jpg`，順序同清單編號），跟 PHP 線上版一致；相簿失敗只記 log，不影響文字。圖片由 Telegram 端自行下載，單張上限 5MB，DMM 封面約 0.3～0.7MB。

### 容錯

- 單筆明細最多試 3 次（間隔 1s、2s），仍然失敗就略過那一筆並計入 `failed`，不會讓整頁失敗。`/dmm/avsearch` API 維持原本行為：任何一筆失敗就回 500。
- 長區間回補的節流與保護（2026-10-30）：
  - 每個 GraphQL 請求有 30 秒逾時（`service/dmm/client.go`），避免對方連線卡住時 job 永遠停住。
  - 每抓完一頁 sleep 1 秒。
  - 某一天明細失敗超過一半，就把那天算成失敗，因為很可能是被擋了。
  - 連續 3 天失敗就中止整段回補，TG 告警會寫出要用哪個 `-dayFrom` 重跑。
  - 告警超過 3500 字就截斷，完整清單看 log。
  - prod 最早的配信日是 2002-06-14，全區間約 59 萬部。建議以一年為單位、從新到舊分段跑。
- 明細沒有配信日（zero value）就略過並計入 `skipped`，**絕不寫入 `0001/01/01`**。沒有 `publish_date` 時省略這個欄位（ES 裡就是 null，跟 logstash 把 `----` 轉 null 的結果一致）。
- 清單本身抓不到（例如 DMM 又改 schema）時，那一天算失敗。跑完後有失敗的日期會發 TG 告警。
- `dmm` 的 `title`／`link`／`thumb` 沿用 Laravel 建表時的長度，寫入前先截斷；完整內容都在 `info`，ES 不受影響。

### ES 文件

- 內容是 `dmm.DmmVideo` 的 JSON，加上 `vid`。logstash 時代的 `@version`、`@timestamp`、`type` 不再寫入，前端也沒有用到。
- index 名稱來自 `DMM_VIDEO_INDEX`（預設 `dmmvideos`）。本機 `.env` 的 `ES_DSN` 指向正式環境的 cluster，**本機測試時一定要改成別的 index 名稱**，測完記得刪掉。

## 已知 Bug 記錄

### 1. DMM 移除 `priceSummary`，明細全部變成 zero value（2026-10-14 起）

- **現象**：從 10/14 起，ES 裡新影片的 `vod_date` 都是 `0001/01/01`，用日期查詢時看起來像資料停在 10/13。
- **Root cause**：DMM GraphQL 拿掉了 `PPVContent.priceSummary`，明細 query 一律回 422 `GRAPHQL_VALIDATION_FAILED`。`dmm.send` 沒檢查 status 和 `errors`，於是 unmarshal 出整包 zero value。
- **解法**：從 query 拿掉這個欄位（原本就被 `@skip` 跳過）；`send` 遇到非 2xx 或有 `errors` 時回傳 error（commit `d83f53d`）。
- **狀態**：已修。ES 中 `vod_date < 1970/01/01` 的 8730 筆已經刪除，等待回補。

### 2. 2026-01-20 ～ 2026-03-19 的資料同樣是 `0001/01/01`

- **現象**：這段期間 ES 每天都是 0 筆，原因是被刪掉的 8730 筆裡，有一大部分配信日落在這段。
- **Root cause**：時間點推測也是明細抓取失敗、被靜默吞掉（同 #1）。git 裡沒有找到對應的修正，可能是 DMM 端自己恢復了。
- **狀態**：等待回補。

### 3. 回補 DB 進不了 ES

- **Root cause**：logstash 只同步 `id >= sql_last_value` 的資料列，被 update 的舊資料列不會再次同步。
- **解法**：改由 Go 直接寫 ES（本文件）。在 Go 版上線前若要救急，可以把 `/var/log/logstash/dmm.flag` 改成受影響範圍的最小 id，讓 logstash 從那裡重新 index。

### 4. 回補時出現「dmm id not found after upsert」（2026-10-26）

- **現象**：`-dayFrom` 回補 2026-03-02 時，page 2 中斷，`no=smgd010`。prod 上這一列存的是大寫 `SMGD010`（id 538498，是這次才新增的），可以排除大小寫問題。
- **Root cause**：walolita 有接 dbresolver replica（`WALOLITA_SLAVE_DSN`）。`IDsByNos` 的 SELECT 打到 replica，剛 INSERT 進 primary 的新作品還沒同步過去，所以查不到 id。
- **解法**：`IDsByNos` 加上 `Clauses(dbresolver.Write)`，強制走 primary。
- **狀態**：已修。本機 replica 和 primary 是同一個 DB，無法重現延遲；中斷的日期要重跑。
