# AV 女優主題頁（規格）

> 狀態：規格 v3（2026-10-31），尚未實作。mockup：`av-actress-topics-mockup/index.html`。前置：[AV同名女優區分_2026-10-30.md](AV同名女優區分_2026-10-30.md)（同名處理與 `actressVideoQuery`）。
>
> v3 變更：
> - 血型、罩杯、身高不再一個值開一頁（跟直接用搜尋沒有差別），改成「棉花糖」「嬌小巨乳」這類身材形容詞主題。
> - 新增管理員自訂主題：用條件組合出主題，例如「A 型處女座的心機女」「東京痴女」。儲存後等下一次每週排程才產生。

## 目的

用「主題」整理女優，例如：牡羊座、90 年代出生、棉花糖、熟女類、新人、東京痴女。每個主題一頁，可以分享，可以換排序。
所有主題**每週算一次**，結果存成 JSON 放到 S3，前端直接透過 CloudFront 讀取，不經過後端 API。

## 現況（查 prod ES，2026-10-31，唯讀）

`dmmactresses` 裡 xcity＋manual 共 16,444 位：

|---|---|---|
| 生日（年月日都有） | 5,848（36%） | `horoscope` 欄位**全部是空的**：xcity 沒有給，上稿也不收，星座只能從生日算 |
| 三圍 | 約 9,120（55%） | |
| 身高 | 8,874（54%） | |
| 罩杯 | 4,172（25%） | |
| 出身地 `born_city` | 約 4,350（26%） | 東京都 1,640、神奈川県 589 … |
| 血型 | 約 3,200（20%） | |

`dmmvideos` 約 59 萬部，`tags` 共 475 種：
- 前 20 名裡有一半不是「類型」：ハイビジョン、単体作品、独占配信、4時間以上作品、ベスト・総集編、デジモ、4K 這些是格式或販售分類，幾乎每位女優都有。
- 後 20 名全是雜訊：亂碼標籤（見最後的「另外發現」）和促銷標籤（`〇〇30％OFF` 共 53 種）。
- 出現 ≥ 1,000 部的標籤有 181 種。這群標籤的尾段是真正的冷門類型，例如：母乳、女医、秘書、スチュワーデス、女捜査官、日焼け。

其他限制：
- 女優文件裡沒有出演數和出演日期。
- 女優頁 `/av/actress/:name` 在找不到女優資料時會顯示 404。
- **DMM 的名字會帶別名**，例如 `澤村レイコ（高坂保奈美、高坂ますみ）`，但 xcity 只存 `澤村レイコ`。全站 5 萬個名字裡有 2.2 萬個帶括號。
- **xcity 的 11/30 生日是預設值**：有 342 位，一般日期大約 40 位，而且年份分散，判斷是只知道年份時填的。
- **ES 聚合桶數有上限**：對 `actresses.keyword` 一次要 9,000 個桶時 prod 回 503，5,000 個可以。實作要用 composite aggregation 分頁。
- 前端放在 Firebase Hosting；公開 JSON 沿用台電統計的做法：S3 `PutObject`，加上 `Cache-Control`，前端用 `VITE_CDN_BASE` 讀取。

## 主題清單

網址是 `/av/actress/topics/:slug`，總覽頁是 `/av/actress/topics`。總覽頁依下表的順序分區。

### 內建主題（程式產生，不能編輯）

| 分組 | slug 範例 | 條件 | 頁數 |
|---|---|---|---|
| 新人與活躍 | `newcomer`、`active` | 第一部配信日在 12 個月內／最後一部在 6 個月內 | 2 |
| 星座 | `horoscope-aries` … `horoscope-pisces` | 生日月日落在該星座區間（西洋星座，日本通用的日期）；**排除 11/30** | 12 |
| 出生年代 | `born-1970s` … `born-2000s` | `birth_year` 落在該年代 | 4 |
| 出身地 | `pref-tokyo`、`pref-kanagawa` … | `born_city` 完全相符；47 個都道府県配羅馬字 slug，人數少於 30 的不開 | ≤47 |
| 熱門類型 | `genre-<tag>` | 每週從標籤 facet 取，見下方「類型主題」 | 20 |
| 冷門類型 | `genre-<tag>` | 同上 | 20 |

- **年齡做「出生年代」，不做「現在幾歲」**：現在幾歲每年都會變，同一個網址的內容會漂移；早就沒拍片的人也會被算進高齡區間。
- **不做「引退」**：一年沒有新片不代表引退。只做正向的「近期活躍」。
- 血型、罩杯、身高不單獨開頁，只當作自訂主題的條件。

### 自訂主題（用條件組合，分成「特輯」「身材」兩組）

### 條件結構

同一個欄位內多個值是 OR，不同欄位之間是 AND。區間用 `[min, max]`，`0` 或空字串代表不限。

```json
{
  "horoscope": ["virgo"],
  "blood": ["A"],
  "birth_year": [1990, 1999],
  "height": [0, 152],
  "cup": ["F", ""],
  "bust": [0, 0], "waist": [0, 58], "hips": [90, 0],
  "hip_waist_diff": [32, 0],
  "born_city": ["東京都"],
  "genres": [{ "tag": "痴女", "min": 5 }],
  "debut_within_months": 0,
  "active_within_months": 0,
  "min_videos": 0
}
```

- 沒有填的欄位不檢查；有條件但女優沒有那個欄位的資料（例如身高是 0），一律視為不符合。
- 星座條件一樣排除 11/30 生日。
- `genres` 的部數算法跟類型主題相同：排除總集編，名字去掉別名後合併。
- 每個自訂主題另外有：標題、slug、分組（特輯／身材）、總覽頁排序、預設排序方式（出演數／最近出演／類型出演數／出道日）。

### 類型主題

每週用 `tags.keyword` 的 terms aggregation（facet）挑：
1. 先排除下面兩種標籤，其他類型標籤不另外過濾：
   - **格式／販售標籤**：寫成常數清單（ハイビジョン、単体作品、独占配信、4時間以上作品、ベスト・総集編、デジモ、4K、VR専用、特典画像付き、ファン感謝・訪問 …）。
   - **雜訊標籤**：促銷標籤（含 `OFF`、`％`、`%`）、亂碼。
2. **熱門類型**：剩下的標籤依部數取前 20 名。
3. **冷門類型**：剩下的標籤中，只看出現 ≥ 1,000 部、而且排行有 ≥ 20 位女優的，取部數最少的 20 個。
   - 直接取最後 20 名會全是只有一部的雜訊。
   - 只看部數不看人數的話，會出現 `処女`（1 位）、`お嬢様・令嬢`（9 位）這種撐不起一頁的主題。
4. 每個類型的女優排行：
   - 對「含該標籤、且不是 `ベスト・総集編`」的影片，聚合出演部數；名字去掉別名後合併。
   - 取 ≥ 5 部的人，最多 1,000 位。`巨乳`、`中出し` 這類標籤有 4～5 千人，全放進去檔案太大。
   - 只列女優資料存在的名字，因為沒有資料的名字點進去是 404。
   - 舊影片只有名字，同名女優的部數會算在一起，**接受這個誤差**。點進去的女優頁本身就有同名切換。

slug 用 `genre-` 加標籤原文（例如 `genre-熟女`）。前端一律先讀 `index.json`，再用 slug 找對應的檔案，不直接用標籤組 S3 路徑。

## 方案

### 1. 每週產生主題 JSON

新增排程 `av-actress-topics`，每週四 04:30 跑，排在週三 01:37 的 xcity 同步之後。手動可以用 `-cmd av-actress-topics` 執行。全部在記憶體裡算：

1. **載入所有女優**：從 `dmmactresses` scroll 出 xcity＋manual，約 1.6 萬筆。
2. **算每位女優的統計**：出演數、第一部配信日、最後一部配信日。
   - 一般女優：對 `dmmvideos` 做 composite aggregation（分頁），以 `actresses.keyword` 分組，取部數、`min(vod_date)`、`max(vod_date)`。名字去掉全形括號的別名後再對回女優，同一位的多種寫法合併計算。
   - 同名女優（現在約 65 組、131 位）：改用 `actressVideoQuery(row)` 逐位查，結果跟女優頁的出演影片一致。
   - 出演數包含總集編，跟女優頁顯示的出演影片一致。
3. **類型出演數**：類型主題，以及自訂主題 `genres` 用到的標籤，每個標籤做一次聚合，得到「女優 → 該類型部數」。
4. **套用主題**：內建主題和自訂主題都用同一個條件引擎在 Go 裡篩女優。
5. **上傳 S3**：每個主題一個 JSON，加上 `index.json`。
6. **回寫結果**（第 3 階段）：把每個自訂主題這次的人數和產生時間寫回 DB，管理介面列表要用。

不用改 ES mapping，也不用改女優搜尋 API。統計只活在 JSON 裡，所以 xcity 同步整份覆寫女優文件也不影響。

### 2. S3 檔案格式

路徑：`opendata/av/actress-topics/`，`Cache-Control: public, max-age=3600`，`Content-Type: application/json; charset=utf-8`。

- `index.json`：
  ```json
  {
    "generated_at": "2026-11-05T04:31:00+08:00",
    "groups": [
      { "key": "special", "label": "特輯",
        "topics": [{ "slug": "tokyo-chijo", "label": "東京痴女", "count": 467, "file": "custom-12.json", "summary": "東京都・痴女 5 部以上" }] }
    ]
  }
  ```
  - `summary` 是條件的文字摘要，由後端產生，主題頁標題下方會用到。
  - 人數為 0 的主題不放進 `index.json`。
- 每個主題 `<file>`：
  ```json
  {
    "slug": "genre-熟女", "label": "熟女", "generated_at": "…", "default_sort": "genre",
    "actresses": [
      { "domain": "xcity", "aid": 123, "name": "…", "photo": "…",
        "video_count": 210, "first_vod_date": "2008/03/01", "last_vod_date": "2026/10/20",
        "genre_count": 88 }
    ]
  }
  ```
  - 只放卡片需要的欄位。`genre_count` 只有類型主題，以及有 `genres` 條件的自訂主題才有（取第一個標籤）。
  - 最大的主題約 2 千人，gzip 後幾十 KB。
- 檔名：
  - 類型主題用標籤的雜湊，例如 `genre-1a2b3c4d.json`。
  - 自訂主題用 DB id，例如 `custom-12.json`，所以改 slug 不用搬檔案。
  - 對應關係都寫在 `index.json` 裡。
- 主題掉出名單、被停用或刪除後，舊檔案留在 S3，但 `index.json` 不再列它，網址會顯示 404，接受。

**寫入保護**：本機也會跑全部排程，所以只有 production 會上傳 S3。非 production 改寫到本機 `tmp/actress-topics/`，方便檢查。

### 3. 前端（讀者）

- `/av/actress/topics`：讀 `index.json`，依分組分區顯示主題 chip，附人數。
- `/av/actress/topics/:slug`：
  - 先讀 `index.json` 找到檔案，再讀主題 JSON。
  - 標題下方是分組、人數；自訂主題再加上條件摘要。
  - 同分組的其他主題排成一列可以橫向捲動的 chip。
  - **排序和分頁都在前端做**，預設排序用主題 JSON 的 `default_sort`：
    - 出演數
    - 最近出演
    - 名字
    - 類型出演數（有 `genre_count` 時才出現）
    - 出道日（只有新人主題）
  - 頁碼和排序存在網址（`?page=&sort=`）。
  - slug 不在 `index.json` 裡時顯示 ErrorPage 404。
- 女優卡片從 `pages/av/actress.tsx` 抽成共用元件。`actress.tsx` 現在 508 行，順便瘦身。
- 兩頁都放在 `AgeConfirmationGate` 裡面。
- 麵包屑：AV 女優搜尋 › 女優主題 › 棉花糖。
- 入口：
  - 女優搜尋頁加「女優主題」按鈕。
  - `navigation.ts` 的 AV 女優搜尋加子頁面。
  - 女優頁的生日（星座）、出生年代、出身地改成主題連結，只在 `index.json` 有這個主題時出現。身材主題要看條件才知道符不符合，女優頁不顯示。
- CDN 讀取失敗時用 snackbar 顯示。

### 4. 管理介面（第 3 階段）

- **DB**：新增 `av_actress_topics` 表（MySQL 5.7）：

  | 欄位 | 說明 |
  |---|---|
  | `id` | PK |
  | `slug` | unique；`^[a-z0-9-]{2,50}$`；不能是 `manage`，也不能用內建主題的前綴（`horoscope-`、`born-`、`pref-`、`genre-`、`newcomer`、`active`） |
  | `title` | 標題 |
  | `group_key` | `special`（特輯）／`body`（身材） |
  | `sort_order` | 總覽頁排序 |
  | `default_sort` | `videos`／`recent`／`genre`／`debut` |
  | `conditions` | 條件 JSON（LONGTEXT，跟 `dmm_actresses.overrides` 一樣） |
  | `is_enabled` | 停用時下一次排程從 `index.json` 拿掉 |
  | `last_count`、`last_generated_at` | 排程回寫，列表顯示用 |
  | `is_deleted`、`deleted_at` | 軟刪除 |
  | `created_by`、`updated_by`、`created_at`、`updated_at` | |

  migration 同時 seed 身材的 12 個主題，程式裡的定義就拿掉。
- **API**（放在既有的 `/admin/av` 群組，`authsession.New` ＋ `RequireAdmin`）：
  - `GET actress-topics`：列表
  - `GET actress-topics/:id`：單筆
  - `POST actress-topics`：新增
  - `PUT actress-topics/:id`：修改
  - `PUT actress-topics/:id/enabled`：啟用／停用
  - `PUT actress-topics/sort`：調整順序
  - `DELETE actress-topics/:id`：軟刪除
- **儲存後不即時產生**：等下一次每週排程才會出現在讀者端。列表上「上次產生」顯示「尚未產生」，直到排程跑過。
- **前端頁面**（`AdminGuard`）：
  - `/av/actress/topics/manage`：主題列表，欄位有標題、slug、分組、條件摘要、上次人數、上次產生時間、啟用開關；可以調整順序。
  - `/av/actress/topics/manage/new`、`/av/actress/topics/manage/:id`：編輯頁。
    - 基本資料：標題、slug、分組、預設排序。
    - 條件：星座和血型用 chip 複選；出生年、身高、三圍、臀腰差用最小／最大值輸入；罩杯用兩個下拉選單；出身地用可複選的自動完成；類型一列一個（標籤＋最少部數）；出道或最後出演在 N 個月內；總出演數至少 N 部。
    - 不做即時預覽人數。
    - 刪除要先 confirm。
  - 入口：帳號選單的管理連結（跟上稿審核放在一起），以及主題總覽頁右上角給管理員看的「管理主題」按鈕。

### 不做

- 管理介面的即時預覽與立即發佈。

## User stories

1. 讀者在總覽頁的「身材」點進「棉花糖」，看到符合條件、出演數最多的女優。
2. 讀者在女優頁看到「牡羊座」，點下去進到牡羊座主題。
3. 讀者打開「新人」，看到最近一年出道的女優，切成「最近出演」排序找最新的。
4. 讀者在冷門類型裡看到「女捜査官」，點進去看到這類作品出演最多的女優，總集編不會灌水。
5. 管理員新增特輯「東京痴女」（出身東京都＋痴女類 ≥5 部），儲存後列表顯示「尚未產生」；下週四排程跑完，讀者端的「特輯」出現這個主題，列表顯示人數 467。

## 常見失敗與處理

| 情境 | 處理 |
|---|---|
| 排程失敗 | 不覆蓋 S3，前端繼續讀上週的檔案；發 TG 告警。先全部產生在記憶體，全部成功才開始上傳；`index.json` 最後上傳。 |
| 上傳到一半失敗 | 主題檔已經更新、`index.json` 還是舊的，前端仍然能讀；下次重跑覆蓋。 |
| 單一自訂主題的條件有問題（JSON 壞掉、標籤不存在） | 跳過那個主題，其他照常產生；TG 告警列出哪個主題。儲存時後端先驗證條件格式。 |
| 自訂主題沒有任何人符合 | 不放進 `index.json`，列表顯示人數 0，管理員自己調條件。 |
| 資料延遲 | 上稿核准、照片更新、主題編輯，最慢都要等到下週才會反映在主題頁，接受。女優頁本身是即時的。 |
| 生日、三圍資料不完整 | 星座、年代只涵蓋約 36% 的女優，身材約 55%，接受。不加說明文字。 |
| 類型主題每週變動 | 掉出名單的類型網址會 404，接受。 |
| ES 聚合太大 | 一律用 composite aggregation 分頁，不用一次要上萬個桶的 terms aggregation。 |
| CDN 快取 | 每週更新後最多延遲 1 小時（max-age=3600）。 |
| 本機誤跑 | 非 production 不上傳，只寫本機目錄。 |

## 分階段

1. 後端排程：統計、條件引擎、內建主題、類型主題、身材主題（先寫在程式裡）、上傳 S3。
2. 前端（讀者）：總覽頁、主題頁、入口。
3. 管理介面：`av_actress_topics` 表（含身材 seed）、管理 API、列表與編輯頁；排程改從 DB 讀自訂主題並回寫人數。

## 部署流程

1. 第 1、2 階段：部署後端，手動跑一次 `-cmd av-actress-topics`，確認 S3 上有 `opendata/av/actress-topics/index.json`；再部署前端。
2. 第 3 階段：跑 migration `create_av_actress_topics`，部署後端和前端，再手動跑一次排程。

## 另外發現（不在這次範圍）

- **女優頁漏掉帶別名的影片**：女優頁用 `actresses.keyword` 完全相符查出演影片，所以 DMM 名字帶別名的影片都查不到。例如 `澤村レイコ` 的女優頁是 0 部，但 `澤村レイコ（高坂保奈美、高坂ますみ）` 有 2,227 部。這是既有的 bug，另外開了一個 session 在處理；主題頁的「去掉別名」規則最好跟它共用。
- **亂碼標籤**：`dmmvideos` 裡的亂碼標籤，是 10/26 切換到 Go 版當天 logstash 還沒停，把 36 部影片蓋掉造成的，Go 版本身沒問題。正在跑的回補會把它們覆寫成正確資料；主題頁的排除規則仍然保留。
