# AV 女優上稿與審核（規格草稿）

> 狀態：已實作（2026-10-30）。mockup：`av-actress-submission-mockup/index.html`
>
> 部署：要跑兩支 migration（`20261030120000-create_dmm_actress_submissions.sql`、`20261030120100-alter_dmm_actresses_add_overrides.sql`）。

## 目的

xcity 的女優名冊不完整（新人、引退、無專屬的女優常常沒有），要提供手動上稿：
使用者可以**新增**女優或**修改**既有女優資料，管理者看 diff 後**核准**或**否決**，核准後才進入搜尋。
網頁與 MCP 兩個入口走同一套流程。

## 現況（會影響設計的地方）

- 女優資料存在 MySQL `lab_jp.dmm_actress`（PK = `domain` + `id`，資料放 `info` JSON）與 ES `dmmactresses`（`_id` = `{domain}-{aid}`）。
- `ActressSearch` 在 xcity 資料夠多時只搜 `domain = xcity`，手動資料需要另一個 domain，且搜尋條件要一起放寬。
- xcity 同步會整筆覆蓋 `info` 與 ES 文件；若直接改 xcity 女優的資料，下次同步就被蓋回去。
- 本機 `.env` 的 ES 指向 prod，寫入 `dmmactresses` 前要比照影片同步加 `IsProduction()` 保護。
- galgame 已有「匿名投稿＋管理審核」前例（網頁與 MCP 都可投稿，`IsAdmin` 才能審核）。

## 資料設計

### 新表 `dmm_actress_submissions`

| 欄位 | 說明 |
|---|---|
| `id` | PK |
| `kind` | `create`／`edit` |
| `target_domain`, `target_aid` | 修改時指向哪位女優；新增時為空 |
| `payload` | JSON，提交的**完整**欄位值（不是只有變更的部分，diff 由後端算） |
| `base_snapshot` | JSON，提交當下目標女優的資料；用來顯示 diff，也用來偵測「提交後資料又被改過」 |
| `resolution`, `merged_domain`, `merged_aid` | 核准時的處理方式：`created`（新增）／`updated`（修改）／`merged`（新增單合併到同名女優），合併時記錄合併到哪位 |
| `channel` | `web`／`mcp` |
| `submitter_user_id` | 有登入才有；匿名為 NULL |
| `submitter_ip_hash` | 限流與找出洗版來源用，不存明碼 IP |
| `status` | `pending`／`approved`／`rejected` |
| `reviewer_user_id`, `review_note`, `reviewed_at` | 審核紀錄；否決原因會顯示給查詢狀態的人 |
| `created_at`, `updated_at` | |

### 手動新增的女優

- 寫進 `dmm_actress`，`domain = manual`，`id` 直接用提交單的 `id`（保證唯一，不用另外發號）。
- ES 文件 `_id = manual-{id}`，欄位與 xcity 相同。

### 參考連結

- 女優資料新增 `links`：`[{title, url}]`，`title` 選填（沒填時前端顯示網域）。存在 `info` JSON 與 ES 文件，不參與搜尋。
- 提交表單的「參考連結」可以填多筆，核准後直接成為女優的連結，顯示在女優頁新的「連結」區塊（沒有連結就不顯示）。
- 只收 `http`／`https`，同一位女優的連結以 URL 去重。

### 修改 xcity 女優：欄位覆寫

- `dmm_actress` 加 `overrides` JSON 欄位，只存核准過、被手動改的欄位（xcity 沒有連結，`links` 一律存在這裡）。
- xcity 同步開始時先載入所有 `overrides`（筆數少），寫入 DB／ES 前把覆寫值蓋上去，手動修正不會被同步洗掉；沒被改的欄位照常跟著 xcity 更新。
- 修改 manual 女優就直接改 `info`，不走 overrides。

### 搜尋

- `domain = xcity` 改成 `domain ∈ {xcity, manual}`；xcity 資料不足時的「不限 domain」fallback 不變。
- MCP `av_actress_search` 走同一支 service，自動帶到 manual。

## 流程

1. 提交（網頁或 MCP）→ 驗證欄位、限流 → 建立 `pending` 提交單。
   - 新增：姓名完全相同時，表單上直接提醒並連到該女優頁；假名相同只標「可能重複」。兩者都不擋送出。
   - 修改：payload 跟現值完全一樣就直接拒收（沒有變更）。
2. 管理者在審核頁看 diff：
   - 欄位逐列比「目前 → 提交」，只有變更的會標色，預設只顯示有變更的欄位。
   - 現值已經不等於 `base_snapshot`（提交後 xcity 同步或另一張單先核准）→ 顯示警告，並把三個值都列出來。
3. 核准（新增單遇到同名女優見下節）→ 交易內寫 DB（新增寫 `manual`、修改寫 `info` 或 `overrides`）→ ES index（`refresh=wait_for`）→ 提交單改 `approved`。ES 失敗時整筆不算核准，維持 `pending`，回錯誤讓管理者重試。
4. 否決 → 填原因（可空白，提供常用原因快選）→ `rejected`。
   - 已否決的單可以**改為核准**：一樣用「現在的資料」重新算 diff（含資料已變更警告、同名合併），核准後覆寫審核者與時間，`review_note` 保留原本的否決原因方便追查。
   - 已核准的不能改成否決（資料已寫進搜尋，要撤回得另開一張修改單）。
5. 同一位女優同時有多張 pending 單：各自審，後核准的那張會出現步驟 2 的「資料已變更」警告。

### 新增單遇到重複時核准

- **姓名完全相同**：審核頁直接拿提交內容跟同名女優比 diff。核准時只能「合併到既有女優」，或改按否決。
  不能「新增為另一位」，因為女優頁網址是 `/av/actress/:name`，同名的兩位會打不開其中一位。
- **合併規則**：提交有填的欄位覆寫、沒填的保留原值；參考連結與興趣取聯集。既有女優是 xcity 的就寫進 `overrides`。
  提交單記為 `approved`＋`resolution = merged`，列表上看得出是合併。
- **只有假名相同／名字相近**：照一般新增處理，對話框不出現合併選項。

### 已知限制：同名女優

- xcity 現有資料就有 65 個名字重複（共 131 筆），多半是不同年代、不同人用同一個藝名（例如七瀬くるみ：1984 年生 D cup 與另一位 G cup）。
- 影片的出演只存名字（DMM GraphQL 有女優 ID，但目前沒存），女優頁網址也是用名字，所以「名字＝同一位」是整個 AV 功能本來的前提，同名問題不是上稿才出現的。
- 要真正區分同名不同人，需要影片存 DMM 女優 ID、並把 xcity 女優對應到 DMM ID，屬於另一個專案，這次不做。上稿沿用「名字＝同一位」的規則，所以同名只能合併。
- 修改單用 `target_domain` + `target_aid` 指向提交當下女優頁顯示的那一筆，不會改到另一位同名的。

## 權限與限流

- 新增／修改頁與提交 API：**不擋登入**（MCP 也是匿名），有登入就記錄提交者。限流：每個 IP 每小時 60 張（從第一張起算的固定一小時，數值寫死在 `service/av/actress_submit_limit.go`）；超過時回 429，錯誤訊息附上還要等多久（MCP 給 agent 判斷何時重試）。
- 審核頁與審核 API：主站登入且 `users.is_admin = 1`，與 galgame 管理共用同一個旗標（同一張 `users` 表），其他人一律 403；未登入顯示登入。不開放給 MCP（`/mcp` 沒有身分）。
- 管理者判斷沿用 galgame 的 `requireGalgameAdmin` 邏輯，抽成共用的 helper，兩邊一起用。

## API（草案）

| Method | Path | 說明 |
|---|---|---|
| POST | `/opendata/av/actress/submissions` | 提交（新增／修改） |
| GET | `/opendata/av/actress/submissions/:id` | 查單一提交單狀態（給提交者看結果） |
| GET | `/admin/av/actress-submissions?status=` | 管理列表 |
| GET | `/admin/av/actress-submissions/:id` | 單筆＋diff＋可能重複 |
| PUT | `/admin/av/actress-submissions/:id/approve` | 核准 |
| PUT | `/admin/av/actress-submissions/:id/reject` | 否決（`review_note`） |

## MCP

- `av_actress_submit`：`kind`（create／edit）、`target`（修改時用女優姓名指定）、各欄位、`links`（`[{title, url}]`）。
  回傳提交單 id、狀態、變更欄位清單、可能重複的女優。
- `av_actress_submission_status`：`id` → 狀態與否決原因。
- 不提供核准／否決（理由見權限）。

## 頁面

| 路徑 | 內容 | 入口 |
|---|---|---|
| `/av/actress/submit` | 新增女優表單 | 女優搜尋頁標題列「＋ 新增女優」 |
| `/av/actress/:name/edit` | 修改表單（預填現值，改過的欄位標色） | 女優詳細頁資料卡下方「修改資料」 |
| `/av/actress/submissions?status=&page=` | 管理列表（待審核／已核准／已否決） | 頭像選單「AV 女優上稿審核（待審數）」，只有管理者（`is_admin`）看得到；有待審時頭像加提示點 |
| `/av/actress/submissions/:id` | diff＋核准／否決 | 列表 |

- 管理頁放在 `/av/actress/` 底下，header 才會出現帳號選單（帳號選單依導覽項目顯示）；「AV 女優搜尋」因此設成 `requiresAuth`，女優頁會出現登入按鈕，但上稿仍不需登入。
- 本機假登入（`/auth/dev-session`）沒有 Firebase 使用者，頭像選單不會出現，管理頁要直接輸入網址進去。

- 可編輯欄位：姓名、假名、照片網址、身高、B／W／H、罩杯、血型、出生地、生日（年／月／日）、興趣、參考連結。星座不開放填。
- 罩杯用**文字框**：自動轉大寫，格式限 `AAA`、`AA`、`A`～`Z`。xcity 現有資料最大到 U（K 24、L 11、M 4、O 1、P 2、T 1、U 1），列選項會不夠用。
- 頭像選單依導覽項目的 `accountLinks` 顯示；連結可設 `adminOnly`（只給管理者）與 `badge`（待處理數量，查詢集中在 `helpers/accountLinkBadges.ts`）。

## 已定案

- 照片只收網址，暫不開放上傳。
- 不做別名／改名欄位：同一人用不同名義出演就當成不同女優。
- 不開放刪除／隱藏女優的申請。
- 不做「修改後核准」：要修正的話先核准，再自己送一張修改單核准，或直接否決。

## 實作備註

- 欄位格式：`model/entity/opendata/av/actress_fields.go` 的 `ActressFields` 是 `dmm_actresses.info`、ES 文件、提交內容共用的唯一格式；可編輯欄位清單是 `ActressEditableFields`。
- 驗證、diff、合併、覆寫都在 `service/av/actress_fields.go`（有單元測試）；前端預覽合併用 `helpers/avActressFields.ts` 的 `mergeActressFields`，規則要跟後端一致。
- MCP 修改單只採用有傳的欄位（`present`），其他沿用目前資料；網頁送的是完整欄位。
- ES 寫入：`DMM_ACTRESS_INDEX`（預設 `dmmactresses`）。非 production 且用正式索引名時不寫 ES：核准回 503、xcity 同步跳過 ES。本機要測核准時設成 `dmmactresses_localtest`，用 `_reindex` 從正式索引複製幾筆過去，測完刪掉。
- 提交者 IP 取自 `X-Real-IP`（Fiber `ProxyHeader`），本機沒有這個 header 時 IP 為空、不限流也不記雜湊。
