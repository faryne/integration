# 台電敦親睦鄰：異體字、資料同步與用途透視鏡規格（草案，2026-11-10）

## 目標與現況

- 目標：讓同一行政區的「台／臺」資料能一起查詢與統計；讓台電來源、MySQL、Elasticsearch、CDN 統計維持可追蹤的一致狀態；新增以核准用途理解資料的入口。
- 現有資料流：台電網站 → `taipower_neighbor`（MySQL）→ `taipower_neighbor`（Elasticsearch）→ `cityarea.json`／`unit.json`（S3/CDN）。逐筆頁查 Elasticsearch，年度統計頁讀 CDN JSON。
- 2026-11-10 觀察：逐筆頁已看到 2026-09 的紀錄，兩個年度統計檔的產生時間仍是 2026-06-14。`cronjobs.go` 裡台電相關 job 均無自動排程。
- 現有 `cityarea` 在匯入時可能依 `unit` 補上縣市，歷史資料也曾由 migration 修補；因此既有欄位**不保證是台電網站逐字原文**。本規格不宣稱能還原已遺失的原文。

## 範圍與順序

1. **異體字與查詢一致性**：行政區及明確的單位地名片段建立標準化 key，回填 Elasticsearch，修正統計與統計列的鑽取連結。
2. **資料同步**：把近期月份抓取、索引驗證及三份統計檔產生串成一次可重跑的流程，保留手動區間回補。
3. **用途透視鏡**：依申請摘要產生可解釋、可重算的主用途類別；提供年度／行政區的案件數、核准金額與占比，可鑽回逐筆資料。

本期不做行政區改制對照、單位改名／簡稱辨識、補助先例推薦、電廠位置因果分析或以 AI 自動判讀個案。這些需要另外確認資料語意與誤判成本。

## 1. 異體字與資料欄位

### 規則

- 保留 MySQL 現有 `cityarea`、`unit`、`summary` 值；不以全表字串替換改寫內容。新增可空的 `source_cityarea`，往後匯入時保存台電該欄原文；舊資料維持 `NULL`，不拿已修補的 `cityarea` 假裝原文。
- 在 Elasticsearch 文件另存 `cityarea_key`、`unit_key` 與 `normalization_version`（key 欄位使用 `keyword`）。`cityarea_key` 先沿用現有補縣市／有效性規則，再把行政區內的「台」統一為「臺」；例如「台中市龍井區」與「臺中市龍井區」同 key。無法辨識的地名進「未辨識行政區」統計桶，保留原列供查核，不從總額消失。`unit_key` 僅統一已辨識的行政區名稱片段，例如「台中市龍井區公所」；其他「台」字、自由文字與正式名稱不一律替換。
- `臺中縣龍井鄉` 與 `臺中市龍井區` 仍是不同 key。key 規則要有版本，後續若加入改制對照須另設對照層，不能悄悄改變既有年度排名的定義。
- 總額排名依 key 聚合，顯示名稱採固定的標準寫法；`query_name` 指向該 key。舊的 `/cityarea/:cityarea`、`/unit/:unit` URL 仍接受兩種寫法，查詢時轉成 key，避免只查到其中一種原始拼法。逐筆列可繼續顯示既有儲存值。
- `duplicate_hash` 暫不因統計 key 而重算或自動刪資料。來源紀錄若只改拼法而造成疑似重複，列入同步差異報告人工查核；這一版不假定相似列必然是同一筆核准案。

### 回填

- 先列出 key 合併前後的行政區／單位名稱數、每組合併的原名稱與金額差異，供檢查；異常地名進清單，不默默丟棄。
- 以 MySQL 為基準，分批重建／更新全部 Elasticsearch 文件的衍生欄位。回填可重跑；中斷後重跑不得倍增文件或金額。完成後才重算 CDN 統計。
- 既有統計與逐筆 API 的查詢結果不得因異體字合併而減少原有紀錄；任何變動要能追到原始列及規則版本。

## 2. 資料同步與發布

- 新增單一同步 job，每週一 04:30（**Asia/Taipei**，排程器須明確設定時區）抓最近三個已結束月份；來源尚未發布的月份視為待重試，不刪除既有資料。排程與手動回補不可同時發布，須以單一執行鎖避免互相覆蓋。保留現有手動 `range`、全量索引與產生統計指令，供較早月份修正與災難回補。
- 流程順序：抓取並寫 MySQL → 將成功取得的紀錄同步 Elasticsearch → 核對 MySQL／索引筆數及最新月份、核准金額總和 → 產生 `cityarea`、`unit`、`purpose` 統計 → 發布。任一步失敗須記錄失敗月份與階段，停止發布新的統計版本；下一次可重跑。
- 因來源可能修改舊案，而現有 `duplicate_hash` 含地名、單位、摘要及金額，同步報告應列出同月份疑似修正／重複的項目；本期不自動判定刪除或覆蓋舊案。來源實際消失的列也不自動刪除。
- 三份 JSON 先產生並驗證，再上傳到同一版本路徑；最後更新 `taipower/neighbor/manifest.json` 指向該版本。前端以 manifest 讀取同一代統計，避免看到行政區新、用途舊的混合結果。舊版物件保留供快速回退。
- manifest 至少記錄 `generation_id`、`generated_at`、`source_latest_month`、`indexed_count`、`normalization_version`、`purpose_rule_version` 與三份檔案位置。頁面要區分「統計產生時間」和「來源最新月份」；當年度標示為未滿一年。
- 部署順序：先執行 `source_cityarea` migration，再部署能產生衍生欄位與新版統計的後端並完成回填／發布，最後啟用讀 manifest 的前端與新頁。切換前保留既有固定 JSON 路徑可用；同步失敗時前端仍讀上一個完整版本，並顯示資料時間。
- 正式環境操作：依現有 `sql-migrate` 的 `master` 設定套用 migration；部署新版後端後，執行 `-cmd taipower-neighbor-sync-es` 完整回填索引並發布 manifest，確認三份版本化 JSON 與來源最新月份，再部署前端。之後每週排程使用 `taipower-neighbor-recent-sync`；需重抓舊月份時使用 `taipower-neighbor-range`，該指令會一併重發統計。這些步驟由部署者在正式環境執行，本規格與本次施工均不代跑。
- 現有 `-cmd` 入口由 handler 記錄錯誤後仍可能以成功代碼結束；**不可只看 process exit code**。回填後要檢查錯誤 log、manifest 的 `generation_id`／`indexed_count` 與三份 JSON 都能讀取。
- 同步 JOB 的 MySQL 讀取固定走 primary。既有 `taipower_neighbor` 索引的 `cash` 被推斷為 `long`，全量索引指令改為先建立 `cash: double` 的版本化索引，完成主庫筆數／總額／最新月份／規則版本核對，再以原子 alias 操作切換 `taipower_neighbor` 並移除舊索引；失敗時不切換。正式環境須重新執行一次 `-cmd taipower-neighbor-sync-es` 才能修正舊索引。

## 3. 用途透視鏡

### 分類與資料契約

- 以 `summary`（活動名稱／申請摘要）為主要依據；`apply_reason` 多為制式理由，不作主要分類依據。第一版使用版本化、可重現的文字規則，不對每次請求即時分類。
- 每筆資料恰有一個主類別：`社福／急難救助`、`教育／校園`、`社區／節慶／藝文體育`、`公共設施／環境`、`節能／能源宣導`、`未分類`。複合用途依明定的規則優先序決定；證據不足或衝突無法判斷時留在「未分類」，不硬猜。
- Elasticsearch 文件存 `purpose_key` 及規則版本；重新跑同版本須得到相同結果。規則升版需重算全量文件與統計，不能只套用到新資料。
- `purpose.json` 提供每年 × 標準化行政區 × 主用途的**案件數與核准金額（千元）**，另有全站及行政區／年度總計。分類桶互斥；各桶加總須等於相同範圍的逐筆資料總數與金額。「未分類」比例公開呈現。
- `GET /taipower/neighbor` 增加可選 `purpose` 篩選，與現有月份、地區、金額條件交集；無效類別回 400。用途頁點選某個統計格時，可帶條件鑽回既有逐筆頁。既有 API 不帶 `purpose` 的語意維持不變。

### 頁面

- 從敦親睦鄰資料頁加入「用途透視鏡」入口；新頁有中文 breadcrumb、資料時間、年度與行政區篩選、各用途的案件數／金額／占比及趨勢。金額顯示時沿用前端由千元轉新台幣元的規則。
- 清楚標示這是**核准案件的文字分類**，不代表實際撥款或成效；當年度屬部分年度。載入或 API 失敗以現有 `Alert`／SNACK 模式告知，不留空白畫面。
- 公開頁以彙總為主，不製作個人受助案件的精選卡片或自動故事；若細分格案件數少於 5，合併至較高層級顯示，降低個人敏感處境被再次突出。逐筆原文已公開，這項展示限制不等於隱私保護或資料去識別化。
- 依 `AGENTS.md` 的前端流程，**實作前另做 mockup 供確認**；本文件不含 mockup，也不代表已核准頁面設計。

## 驗收

1. **異體字**：以「台中市龍井區／臺中市龍井區」為例，統計只出現一個現行行政區列；兩種舊連結與地圖連結都能查到兩種拼法的原紀錄。`臺中縣龍井鄉` 仍獨立。單位只合併已辨識的地名異體字。
2. **數量守恆**：回填前後 MySQL 筆數、Elasticsearch document 數與全站金額核對；統計同範圍的各地區／用途加總等於逐筆查詢總數與金額（浮點誤差以千元欄位的既有精度處理）。重跑回填與同步兩次，第二次不得新增重複文件或改變統計。
3. **同步新鮮度**：模擬來源已有新月份、來源月份尚未發布、單月抓取失敗及 S3 上傳失敗。成功時 manifest 的最新月份、筆數與三份統計一致；失敗時 manifest 仍指舊完整版本，log 可找出失敗階段。正式環境成功排程後，統計產生時間須晚於該次索引完成時間。
4. **分類品質**：每個已分類類別隨機抽查至少 50 筆（不足則全查），以摘要判斷的 precision 達 90% 以上；公布未分類比例。若未達標，調整規則並升版後重跑，不用錯誤分類填滿畫面。
5. **用途頁**：年度／行政區切換後的案件數、金額與占比符合 CDN 資料；點選用途可鑽回對應逐筆資料，無效篩選回 400；當年度、未分類、載入失敗及少量個案的顯示符合上節規則。確認手機與桌面版，並通過前端編譯。
6. **回退**：保留前一代 manifest 與 JSON；切回前一代後，三種統計與用途頁讀到同一代資料，既有逐筆查詢仍可用。

## 施工驗證紀錄

- 2026-11-10 以正式站公開 API 六個年度各取前 100 筆，第一版保守文字規則的分類涵蓋率約 52%～76%；這是非隨機抽樣，不能代表全站涵蓋率，更不能當成分類正確率。
- 分類正確率須在正式資料完成回填後，依前述「每個已分類類別至少 50 筆」逐筆抽查；未完成前不宣稱已達 90% 門檻。抽樣檔已刪除，文件不保存個案摘要。
