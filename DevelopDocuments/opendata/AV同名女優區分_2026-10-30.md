# AV 同名女優區分（規格草稿）

> 狀態：已定案，尚未實作（2026-10-30）。前置：[AV女優上稿審核_2026-10-30.md](AV女優上稿審核_2026-10-30.md)「已知限制：同名女優」。

## 目的

現在「女優名字＝同一位」：同名的兩位共用一個女優頁（`/av/actress/:name` 只顯示其中一位），出演影片也混在一起，上稿新增同名只能合併。
這次讓同名女優**各有自己的頁面**，並從現在起用 DMM 女優 ID 分開她們的**新**影片。

## 現況（查 prod ES，2026-10-30，唯讀）

- `dmmvideos`：53 萬筆，`actresses` 只存名字。DMM GraphQL 明細的 `actresses` 其實有 `id`、`nameRuby`、`imageUrl`，`service/dmm/video.go` 只取了 `name`。
- `dmmactresses`：xcity 16,431 筆、manual 9 筆，另有約 4.27 萬筆 2021 年舊文件（沒有 `domain`，`type=dmmactress`，`aid` 就是 DMM 女優 ID，照片在 `pics.dmm.co.jp`）。搜尋用 domain 過濾，所以這批舊文件不會出現在搜尋結果。
- DMM 本身也有同名：舊文件 42,229 個名字中有 264 個重複，同名但 ID 不同。
- xcity 名字對到舊 DMM 文件的情況：一對一 74%、對不到 25%、對到多筆 1%。
  **xcity 的 65 個同名**對到 DMM 的情況：0 筆 17 個、1 筆 34 個、2 筆以上 14 個。所以靠名字自動對應解決不了同名，同名女優只能手動指定 DMM ID。
- xcity 頁面沒有 DMM 的連結或 ID，無法直接對應。

## 建議方案

### 1. 用什麼 key 串影片與女優

- **影片**：存 DMM 女優 ID。`DmmVideoBody` 加 `actress_ids []string`，順序跟 `actresses` 一樣，存進 MySQL `dmm.info` 和 ES。舊影片不回補，但詳細頁的「同步資料」會順手補上。
- **女優**：`ActressFields` 加 `dmm_id string`，存在 `info`／ES／上稿內容，空字串代表未對應。
  - **不做自動對應**：從上面的數字看，自動對應幫不到同名的情況，只會讓沒有同名問題的女優多一個欄位。
  - 透過上稿「修改資料」填 DMM ID，經管理者核准。xcity 女優的 `dmm_id` 會記進 `overrides`，同步時不會被洗掉（沿用既有機制，不用另外處理）。
  - 欄位接受純數字，也接受貼上 DMM 女優頁網址（從 `actress=` 參數取出 ID）。
- 女優頁網址用既有的 `{domain}-{aid}`（MCP 修改單已經在用），不用 DMM ID。原因是沒有 DMM ID 的女優（未對應的、手動新增的）也要能指到。

### 2. 女優頁出演影片怎麼查（含舊影片退回用名字）

影片搜尋新增 `actress_key={domain}-{aid}` 參數。service 會找出這位女優（名字 N、DMM ID D），以及同名其他女優已登記的 DMM ID（集合 S），再組查詢：

| 這位女優 | 條件 |
|---|---|
| 有 D | `actress_ids = D` **或**（`actresses = N` 且影片沒有 `actress_ids`，也就是舊影片） |
| 沒有 D | `actresses = N` 且 `actress_ids` 不在 S 裡（S 是空的時候就跟現在一樣） |

- 結果：新影片照 ID 分開；舊影片因為沒有 ID 無法區分，會出現在同名的每一位頁面上，跟現在一樣，不會退步。
- 改名的情況：DMM 改名後 ID 不變，新同步的影片會帶 ID，所以有 D 的女優頁也會出現改名前後的作品。
- 原本的 `actress`（名字）參數保留，給 MCP 和舊呼叫端用。

### 3. 同名女優頁網址，舊網址相容

- 網址維持 `/av/actress/:name`，另外加 `?id={domain}-{aid}` 指定是哪一位。
  - 站內連結（搜尋結果、上稿表單的「同名提醒」、審核頁）**一律**帶 `?id=`，以後新出現同名也不用改。
  - 沒有帶 `?id=`（舊網址、外部連結）：顯示同名中排第一的那位（沿用現在的搜尋排序），跟現在一樣。
- 同名有兩位以上時，資料卡上方顯示同名切換（照片縮圖＋出生年／罩杯），點了換成 `?id=` 那位。只有一位就不顯示。
- `?id=` 對到的女優名字跟網址不一樣（核准改名）→ 用 `replace` 換成新名字的網址；`?id=` 找不到 → 忽略，當成沒帶。
- 分頁要保留 `?id=`（現在 `setSearchParams({page})` 會把其他參數洗掉）。
- `/av/actress/:name/edit` 用同樣的規則。
- 女優搜尋 API 加 `key` 參數（精確比對 `domain`＋`aid`），給上面「改名後找回來」用。

### 4. 上稿審核：同名開放「新增為另一位」

- 網址可以區分同名後，新增單遇到同名時，核准對話框除了「合併到 X」之外，再加一個「新增為另一位」，由管理者選，沒有預設值。
- API：`approve` 的 `merge_target` 可以是 `{domain}-{aid}` 或 `new`。
- 提交表單的同名提醒不變，連結改成帶 `?id=`。
- **DMM ID 衝突**：核准時如果這個 `dmm_id` 已經被其他女優使用，就擋下來（409，訊息附上是哪一位）。一個 DMM ID 只能對到一位女優。
- 審核頁 diff 遇到 `dmm_id` 有變更時，附上「這個 ID 在幾部影片中出現、最常一起出現的名字」，讓管理者確認沒有填錯。

### 5. ES mapping／reindex

- **不用 reindex**：兩個都是新增欄位，可以直接 PUT mapping 加上去，舊文件沒有這個欄位就代表是舊資料。
- 部署前先跑（在第一次寫入新欄位之前）：
  - `PUT dmmvideos/_mapping {"properties":{"actress_ids":{"type":"keyword"}}}`
  - `PUT dmmactresses/_mapping {"properties":{"dmm_id":{"type":"keyword"}}}`
  - 忘記跑的話，dynamic mapping 會建成 `text`＋`keyword`，數字字串用 term 查一樣查得到，不會壞，只是型別不一致。
- MySQL 不加欄位，`dmm_id` 和 `actress_ids` 都放在既有的 `info` JSON 裡，不用跑 migration。
- 2021 年那批舊 DMM 女優文件先不動。之後如果要做「DMM ID 候選清單」，可以拿它當種子資料（見「不做」）。

### 6. MCP：不動

同名是少數，`service/mcp/` 不改程式。連帶影響：
- `av_video_search`／`av_actress_search` 直接序列化 service 的結果，回傳會自然多出 `actress_ids`／`dmm_id`，不另外處理。
- `av_actress_submit` 的 schema 沒有列 `dmm_id`，agent 不會主動填。修改單只採用有傳的欄位，所以不會把既有的 `dmm_id` 洗掉。
- 工具說明裡「同名時管理者會合併」的描述維持原樣。核准時可以選「新增為另一位」是網頁審核頁的事，不影響 agent 送單。

## User stories

1. 讀者從搜尋結果點進「七瀬くるみ（1984 生）」，網址帶 `?id=xcity-123`，看到的是這一位的資料卡，上方可以切到另一位同名的。
2. 讀者用舊網址 `/av/actress/七瀬くるみ` 進來，看到的跟現在一樣，可以從同名切換換到另一位。
3. 使用者在女優修改頁填 DMM ID（或貼 DMM 女優頁網址）送出。管理者核准後，這位女優頁的新影片只剩這個 ID 的作品，同名另一位的頁面也自動把這些影片排除掉。
4. 使用者新增一位跟既有女優同名、但其實是不同人的女優。管理者選「新增為另一位」，核准後兩位各有自己的頁面。

## 常見失敗情境

| 情境 | 處理 |
|---|---|
| `?id=` 對到的女優不存在（被合併、打錯） | 忽略 `?id=`，照名字顯示，網址換成不帶 `?id=` |
| `?id=` 對到的女優已改名 | `replace` 成新名字的網址 |
| 填的 DMM ID 已被其他女優使用 | 核准時回 409，訊息附上是哪一位 |
| DMM ID 填錯（不存在或填成別人） | 審核頁顯示這個 ID 的影片數和最常一起出現的名字；已經核准的就再送一張修改單改正 |
| DMM 明細的女優沒有 id | `actress_ids` 那一格存空字串，維持跟 `actresses` 同順序 |
| 舊影片（沒有 `actress_ids`） | 照名字比對，出現在同名每一位的頁面上（跟現在一樣） |
| 同名女優都沒有 DMM ID | 頁面分開，但出演影片列表一樣（跟現在一樣） |
| 沒有先 PUT mapping | dynamic mapping 也查得到，事後補 PUT 會報型別衝突，就維持現狀 |

## 不做

- 舊影片回補 DMM ID（53 萬筆要重打 DMM 明細，不划算；詳細頁「同步資料」會一筆一筆補）。
- xcity ↔ DMM 自動對應、DMM ID 候選清單（拿 2021 年舊文件和影片同步建字典）。同名的情況靠自動對應解決不了，等手動填的需求真的很多再評估。
- 影片詳細頁的出演 chip 直接連到正確的那位（現在連到搜尋頁，同名會兩位都列出來，可以接受）。
- 別名／改名欄位（沿用上稿規格的決定）。
- MCP 工具不加 `actress_key`／`dmm_id` 參數（見第 6 節）。如果之後 agent 常常需要分開查同名女優的作品，再補參數，service 那邊已經有現成的了。
