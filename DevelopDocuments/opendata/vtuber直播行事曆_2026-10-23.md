# VTuber 直播行事曆：全部集中到 Go

> 狀態：已實作（2026-10-23，branch `feat/vtuber-live-pipeline`），本機驗證過偵測、統計、API 與前端；行事曆同步要等新 Firebase 專案與 service account 準備好才能實測（見〈上線順序〉）。Apps Script 退場，直播偵測、Google Calendar 同步、Firebase 讀寫都由 Go 負責。只處理 hololive，propro 不做。MySQL 舊表改名 `*_legacy` 保留、暫不遷移。前端 mockup：`DevelopDocuments/opendata/vtuber-schedule-mockup/`。

## 背景

- Apps Script `hololive()` 讀的是 `https://faryne.dev/api/opendata/vtubers/lives`。這支 API 在 PHP 下線後就不存在了，hololive 行事曆同步早已停擺。prod 的 `vtuber_lives`／`vtuber_stats` 也是 2022-04 之後就沒有新資料。
- 行事曆事件只建不改。待機室改時間、直播取消都不會反映；結束時間一律抓開始後 2 小時。
- 舊版前端：上方一排藝人大頭貼，點進藝人頁；左側個人檔案（資料多半來自 `hololive.json`），右側「正在直播」「即將直播」「所有影片」和嵌入的個人 Google 行事曆，點影片開 modal 嵌入 YouTube。新版沿用這個骨架，但大頭貼牆會隨人數長高，改成固定一列的選擇列＋全部藝人面板。

## 目標

- Go 負責：頻道名冊、直播偵測與狀態追蹤、每日頻道統計、Google Calendar 同步、Firebase 讀寫。
- MySQL 存頻道（含個人行事曆 ID）、直播與統計；Firebase（新專案）只存「影片 ↔ 行事曆事件」對應。
- Apps Script 時代建好的行事曆沿用，訂閱的人不受影響：總表 ID 寫死成常數（前後端各一份），個人行事曆 ID 從舊 Firebase 匯入 `vtuber_channels.calendar_id`；沒有的才由 Go 新建。
- 前端新增 `/data/vtubers`（總覽）與 `/data/vtubers/:handle`（藝人頁），另外提供 MCP tool 查直播。
- Apps Script 全部停用。

### 不做

- propro：Go 不追蹤。Apps Script 停用後，propro 的舊行事曆就不會再更新。
- ICS feed 自己產：Google 公開行事曆本身就有 ICS 網址，直接給 Apple Calendar 等用戶端訂閱就好。
- 舊資料遷移：`*_legacy` 先保留，之後真的需要再評估。

## User stories

1. 我打開 `/data/vtubers`，最上面一列可以搜尋藝人、看誰正在直播；下面是直播中卡片和接下來幾天的直播時間表。
2. 我搜尋或從「全部藝人」面板（依分部、期別分組）點某位藝人，進到她的頁面：左邊是個人檔案和頻道數據，右邊是正在直播、即將直播、所有影片，以及她的 Google 行事曆。
3. 我點任何一部直播或影片，會開 modal 直接在頁面裡播放。
4. 我可以訂閱 hololive 總表或某位藝人的個人行事曆；藝人一開待機室，10 分鐘內行事曆就會出現事件。待機室改時間、直播取消、直播結束，事件都會跟著更新。
5. 新藝人出道，下次週更 job 跑完會自動出現在頁面上並建立個人行事曆；畢業的藝人留在原本的期別、頭像改用虛線圓環標示，從官網上消失的才不再追蹤（舊事件保留）。
6. 在 Claude 問「今天晚上 hololive 誰有開台」，MCP tool 可以回答。

## 資料流

```
週一 02:30  vtuber-hololive-talents（既有，改）
            爬官網列表＋分組頁 → YouTube channels.list → upsert vtuber_channels ＋ 照舊寫 CDN hololive.json

每 5 分鐘   vtuber-lives-detect（新）
            ① 各頻道 RSS → 沒看過的 video_id（Redis 去重）
            ② DB 中 upcoming / live 的 video_id
            ①＋② → videos.list（50 筆一批）→ upsert vtuber_lives
            ③ 接著跑 calendar sync：MySQL 對照 Firebase 上次同步的內容 → Google Calendar create / update / delete

每日 03:10  vtuber-stats-daily（新）
            channels.list → upsert vtuber_stats ＋ 更新 vtuber_channels 的頻道資訊
            頻道改名時改個人行事曆名稱；順便清掉 Firebase 中結束超過 30 天的事件記錄

手動        vtuber-import-calendars（一次性）
            讀舊 Firebase 的 hololive/calendar，把個人行事曆 ID 寫進 vtuber_channels.calendar_id
```

偵測和行事曆同步放在同一支 cron 裡依序執行，這樣同步一定拿得到這輪最新的資料。偵測失敗也照樣同步，同步失敗只會 error log，下一輪重新比對時會再補上。上一輪還沒跑完時，這一輪直接跳過（cron 本身不會擋重疊）。

## 憑證與設定

你會建一個新的 Firebase 專案給這個功能用。Firebase 專案本身就是一個 GCP 專案，所以**同一把 service account 金鑰就能同時打 Firebase RTDB 和 Google Calendar API**：

1. 新的 Firebase 專案建好 Realtime Database，security rules 全部擋掉（只有 service account 能存取）。
2. 到 GCP console 為同一個專案啟用 Google Calendar API。
3. 在 Firebase console 產生 service account 私鑰（JSON）。

新增環境變數（任一留空就不同步行事曆，例如本機）：

| 變數 | 說明 |
|---|---|
| `VTUBER_GOOGLE_CREDENTIALS` | service account JSON 的檔案路徑 |
| `VTUBER_FIREBASE_DATABASE_URL` | RTDB 網址，例如 `https://<project>-default-rtdb.<region>.firebasedatabase.app` |
| `VTUBER_LEGACY_FIREBASE_SECRET` | 一次性：舊 Firebase（`faryne-firebase`）的 legacy database secret，只有匯入行事曆時用，匯入完就可以移除 |

`GOOGLE_CALENDAR_CRED` 原本沒有任何程式在用，已移除。

### 行事曆歸屬

- **總表**：`tisupenl6m3lnrjs26kipm1iu0@group.calendar.google.com`（舊 Firebase `hololive/calendar/all`），寫死在 `service/vtuber/calendar_sync.go` 的 `AllCalendarID` 與前端 `components/vtuber/calendar.ts` 的 `ALL_CALENDAR_ID`，兩邊要一起改。Go 不會自動建總表。
- **個人行事曆 ID**：`-cmd vtuber-import-calendars` 直接讀舊 Firebase 的 `hololive/calendar` 節點（`{"all": …, "UC…": …}`，2026-10-23 有 90 筆個人行事曆），寫進名冊裡對得到的頻道。要先跑過週更 job；可以重跑，會覆蓋。事件記錄（`hololive/<videoId>`，約 1.4 萬筆）裡的 `calendarByArtistId` 也能反推出同樣的對應，但不需要。
- **權限**：舊行事曆的擁有者是你的 Google 帳號，service account 沒有權限就不能改事件，而只有擁有者能幫它加權限。所以還是要在舊 Apps Script 專案跑一次 `DevelopDocuments/opendata/vtuber-calendar-grant.gs`：把 service account 加成每個行事曆的**擁有者**（藝人改名時 Go 也要能改行事曆名稱），並確保行事曆是公開的。
- **新藝人**：沒有個人行事曆的頻道由同步 job 自動建立，擁有者是 service account，並設成公開。這種行事曆不會自動出現在你自己的 Google 日曆裡，要看的話用頁面上的訂閱連結加入。

### `vtuber_lives`

| 欄位 | 型別 | 說明 |
|---|---|---|
| `id` | int unsigned PK | |
| `video_id` | varchar(16) UNIQUE | |
| `channel_id` | varchar(32) | INDEX `(channel_id, scheduled_start_at)` |
| `title` | varchar(255) | |
| `status` | varchar(10) | `upcoming`／`live`／`ended`／`cancelled`，INDEX `(status, scheduled_start_at)` |
| `scheduled_start_at` | datetime NULL | |
| `actual_start_at`、`actual_end_at` | datetime NULL | |
| `concurrent_viewers` | int unsigned NULL | 最後一次看到的同接人數（只在 live 時有值） |
| `thumbnail_url` | varchar(255) | 影片縮圖，前端卡片用 |
| `checked_at` | datetime | 最後一次向 YouTube 確認的時間 |
| `created_at`、`updated_at` | | |

- **時間欄位存的不是固定 UTC**：`DATETIME` 不帶時區，Go 的 MySQL driver 寫入時轉成 DSN `loc` 的時區、讀出時也用它解讀，所以來回一致；API 輸出時一律轉成 UTC。
  - 本機 DSN 是 `loc=Local`、Mac 時區是台北，所以本機存的是台北時間（實測 YouTube `04:00:31Z` → DB `12:00:31`）。prod 存哪個時區取決於 prod 的 DSN 與 server 時區。
  - 直接下 SQL 看資料要知道這點；之後若改了 DSN 的 `loc` 或 server 時區，舊資料會整批偏移。walolita 的 DSN 是多張表共用的，不為了這張表改成 `loc=UTC`。
- 不存影片說明。行事曆事件說明只放 `https://youtu.be/<id>`，舊版塞的說明文字大多是固定版頭，沒有實質內容。

### Migration 做法

一支 migration（`20261023100000-create_vtuber_tables.sql`），Up 依序：

1. `CREATE TABLE IF NOT EXISTS` 照抄 prod 舊的 `vtuber_lives`、`vtuber_stats`。prod 上是 no-op，本機才建得出空表，下一步的 `RENAME` 才不會失敗（MySQL 5.7 沒有 `RENAME TABLE IF EXISTS`）。
2. `RENAME TABLE vtuber_lives TO vtuber_lives_legacy, vtuber_stats TO vtuber_stats_legacy`。
3. 建新的 `vtuber_channels`、`vtuber_lives`、`vtuber_stats`。

Down：DROP 三張新表，再把 `*_legacy` 改回原名。直播與統計可以從 YouTube 重新收集；`calendar_id` 會跟著刪掉，重新 up 後再跑一次匯入。

## Firebase 結構（新專案，只有 Go 讀寫）

```
vtuber/
  events/<videoId> → {
      channelId, title,
      startAt, endAt, status,      // 上次寫進行事曆的值，用來判斷要不要更新
      eventIds: { all: "<eventId>", channel: "<eventId>" }
  }
```

- 用 RTDB 的 REST API（`<url>/<path>.json`）搭配 service account 的 OAuth token，沒有另外引入 Firebase Admin SDK。
- 每日清掉 `endAt` 超過 30 天的 `events`，讓同步時整包讀取 `vtuber/events` 的量維持在幾百筆以內。

## Go 端細節

### 直播偵測（`vtuber-lives-detect`，`*/5 * * * *`）

1. 讀未刪除的頻道（2026-10-23 是 79 個），用 8 個 goroutine 並行抓 `https://www.youtube.com/feeds/videos.xml?channel_id=<id>`。
2. RSS 每個頻道列最近 15 部。Redis `vtuber:seen:<video_id>`（TTL 30 天）去重，只把第一次看到的 ID 送去查。**`videos.list` 成功後才記 seen**，quota 用完那輪的影片下一輪會再查。
3. 再加上 DB 中 `status IN (upcoming, live)` 的 ID，用 `videos.list(part=snippet,liveStreamingDetails)` 每 50 筆一批查詢。
4. 狀態判斷：
   - 沒有 `liveStreamingDetails` → 一般上傳影片，不寫入。
   - `actualEndTime` 有值 → `ended`；`actualStartTime` 有值 → `live`；其餘 → `upcoming`。
   - `scheduledStartTime` 在 60 天以後（或沒有預定時間）→ 視為「フリーチャット」（常駐聊天室），不寫入。
   - 追蹤中的直播這次查不到（轉私人、刪除），或已經不算直播（例如改成フリーチャット）→ `cancelled`。
5. Quota（本機實測）：第一輪 1,185 部約 24 units，之後每輪只查追蹤中的（約 27 部，1 unit）。

### 行事曆同步（接在偵測後面）

1. 從 MySQL 撈跟 `now-1d ~ now+14d` 有重疊的直播（見〈API〉的區間規則）與頻道（含 `calendar_id`），從 Firebase 一次讀 `vtuber/events`。總表用常數 `AllCalendarID`。
2. 還沒有個人行事曆的頻道先建立：名稱沿用「Live Schedule of <頻道名>」，建好後加上公開的 ACL（`scope=default, role=reader`），寫回 `vtuber_channels.calendar_id`。**每輪最多建 5 個**，避免撞到 Calendar API 建立行事曆的頻率限制。舊行事曆有先匯入的話，只有新藝人需要建。
3. 逐筆比對直播（`planEvent`）：
   - Firebase 沒有記錄、狀態不是 `cancelled` → 建立事件。
   - 狀態變成 `cancelled` → 刪除事件，記錄的 `status` 改成 `cancelled`（保留記錄，避免下一輪又被建立）；取消過又回來的直播當成全新處理。
   - 標題、開始或結束時間跟記錄不同 → patch 事件。`upcoming → live` 只改狀態，不算變動。
   - 個人行事曆後來才建好 → 只補建那一邊。
   - 都一樣 → 跳過，不呼叫 Calendar API。
4. **建立事件前先查重**：事件的 private extended property 寫了 `key=<videoId>`，建立前用它在該行事曆找有沒有已經存在的事件，有的話直接沿用。處理「建立事件成功、但寫 Firebase 之前程式中斷」的情況。
5. 中途失敗時，已經建立的事件 ID 照樣寫回 Firebase，標題／時間則沿用上次的值，下一輪才會再判定成有變動重試。撞到限流就停掉這輪。
6. 事件時間：開始時間用 `actual_start_at`，沒有的話用 `scheduled_start_at`；結束時間用 `actual_end_at`，沒有的話用開始時間加 2 小時。標題格式維持 `[頻道名] 直播標題`。
7. `service/google/calendar.go` 原本沒有任何地方在用，而且只支援全天事件，已改寫成：有時間的事件、建立公開行事曆、改名、依 key 查詢事件；scope 是 `calendar`（建立行事曆需要完整權限）。

### 每日統計（`vtuber-stats-daily`，`10 3 * * *`）

- `channels.list(part=snippet,brandingSettings,statistics)` 每 50 個一批，約 2 units。
- `vtuber_stats` 用 `INSERT ... ON DUPLICATE KEY UPDATE`，同一天重跑會覆蓋。同時更新 `vtuber_channels` 的名稱、說明、頭像、橫幅和最新統計（不碰官網來的 slug、順序、期別）；頻道名稱有變時，個人行事曆的名稱也跟著改。
- 舊表大約是每小時記一筆；新的改成每天一筆就好。要改回每小時也很便宜（每次約 2 units），之後想要再調。
- YouTube 對外公開的訂閱數是取過近似值的（三位有效數字），每日曲線會呈階梯狀，這是正常的。

### 週更 job（`vtuber-hololive-talents`，改）

- 先 upsert `vtuber_channels`（含 `talent_slug`、`sort_order`、`unit_slug`），再照舊寫 CDN `hololive.json`；CDN 寫失敗不影響名冊。
- **期別**：逐一抓官網分組頁 `/talents?gp=<slug>`（約 23 頁，間隔同樣 500ms），記下每位藝人屬於哪些分組。一位藝人可能同時在好幾組（例如白上フブキ同時是 1期生和ゲーマーズ），依常數表順序取第一個當 `unit_slug`，畫面上就不會重複出現。
- 分組 slug、顯示名稱、所屬分部（JP／EN／ID／DEV_IS）寫成常數表（`service/vtuber/units.go`）。官網出現常數表裡沒有的新分組時：該藝人的 `unit_slug` 照樣寫入，前端歸到「其他」分段；job 印 warn 提醒補常數表。
- **卒業生**：官網主列表仍列著畢業的人，而且還掛在原本的期別下（例如天音かなた也在 4期生）。`alum` 分組不當成期別、也不在常數表裡，成員只標記 `is_graduated`，期別維持原本的。
- **工作人員也列出來**：`holoan`、`tag_office-staff`（事務所スタッフ）放在常數表最後，分部是 `OTHER`。`friend-a`（友人A）的個人頁連到 hololive 官方頻道，`izuki-michiru` 連到 holoAN room，官網把她們定義成這兩組的成員，照樣列出。
- **名冊清理的保護**：如果這次寫入的頻道數不到目前在籍數的 80%，就跳過 soft delete 並 warn。上次官網把連結改成相對路徑，爬蟲就整個爬空過，這個保護是防同樣的事。

### API

prod 對外網址是 `https://faryne.dev/api-integration/opendata/vtubers/...`，回應用標準的 `output` 格式。

| Method | 路徑 | 參數 | 說明 |
|---|---|---|---|
| GET | `/opendata/vtubers/channels` | | 藝人選擇列與全部藝人面板用：頭像、名稱、handle、期別、是否正在直播；另附分組常數表（總表行事曆前端寫死，不經 API） |
| GET | `/opendata/vtubers/channels/:handle` | | 藝人頁左側：完整頻道資訊、最新統計、7 日／90 日增減、個人行事曆連結；找不到回 404 |
| GET | `/opendata/vtubers/channels/:handle/stats` | `days`（預設 90，上限 365） | 每日統計，畫曲線用 |
| GET | `/opendata/vtubers/channels/:handle/videos` | `type`（`all` 預設／`live`／`video`／`short`）、`page_token` | 「所有影片」：依分類讀 YouTube 上傳清單，一頁 24 部；分類不合法回 400 |
| GET | `/opendata/vtubers/videos/:video_id` | | 影片 modal 與 SEO 用：標題、說明、縮圖、上傳時間、頻道（id／名稱／handle／頭像）、`live`（vtuber_lives 的狀態與時間，不是直播為 null）。YouTube 那段點開時才查（`videos.list`，1 unit），Redis 快取 6 小時（key `vtuber:video:v2:*`，查不到也快取成 null）；頻道與 `live` 每次從 DB 補。影片不存在或不是追蹤中的頻道回 404、ID 格式不對回 400；同一個 IP 每分鐘 60 次，超過回 429 |
| GET | `/opendata/vtubers/lives` | `channel_id`、`status`、`from`、`to` | 預設範圍 `now-1d ~ from+15d`，上限 31 天；回傳跟區間**有重疊**的直播，依開始時間排序。`from`／`to` 接受 RFC 3339 或 `YYYY-MM-DD`（台北午夜）；參數錯誤回 400 |

- `:handle` 帶不帶 `@` 都可以。
- **區間是「重疊」不是「開始時間落在區間內」**：開始時間不晚於 `to`，且「還在直播」或「結束時間（沒結束就看開始時間）不早於 `from`」。YouTube 直播本身沒有時間上限（超過 12 小時只是不保留完整存檔），連播超過一天的直播如果只看開始時間，會掉出預設區間，行事曆的結束時間不會更新，總覽的「直播中」也看不到它。行事曆同步、API、MCP 共用同一個查詢（`repository/vtuber/live.go` 的 `FindLives`）。
- **所有影片**：用 `playlistItems.list` 讀上傳清單，每頁 1 unit，不存 DB。清單 ID 是「字首＋channel ID 去掉開頭的 `UC`」：
  - `all` → `UU`（官方的上傳清單）；`live` → `UULV`（直播存檔）；`video` → `UULF`（一般影片）；`short` → `UUSH`（Shorts）。三類加起來等於 `UU`（2026-10-24 用 Marine 實測：1,056＋132＋426＝1,614）。
  - 分類字首是**沒有公開文件**的用法，廣泛使用但 YouTube 隨時可能改；會員限定（`UUMO`）刻意不提供，非會員點了也播不了。
  - 某類沒有影片時 YouTube 回 `404 playlistNotFound`，當成空清單（前端顯示「沒有影片」）。字首真的失效時也會是 404，所有分類都會變成空的，到時要改程式。
  - 不是先撈全部再過濾：上傳清單的回傳資料沒有分類資訊，撈全部也分不了類，而且一個頻道要幾十 units。改成按需讀取、每頁各自快取。
  - Redis 快取 key 是「頻道＋分類＋page token」：**第一頁 30 分鐘**（可能出現新上傳的影片），**第二頁以後 6 小時**（幾乎不會變）。代價是新影片上傳後清單往後擠一格，舊的後頁快取在交界可能重複或少一部。
- 每個行事曆提供三種連結：
  - 加入 Google 日曆：`https://calendar.google.com/calendar/r?cid=<calendarId>`
  - 嵌入（藝人頁右側）：`https://calendar.google.com/calendar/embed?src=<calendarId>&ctz=Asia/Taipei&mode=AGENDA`
  - ICS（Apple Calendar 等）：`https://calendar.google.com/calendar/ical/<calendarId>/public/basic.ics`
- `lives` 每筆欄位：`video_id`、`channel_id`、`channel_title`、`channel_handle`、`channel_thumbnail_url`、`title`、`thumbnail_url`、`status`、`scheduled_start_at`、`actual_start_at`、`actual_end_at`、`concurrent_viewers`、`updated_at`（時間一律 RFC 3339 UTC）。畢業頻道的直播不回傳。

### MCP tool `vtuber_live_query`

- 參數：`channel`（頻道 ID、@handle 或名稱的一部分）、`status`、`from`、`to`。區間預設與上限跟 API 相同。名稱關鍵字可能對到多個頻道（例如「Ch.」），會一起查。
- 跟 `exchange_rates_query` 一樣，查詢邏輯放 `service/vtuber/query.go`，MCP 只做參數轉換。

## 前端

導覽列「資料」分類加一項「VTuber 直播行事曆」。時間一律用台北時間顯示（`Intl.DateTimeFormat`，不跟著瀏覽器時區），在時間清單旁用 `TimeZoneNote` 標出「台北時間（UTC+8）」：總覽的「過去的直播」「即將直播」標題旁、藝人頁「即將直播」分頁上方。

Google 日曆不用標：事件寫入的是帶時區的 RFC 3339（UTC，`…Z`），每個人看到的是自己日曆設定的時區；行事曆本身的預設時區（新建的設 Asia/Taipei）只影響沒登入時網頁版的預設顯示。

### 藝人頁 `/data/vtubers/:handle`

- 麵包屑：首頁 / 資料 / VTuber 直播行事曆（可點回總覽）。共用的麵包屑元件只有三層，藝人名稱放在頁面標題（`<title>`）與左側個人檔案，不另外加第四層。
- **左側**：橫幅、頭像、名稱、handle・期別、頻道說明（可展開）；訂閱數、觀看數、影片數，以及 7 日／90 日增減（統計不夠久時顯示「—」）；頻道建立日期；「訂閱個人行事曆」選單（沒有個人行事曆時不顯示）；YouTube、官網連結。
- **右側**：
  - 「正在直播」：有直播時才出現，大卡片。
  - 分頁：「即將直播」「所有影片」「行事曆」「統計」。所有影片（mockup：`vtuber-videos-mockup/`）上方可切換全部／直播／影片／短片，縮圖格狀、捲到底自動載入下一頁，短片用直式 9:16 縮圖、一列放比較多張；行事曆是嵌入的 Google 行事曆（agenda 模式），沒有個人行事曆時不顯示這個分頁。
- **統計分頁**（mockup：`vtuber-stats-mockup/`）：訂閱者、觀看、影片三張圖，用 Google Charts（`react-google-charts`，執行時從 gstatic 載入）。
  - 期間切換 30 天／90 天／180 天／1 年（對應 API `days`，上限 365）。
  - 每張圖可切「累計（折線）／每日增減（長條）」，預設依數字特性：訂閱者累計（YouTube 公開訂閱數只有三位有效數字，大頻道每日增減幾乎都是 0）、觀看每日增減（累計幾乎是斜直線）、影片累計。
  - 每張圖上方是目前數字與這段期間的增減；少於 2 天不畫圖，顯示「資料累積中（目前 N 天）」。prod 從 2026-10-23 才開始記錄。
  - 每日增減是跟前一筆相比，某天 job 沒跑時會是兩天的合計。
  - 原本側欄的 90 天小曲線（`@mui/x-charts`）拿掉，曲線集中在這個分頁，同一頁不混用兩套圖表。
  - Google Charts 不吃 MUI 主題，而且不支援 `rgba` 的透明度（會畫成不透明），文字與格線的顏色依深淺色模式傳實色。
- 分頁列捲到 header 下方就黏住（桌機、手機同一種做法）；黏住時切換分頁會捲回內容頂端，不用再爬回去。曾評估「捲動後把分頁移到左欄、個人檔案收合」，因為要兩份分頁 UI、捲動時版面會跳而不採用（mockup 有切換可比較）。
- 桌機左側個人檔案黏在 header 下方（top＝header 高度＋16px）。header 高度抽成 `SITE_HEADER_HEIGHT`（`components/common/siteLayout/siteTheme.ts`），header 本身與要黏在它下方的元素共用。
- 找不到藝人（API 404）顯示 404 頁。手機版左右改成上下堆疊，個人檔案在上。

### 藝人分頁與影片網址

| 網址 | 內容 |
|---|---|
| `/data/vtubers/@name` | 藝人頁「即將直播」（預設分頁） |
| `/data/vtubers/@name/videos`、`/calendar`、`/stats` | 「所有影片」「行事曆」「統計」分頁；沒有行事曆或不認得的分頁回到預設分頁 |
| `/data/vtubers/@name/videos/:videoId` | 影片 modal，掛在上傳頻道底下 |

- App.tsx 只掛 `/data/vtubers/*`，由 `pages/opendata/vtuber_section.tsx` 分派：index 是總覽，`:handle/*` 是藝人頁（分頁與影片都用同一個 route，切分頁不會重新掛載）。網址 helper 在 `components/vtuber/routes.ts`。
- 切分頁是 push：重新整理、分享、上一頁都回到同一個分頁。「所有影片」裡的全部／直播／影片／短片篩選不進網址。
- 站內點開（`useOpenVideo`）：導到影片網址，history state 帶 `background`（原頁面）與 `video`（已有的資料）。原頁面照 background 繼續渲染、不重新掛載，捲動與分頁都保留；上一頁或關閉都是 `navigate(-1)`。
- 直接打開：沒有 background，墊該藝人的「所有影片」分頁；modal 等 `/videos/:video_id` 回來才打開，關閉後 replace 到 `/@name/videos`。查不到（404、額度用完）跳 snack 並關閉。
- 網址的 handle 跟影片頻道對不上（打錯、藝人改了 handle）：前端 replace 成正確網址，SEO 的 canonical 也指向正確網址，舊連結不會 404。
- 找不到的處理（snack 放在 `VtuberSection`，跳轉後才不會跟著頁面消失）：
  - 影片 ID 不是 11 碼（含帶斜線、編碼過的 `%2F`、多段網址）：不打 API，「找不到這部影片」並回到 `/@name/videos`。
  - 找不到藝人：「找不到這位藝人」並回總覽。`/channels/:handle` 的 404 不重試（react-query 預設重試 3 次會讓進度條轉 7 秒）。
  - 影片網址上藝人不存在時先等影片結果：影片找得到就換成正確藝人、不跳錯誤；影片也找不到才依序關 modal、回總覽。
- 直接打開時不知道是不是短片，一律用橫式播放器。

| 路徑 | 標題／描述 | 預覽圖 | 找不到 |
|---|---|---|---|
| `/data/vtubers` | 固定文案 | 站台預設圖 | — |

## 常見失敗與應對

| 狀況 | 應對 |
|---|---|
| YouTube quota 用完（403 `quotaExceeded`） | 這輪放棄，不記 seen，下輪再試。upcoming 的狀態會晚一點更新，但不會遺失；「所有影片」回錯誤，前端顯示 snackbar |
| 某頻道 RSS 抓失敗或逾時 | 跳過該頻道並 warn，不影響其他頻道 |
| cron 停超過 15 部影片的量 | 補不回 RSS 外的舊影片。對直播行事曆影響不大，因為待機室通常是最新的幾部 |
| Redis 掛掉或被清空 | 去重失效，該輪會多查一些（約 21 units），不影響正確性；「所有影片」不走快取，直接打 YouTube |
| 官網改版爬空 | 80% 保護會跳過 soft delete，`vtuber_channels` 維持上次的名單 |
| 上一輪偵測還沒跑完 | 這一輪直接跳過並 warn |
| Calendar API 限流（429、403 `rateLimitExceeded`／`usageLimits` 等） | 這輪剩下的同步全部停掉，下一輪重新比對時補上 |
| 有人手動刪了行事曆事件 | patch 回 404／410 時改成重建事件並寫回新的 eventId；刪除時遇到 404 直接當成功 |
| 建立事件後、寫 Firebase 前程式中斷 | 下一輪建立前用 key 查重，找到就沿用，不會重複 |
| Firebase 讀寫失敗 | 這輪不同步並 log，偵測結果照常寫入 MySQL；網站的行事曆連結讀 MySQL，不受影響 |
| 建立行事曆失敗 | 不擋事件同步（沒有行事曆的那一邊先跳過），下一輪再試 |
| 舊行事曆沒有給 service account 權限 | 該行事曆的事件操作回 403／404 並 warn；跑一次 `vtuber-calendar-grant.gs` 補權限 |
| 待機室過了預定時間還沒開 | 維持 `upcoming`，事件留在原時間；開台後會更新成實際開始時間 |
| 藝人改 handle | 每日統計會更新 `custom_url`，舊網址會 404。影響小，先不做轉址 |

## 已知注意事項

- **YouTube 頻道頭像與橫幅（`yt3.ggpht.com`、`yt3.googleusercontent.com`）收到外站 referrer 會拒絕**，前端一律用 `referrerPolicy="no-referrer"`（`ChannelAvatar`、橫幅用 `<img>` 而不是 CSS 背景圖）。影片縮圖（`i.ytimg.com`）沒有這個限制。
- API 給的頭像是 800px，前端改抓 176px（網址的 `=s800-` 換成 `=s176-`），全部藝人面板一次幾十張才不會慢。
- 總表行事曆累積了 2021 年以來的所有事件，公開 ICS 有 59MB。Google 日曆訂閱沒影響，用 ICS 訂閱的用戶端（Apple Calendar 等）會很重；之後要的話可以清掉舊事件。
- 本機 DB 的 `migrations` 表有一筆 repo 裡沒有的紀錄（`20260918100000-add_actor_to_storyteller_versions.sql`），`make mig-up` 會直接失敗。這支 migration 在本機是手動執行 Up 區段後補上 migrations 紀錄的；prod 不受影響。
- **名冊清理只限 hololive**（2026-10-24）：`vtuber_channels.org_slug`（migration `20261024120000-add_vtuber_channels_org_slug.sql`，既有資料預設 `hololive`）。週更 job 的軟刪除與 80% 門檻的分母都只算 `org_slug = 'hololive'`，之後手動加入的其他事務所／個人勢頻道不會被當成「官網上不見了」刪掉。entity 的 `OrgSlug` 帶 `default:hololive`，新增頻道漏填時用 DB 預設，不會寫成空字串。
  - 已知邊角：hololive 卒業生仍列在官網卒業生分組，週更 job 會把 `org_slug` 寫回 `hololive`；之後若要把畢業後轉個人勢的人改掛 `indie`，要先決定以官網名冊為準還是以手動登錄為準。

## 上線順序

1. 你準備：新 Firebase 專案（RTDB＋security rules 全擋）、啟用 Calendar API、service account 金鑰。
2. 在**舊** Apps Script 專案貼上 `vtuber-calendar-grant.gs`，啟用 Google Calendar 進階服務，填入 service account email，執行 `grantCalendarsToServiceAccount`。
3. 跑 migration，部署 Go，設定 `VTUBER_GOOGLE_CREDENTIALS`、`VTUBER_FIREBASE_DATABASE_URL`。依序手動執行：
   - `-cmd vtuber-hololive-talents`（讓 `vtuber_channels` 有資料）
   - `VTUBER_LEGACY_FIREBASE_SECRET=<舊 secret>` 帶著執行 `-cmd vtuber-import-calendars`
   - `-cmd vtuber-lives-detect`（第一輪偵測＋同步）
4. 部署完就停用 Apps Script 的所有 trigger。
5. 觀察一天：`vtuber_lives` 有在累積、新藝人的行事曆陸續建好、舊行事曆上的事件有正確新增與更新。
6. 收尾：舊 Firebase 專案與那把 secret 可以停用（`VTUBER_LEGACY_FIREBASE_SECRET` 一併移除）；CDN 上的 `vtuber/hololovie.json` 可以刪除；propro 行事曆要不要刪，你決定。
