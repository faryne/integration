# VTuber 藝人頁：直播統計

## 背景

YouTube API 的訂閱數只給三位有效數字（2.04M 的頻道每 1 萬才跳一格），畫成圖不管累計或每日增減都是平的，看起來像頻道沒在活動。2026-11-01 已把訂閱者改成只顯示數字（`956825f`）。這次改用 `vtuber_lives` 已經在收的直播資料，補上真的看得出活動與人氣的數據。

## 範圍

四項，都放在藝人頁「統計」分頁，跟現有的期間切換（30 天／90 天／180 天／1 年）連動：

1. **直播場次／時數**：每週一根長條，可切「場次／時數」；卡片上方顯示期間合計與平均單場長度。
2. **直播時段熱力圖**：星期 × 小時（台北時間），顏色深淺＝該時段累計在直播的時間。
3. **同接峰值**：每場直播一根長條。
4. **每場觀看數／按讚數**：每場直播一根長條，跟同接峰值放同一張卡片切換。

### 不做

- 不回補 10/23 之前的直播（`vtuber_lives` 從上線才開始累積）。回補要掃上傳清單再寫進 `vtuber_lives`，會跟行事曆同步互相影響，要另外評估。
- 同接峰值補不回來：YouTube 只在直播進行中回傳 `concurrentViewers`，已結束的直播沒有。
- 不區分直播與首播（兩者都有 `liveStreamingDetails`，API 沒有欄位能分）。
- MCP 先不加。

## User stories

- 讀者想知道某位藝人最近還有沒有在播、播多久 → 看直播場次／時數。
- 讀者想知道她通常幾點開台 → 看時段熱力圖。
- 讀者想知道哪一場最多人看 → 看每場同接峰值／觀看數，滑到長條上顯示標題。

## 資料

### `vtuber_lives` 加欄位（migration，MySQL 5.7 相容）

| 欄位 | 型別 | 說明 |
|---|---|---|
| `peak_viewers` | `INT UNSIGNED NULL` | 偵測時看過的最高同接。現有的 `concurrent_viewers` 是「最後一次看到的值」，結束時會被清成 NULL，不能拿來用 |
| `view_count` | `BIGINT UNSIGNED NULL` | 觀看數 |
| `like_count` | `BIGINT UNSIGNED NULL` | 按讚數；頻道關掉公開讚數時為 NULL |
| 索引 `(channel_id, actual_start_at)` | | 查某頻道一段期間的直播 |

### 寫入

- **偵測（每 5 分鐘）**：`videos.list` 多拿 `statistics` part。`videos.list` 不管拿幾個 part 都是 1 unit，額度不變。
  - `peak_viewers`：upsert 時取「舊值」和「這輪同接」比較大的那個（`GREATEST`），結束、取消時都保留。
  - `view_count`／`like_count`：這輪有值就覆蓋，沒有就保留舊值。
- **`vtuber-live-counts`（每天 03:20）**：再更新「結束不到 7 天」的直播的觀看與按讚，7 天後就不再動。所以觀看數大約是「結束後一週的觀看數」，場次之間可以互相比較。79 個頻道一週約 300 場，每天大概 7 units。
  - 一開始規劃接在每日統計後面，實作時改成獨立 job：失敗互不影響，也能用 `-cmd vtuber-live-counts` 單獨手動跑。
  - 沿用偵測的 `listVideos`／`liveFromVideo`／`UpsertLives`，峰值與其他欄位照同一套規則合併。查不到的（轉私人、刪除）只略過，不改狀態。

## API

| Method | 路徑 | 參數 | 說明 |
|---|---|---|---|
| GET | `/opendata/vtubers/channels/:handle/lives/history` | `days`（預設 90，上限 365，跟 `/stats` 一樣） | 期間內**已結束**的直播，依開始時間排序。每筆：`video_id`、`title`、`thumbnail_url`、`actual_start_at`、`actual_end_at`、`peak_viewers`、`view_count`、`like_count`；找不到頻道回 404 |

依週分組、熱力圖這些統計在前端算（`components/vtuber/liveHistory.ts`）：一年最多幾百筆，資料量小。台北沒有日光節約，時間加 8 小時後用 UTC getter 切日與小時。

## 前端

- 統計分頁由上而下：**直播**（場次／時數）→ **直播時段**（熱力圖）→ **每場直播**（同接峰值／觀看／按讚）→ 訂閱者（只顯示數字）→ 觀看 → 影片。
- 熱力圖用 MUI Box 排的 CSS grid（7 × 24），不用 Google Charts；手機寬度下一格約 12px。
- 每場直播的長條圖：X 軸是開播時間，tooltip 顯示日期、標題、數值。同一天播兩場會是兩根靠很近的長條。
- 期間內沒有直播的話，三張直播卡片都只顯示「沒有直播」。
- **追蹤起點 `TRACKING_SINCE`（2026-10-23）**：之前的週不畫（不然選 90 天時前面兩個多月是一排 0，看起來像藝人沒在播）。之前的直播只有第一次掃 RSS 時順帶撿到的幾場，不完整，三張卡片一律不算，合計與長條才對得起來。
- 每場直播的長條用 discrete X 軸（一場一格）：時間軸會把同一天的兩場擠在一起，還會出現重複的日期標籤。
- 長條圖數值都 ≥ 0 時 Y 軸從 0 起算，不然 5 場和 6 場會被縮放成差好幾倍（每日增減的長條也一起受惠）。
- 卡片外框、標題列、切換鈕抽成 `StatCard`／`StatToggle`／`StatEmpty`，既有的訂閱者／觀看／影片卡片也改用。

## 常見失敗與應對

| 狀況 | 應對 |
|---|---|
| 剛上線，峰值、觀看數都還沒資料 | 已結束的直播 `peak_viewers` 都是 NULL，長條圖略過 NULL；整張卡片都沒資料時顯示「資料累積中」 |
| 短直播在兩輪偵測之間就開始又結束、會員限定直播不給同接 | `peak_viewers` 為 NULL，平均與長條都略過 |
| 偵測每 5 分鐘一次 | 峰值是「輪詢時看過的最高值」，會比真正的峰值低一點 |
| 直播超過 24 小時（耐久） | 熱力圖照實際時間分攤到每個小時格；場次算在開播那一週 |
| quota 用完、每日更新失敗 | 只 log，觀看數晚一天更新；結束超過 7 天才失敗的那幾場會停在舊值 |
| 首播 | 會算進場次（通常很短，時數影響小） |

## 上線順序

1. 跑 migration、部署 Go。
2. 從上線那一刻起，直播中的場次才會有峰值。觀看數不用等：部署後手動跑一次 `-cmd vtuber-live-counts`，結束不到 7 天的直播馬上補上（本機實測 304 場、約 2 秒）。

## 本機驗證（2026-11-01）

- upsert 在本機 MySQL 交易內實測：同接 100 → 300 → 200 時峰值停在 300；結束後同接清空、峰值與讚數保留；從沒看過同接的直播峰值維持 NULL。
- `-cmd vtuber-live-counts`：304 場裡 292 場拿到觀看數、299 場拿到讚數（其餘推測是會員限定或不公開）。
- 本機 `make mig-up` 會連帶套到其他本機手動套過的舊 migration，這支是手動執行 Up 區段後補 migrations 紀錄。
