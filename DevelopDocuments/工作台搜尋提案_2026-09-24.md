# SteamLoom 工作台搜尋提案

## 結論

工作台搜尋獨立於左上角既有的「全站搜尋」：

- 全站搜尋：搜尋公開作品，沿用 Elasticsearch `storyteller_works` 索引。
- 工作台搜尋：只搜尋目前登入者擁有的單一專案，包含私人草稿、設定與資產。
- 入口放在工作台第二層 header，桌機顯示「搜尋目前專案」，手機顯示搜尋圖示。
- 搜尋結果以對話框呈現；桌機為清單＋Preview 雙欄，手機只顯示含摘要的結果清單，點擊即開啟。

兩種搜尋不可共用公開索引，避免私人內容進入公開作品的索引與同步流程。

## 使用流程

1. 使用者在專案工作台點擊「搜尋目前專案」。
2. 輸入框 focus 時，用 autocomplete 顯示該專案最近搜尋。
3. 輸入停止 250ms 後送出搜尋；可切換「全部／作品／設定／資產」。
4. 桌機第一筆結果預設顯示 Preview，可用滑鼠或 ↑↓ 切換、Enter 開啟；手機點擊結果即開啟，不另外顯示 Preview。
5. 桌機點擊「在工作台開啟」或手機點擊結果後，前往對應的作品、設定或資產編輯畫面。
6. 若目前編輯器有未儲存內容，沿用工作台既有的離開確認流程。

## 搜尋範圍

| 類型 | 搜尋欄位 | Preview 來源 | 開啟目標 |
| --- | --- | --- | --- |
| 作品 | 標題、摘要、最新內容 | 關鍵字附近的純文字 | 文字故事或圖像作品編輯器 |
| 設定 | 標題、最新內容 | 關鍵字附近的純文字 | 設定編輯器 |
| 資產 | 標題、原始檔名、替代文字、描述 | 資產文字資訊 | 資產詳細面板 |

冊、設定分類與資產集名稱會顯示在結果位置，但第一版不把分類本身當成獨立搜尋結果。

## API

```http
GET /storyteller/projects/:project/search?keyword=艾莉絲&kind=story
X-Encrypt-Key: <session key>
```

- `keyword`：必填；空字串回傳空陣列，最長 100 個 Unicode 字元。
- `kind`：選填；`story`、`lore`、`asset`，省略代表全部。
- API 必須通過 storyteller session，並以 `ProjectByPublicIDForUser` 驗證專案擁有者。
- MySQL 每一類先依 relevance 取 60 筆候選，再以使用者可見純文字二次比對，排除 WYSIWYG marker 與圖像作品 JSON 欄位造成的誤命中。
- 二次比對後每一類最多保留 20 筆，合併後最多回傳 40 筆。

結果依序考慮：標題完全相符、標題前綴、標題包含、其他欄位包含；同一層級再按更新時間倒序。

## 最近搜尋

最近搜尋只屬於操作便利資料，第一版使用 `localStorage`，不建資料表：

- Key：`steamloom:workspace-search-history:${projectPublicId}`
- 每個專案最多 8 筆。
- 不分大小寫去重，新搜尋移到最前。
- 90 天未使用即淘汰。
- 只在 Enter、選取 autocomplete 或開啟結果時記錄，不記錄每個輸入中的字。

這樣不需要增加同步 API，也不會把可能敏感的私人搜尋詞主動留存在伺服器。若未來確定需要跨裝置同步，再改成帳號層級資料表。

## 技術方案

第一版直接查 MySQL 5.7，以 `LIKE` 搜尋三張既有資料表，不新增 migration。公開 Elasticsearch 索引只包含已公開作品，不能支援工作台的私人草稿、設定與資產。

目前方案適合側專案與單一專案內的中小型資料量；若單一專案內容量明顯增加、查詢延遲超過可接受範圍，後續改為：

1. 建立獨立的私有工作台索引，不與公開索引共用。
2. 索引文件帶 `project_id` 與擁有者／授權範圍，查詢必須附帶權限 filter。
3. 配合未來 Manticore Search 遷移，不在 MySQL 先加入難以維護的中文 FULLTEXT 設定。

## 錯誤與空狀態

- API 失敗：顯示 error snackbar「搜尋失敗，請稍後再試。」
- 無結果：提示更換關鍵字或切回「全部」。
- 無可預覽文字：保留結果，Preview 顯示「這筆內容沒有可顯示的文字預覽。」
- 專案不存在或不屬於登入者：回傳 404，不洩漏專案是否存在。
